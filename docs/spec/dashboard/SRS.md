# CHILL Dashboard SRS

## 1. 목적과 범위

`chill-dashboard`는 CHILL 전반의 조회 및 제어 API를 웹에서 제공하는 독립
웹서비스 모듈이어야 한다. 사용자는 안내형 화면으로 서비스를 사용하고, 운영을
제어하며, 관측 결과와 판단 근거를 확인할 수 있어야 한다.

이 문서는 [CHILL 시스템 명세](../README.md)를 웹 사용자 관점에서 구체화한다.
요구사항 ID의 `DB`는 Dashboard를 뜻한다. 각 요구사항은 구현과 수용 검증의
기준이다. 구현 및 API 준비 현황은 구현 설계에 기록해야 한다.
제어 규칙은 `docs/spec/`을 따르고,
[운영자 콘솔 설계](../../design/operator-console/README.md)는 사용자 흐름의
참고 자료로 사용해야 한다.

| 영역 | 제공해야 하는 기능 |
|---|---|
| 시스템 | 구성요소 상태와 운영 설정 조회 |
| 모델과 워크로드 | 모델, 전처리기, 데이터셋과 워크로드의 등록, 조회, 수정, 삭제, SLO 설정과 단일 추론 |
| 자원과 POOL | 디바이스와 노드 인벤토리, 실제 구성과 할당 조회, 허용 자원 관리 |
| 측정과 Evidence | 측정 가능 범위 확인, 사전 확인과 측정 요청, 진행 및 실패 확인, 프로파일과 원시 근거 탐색 |
| 구성과 전환 | 판단 근거 조회, 운영 설정 변경, 실제 전환 감독 |
| 관측과 실험 | 요청 결과, 지연, 전력과 에너지 조회, 실험 비교와 자료 내보내기 |
| 작업과 이력 | 변경 대상, 적용 정의, 진행 및 실제 결과 조회 |

CHILL 설치, 업그레이드와 제거는 Helm 또는 GitOps의 배포 경로에서 수행해야 한다.
런타임 운영 변경은 ChillServer의 공통 관리 API를 통해 수행해야 한다.
전체 범위의 요구사항과 수용 시나리오를 충족한 경우에 Dashboard 구현을 완료로 판정해야 한다.

## 2. 사용자와 접근 범위

기존 인증 및 권한 체계에서 사용자별 업무 권한을 적용해야 한다.
한 사용자가 여러 업무 권한을 가질 수 있어야 한다.

| 사용자 | 주요 업무 |
|---|---|
| 서비스 사용자 | 허용된 워크로드 탐색, 입력 계약 확인, 단일 추론과 결과 확인 |
| 운영자 | 모델과 워크로드 관리, 허용 자원과 운영 설정 변경, 전환과 장애 감독 |
| 측정 담당자 | 측정 조건 작성, 실행 요청, 실패 확인, Evidence 검토 |
| 분석자 및 관찰자 | 허용된 상태와 근거 조회, 관측 구간 분석, 재현 자료 내보내기 |

- `DB-SEC-01` 기존 인증 및 권한 체계를 사용해야 한다. 조회, 추론, 관리 변경,
  측정 요청과 자료 내보내기는 서버에서 대상과 동작별 호출 권한을 검사해야 한다.
- `DB-SEC-02` ChillServer가 검증할 수 있는 사용자 신원을 전달해야 한다.
  실제 호출자의 권한과 행위자를 유지하고, 검증된 신원만 인증 근거로 사용해야 한다.
- `DB-SEC-03` 브라우저와 외부 API 연결에 TLS를 사용해야 한다. 인증정보와 저장소
  credential을 안전하게 취급하고 URL, 브라우저 영속 저장소, 다운로드와 로그에서
  제거해야 한다. 세션 cookie를 사용하면 안전한 속성과 CSRF 방어를 적용해야 한다.
- `DB-SEC-04` 권한 거부, 인증 만료와 인증 서비스 장애를 구분해야 한다.
  인증 또는 권한 확인 실패 시 변경을 거부하고, 설정된 ChillServer만 중계해야 한다.

## 3. 웹서비스와 API의 책임 경계

```text
사용자 브라우저
    → chill-dashboard: 화면, 입력 안내, 조회 조합과 API 중계
    → ChillServer: 조회 및 관리 API, 권한, 검증, 선언, 작업 및 관측 계약
    → 제어기, 실행기, Serving과 관측 원본
```

- `DB-INT-01` 별도 빌드, 실행 및 배포 가능한 웹서비스 모듈로 제공해야 한다.
  API 주소와 인증 및 배포 설정을 분리하고, 웹 기술은 템플릿과 배포 환경에 맞게 선택해야 한다.
- `DB-INT-02` 널리 사용되고 유지보수되는 웹 대시보드 템플릿의 Git 저장소를
  가져와 개발해야 한다. 출처, 고정 tag 또는 commit, 라이선스와 재배포 조건을
  기록하고 기존 화면 컴포넌트를 재사용해야 한다. 불필요한 예제 기능은 제거해야 한다.
- `DB-INT-03` ChillServer의 상태와 결과를 권위 있는 원본으로 사용해야 한다.
  조회 조합은 원본 식별자와 관측 시각을 보존하고 오류, 충돌, 접수 및 완료의 의미를 유지해야 한다.
- `DB-INT-04` 변경은 해당 영역의 공통 관리 API로 제출해야 한다.
  권한, 검증, 단일 writer, 참조 보호와 드레인은 CHILL의 기존 계약을 따라야 한다.
- `DB-INT-05` 필요한 조회 및 관리 API는 ChillServer가 해당 책임 영역별로 제공해야 한다.
  Dashboard는 ChillServer의 실제 결과를 사용하고 기능별 지원 여부를 표시해야 한다.
  요구사항이 ChillServer가 제공할 조회를 명시하면 Dashboard는 해당 조회가 제공되는 기능을 활성화하고, 다른 조회 결과와 기능별 지원 여부는 독립적으로 표시해야 한다.
- `DB-INT-06` 미지원, 권한 없음, 데이터 없음, 오래된 관측, 조회 실패와 동작
  실패를 구분해야 한다. 영역별 조회 결과와 마지막 관측 시각을 독립적으로 표시해야 한다.

템플릿 저장소, 웹 기술, URL, API schema와 배포 방법은 구현 설계에서 정해야 한다.
템플릿은 개발 단계에 가져오고 고정된 버전으로 빌드해야 한다.

## 4. 사용자 흐름

목록에서 상세와 연관 객체 및 근거로 이동할 수 있어야 한다.

| 업무 영역 | 제공해야 하는 흐름 |
|---|---|
| 시스템 개요 | 구성요소 상태, 워크로드 SLO와 요청 결과, 전체 POOL 소비 및 진행 작업 조회 |
| 모델과 워크로드 | 모델, 전처리기와 데이터셋 등록 → 워크로드와 SLO 설정 → 부족한 근거 확인 → 준비 확인 → 단일 추론 |
| 자원과 POOL | 디바이스와 노드 조회 → 실제 할당 확인 → 허용 범위와 유지보수 변경 |
| 측정과 Evidence | 측정 가능 범위 확인 → 조건 작성 → 사전 확인 → 측정 요청 → 단계별 진행 → 원시 근거와 프로파일 확인 |
| 구성과 전환 | 판단 근거 확인 → 운영 설정 변경 → 실제 전환과 실패 감독 |
| 관측과 실험 | 구간과 대상 선택 → 지연, 처리 결과와 에너지 비교 → 자료 내보내기 |
| 작업과 이력 | 변경 대상과 전후 정의 확인 → 진행 및 실제 결과 조회 → 관련 근거 탐색 |

- `DB-UX-01` 기본 등록, 조회, 수정과 측정 요청은 안내형 폼과 참조 선택으로
  수행할 수 있어야 한다. 필요한 입력은 사용자 업무 용어로 제공해야 한다.
- `DB-UX-02` 폼에 단위, 허용 범위와 필수 항목을 표시해야 한다. 서버 오류를
  해당 항목과 이유에 연결하고, 거부된 변경에서는 작성한 입력을 유지해야 한다.
- `DB-UX-03` 목록에서 상세와 작업에 직접 접근할 수 있어야 한다. CHILL 대상, namespace와 시간 구간 등 실제 조회 범위를 명시해야 한다.
- `DB-UX-04` 지원 입력 예시, 제출할 정의와 실제 응답을 확인할 수 있어야 한다.
  연관 객체와 근거로 이동할 때 원본 identity를 유지해야 한다.

## 5. 기능 요구사항

### 5.1 시스템 상태와 인벤토리

- `DB-FR-01` 구성요소의 요청 상태와 관측 availability, 이유 및 시각을 조회해야 한다.
  웹서비스 health, Kubernetes Ready, Serving 준비, 접수 여부와 SLO 관측을 구분해야 한다.
- `DB-FR-02` DeviceClass의 선언된 능력과 대응 노드, Node identity, Ready,
  schedulability와 자원 할당을 조회해야 한다. 실행 적합성과 가용 자원은 CHILL이
  제공하는 측정 근거와 실제 할당 상태에 따라 표시해야 한다. 전력모드마다 제어 방식과
  목표를 쉬운 말로 표시하고 측정 요청의 전력모드 선택에도 같은 설명을 사용해야 한다.
- `DB-FR-03` 개요에 구성요소 상태와 이유, 워크로드별 SLO와 요청 결과, 부하와 큐,
  전체 및 활성 POOL의 전력과 에너지, 진행 작업과 관측 공백을 범위 및 구간과 함께 표시해야 한다.

### 5.2 모델과 워크로드 관리

- `DB-FR-04` 모델 등록, 조회, 수정과 삭제를 제공해야 한다. 산출물, 실행 경로,
  입력 계약과 측정 근거를 조회하고, 관련 워크로드와 변경 영향 및 삭제 거부 사유를 표시해야 한다.
  실행 경로의 runtime 계열과 backend를 사용자 용어로 표시하고, 등록과 수정에서는
  ChillServer가 허용하는 runtime 계열과 산출물 형식에 맞는 backend에서 선택하게 해야 한다.
- `DB-FR-05` 워크로드 등록, 조회, 수정과 삭제를 제공해야 한다. 식별자, 모델
  참조, 전처리기 참조, 선택 항목인 데이터셋 참조, `0 < p ≤ 100`인 지연 백분위와
  유한한 양의 목표 시간을 설정해야 한다. 같은 모델을 서로 다른 SLO의 워크로드에서
  참조할 수 있어야 한다.
- `DB-FR-06` 원하는 정의, 적용 정의, 지원 입력, 실제 준비, 접수 여부와 관리
  진행을 구분해야 한다. 근거 부족 시 필요한 실행 조건과 측정으로 안내해야 한다.
  ChillServer가 제공하는 준비 상태와 사유마다 쉬운 결론 문장과 다음 행동을 표시하고,
  원본 코드는 원본 보기에서 제공해야 한다.
- `DB-FR-07` SLO 변경의 신규 수락 요청 적용과 모델 또는 전처리 참조 변경과 삭제의
  기존 요청 마무리 계약을 안내해야 한다. 공유 모델의 영향 대상, 드레인과 실제 삭제
  완료를 조회하고 삭제된 등록 건의 관측을 같은 이름의 새 등록 건과 구분해야 한다.
- `DB-FR-28` 전처리기와 데이터셋 등록, 조회, 수정과 삭제를 제공해야 한다.
  전처리기의 입력 및 출력 계약과 모델 산출물별 전처리 산출물, 데이터셋의 레코드
  필드와 프로파일링 및 평가 부분집합을 조회하고, 참조하는 워크로드와 변경 영향 및
  삭제 거부 사유를 표시해야 한다. 대상 규칙은 [데이터셋과 전처리 관리 SRS](../catalog/SRS.md#3-요구사항)를 따라야 한다.

### 5.3 단일 추론

- `DB-FR-08` 허용된 워크로드의 지원 입력으로 추론 한 건을 제출하고 실제 결과
  또는 오류를 확인할 수 있어야 한다. 독립 입력 하나를 요청 하나로 제출하고,
  모델과 SLO는 등록된 정의를 적용하며 실행 배치는 firstfloor가 구성해야 한다.
- `DB-FR-09` 명시적 timeout과 SLO를 구분해야 한다. 요청 식별자와 결과를
  연결하고 CHILL 종단 지연, 브라우저 왕복과 웹 중계 지연을 구분해야 한다.
  응답 미수신 시 결과 미확인으로 표시하고 재제출은 사용자의 명시적 동작으로 수행해야 한다.
- `DB-FR-29` 입력 화면은 참조 전처리기의 원시 입력 계약에 있는 필드 이름, 형식과
  크기로 구성하고, 결과 화면은 원시 출력 계약에 있는 필드 이름과 형식으로 구성해야 한다.
  필드 이름은 계약의 이름을 그대로 표시하고, 쉬운 말은 형식과 입력 크기 설명에 사용해야 한다.
  출력 필드는 계약 순서대로 표시하고, 모든 워크로드와 모델에 같은 화면 규칙을 적용해야 한다.

### 5.4 POOL과 허용 자원

- `DB-FR-10` 전체 POOL, 워크로드별 활성 POOL, 측정 POOL과 가용 노드를 구분하고 소속 노드, 워크로드,
  인스턴스, 모델과 실행 경로, CPU, GPU, 메모리 할당 및 노드 전력모드를 조회해야 한다.
  여러 활성 POOL이 함께 쓰는 노드와 공유 인스턴스의 관계, 목표 및 실제 자원 조건을 구분해야 한다.
- `DB-FR-11` 운영자가 제공할 노드, 실행 대상과 전력모드의 허용 범위를 선언하고
  유지보수 제외 및 복귀를 요청할 수 있어야 한다. ChillServer의 관리 API를 사용하고,
  영향받는 워크로드, 용량과 실제 POOL 관계 및 적용 진행을 표시해야 한다.
- `DB-FR-33` 워크로드마다 자동제어를 켜고 끌 수 있어야 하며, 현재 상태와 측정 근거
  대기 같은 판단 상태와 사유를 표시해야 한다. 꺼진 워크로드는 마지막 구성을 유지한다는
  사실과 그 워크로드에만 적용되는 수동 변경 결과를 표시해야 한다.

### 5.5 측정과 Evidence

- `DB-FR-12` 실행 경로, 대상 장비, 전력모드, 자원과 연동 스레드, 배치 조건,
  워밍업, 반복과 측정 구간을 지정하여 측정을 요청할 수 있어야 한다. 활성 측정은
  워크로드를 선택해 그 워크로드의 데이터셋으로 요청할 수 있어야 한다. 활성, 모델 로드
  유휴와 전환 측정 조건을 구분하고 실행에 사용한 조건은 읽기 전용으로 제공해야 한다.
  활성 및 모델 로드 유휴 측정 제출 전 ChillServer의 사전 확인 결과로 측정 가능 여부와 사유,
  실행할 측정 계획의 요약을 표시해야 한다.
- `DB-FR-13` 측정 접수와 API가 제공하는 실제 진행, 실행 결과 및 검증 결과를 조회해야 한다.
  실패, 필수 관측 누락, 실제 실행 대상과 요청 및 적용 조건의 차이를 조회해야 한다.
  측정 결과에는 실제 사용한 runtime과 backend, 실행 provider와 실행 장치를 표시해야 한다.
  측정 완료 결과와 검증 실패 사유마다 쉬운 결론 문장과 다음 행동을 표시하고, 원본 코드는
  원본 보기에서 제공해야 한다.
- `DB-FR-14` 프로파일의 실행 조건, 실행시간 분포, 처리량, 메모리, 전력과 에너지,
  유휴 기준, 반복 trial과 원시 Evidence를 탐색할 수 있어야 한다. 조건에 맞는 성공
  측정과 공백을 조회하고, 최신 성공 결과 선택과 Run 내부 trial 집계를 구분해야 한다.
  프로파일마다 모델 산출물, runtime, 전처리 산출물과 데이터셋의 측정 조건을 구분해
  표시하고, 같은 워크로드에서 조건이 다른 프로파일을 구분해야 한다.
- `DB-FR-30` 워크로드와 실행 경로마다 DeviceClass별 측정 가능 여부와 사유를 조회해야
  한다. 측정 요청에서 장비별 선택 가능 여부와 사유를 표시해야 한다.
- `DB-FR-32` 전력모드 전환 비용의 원시 기록을 조회해야 한다. 출발과 도착 전력모드,
  방향별 반복 측정의 소요 시간과 에너지, 관측 구간, 측정 상태와 원본 참조를 표시하고
  판단에 사용한 전환 비용과 연결해야 한다. 각 반복의 검증 판정과 사유, 경계 불확실성 및
  전환 중 Serving 지속 여부를 함께 표시해야 한다.
- `DB-FR-34` 측정 요청에서 대상 노드의 소속 상태를 표시하고, 서빙 중인 노드를 선택하면
  측정 거절 사유를 보여야 한다. 측정 중 노드의 측정 POOL 이동과 반환 진행, 측정 결과에 기록된
  CHILL이 배치하지 않은 파드 목록을 표시해야 한다.

### 5.6 구성 판단과 운영 설정

- `DB-FR-15` 실제 현재 구성, 비교 후보와 선택 목표를 구분해야 한다. 판단 결과의 제공 여부와 적용 조건을 표시해야 한다.
- `DB-FR-16` 판단에 사용한 부하, 큐, SLO, 실제 구성, 프로파일과 전환 근거,
  비교 기간 및 제외 이유를 연결해야 한다. SLO 충족 가능성과 전환 및 Serving의
  총에너지 비교를 구분하고 예측값과 실측값을 표시해야 한다.
- `DB-FR-17` 시스템 전체의 비교 기간, 제어 및 관측 주기와 운영 설정을 조회하고 변경할 수
  있어야 한다. 허용 자원과 제어요소 활성 여부의 전후 정의, 검증 결과, 영향 범위와
  적용 진행을 표시해야 한다. 예측 영향은 ChillServer의 값을 사용하고 평가 불가 상태를 표시해야 한다.
- `DB-FR-18` 인스턴스 배치, 자원 할당, 전력모드, 라우팅과 배칭 결정은 CHILL이
  수행해야 한다. 비교 실험의 정적 구성 및 제어요소 비활성화는 자동 제어와 구분하고,
  선택 근거와 설정을 실행 기록에 연결해야 한다. 설정 기반 요청 분배는 워크로드별 인스턴스
  분배 비율의 선언과 실제 반영 결과를 나란히 표시하고, 반영 대기와 실패 이유를 표시해야 한다.

### 5.7 전환과 장애 감독

- `DB-FR-19` 전환의 출발, 목표와 판단, 대상 동작과 의존관계, 준비, 유입 중지,
  기존 요청 마무리와 자원 해제 단계를 조회해야 한다. 동작별 시작 및 완료 시각,
  예상 및 실제 시간과 에너지를 요청 관측과 연결해야 한다.
- `DB-FR-20` 접수, 진행, 실제 완료, 실패와 일부 적용을 구분하고 실패 대상,
  원인과 마지막 실제 상태를 표시해야 한다. 모델 준비와 전환 완료는 CHILL의 완료 기준을 따라야 한다.
- `DB-FR-21` 부하 변화, 노드와 backend 소실, 관측 공백 및 용량 감소를 표시하고
  후속 판단으로 연결해야 한다. 개입은 해당 동작의 API가 허용하는 기능과 조건으로 제공해야 한다.

### 5.8 관측과 실험 및 이력

- `DB-FR-22` 등록 건, 적용 정의, 시간 구간과 처리 결과 조건으로 요청 기록과
  통계를 조회해야 한다. 유입, 미배정, 인스턴스 대기와 실행을 구분하고 실제 결과를
  표시해야 한다. 완료, 오류, 거절, timeout, 취소, 미완료와 전달 실패 및 SLO 초과를 구분해야 한다.
  요청별 단계 소요시간과 단위 수는 [워크로드 SRS 입력과 요청 결과](../workloads/SRS.md#6-입력과-요청-결과)의 요청 기록 항목으로 표시해야 한다.
- `DB-FR-23` 선택 구간의 지연 분포와 백분위, 모집단, 포함 및 제외 조건, 표본
  수와 집계 설정을 표시해야 한다. 통계는 전체 선택 구간을 기준으로 사용하고,
  표본 수가 0인 구간은 0개와 빈 통계 값으로 표시해야 한다.
- `DB-FR-24` 전력과 에너지에 대상, 단위, 시각과 구간 및 범위를 표시해야 한다.
  전체 POOL의 비참여 노드와 전환 소비를 포함하고 활성 POOL 소비 및 전체와 증분
  에너지를 구분해야 한다. 노드 소비는 한 번씩 집계한 값을 사용하고 관측 누락은 값 없음으로 표시해야 한다.
- `DB-FR-25` 부하 시나리오, 프로파일과 설정, 초기 구성, 제어 동작과 실제 상태,
  요청 결과와 전력을 같은 시간축에서 조회하고 비교해야 한다. 부하 변화, 반복 전환,
  POOL 한계와 장애 구간 및 예측과 실측의 차이를 제공하고 실험 해석은 분석자가 수행해야 한다.
- `DB-FR-26` 권한 범위의 원시 기록, 집계 조건과 원본 참조를 구조화된 자료로
  내보낼 수 있어야 한다. 시간 구간, 단위, 적용 정의와 출처를 보존하고 비밀정보를 제거해야 한다.
- `DB-FR-27` 변경의 행위자와 대상, 전후 정의, 접수와 적용 시각, 진행과 결과 및
  실패 원인을 조회해야 한다. 웹 접근 기록과 CHILL 변경 이력을 구분하고 과거 증거는 읽기 전용으로 제공해야 한다.

## 6. 공통 변경과 오류 처리

- `DB-OP-01` 변경 전 대상, 전후 정의와 확인 가능한 영향을 제시해야 한다.
  삭제, 공유 모델 변경과 자원 제외는 명시적 확인을 받고 영향 정보의 공백을 표시해야 한다.
- `DB-OP-02` 수정 및 삭제에 API의 버전 전제조건을 전달해야 한다. 충돌 시 최신
  상태와 작성한 변경을 비교하게 하고 재제출은 사용자 확인을 거쳐야 한다.
- `DB-OP-03` 접수와 실제 완료를 구분하고 원본 작업 또는 대상 identity로 진행을
  조회해야 한다. 새로고침과 재접속 후 상태를 복원하고 관리 작업의 수명은 CHILL 계약을 따라야 한다.
- `DB-OP-04` 제출 중 중복 클릭을 막고 응답 미확인 시 결과 미확인으로 표시해야 한다.
  후속 행동은 상태 조회와 사용자 확인으로 정하고 변경, 추론과 측정 재제출은 명시적으로 수행해야 한다.
- `DB-OP-05` 검증 오류, 권한 거부, 대상 없음, 충돌, 접수 제한, backend 오류와
  timeout을 구분해야 한다. 추론, 관리 변경과 조회에서 받은 ChillServer 오류의 쉬운 의미와
  다음 행동을 표시하고, API가 제공하는 대상, 항목과 사유를 함께 표시해야 한다.
  원본 코드는 원본 보기에서 제공해야 한다.

## 7. 품질과 배포 요구사항

- `DB-NFR-01` 주요 흐름을 키보드로 수행할 수 있어야 한다. 입력 label, 오류,
  focus와 진행 상태를 식별할 수 있게 제공하고 상태에 텍스트 또는 기호를 함께 사용해야 한다.
  데스크톱과 좁은 화면에서 핵심 흐름을 사용할 수 있어야 한다.
- `DB-NFR-02` 시간대, 기간과 단위를 명시하고 원본 시각을 보존해야 한다.
  사용자 SLO 값을 그대로 제출하고 UI 표시 정밀도와 저장 값을 구분해야 한다.
- `DB-NFR-03` 조회 범위, page 크기, 갱신 주기와 timeout을 제한해야 한다.
  API의 통계를 사용하고 마지막 관측 시각과 조회 오류를 표시해야 한다. 조회는 읽기 전용으로 수행해야 한다.
- `DB-NFR-04` 성능 검증에 데이터 규모, 동시 사용자, 조회 구간과 갱신 설정을
  기록해야 한다. 웹 중계 비용을 CHILL 추론 및 제어 비용과 구분하고 성능 예산은 검증 계획에서 정해야 한다.
- `DB-NFR-05` 독립 실행 및 배포와 API 연결 및 인증 설정 주입을 제공해야 한다.
  credential은 배포 시 주입하고 Dashboard 중단 및 재시작 동안 CHILL Serving과
  제어 및 관리 작업은 기존 계약을 유지해야 한다.
- `DB-NFR-06` 외부 문자열은 안전한 텍스트로 렌더링해야 한다. 예제 인증, mock
  API와 가짜 메트릭을 제거하고 진단정보에서 비밀정보를 제거해야 한다.

실제 브라우저, ChillServer와 실행 및 관측 결과를 연결하여 검증해야 한다.

| 시나리오 | 확인 결과 | 요구사항 |

| 독립 모듈과 템플릿 | 빌드, 기동과 배포 및 Git 출처, 고정 버전과 라이선스 확인 | DB-INT-01~02, DB-NFR-05~06 |

## 10. 구현 설계의 산출물

구현 구조와 현재 API 준비 현황은
[Dashboard 구현 설계](../../design/dashboard/README.md)에 기록해야 한다.

다음을 구현 설계에 기록해야 한다.

- 템플릿 Git 출처, 라이선스, 고정 버전, 재사용 컴포넌트와 웹 기술 및 모듈 배치.
- 요구사항별 조회 및 관리 API, 제공 여부, 필요한 생산자와 인증 및 권한 전달 방식.
- 안내형 화면과 연관 객체 탐색, 조회 조합과 API 중계 및 작업 진행 갱신 방식.
- 독립 배포, 환경 설정과 API 연결 계약 및 요구사항별 브라우저 수용 검증 계획.
