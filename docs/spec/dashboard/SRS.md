# CHILL Dashboard SRS

## 1. 목적과 범위

`chill-dashboard`는 CHILL 전반의 조회 및 제어 API를 웹에서 제공하는 독립
웹서비스 모듈이어야 한다. 사용자는 안내형 화면으로 서비스를 사용하고, 운영을
제어하며, 관측 결과와 판단 근거를 확인할 수 있어야 한다.

이 문서는 [CHILL 시스템 명세](../README.md)를 웹 사용자 관점에서 구체화한다.
요구사항 ID의 `DB`는 Dashboard를 뜻한다. 각 요구사항은 구현과 수용 검증의
기준이다. 구현 및 API 준비 현황은 구현 설계에 기록해야 한다.
제어 규칙은 `docs/spec/`을 따르고,
[운영자 콘솔 설계](../../design/operator-console/README.md)는 사용자 흐름의
참고 자료로 사용해야 한다.

| 영역 | 제공해야 하는 기능 |
|---|---|
| 시스템 | 구성요소 상태와 운영 설정 조회 |
| 모델과 워크로드 | 모델, 전처리기, 데이터셋과 워크로드의 등록, 조회, 수정, 삭제, SLO 설정과 단일 추론 |
| 자원과 POOL | 디바이스와 노드 인벤토리, 실제 구성과 할당 조회, 허용 자원 관리 |
| 측정과 Evidence | 측정 가능 범위 확인, 사전 확인과 측정 요청, 진행 및 실패 확인, 프로파일과 원시 근거 탐색 |
| 구성과 전환 | 판단 근거 조회, 운영 설정 변경, 실제 전환 감독 |
| 관측과 실험 | 요청 결과, 지연, 전력과 에너지 조회, 실험 비교와 자료 내보내기 |
| 작업과 이력 | 변경 대상, 적용 정의, 진행 및 실제 결과 조회 |

CHILL 설치, 업그레이드와 제거는 Helm 또는 GitOps의 배포 경로에서 수행해야 한다.
런타임 운영 변경은 ChillServer의 공통 관리 API를 통해 수행해야 한다.
전체 범위의 요구사항과 수용 시나리오를 충족한 경우에 Dashboard 구현을 완료로 판정해야 한다.

## 2. 사용자와 접근 범위

기존 인증 및 권한 체계에서 사용자별 업무 권한을 적용해야 한다.
한 사용자가 여러 업무 권한을 가질 수 있어야 한다.
본 대시보드의 주 사용자는 **엣지 클러스터 운영 담당자**다. 화면은 현재 스케줄러의 사용 여부,
운영에 필요한 측정 공백과 조치를 설명해야 한다. 평가자의 학술 역할을 제품 메뉴·상태명으로 사용하지 않아야 한다.

| 사용자 | 주요 업무 |
|---|---|
| 서비스 사용자 | 허용된 워크로드 탐색, 입력 계약 확인, 단일 추론과 결과 확인 |
| 운영자 | 모델과 워크로드 관리, 허용 자원과 운영 설정 변경, 전환과 장애 감독 |
| 측정 담당자 | 측정 조건 작성, 실행 요청, 실패 확인, Evidence 검토 |
| 분석자 및 관찰자 | 허용된 상태와 근거 조회, 관측 구간 분석, 재현 자료 내보내기 |

- `DB-SEC-01` 기존 인증 및 권한 체계를 사용해야 한다. 조회, 추론, 관리 변경,
  측정 요청과 자료 내보내기는 서버에서 대상과 동작별 호출 권한을 검사해야 한다.
- `DB-SEC-02` ChillServer가 검증할 수 있는 사용자 신원을 전달해야 한다.
  실제 호출자의 권한과 행위자를 유지하고, 검증된 신원만 인증 근거로 사용해야 한다.
- `DB-SEC-03` 브라우저와 외부 API 연결에 TLS를 사용해야 한다. 사용자 bearer는
  탭 메모리와 승인된 **sessionStorage(탭 범위)**에만 보관할 수 있다. 새로고침·같은 탭
  딥링크에서 복원하되 localStorage·IndexedDB·cookie·URL·로그·다운로드에는 저장하지 않아야 한다.
  key는 버전+system 단위로 분리하고 namespace 이동으로 재로그인하지 않아야 한다.
  **‘이 탭에서 토큰 지우기’**와 신원 변경·확정 401/WS 4401 때 저장 토큰·메모리·진행 요청·
  Query cache·socket을 같은 인증 epoch로 정리해야 한다. 이 탭 삭제는 bearer 자체나 다른 탭의 폐기가 아니다.
  403/4403·인증 서비스 장애는 만료가 아니며 storage 거부는 메모리 전용과 유지 불가 안내를 제공해야 한다.
  앱이 여는 모든 새 창은 opener를 제거해야 한다. 복제 탭/세션 복원이 storage를 복원할 수 있으므로
  탭 닫기를 안전 삭제 보장으로 표현하지 않아야 한다. sessionStorage와 현 unsafe-inline CSP를
  XSS 방어/토큰 보호 보장으로 표현하지 않아야 한다. 서버 credential은 브라우저에 노출하지 않아야 한다.
- `DB-SEC-04` 권한 거부, 인증 만료와 인증 서비스 장애를 구분해야 한다.
  인증 또는 권한 확인 실패 시 변경을 거부하고, 설정된 ChillServer만 중계해야 한다.

## 3. 웹서비스와 API의 책임 경계

```text
사용자 브라우저
    → chill-dashboard: 화면, 입력 안내, 조회 조합과 API 중계
    → ChillServer: 조회 및 관리 API, 권한, 검증, 선언, 작업 및 관측 계약
    → 제어기, 실행기, Serving과 관측 원본
```

- `DB-INT-01` 별도 빌드, 실행 및 배포 가능한 웹서비스 모듈로 제공해야 한다.
  API 주소와 인증 및 배포 설정을 분리하고, 웹 기술은 템플릿과 배포 환경에 맞게 선택해야 한다.
- `DB-INT-02` 널리 사용되고 유지보수되는 웹 대시보드 템플릿의 Git 저장소를
  가져와 개발해야 한다. 출처, 고정 tag 또는 commit, 라이선스와 재배포 조건을
  기록하고 기존 화면 컴포넌트를 재사용해야 한다. 불필요한 예제 기능은 제거해야 한다.
- `DB-INT-03` ChillServer의 상태와 결과를 권위 있는 원본으로 사용해야 한다.
  조회 조합은 원본 식별자와 관측 시각을 보존하고 오류, 충돌, 접수 및 완료의 의미를 유지해야 한다.
- `DB-INT-04` 변경은 해당 영역의 공통 관리 API로 제출해야 한다.
  권한, 검증, 단일 writer, 참조 보호와 드레인은 CHILL의 기존 계약을 따라야 한다.
- `DB-INT-05` 필요한 조회 및 관리 API는 ChillServer가 해당 책임 영역별로 제공해야 한다.
  Dashboard는 ChillServer의 실제 결과를 사용하고 기능별 지원 여부를 표시해야 한다.
  요구사항이 ChillServer가 제공할 조회를 명시하면 Dashboard는 해당 조회가 제공되는 기능을 활성화하고, 다른 조회 결과와 기능별 지원 여부는 독립적으로 표시해야 한다.
- `DB-INT-06` 미지원, 권한 없음, 데이터 없음, 오래된 관측, 조회 실패와 동작
  실패를 구분해야 한다. 영역별 조회 결과와 마지막 관측 시각을 독립적으로 표시해야 한다.
- `DB-INT-07` 실시간 화면은 WebSocket 라이브 채널의 서버 push로 현재 상태,
  변경분, 이벤트와 집계 지표를 갱신해야 한다. 큰 상태 전체를 주기적으로 다시 조회하지 않아야 한다.
- `DB-INT-08` WebSocket 연결 직후 첫 메시지로 기존 사용자 신원을 인증하고,
  인증과 권한 확인을 마치기 전에는 상태나 이벤트를 전달하지 않아야 한다. 인증 실패 시 즉시 연결을 닫고 인증정보를 URL에 넣지 않아야 한다.

템플릿 저장소, 웹 기술, URL, API schema와 배포 방법은 구현 설계에서 정해야 한다.
템플릿은 개발 단계에 가져오고 고정된 버전으로 빌드해야 한다.
웹 전달 방식은 구현 영역이므로 T5의 별도 시스템 spec 보완은 생략하고 이 SRS와 구현 설계에서 계약을 정한다.

## 4. 사용자 흐름

기본 탐색은 **개요 → 측정 커버리지와 결과 행 → 필요한 측정 요청 / 실험 득실**이어야 한다.
운영 흐름 보드·근거·재생·관리 기능은 별도 경로로 유지하고 개요를 라이브 연결에 종속시키지 않아야 한다.
측정은 커버리지(기본), 요청, 회차, 프로파일, 동작 비용, 분배 점유의 보이는 링크 탭을 제공하고
실험은 전역 메뉴에서 직접 접근해야 한다. 제목은 화면마다 H1 한 번, 목록은 breadcrumb 없이,
상세만 상위 맥락 breadcrumb를 사용해야 한다. 중첩 카드와 중복 제목·가운뎃점 메타 나열을 피해야 한다.

| 업무 영역 | 제공해야 하는 흐름 |
|---|---|
| 개요·측정 | 지원 범위/스케줄러 사용 여부/최근 전 단계 득실/다음 조치 → 정확 조건 결과 행 → 요청 가능 범위 확인 |
| 실험 | 전역 메뉴 → 캠페인 득실 → 비대응 포함 단계 요약 → 모든 서비스 성공률/p95와 실제 순서 |
| 라이브 무대 | CHILL 구조 그림 위의 실시간 흐름(요청 → 게이트웨이 → POOL → 인스턴스 → 응답, 관측 → 판단 → 작업) 한 장 → POOL(워크로드)마다 카드·페이지 → 인스턴스·Node·예약 → 선택 판단의 근거 순으로 내려가며 확인 |
| 근거 | 판단 또는 작업 이벤트 선택 → 그 시점의 수요, 용량, 시간과 에너지 근거 및 대기 이유 확인 → 원본 근거 탐색 |
| 재생 | 실험과 단계 선택 → 라이브 무대와 같은 화면에서 기록 재생 → 단계별 요약과 두 실행 또는 두 단계 비교 |
| 운영자 | 카탈로그와 워크로드 관리, 단일 추론, 허용 자원과 설정 변경, 측정 요청과 근거 및 원본 이력 조회 |

- `DB-UX-01` 기본 등록, 조회, 수정과 측정 요청은 안내형 폼과 참조 선택으로
  수행할 수 있어야 한다. 필요한 입력은 사용자 업무 용어로 제공해야 한다.
- `DB-UX-02` 폼에 단위, 허용 범위와 필수 항목을 표시해야 한다. 서버 오류를
  해당 항목과 이유에 연결하고, 거부된 변경에서는 작성한 입력을 유지해야 한다.
- `DB-UX-03` 목록에서 상세와 작업에 직접 접근할 수 있어야 한다. CHILL 대상, namespace와 시간 구간 등 실제 조회 범위를 명시해야 한다.
- `DB-UX-04` 지원 입력 예시, 제출할 정의와 실제 응답을 확인할 수 있어야 한다.
  연관 객체와 근거로 이동할 때 원본 identity를 유지해야 한다.
- `DB-UX-05` 측정·실험의 데이터 화면은 데스크톱 가용 폭을 사용해야 한다.
  좁은 단일 열에 표를 가두거나 마지막 열을 잘라내지 않아야 한다. 숫자는 고정폭 숫자
  (tabular-nums)와 오른쪽 정렬을 사용하고, 단위·반올림·원본 정밀도를 구분해야 한다.
  좁은 화면에서도 표의 모든 열을 읽을 수 있어야 하며, sticky CTA가 마지막 내용이나
  키보드 focus를 가리지 않아야 한다. 데이터 화면의 주 CTA는 상단에 제공해야 한다.
- `DB-UX-06` 측정과 실험은 활성 링크 탭·상위 이동·브라우저 뒤로가기가 같은 탐색 맥락을
  유지해야 한다. 목록은 중복 breadcrumb 없이, 상세는 상위 맥락 breadcrumb 하나를 제공해야 한다.
  필터·선택 대상·원본 UID를 URL로 복원하고 패널을 닫으면 원래 셀/행에 focus를 돌려야 한다.
  외부 return URL로 이동하지 않아야 한다.

## 5. 기능 요구사항

### 5.1 시스템 상태와 인벤토리

- `DB-FR-01` 구성요소의 요청 상태와 관측 availability, 이유 및 시각을 조회해야 한다.
  웹서비스 health, Kubernetes Ready, Serving 준비, 접수 여부와 SLO 관측을 구분해야 한다.
- `DB-FR-02` DeviceClass의 선언된 능력과 대응 노드, Node identity, Ready,
  schedulability와 자원 할당을 조회해야 한다. 실행 적합성과 가용 자원은 CHILL이
  제공하는 측정 근거와 실제 할당 상태에 따라 표시해야 한다. 전력모드마다 제어 방식과
  목표를 쉬운 말로 표시하고 측정 요청의 전력모드 선택에도 같은 설명을 사용해야 한다.
- `DB-FR-03` 라이브 무대에 구성요소 상태와 이유, 워크로드별 SLO와 요청 결과, 부하와 큐,
  전체 및 활성 POOL의 전력과 에너지, 진행 작업과 관측 공백을 범위 및 구간과 함께 표시해야 한다.

### 5.2 모델과 워크로드 관리

- `DB-FR-04` 모델 등록, 조회, 수정과 삭제를 제공해야 한다. 산출물, 실행 경로,
  입력 계약과 측정 근거를 조회하고, 관련 워크로드와 변경 영향 및 삭제 거부 사유를 표시해야 한다.
  실행 경로의 runtime 계열과 backend를 사용자 용어로 표시하고, 등록과 수정에서는
  ChillServer가 허용하는 runtime 계열과 산출물 형식에 맞는 backend에서 선택하게 해야 한다.
- `DB-FR-05` 워크로드 등록, 조회, 수정과 삭제를 제공해야 한다. 식별자, 모델
  참조, 전처리기 참조, 선택 항목인 데이터셋 참조, `0 < p ≤ 100`인 지연 백분위와
  유한한 양의 목표 시간을 설정해야 한다. 같은 모델을 서로 다른 SLO의 워크로드에서
  참조할 수 있어야 한다.
- `DB-FR-06` 원하는 정의, 적용 정의, 지원 입력, 실제 준비, 접수 여부와 관리
  진행을 구분해야 한다. 근거 부족 시 필요한 실행 조건과 측정으로 안내해야 한다.
  ChillServer가 제공하는 준비 상태와 사유마다 쉬운 결론 문장과 다음 행동을 표시하고,
  원본 코드는 원본 보기에서 제공해야 한다.
- `DB-FR-07` SLO 변경의 신규 수락 요청 적용과 모델 또는 전처리 참조 변경과 삭제의
  기존 요청 마무리 계약을 안내해야 한다. 공유 모델의 영향 대상, 드레인과 실제 삭제
  완료를 조회하고 삭제된 등록 건의 관측을 같은 이름의 새 등록 건과 구분해야 한다.
- `DB-FR-28` 전처리기와 데이터셋 등록, 조회, 수정과 삭제를 제공해야 한다.
  전처리기의 입력 및 출력 계약과 모델 산출물별 전처리 산출물, 데이터셋의 레코드
  필드와 프로파일링 및 평가 부분집합을 조회하고, 참조하는 워크로드와 변경 영향 및
  삭제 거부 사유를 표시해야 한다. 대상 규칙은 [데이터셋과 전처리 관리 SRS](../catalog/SRS.md#3-요구사항)를 따라야 한다.

### 5.3 단일 추론

- `DB-FR-08` 허용된 워크로드의 지원 입력으로 추론 한 건을 제출하고 실제 결과
  또는 오류를 확인할 수 있어야 한다. 독립 입력 하나를 요청 하나로 제출하고,
  모델과 SLO는 등록된 정의를 적용하며 실행 배치는 firstfloor가 구성해야 한다.
- `DB-FR-09` 명시적 timeout과 SLO를 구분해야 한다. 요청 식별자와 결과를
  연결하고 CHILL 종단 지연, 브라우저 왕복과 웹 중계 지연을 구분해야 한다.
  응답 미수신 시 결과 미확인으로 표시하고 재제출은 사용자의 명시적 동작으로 수행해야 한다.
- `DB-FR-29` 입력 화면은 참조 전처리기의 원시 입력 계약에 있는 필드 이름, 형식과
  크기로 구성하고, 결과 화면은 원시 출력 계약에 있는 필드 이름과 형식으로 구성해야 한다.
  필드 이름은 계약의 이름을 그대로 표시하고, 쉬운 말은 형식과 입력 크기 설명에 사용해야 한다.
  출력 필드는 계약 순서대로 표시하고, 모든 워크로드와 모델에 같은 화면 규칙을 적용해야 한다.

### 5.4 POOL과 허용 자원

- `DB-FR-10` 전체 POOL, 워크로드별 활성 POOL, 측정 POOL과 가용 노드를 구분하고 소속 노드, 워크로드,
  인스턴스, 모델과 실행 경로, CPU, GPU, 메모리 할당 및 노드 전력모드를 조회해야 한다.
  여러 활성 POOL이 함께 쓰는 노드와 그 위 워크로드별 인스턴스, 목표 및 실제 자원 조건을 구분해야 한다.
- `DB-FR-11` 운영자가 제공할 노드, 실행 대상과 전력모드의 허용 범위를 선언하고
  유지보수 제외 및 복귀를 요청할 수 있어야 한다. ChillServer의 관리 API를 사용하고,
  영향받는 워크로드, 용량과 실제 POOL 관계 및 적용 진행을 표시해야 한다.
- `DB-FR-33` 워크로드마다 자동제어를 켜고 끌 수 있어야 하며, 현재 상태와 측정 근거
  대기 같은 판단 상태와 사유를 표시해야 한다. 꺼진 워크로드는 마지막 구성을 유지한다는
  사실과 그 워크로드에만 적용되는 수동 변경 결과를 표시해야 한다.

### 5.5 측정과 Evidence

- `DB-FR-12` 실행 경로, 대상 장비, 전력모드, 자원과 연동 스레드, 배치 조건,
  워밍업, 반복과 측정 구간을 지정하여 측정을 요청할 수 있어야 한다. 활성 측정은
  워크로드를 선택해 그 워크로드의 데이터셋으로 요청할 수 있어야 한다. 활성, 모델 로드
  유휴와 전환 측정 조건을 구분하고 실행에 사용한 조건은 읽기 전용으로 제공해야 한다.
  활성 및 모델 로드 유휴 측정 제출 전 ChillServer의 사전 확인 결과로 측정 가능 여부와 사유,
  실행할 측정 계획의 요약을 표시해야 한다.
- `DB-FR-13` 측정 접수와 API가 제공하는 실제 진행, 실행 결과 및 검증 결과를 조회해야 한다.
  실패, 필수 관측 누락, 실제 실행 대상과 요청 및 적용 조건의 차이를 조회해야 한다.
  측정 결과에는 실제 사용한 runtime과 backend, 실행 provider와 실행 장치를 표시해야 한다.
  측정 완료 결과와 검증 실패 사유마다 쉬운 결론 문장과 다음 행동을 표시하고, 원본 코드는
  원본 보기에서 제공해야 한다.
- `DB-FR-14` 프로파일의 실행 조건, 실행시간 분포, 처리량, 메모리, 전력과 에너지,
  유휴 기준, 반복 trial과 원시 Evidence를 탐색할 수 있어야 한다. 조건에 맞는 성공
  측정과 공백을 조회하고, 최신 성공 결과 선택과 Run 내부 trial 집계를 구분해야 한다.
  프로파일마다 모델 산출물, runtime, 전처리 산출물과 데이터셋의 측정 조건을 구분해
  표시하고, 같은 워크로드에서 조건이 다른 프로파일을 구분해야 한다.
- `DB-FR-30` 워크로드와 실행 경로마다 DeviceClass별 측정 가능 여부와 사유를 조회해야
  한다. 측정 요청에서 장비별 선택 가능 여부와 사유를 표시해야 한다.
- `DB-FR-32` 전력모드 전환 비용의 원시 기록을 조회해야 한다. 출발과 도착 전력모드,
  방향별 반복 측정의 소요 시간과 에너지, 관측 구간, 측정 상태와 원본 참조를 표시하고
  판단에 사용한 전환 비용과 연결해야 한다. 각 반복의 검증 판정과 사유, 경계 불확실성 및
  전환 중 Serving 지속 여부를 함께 표시해야 한다.
- `DB-FR-34` 측정 요청에서 대상 노드의 소속 상태를 표시하고, 서빙 중인 노드를 선택하면
  측정 거절 사유를 보여야 한다. 측정 중 노드의 측정 POOL 이동과 반환 진행, 측정 결과에 기록된
  CHILL이 배치하지 않은 파드 목록을 표시해야 한다.

- `DB-FR-53` 동작 비용 측정(`OperationCostMeasurement`)을 전력모드 쌍의 양방향 반복
  측정(`PowerModeTransitionCost`, DB-FR-32)과 구분해야 한다. 현재 제공되는 동작 비용
  목록과 상세에서 Node, 순서 있는 동작 조건, 단계별 저장 key와 판정, 진행과 사유,
  CR identity 및 Evidence 위치를 조회해야 한다. 제공되지 않는 시간·에너지와
  전력모드 쌍을 추정하지 않아야 한다. 자료 종류는 실제 API 이름과 일치해야 한다.
- `DB-FR-54` 분배 점유시간(`DispatchOccupancyMeasurement`)의 목록과 상세에서
  워크로드, Node, 측정 프로파일 참조, 배치, 공급 방식, 예열·측정 초와 worker 수,
  진행과 사유, 결과의 전력모드, 요청당 점유시간 d(ns/request), 지속 완료 처리량
  X(req/s) 및 Evidence 위치를 조회해야 한다. 누락 결과와 0인 결과를 구분하고,
  지정하지 않은 공급 방식을 임의로 정하지 않아야 한다.

### 5.6 구성 판단과 운영 설정

- `DB-FR-15` 실제 현재 구성, 비교 후보와 선택 목표를 구분해야 한다. 판단 결과의 제공 여부와 적용 조건을 표시해야 한다.
- `DB-FR-16` 판단에 사용한 부하, 큐, SLO, 실제 구성, 프로파일과 전환 근거,
  비교 기간 및 제외 이유를 연결해야 한다. SLO 충족 가능성과 전환 및 Serving의
  총에너지 비교를 구분하고 예측값과 실측값을 표시해야 한다.
- `DB-FR-17` 시스템 전체의 비교 기간, 제어 및 관측 주기와 운영 설정을 조회하고 변경할 수
  있어야 한다. 허용 자원과 제어요소 활성 여부의 전후 정의, 검증 결과, 영향 범위와
  적용 진행을 표시해야 한다. 예측 영향은 ChillServer의 값을 사용하고 평가 불가 상태를 표시해야 한다.
- `DB-FR-18` 인스턴스 배치, 자원 할당, 전력모드, 라우팅과 배칭 결정은 CHILL이
  수행해야 한다. 비교 실험의 정적 구성 및 제어요소 비활성화는 자동 제어와 구분하고,
  선택 근거와 설정을 실행 기록에 연결해야 한다. 설정 기반 요청 분배는 워크로드별 인스턴스
  분배 비율의 선언과 실제 반영 결과를 나란히 표시하고, 반영 대기와 실패 이유를 표시해야 한다.
- `DB-FR-55` 스케줄러가 제공하는 용량 행의 입력과 결과를 조회해야 한다. 행 key,
  워크로드 UID, SLO, Node identity, 전력모드, 프로파일, 자원 할당, 최대 배치,
  완료 여유, 계산 구간과 반복·합격·최소 요청 수 및 `capacityGridSteps`,
  `capacityBisectionWidth`, `capacityTailSamples`를 표시해야 한다. 입력의 분배
  점유시간 출처, μ와 κ(req/s), 계산 시각·소요시간, 이전 계산 여부 및 grid/bisection
  판정을 연결해야 한다. 계산 대기·거부·κ 없음·κ=0을 구분하고, 행에 고정된
  설정과 현재 운영 설정을 대조하되 현재 설정으로 과거 입력이나 판정을 덮지 않아야 한다.

### 5.7 전환과 장애 감독

- `DB-FR-19` 전환의 출발, 목표와 판단, 대상 동작과 의존관계, 준비, 유입 중지,
  기존 요청 마무리와 자원 해제 단계를 조회해야 한다. 동작별 시작 및 완료 시각,
  예상 및 실제 시간과 에너지를 요청 관측과 연결해야 한다.
- `DB-FR-20` 접수, 진행, 실제 완료, 실패와 일부 적용을 구분하고 실패 대상,
  원인과 마지막 실제 상태를 표시해야 한다. 모델 준비와 전환 완료는 CHILL의 완료 기준을 따라야 한다.
- `DB-FR-21` 부하 변화, 노드와 backend 소실, 관측 공백 및 용량 감소를 표시하고
  후속 판단으로 연결해야 한다. 개입은 해당 동작의 API가 허용하는 기능과 조건으로 제공해야 한다.

### 5.8 관측과 실험 및 이력

- `DB-FR-22` 등록 건, 적용 정의, 시간 구간과 처리 결과 조건으로 요청 기록과
  통계를 조회해야 한다. 유입, 미배정, 인스턴스 대기와 실행을 구분하고 실제 결과를
  표시해야 한다. 완료, 오류, 거절, timeout, 취소, 미완료와 전달 실패 및 SLO 초과를 구분해야 한다.
  요청별 단계 소요시간과 단위 수는 [워크로드 SRS 입력과 요청 결과](../workloads/SRS.md#6-입력과-요청-결과)의 요청 기록 항목으로 표시해야 한다.
- `DB-FR-23` 선택 구간의 지연 분포와 백분위, 모집단, 포함 및 제외 조건, 표본
  수와 집계 설정을 표시해야 한다. 통계는 전체 선택 구간을 기준으로 사용하고,
  표본 수가 0인 구간은 0개와 빈 통계 값으로 표시해야 한다.
- `DB-FR-24` 전력과 에너지에 대상, 단위, 시각과 구간 및 범위를 표시해야 한다.
  전체 POOL의 비참여 노드와 전환 소비를 포함하고 활성 POOL 소비 및 전체와 증분
  에너지를 구분해야 한다. 노드 소비는 한 번씩 집계한 값을 사용하고 관측 누락은 값 없음으로 표시해야 한다.
- `DB-FR-25` 부하 시나리오, 프로파일과 설정, 초기 구성, 제어 동작과 실제 상태,
  요청 결과와 전력을 같은 시간축에서 조회하고 비교해야 한다. 부하 변화, 반복 전환,
  POOL 한계와 장애 구간 및 예측과 실측의 차이를 제공하고 실험 해석은 분석자가 수행해야 한다.
- `DB-FR-26` 권한 범위의 원시 기록, 집계 조건과 원본 참조를 구조화된 자료로
  내보낼 수 있어야 한다. 시간 구간, 단위, 적용 정의와 출처를 보존하고 비밀정보를 제거해야 한다.
- `DB-FR-27` 변경의 행위자와 대상, 전후 정의, 접수와 적용 시각, 진행과 결과 및
  실패 원인을 조회해야 한다. 웹 접근 기록과 CHILL 변경 이력을 구분하고 과거 증거는 읽기 전용으로 제공해야 한다.
- `DB-FR-43` 삭제된 워크로드의 과거 기록에도 당시 이름과 모델을 표시해야 한다.
  등록 건의 UID와 적용 정의를 유지해 같은 이름으로 재등록한 워크로드의 기록과 구분해야 한다.
- `DB-FR-44` ChillServer의 실험 결과 조회로 실험 ID, 단계 경계, 단계별 결과와
  고정된 출처를 가진 불변 기록을 읽어야 한다. 로컬 보존 범위를 벗어난 구간도 근거 저장소 조회로 재생하고, 원본이 없는 구간은 관측 공백으로 표시해야 한다.
- `DB-FR-45` 동작 비용과 분배 점유시간(d) 측정 CR의 목록과 상세를 ChillServer에서
  조회해야 한다. 측정 조건, 진행, 성공과 실패 및 제공되는 결과 요약을 원본 CR identity와
  측정 근거 위치에 연결해야 한다(DB-FR-53~54). 전력모드 쌍의 원시 전환 기록은 DB-FR-32다.

### 5.9 라이브 무대와 근거

- `DB-FR-35` 라이브 무대의 모든 계층 맨 위 띠에 실시간 또는 기록 재생 모드, 시나리오 단계, 자동제어 켜짐
  여부, 마지막 관측 시각과 경과 초를 표시해야 한다. UTC와 KST를 함께 표시해야 한다.
- `DB-FR-50` 라이브 무대는 정보를 **개요(레벨 0) → POOL(레벨 1) → 인스턴스·Node·예약(레벨 2) → 판단 근거·원문(레벨 3)**의
  트리로 나누어야 한다. 한 화면에는 그 계층의 요약만 두고, 하위 값은 선택했을 때 하위 페이지, 펼침 카드 또는 옆 패널로 열어야 한다.
  열린 계층은 URL로 다시 열 수 있어야 하고, 닫기는 상위 계층의 같은 대상에 focus를 되돌려야 한다. 같은 페이지 안의 계층(레벨 2·3)은 뒤로가기도 같다.
- `DB-FR-51` 레벨 0은 CHILL 시스템 구조 그림(클라이언트 → ChillServer 게이트웨이 → 워크로드별 큐·분배 → Node의 인스턴스 → 응답,
  관측 → 스케줄러 판단 → 준비·분배·제거·전력 작업 → 예약 장부)을 그리고, 그 구성요소와 경로 위에 실시간 값과 사건을 표시해야 한다.
  데이터 경로와 제어 경로를 구분하고, 각 값의 출처를 라이브 채널의 실제 필드로 한정해야 한다. 서버가 주지 않는 값은 추정하지 않고 그리지 않으며, 관측 공백은 0이 아닌 공백으로 표시해야 한다.
- `DB-FR-52` 실시간 배치는 워크로드 UID(POOL)마다 하나의 묶음으로 표시해야 한다. 묶음 안에 그 워크로드가 분배 가능한 인스턴스와 소속 Node를 두고,
  여러 워크로드에 묶인 인스턴스는 각 묶음에 모두 나타내야 한다. 임의 목록 첫 N개나 모델 이름으로 묶지 않아야 한다.
- `DB-FR-36` 레벨 1의 POOL 카드·페이지에는 워크로드 UID마다 요청률, 분모를 명시한 성공률, 지연 백분위와 SLO
  목표 및 SLO 안·밖·실패 비율을 표시해야 한다. 레벨 0 묶음에는 수신 요청률, 성공률(분모 0이면 "비율 없음"), 상태 문구와 Node별 인스턴스 기호만 둔다.
  상태 문구는 등록됨·요청 받음·실행 준비됨·실제 처리 중의 4단계를 실제 상태에 맞게 구분해야 한다.
- `DB-FR-37` 레벨 2에는 POOL 묶음 안의 인스턴스와 Node를 표시해야 한다. 인스턴스는 준비 중, 준비·미분배, 분배 중, 실제 처리, 분배 해제 뒤 잔여 실행, 제거를 서로 다르게 그리고 실제 분배 비율을 표시해야 한다.
  Node는 전력모드와 현재 W, 사용 가능 여부와 사유를 표시해야 한다. 예약 장부는 owner, 영향 범위(Node·워크로드·인스턴스), 진행 중 또는 실패 후 잔류 사유를 표시하고, 작업 종료만으로 해제를 추정하지 않아야 한다.
- `DB-FR-38` 레벨 1에서 최근 10분의 공통 시간축에 부하, 성공률과 지연, 전체 및 활성 POOL
  전력(W), 판단과 작업 이벤트의 4레인을 맞춰 표시해야 한다. 레벨 0에는 판단·작업 사건 레인 하나만 둔다. 일시정지와 되감기를 제공하고 이벤트 선택 시 그 시점의 근거(레벨 3)를 열어야 한다.
  브라우저가 받은 구간만 그리고, 받지 못한 구간은 공백으로 둔다.
- `DB-FR-39` 레벨 3 근거 패널에 판단 당시의 관측 수요와 최소 수요, 후보별 용량(κ)과
  분배 점유시간(d), 예상 에너지, 전환 비용과 판단 여유(B) 및 대기 이유를 쉬운 문장으로 표시해야 한다. 원본 근거와 JSON은 선택해서 펼칠 수 있어야 한다. 선택한 판단은 새 판단이 와도 바뀌지 않아야 한다.

### 5.10 실험 재생과 결과

- `DB-FR-40` 시연과 E5 실행을 단계별로 선택하고 라이브 무대와 같은 화면 구성 및
  공통 시간축으로 기록 재생할 수 있어야 한다.
- `DB-FR-41` 단계별 표에 워크로드별 보낸 요청 수, 성공률, SLO 안 비율, 지연,
  배치 변경 수와 단계 에너지를 표시해야 한다. 부하 생성기의 보낸 요청 기준 성공률과 서버 수신 기준 성공률은 출처 및 같은 요청 집단의 분자·분모와 함께 구분해야 한다.
- `DB-FR-42` 두 실행 또는 두 단계를 같은 지표와 범위로 나란히 비교해야 한다.
  워크로드 행에 반복 표시된 공유 POOL 에너지는 행을 합산하지 않아야 하며 화면에 합산 금지를 명시해야 한다.

### 5.11 폐기 화면 요구사항 이력

기존 FR의 조회와 변경 기능은 위 흐름으로 유지한다. 화면 경로 전용 ID가 없던 다음
요구사항에는 이력 추적용 ID를 부여하며, 폐기된 화면을 구현 완료 조건으로 사용하지 않는다.

- `DB-FR-46` **폐기:** `/records`의 별도 링크 모음 화면 요구사항.
  원본 기록과 이력은 근거, 재생 및 운영자 영역에서 조회한다.
- `DB-FR-47` **폐기:** `/settings`의 별도 링크 모음 화면 요구사항.
  실제 설정 변경은 운영자 영역의 `/configuration`에서 유지한다.
- `DB-FR-48` **폐기:** `/experiments`의 “준비 중” 화면 요구사항.
  실험 조회는 DB-FR-40~42와 DB-FR-44의 재생 및 결과 화면으로 대체한다.
- `DB-FR-49` **폐기:** `/measurements/:kind/...`의 “연결 준비 중” 일반 분기 요구사항.
  지원하는 측정 종류만 명시하고, 측정 조회 및 요청 기능은 유지한다.

### 5.12 측정 커버리지와 측정·실험 해석

이 절은 [5차 구조 재설계](../../plans/2026-10-31-dashboard-measurement-redesign.md)의 정본이다.
기존 측정·catalog 채택·admission·저장 의미는 바꾸지 않고 운영 흐름과 읽기 projection을 정한다.
제품 UI/API는 개요·기준 충족·결과 행 등 시스템 중립 어휘를 써야 한다.

- `DB-FR-56` 개요는 지원 확인 범위의 사용 가능 수·기준 충족 수·재사용 수·지원 미확인 수와
  기준 시각을 먼저 제공해야 한다. 최근 비교는 **대응 단계 전부의 에너지 Δ와 서비스별 최악 단계**
  성공률/p95를 보여 주고 가장 유리한 단계를 골라 전체 결론으로 쓰지 않아야 한다.
  운영 보드는 별도 경로, 측정 기본은 커버리지여야 한다. 모델×장치 개요/전력모드×경로 상세,
  Compatible 분모·Unknown/미지원 제외·고정 장치 순서를 제공해야 한다.
  헤더 목표 batch 칩은 URL에 반영하고 목표가 없으면 ‘요청 범위’로 표시해야 한다.
  요청/회차/profile 건수를 완료율이나 표준 batch 스윕 달성으로 쓰지 않아야 한다.
- `DB-FR-57` 모든 측정 화면은 서버가 제공한 **사용 가능/부족/문제/진행/미측정**과 별도의
  **지원 안 함/확인 불가**를 그대로 표시해야 한다. 세부 complete/criteria_met/partial/warning/failed 등은
  서버 사유 행과 공통 도움말 한 곳에서 설명하고 클라이언트 상태/CI/체크 재판정을 제거해야 한다.
  complete는 채택·목표 batch 충족, criteria_met는 그중 결과 체크리스트 충족으로 분리해야 한다.
  sourceTimestampAbsent와 노드 전체 전력은 **두 판정의 gate가 아닌 고정 계측 각주**여야 한다.
  warning은 실제 catalog 기각·근거 파손/누락·선언 충돌·음수 d 등 문제에만 적용해야 한다.
  superseded/catalog 범위 밖 정상 결과는 complete+현재 스케줄러 미사용 사실, reuse는
  complete 가능·criteria_met 불가로 표시해야 한다. 과거 유효 결과 뒤 새 실패는 이력으로 보존해야 한다.
  실패 요청/후속 포함 셀의 평가 범위, 원본 phase/수용 여부를 구분하고 idle 성공을 active 반복으로 세지 않아야 한다.
- `DB-FR-58` 커버리지는 서버 집계 GET 한 번으로 상태/진척/원인/정확 조건 결과 행을 제공해야 한다.
  server query는 batches/node만, model/class/path/mode/status/CPU는 URL의 표시 필터여야 한다.
  여러 variant 셀은 **조건 k개**, batchProgress/대표값 null이어야 하며 variant 선택 후 수치를 표시해야 한다.
  서로 다른 CPU/dataset/protocol의 batch를 합쳐 완료를 만들지 않아야 한다.
  source 불완전/403/오류를 미측정·0건으로 바꾸지 않아야 한다. 지원 Unknown은 별도 사유/분모 제외다.
  1024px 이상과 중간 폭은 표 아래 상세를 유지하고 대체/Sheet는 768px 미만만 적용해야 한다.
  선택 variant/batch/필터와 focus 복귀를 유지해야 한다.
- `DB-FR-59` 목록은 실제 model/class/Node/mode/path/서버 상태·시각을 표시해야 한다.
  실제 실패 원인 한 줄과 후속 링크가 첫 화면·모바일에서 읽히고 긴 JSON diff는 상세에만 있어야 한다.
  Run 그룹은 정확 condition·namespace/controller UID 또는 completed/excluded 참조로만 연결해야 한다.
  이름/label 유사성으로 소유·해결됨을 만들거나 회차를 재번호하지 않아야 한다.
  기존 list/detail의 같은 서버 assessment를 제공해 단건 열람에 전체 aggregate 권한/준비를 강제하지 않아야 한다.
  동작 비용/점유 source 실패가 무관한 batch coverage를 막지 않아야 한다.
- `DB-FR-60` 요청은 모델×장치×mode×batch부터 고르는 한 편집 화면+동일 화면 검사/검토여야 한다.
  셀 진입 시 variantId/목표 batch를 전달하고 조건 변경은 기존 missing 자동 제외/검사를 무효화해야 한다.
  preflight에서 최신 exact/planned-only/unknown 대조와 **요청 가능 범위/실제 실행 예정 범위**를 제공해야 한다.
  부분집합 가능 경로만 ‘부족 배치만 요청’, declaredBatchSizes 경로는 읽기 전용 batch/기존 batchSizes 생략,
  중복·전체 탐색·조기 종료 가능성을 명시해야 한다. 모든 batch 실행을 보장하지 않아야 한다.
  Compatible 기본/Incompatible 숨긴 이유/Unknown 담당 조치, 입력 프리셋의 복수 후보 선택을 제공해야 한다.
  active/idle 시간·반복·warmup/settling·계측 주기/timeout·CPU의 실제 기본/복사값은 숨기지 않아야 한다.
  mode/path/CPU 포함 자동 이름의 suffix는 검사 통과 때 고정하고 응답 미확인 뒤 재생성하지 않아야 한다.
  URL 진입 자동 POST 없음, 명시 dryRun/preflight 검사·입력별 실패 원인·조치·사용자 제출만 허용해야 한다.
- `DB-FR-61` 결과 행은 정확 condition, pooled client p95/N, idle/active W, 총/증분 J/건,
  증분 CI, 독립 active/공유 idle n, 전력 출처·계측 각주·원근거를 함께 제공해야 한다.
  채택 profile은 catalog가 이미 읽은 trial에서 산출한 메모리 통계를 재사용하고 전체 Console 재로딩을 하지 않아야 한다.
  catalog 밖 단건은 기존 retained 경로로 구분해야 한다. CSV/LaTeX는 같은 서버 행/단위/null 이유를 안전하게 내보내야 한다.
  다른 회차 처리량으로 W를 나눠 총 J를 만들지 않고 노드 전력을 모듈 전력으로 해석하지 않아야 한다.
  reuse는 대상 confirmation 실측 행/source 참조 행을 구분하고 혼합 총 J를 만들지 않아야 한다.
  CI 음수 하한/0폭/null·N/n을 구분하고 개별 CI 중첩만으로 유의성을 판단하지 않아야 한다.
- `DB-FR-62` 실패 상세는 정확 owner의 원본 reason/message·제공 로그/종료 코드와 다음 조치를
  최상단에서 읽을 수 있어야 한다. Run 본문과 Passport 열람은 독립이며 미생성/404/장애를 구분해야 한다.
  실제 원인 미기록을 OOM으로 꾸미지 않아야 한다. 정확 후속은 먼저, 유사 조건은 관련 후보로 남겨야 한다.
  CPU/batch/반복/protocol diff는 전/후 표로 제공하고 원래 실패 이력을 숨기지 않아야 한다.
- `DB-FR-63` 음수/비유한/변환 불가 d는 서버 문제 상태, 원값은 원본/내보내기에 보존해야 한다.
  정상 0/null과 구분하고 동작 비용은 수용된 전체 Node J/실측 시간으로 표시해야 한다.
  계획 시간을 실측으로 대체하거나 key를 URL로 만들지 않아야 한다. 목록에서 d/X·전환 비용을 한 줄로 설명해야 한다.
- `DB-FR-64` 실험은 직접 전역 메뉴, 모든 대응/비대응/중복 단계의 요약과 이유를 제공해야 한다.
  대응 관계의 출처는 DB-FR-66을 따라야 한다(기존 full/static suffix 자동 대응 요구를 대체).
  CHILL−정적 또는 실제 A−B 이름과 에너지/모든 서비스 성공률·p95를 함께 보여야 한다.
  수동 비교는 실제 선택 이름으로 낮음/높음을 쓰고 부호만으로 CHILL 유리라 하지 않아야 한다.
  단위별 고정 자릿수, Δ 원값 계산, 작은 차이 `|Δ|<표시단위`는 **방향 없이** 제공해야 한다.
  유효 A/B이면 기준 0도 절대 차이/%p는 계산하고 상대 %/배율만 계산 불가로 구분해야 한다.
  모집단 분모 0/누락은 별도 이유이며 공유 에너지를 서비스별 합산/배분하지 않아야 한다.
- `DB-FR-65` 공통 부하/POOL W와 모든 서비스 성공률/p95 small multiples, 원값 표를 제공해야 한다.
  비대응은 선 끊김/속 빈 마커, 정책별 선/마커/범례와 명시 단위를 제공해야 한다.
  SLO의 출처는 DB-FR-66을 따라야 하며 현재 Workload 값을 소급하지 않아야 한다(기존 동결 stage KPI 한정 요구를 대체).
  실제 시간순과 대응 축·예정 α/설명/관측 평균을 구분하고 초별 보간·인과 주장을 만들지 않아야 한다.
- `DB-FR-66` 실험 화면은 [실험 관리 SRS](../experiments/SRS.md)의 정의·상태·실행 결과를 읽고,
  정책·비교 관계는 실험 정의에서, SLO는 정의와 실행 결과의 기록에서 읽어야 한다.
  단계 이름이나 요청률 유사성으로 추측하지 않아야 한다. 정의가 없는 과거 게시는
  비교 관계를 ‘미기록’으로 표시하고 추측으로 대체하지 않아야 한다.

## 6. 공통 변경과 오류 처리

- `DB-OP-01` 변경 전 대상, 전후 정의와 확인 가능한 영향을 제시해야 한다.
  삭제, 공유 모델 변경과 자원 제외는 명시적 확인을 받고 영향 정보의 공백을 표시해야 한다.
- `DB-OP-02` 수정 및 삭제에 API의 버전 전제조건을 전달해야 한다. 충돌 시 최신
  상태와 작성한 변경을 비교하게 하고 재제출은 사용자 확인을 거쳐야 한다.
- `DB-OP-03` 접수와 실제 완료를 구분하고 원본 작업 또는 대상 identity로 진행을
  조회해야 한다. 새로고침과 재접속 후 상태를 복원하고 관리 작업의 수명은 CHILL 계약을 따라야 한다.
- `DB-OP-04` 제출 중 중복 클릭을 막고 응답 미확인 시 결과 미확인으로 표시해야 한다.
  후속 행동은 상태 조회와 사용자 확인으로 정하고 변경, 추론과 측정 재제출은 명시적으로 수행해야 한다.
- `DB-OP-05` 검증 오류, 권한 거부, 대상 없음, 충돌, 접수 제한, backend 오류와
  timeout을 구분해야 한다. 추론, 관리 변경과 조회에서 받은 ChillServer 오류의 쉬운 의미와
  다음 행동을 표시하고, API가 제공하는 대상, 항목과 사유를 함께 표시해야 한다.
  원본 코드는 원본 보기에서 제공해야 한다.

## 7. 품질과 배포 요구사항

- `DB-NFR-01` 주요 흐름을 키보드로 수행할 수 있어야 한다. 입력 label, 오류,
  focus와 진행 상태를 식별할 수 있게 제공하고 상태에 텍스트 또는 기호를 함께 사용해야 한다.
  데스크톱과 좁은 화면에서 핵심 흐름을 사용할 수 있어야 한다.
- `DB-NFR-02` 시간대, 기간과 단위를 명시하고 원본 시각을 보존해야 한다.
  사용자 SLO 값을 그대로 제출하고 UI 표시 정밀도와 저장 값을 구분해야 한다.
- `DB-NFR-03` 조회 범위, page 크기, 갱신 주기와 timeout을 제한해야 한다.
  측정 커버리지는 서버 읽기 snapshot을 사용하고 마지막 정상 기준 시각·갱신·stale·부분 실패를
  표시해야 한다. 브라우저의 전체 Run/page 조인·Passport 전수 fan-out으로 첫 화면을 만들지 않아야 한다.
  source 실패 때 분모/미측정을 추정하지 않아야 한다. HTTP no-store와 인증 epoch별 메모리 cache,
  서버 TTL cache를 구분하고 권한 확인 전 cache 데이터를 제공하지 않아야 한다.
- `DB-NFR-04` 성능은 데이터 규모/동시 사용자와 웹 집계의 serving 제어 부하를 함께 기록해야 한다.
  3모델/8class/88요청/1,155Run/78profile, 동시 1·5에서 성공 GET·첫 사용 가능 coverage·선택 채택
  결과 행 판정 완료를 각각 p95 **2초 미만**으로 수용해야 한다. cold process→사용 가능/판정 완료는
  **30초 이내 목표**, warming/partial 비율·지속시간을 별도 수용해야 한다. 빠른 503/unknown으로 통과하지 않아야 한다.
  catalog 성공 확인 시각/오류·무변경 refresh, memo Get/ConfigMap 파싱 수·CPU/I/O·인증/BFF 비용을 구분해야 한다.
- `DB-NFR-05` 독립 실행 및 배포와 API 연결 및 인증 설정 주입을 제공해야 한다.
  credential은 배포 시 주입하고 Dashboard 중단 및 재시작 동안 CHILL Serving과
  제어 및 관리 작업은 기존 계약을 유지해야 한다.
- `DB-NFR-06` 외부 문자열은 안전한 텍스트로 렌더링해야 한다. 예제 인증, mock
  API와 가짜 메트릭을 제거하고 진단정보에서 비밀정보를 제거해야 한다.
- `DB-NFR-07` “실시간”은 라이브 채널이 연결되고 관측이 신선할 때만 표시하며,
  끊김·재연결 중·오래된 관측, 마지막 수신 및 관측 시각과 공백 구간을 구분해야 한다. 재접속 시 놓친 구간을 재동기화하고, 재개 가능한 범위를 넘으면 현재 상태를 다시 받아 공백을 숨기지 않아야 한다.

### 라이브 무대의 연속 흐름

요구사항: DB-FR-03, DB-FR-35~40, DB-FR-44, DB-FR-50~52, DB-NFR-07.

- **Given** 빈 상태부터 첫 구성, 부하 급증에 따른 확장과 급감에 따른 축소까지의 저장된 시연 기록이 있다.
- **When** 실제 브라우저에서 같은 라이브 무대를 기록 재생하고 레벨 0 흐름 보드에서 POOL을 열고 판단 및 작업 이벤트를 선택한다.
- **Then** 레벨 0만으로 “빈 상태 → 첫 구성 → 확장 → 축소”의 원인과 결과를 구조 그림 위에서 이해할 수 있고, 레벨 1·2에서 네 상태 문구와 준비됐지만 미분배인 인스턴스가 실제 처리와 구분되며, 보드로 돌아가면 열었던 POOL 묶음에 focus가 돌아온다.
- **Then** 공통 시간축의 부하, 성과, 전력과 이벤트가 일치하며 근거 패널은 선택 시점의 판단을 보여 준다.

### 라이브 인증과 재동기화

요구사항: DB-INT-07~08, DB-NFR-07, DB-SEC-01~04.

- **Given** 첫 메시지 인증을 요구하는 라이브 채널과 신선한 관측이 있다.
- **When** 미인증 또는 잘못된 신원으로 연결하고, 정상 인증 연결에서는 통신을 끊었다가 재접속한다.
- **Then** 인증 전 데이터가 전달되지 않고 인증 실패 연결은 즉시 닫히며, 정상 연결만 서버 push를 받는다.
- **Then** 끊김과 마지막 수신 시각을 표시하고 놓친 구간을 재동기화하며, 재개 범위 밖이면 현재 상태를 다시 받고 관측 공백을 유지한다.

### 재생 결과의 모집단과 에너지

요구사항: DB-FR-24, DB-FR-40~44.

- **Given** 보낸 요청 수와 서버 수신 요청 수가 다르고 공유 POOL 에너지가 워크로드 행에 반복된 두 실행이 있다.
- **When** 로컬 보존 범위 밖의 기록을 포함해 실험과 단계를 조회하고 나란히 비교한다.
- **Then** 근거 저장소의 불변 기록으로 재생하며 단계별 표에 각 성공률의 출처와 분자·분모를 구분하고 공유 에너지 행을 합산하지 않는다.
- **Then** 삭제된 워크로드의 당시 이름과 모델을 유지하고 같은 이름의 재등록 건과 UID로 구분한다.

### 운영자 조회와 폐기 화면

요구사항: DB-FR-45~49.

- **Given** 동작 비용과 분배 점유시간(d) 측정 CR의 진행 및 결과가 제공된다.
- **When** 운영자 영역에서 두 종류의 측정 목록과 상세를 조회하고 기본 탐색 경로를 따른다.
- **Then** 조건, 진행, 성공과 실패 및 결과 요약이 원본 근거와 연결된다.
- **Then** `/records`, `/settings` 링크 모음, `/experiments` 준비 중 화면과 `/measurements/:kind/...` 일반 준비 중 분기가 노출되지 않고 지원 기능은 새 흐름에서 접근된다.

### 동작 비용의 실제 API와 원본 identity

요구사항: DB-FR-45, DB-FR-49, DB-FR-53, DB-OP-05, DB-NFR-01~03.

- **Given** power/prepare/idle/remove 조건과 일부 단계의 저장 key·판정이 있는 동작 비용,
  빈 목록, 실패·근거 부족 결과 및 같은 이름의 다른 UID가 제공된다.
- **When** `/measurements`에서 동작 비용 목록을 열고
  `/measurements/operation-cost-measurements/[namespace]/[name]?uid=<uid>`를 공유·새로고침한다.
- **Then** 순서 있는 조건과 저장된 단계 결과를 이름으로 연결하고 미기록 단계는
  “아직 기록된 결과가 없어요”로 표시한다. 저장 위치는 `{store,key}` 그대로 보존하고
  HTTP 다운로드 주소나 Passport 링크를 만들어 내지 않는다.
- **Then** 다른 UID는 “같은 이름으로 다시 등록된 다른 측정이에요”로 차단한다.
  빈 목록은 “아직 등록된 동작 비용 측정이 없어요”, 403은 권한 오류로 구분한다.
  자료 찾기에 미지원 `power-mode-transition-costs` 선택지가 없고, 해당 옛 URL은
  미지원 안내와 실제 목록 이동만 제공하며 다른 측정으로 자동 대체하지 않는다.

### 분배 점유시간의 조건과 누락 결과

요구사항: DB-FR-45, DB-FR-54, DB-OP-05, DB-NFR-01~03.

- **Given** Measuring/Complete/Insufficient/Failed, 공급 방식 미지정, `perRequestNanos`
  누락과 0, 문자열 처리량 및 결과 참조가 있는 분배 점유시간 응답이 있다.
- **When** `/measurements/dispatch-occupancy-measurements?namespace=<ns>`에서
  `/measurements/dispatch-occupancy-measurements/[namespace]/[name]?uid=<uid>`를 연다.
- **Then** 실제 조건과 진행·사유를 표시하고 d는 ns/request, X는 req/s로 표시한다.
  0은 0으로, 누락은 “결과 없음”, 공급 방식 미지정은 “기록되지 않았어요”로 보인다.
  CRD에만 있고 API가 투영하지 않은 필드를 화면의 값으로 만들지 않는다.
- **Then** 빈 목록·404·401/403·503·timeout을 구분하고 다른 UID의 결과를 이전 근거로
  사용하지 않는다. 키보드로 상세·원본을 열고 닫으면 선택한 행으로 focus가 돌아온다.

### 용량 입력과 계산 판정 및 현재 설정 대조

요구사항: DB-FR-16~17, DB-FR-55, DB-OP-05, DB-NFR-01~03.

- **Given** Built(양수 및 κ=0), CapacityPending, CapacityRejected(점유시간 누락 및
  NonMonotone), previous=true와 κ 누락 행, 현재 설정과 다른 세 탐색 입력이 있다.
- **When** `/scheduler/capacity?row=<key>`를 새로고침하고 입력, grid, bisection,
  현재 설정 대조를 열며 `/configuration?section=capacity`로 이동한다.
- **Then** key가 일치하는 행만 열리고 모든 CapacityInput 필드와 서버 판정이 보인다.
  grid와 bisection의 실행 순서, rate, requests, passed, met와 percentileMS를 표시하며
  조기 종료한 구간을 전체 구간 합격률로 바꾸지 않고 -1을 음의 지연으로 그리지 않는다.
- **Then** 과거 입력과 현재 설정을 별도 열로 보이며 세 필드 변경 시 다른 key의 행으로
  식별된다. previous는 “이전 계산 결과 · 다시 계산 중”, 없는 key는 “이 용량 행을
  찾을 수 없어요”로 표시하고 최신 행으로 대체하지 않는다. 설정 조회만 실패해도
  용량 행은 유지되며 κ가 실제 부하·처리량 또는 현재 SLO 충족 관측으로 표현되지 않는다.

  1440px 개요에 가로 스크롤이 없고 390px에서는 장치 선택·평평한 행으로 상태/근거를 읽는다.
  이전 snapshot은 기준 시각/stale/갱신 상태를 함께 표시하며 source 실패를 새 정상값으로 포장하지 않는다.
  RKNN 등 비호환은 resolver 근거로만 제외하고 Unknown은 별도로 남긴다.
  source 실패/권한 거부/일부 page는 미측정이 아니다. 완료 수와 논문 적격 수는 별개다.
  정확 variant/Node/reuse·실패 요청과 후속 포함 셀의 범위 차이, 현재/과거 실패 수를 설명할 수 있다.

### 조건 목록과 회차 연결

요구사항: DB-FR-59, DB-FR-62, DB-UX-06.

- **Given** 같은 모델/Node/경로지만 모드·CPU·dataset이 다른 요청과 `195`, `195b`처럼 이름이
  겹치는 Run, 정확 completed/excluded 참조, `result:null` 실패 요청이 있다.
- **When** 목록 필터·그룹·상세·뒤로가기를 사용하고 URL을 새로고침한다.
- **Then** 필터와 UID가 유지되고 다른 조건은 별도 그룹이다. exact 참조 회차는 원래 batch/attempt,
  소유 관계를 알 수 없는 회차는 Run 이름과 ‘관련 후보’를 표시한다. 이름 부분일치로 소유 수를 만들지 않는다.

### 미리 채운 요청과 중복 안내 (M5)

요구사항: DB-FR-60, DB-FR-12, DB-OP-04.

- **Given** 빈 셀, 이미 완료한 조건, 여러 Node/워크로드, 삭제된 prefill 참조와
  architecture가 같지만 명시 가속기가 다른 경로가 있다.
- **When** ‘이 조건으로 측정 요청’으로 진입해 검토까지만 이동한다.
- **Then** 모델/class/Node/path/mode/명시 목표 batch와 복귀 필터가 유지된다.
  부분집합 가능 경로는 부족 batch, 선언형 경로는 고정 범위/조기 종료와 실제 예정 범위를 읽고,
  조건 변경/다중 variant/검사 고정 suffix를 확인하며 실제 active/idle 시간과 계측 설정을 읽는다.
  복수 입력 프리셋은 직접 고르며 비호환 경로는 기본 숨김, Unknown은 지원 확인 목록이다.
  검사 실패 원인과 다음 행동은 접지 않은 본문에 있고 입력 변경은 이전 검사를 무효화한다.
  URL 진입만으로 POST하지 않으며 명시 검사·검토 뒤에만 제출한다. 기존 복사/prefill 충돌도 안내한다.

### 상세 수치의 범위와 품질 (M3·M4)

요구사항: DB-FR-61, DB-FR-63, DB-FR-53~54, DB-UX-05.

- **Given** 배치 하나의 결과, 서로 다른 0.092607…/0.086819… J/건, CI 누락, 지연 표본 1개,
  열 관측 없음, 음수·NaN 변환·정상 0·누락 d와 시간/J 없는 동작 비용 projection이 있다.
- **Then** 요청 배치 1·2·4 중 1·2만 측정되면 서버 ‘부족 2/3’이며 개별 CI 중첩만으로 유의성을 판단하지 않는다.
- **When** 측정 상세 첫 화면과 배치별 표, 점유시간·동작 비용 상세를 연다.
- **Then** 단일 배치에 최적성/전수 측정을 주장하지 않는다. 단위별 고정 자릿수와 정확값으로 범위를 구분하고
  CI 미제공과 회차별 지연 범위/표본 수가 보인다. 유휴 W 오차를 J 오차로 사용하지 않는다.
  모델·장치·Node·전력모드·실행 경로·배치·CPU·데이터셋을 원본 펼침 없이 상단에서 읽는다.
- **Then** 음수/비유한 d는 같은 서버 assessment의 경고이며 정상 0/null과 별개다.
  동작 비용 실측 시간/J는 제공값 또는 이유 있는 미제공이며 계획 시간으로 대체하지 않는다.
  결과 행의 idle/active W·총/증분 J·CI/n/N·계측 각주를 읽고 같은 서버 행을 내보낸다.
  timestamp 부재/node-wall만으로 complete/criteria_met를 강등하지 않으며 reuse는 기준 충족과 구별한다.

### 실패 회차와 후속 측정 (M2)

요구사항: DB-FR-62, DB-OP-05, DB-UX-06.

- **Given** evidence 없는 실패 Run, evidence 참조는 있지만 로드 실패한 Run,
  stale condition, 다른 UID와 상세 원인 없는 RetryLimitExhausted가 있다.
- **When** 실패 측정에서 회차 상세로 이동하고 Run/Passport 영역을 읽는다.
- **Then** 목록의 정확 namespace/name/uid로 선택한 Run 본문·원문 사유/제공 로그는 유지된다.
  evidence 미생성과 근거 조회 장애를 구별하고 502만으로 실행 원인을 단정하지 않는다.
  목록 조회가 끝나지 않으면 대상을 찾지 못했다고 단정하지 않는다.
  정확 owner로 연결된 최신 실패 회차가 있으면 요청 상세 최상단에 로그 발췌·종료 코드·다음 행동이
  보이고 한 번의 링크로 전체 로그에 도달한다. JSON 문자열 Job/실제 실행은 사실 목록으로 읽힌다.
- **Then** 후속 유효 결과 링크를 먼저 안내하되 검증하지 못한 후속은 관련 후보로 남긴다.
  재요청 CTA는 ‘조건을 복사해 새 이름으로 요청’으로 본문과 일치하고 자동 제출하지 않는다.

### 실험의 결론·동명 비교와 단계 (E1·E2)

요구사항: DB-FR-64~66, DB-FR-41~44, DB-UX-05~06.

- **Given** workloads/requests 두 게시 형태, 같은 이름 다른 UID/정의 또는 identity 누락,
  다른 measurementRules, 성공률 분모 0과 기준 에너지 0, α 없는 단계와 정의 없는 과거 게시가 있다.
- **When** `/experiments`에서 캠페인을 선택하거나 기존 `a/as/b/bs` 직접 URL을 열고
  단계를 바꾸며 보조 A/B 선택기를 연속 변경한다.
- **Then** 캠페인 목록의 질문·정책·결론이 보이고 실험 정의에 명시된 유일한 대응 단계만 자동 선택된다.
  연속 선택은 서로 덮어쓰지 않으며, 요약의 같은 서비스 A/B가 나란히 보인다.
  identity·규칙·구간 차이를 유지하고 성공률 의미·분모와 p95 표본을 읽을 수 있다.
  A−B의 %p/ms/J는 기준 0도 계산하고 상대 %/배율만 기준 0에서 계산 불가임을 구분한다.
- **Then** 공유 에너지 합산 금지와 공백 오차 상한의 의미가 보인다. 단계 클릭은 선택·결과 focus를
  갱신하고 α 미제공을 목표 부하로 추측하지 않는다. 게시되지 않은 초별 선을 만들지 않는다.
- **Then** 1440px와 390px에서 비대응 단계 포함 전체 단계명·기간·부하를 읽고 모든 서비스의
  성공률/p95 소형 다중 차트를 동시에 탐색한다. 실제 시간순/대응 축, 예정 α/관측 평균/미기록 설명을 구분한다.
  CHILL−정적 부호와 행별 같은 자릿수·작은 차이·정확값을 확인하며 공유 에너지와 서비스 손실을 함께 말한다.
- **Then** 단계 이름·요청률이 유사해도 정의에 없는 비교 관계를 만들지 않는다.
  정의 없는 과거 게시의 비교 관계는 ‘미기록’이며 정책·SLO도 기록된 출처만 사용한다.

### 데이터 폭·탐색과 재설문

요구사항: DB-UX-05~06, DB-NFR-01~03, DB-FR-56~65.

- **Given** 1440/1024/768/390px 화면과 키보드만 사용하는 탐색이 있다.
- **When** 마지막 열·행/CTA를 보고 필터/셀/회차를 열고 뒤로가기·닫기·직접 진입한다.
- **Then** 모든 수치 열을 읽을 수 있고 tabular 숫자·단위·오류 focus가 구별되며 sticky UI가
  마지막 내용과 focus를 가리지 않는다. 외부 returnTo는 사용하지 않고 패널 닫기는 선택 행/셀로 돌아온다.
- **Then** **엣지 클러스터 운영 담당자 계열 3역할**의 독립 세션에서 표준 SUS와 M1~M5/E1~E2를 평가한다.
  과거 학술 역할 평가와 모집단이 달라졌음을 밝히고 직접 점수 향상으로 단정하지 않는다.
  평균 SUS ≥70와 M1·M3·M5·E1 전원 성공을 모두 만족해야 수용하며 부분 성공은 실패다.
  preflight/`?dryRun=All`은 설문 가드에서 허용하고 실제 제출/삭제/변경은 차단해야 한다.
  M1/E1은 1분 이내, M3은 mode/path 셀부터 정확 결과/운영 사용 여부·제한을 설명해야 한다.
  미달이면 설계·구현·배포·재설문을 반복하고 문서만으로 달성을 선언하지 않아야 한다.
  system storage·이 탭 토큰 삭제·401/4401·403/장애 구분·모든 새 창 opener 제거도 확인해야 한다.
