# 워크로드 관리 SRS

## 1. 목적과 범위

이 문서는 CHILL 워크로드의 등록, 조회, 수정, 삭제와 요청 접수 조건을 정의한다.
[시스템 명세](../README.md)의 관리 계약을 구체화하며, 모델, 전처리, 데이터셋 참조와
측정 근거, 워크로드별 활성 POOL과 실제 Serving 상태를 다룬다.

요구사항 ID의 `WM`은 워크로드 관리를 뜻한다. 각 요구사항은 구현과 검증의 기준이다.
이 문서의 상태명은 외부에서 관찰할 의미를 나타내며, API 필드 표현은 구현 설계에서 정한다.

요청 수신은 CHILL이 요청을 받은 시점이며 종단 지연의 시작이다.
요청 수락은 정의, 입력과 접수 조건을 확인하고 큐 또는 실행 경로에서 처리를 맡기는 시점이다.

| 관련 영역 | 책임과 원본 |
|---|---|
| 모델 등록 | 실행 산출물과 입력 정의는 [모델 경계 ADR](../../adr/0012-model-artifact-compatibility-boundary.md), 산출물별 입력 계약은 [입력 계약 ADR](../../adr/0016-declared-batch-size-artifact-capability.md)을 따름 |
| 전처리와 데이터셋 | 원시 입력과 출력 계약, 전처리 산출물, 데이터셋 표본과 참조 보호는 [데이터셋과 전처리 관리 SRS](../catalog/SRS.md)를 따름 |
| 프로파일 | 실행 조건의 측정과 조회는 [프로파일링과 Evidence](../00_measurement.md)를 따름 |
| 구성 선택 | 자원 배분과 SLO 우선 판단은 [구성 선택](../04_configuration_selection.md)을 따름 |
| 요청 실행 | 큐, 배칭, 시간 정보와 결과 반환은 [라우팅과 배칭](../03_routing.md)을 따름 |
| 전환 | 실제 준비, 기존 요청 마무리와 자원 해제는 [전환 실행](../05_transition_control.md)을 따름 |
| 관측 | 요청 기록과 집계 및 실험 해석은 [SLO 관측과 집계](../README.md#slo-관측과-집계)를 따름 |

## 2. 사용자와 관리 정보

### 2.1 역할

| 역할 | 동작 |
|---|---|
| 운영자 | 모델과 워크로드를 관리하고 측정을 요청 |
| 서비스 사용자 | 워크로드 목록과 상세 조회, 식별자를 지정한 추론 요청 |
| CHILL | 정의 검증, 요청 접수, 실행 준비와 상태 제공, 변경 및 삭제 적용 |
| 분석자 | 원시 요청 기록과 집계 조건을 사용해 지연 및 처리 결과 해석 |

- `WM-01` 관리 변경은 운영 권한을 가진 호출자에게 허용해야 한다. 서비스 사용자의 조회와 추론 권한은 관리 변경 권한과 구분해야 한다. 권한 구현은 배포 환경의 기존 인증 및 권한 체계를 사용한다.

### 2.2 정의와 조회 정보

| 정보 | 소유와 의미 |
|---|---|
| 워크로드 식별자 | 요청과 조회에서 사용할 서비스 식별자. 해당 CHILL 서비스의 워크로드 식별 범위에서 유일 |
| 모델 참조 | 기존 모델 등록정보의 참조. 실행 산출물의 근거 |
| 전처리 참조 | 등록된 전처리의 참조. 원시 입력과 출력 계약, 전처리 산출물의 근거 |
| 데이터셋 참조 | 등록된 데이터셋의 참조. 프로파일링과 평가 부하에 사용할 원시 표본의 근거 |
| SLO | 지연 백분위와 목표 시간. 백분위는 `0 < p ≤ 100`, 목표 시간은 유한한 양수와 명시된 시간 단위 |
| `requestLifetime` | 선택 요청 수명(Duration). SLO 목표 시간 이상이며 게이트웨이 상한 129초 이하 |
| 현재 서빙 관계 | 워크로드별 활성 POOL의 소속 노드와 실제 배정 인스턴스에서 조회 |
| 지원 입력 | 참조 전처리의 원시 입력 계약과 원시 출력 계약 |
| 실제 상태 | 신규 요청 접수 가능 여부, 실행 준비 상태, 상태의 이유와 관측 시각 |
| 관리 작업 | 적용할 정의, 진행 단계, 완료 또는 실패 여부와 원인 |

- `WM-02` 워크로드는 식별자, 모델 참조, 전처리 참조와 SLO를 필수 정보로 가져야 한다. 데이터셋 참조는 선택 정보다. 생존 중인 워크로드의 식별자는 유지해야 한다.
- `WM-03` 같은 모델을 참조하는 워크로드들을 서로 다른 식별자와 SLO로 등록할 수 있어야 한다.
- `WM-04` 지원 입력은 참조 전처리의 원시 입력 계약과 원시 출력 계약에서 제공해야 한다. 측정 근거 확보 여부는 실제 준비 상태와 요청 접수 여부에 반영해야 한다. 요청은 조회된 원시 입력 계약을 따라야 하며, 모델, 전처리와 SLO는 등록된 워크로드 정의에서 적용해야 한다.
- `WM-05` 워크로드의 상태는 선언된 정의, 실제 준비 상태, 관리 작업의 진행을 구분해 제공해야 한다. 서비스 사용자는 모델, SLO, 지원 입력과 요청 접수 여부를 확인할 수 있어야 한다. 운영자는 워크로드의 활성 POOL 상태에서 현재 서빙 관계를 조회하고, 준비 지연이나 접수 제한의 원인과 변경 진행을 확인할 수 있어야 한다.
- `WM-33` 워크로드는 선택 정보로 `requestLifetime`을 가질 수 있어야 한다. 요청의 `X-Chill-Request-Timeout` 헤더가 없으면 워크로드 값을 적용하고, 둘 다 있으면 작은 값을 적용하며, 실제 적용 수명을 응답과 요청 관측 기록에 제공해야 한다.

`minimumDemand`는 A5의 대안 중 D1로 확정된 scheduler의 워크로드별 설정 맵이므로 Workload 정의에 포함하지 않는다.

## 3. 등록과 요청 접수 조건

### 3.1 등록 검증

- `WM-06` 등록과 수정 시 식별자 중복, 필수 정보, SLO 범위, 모델, 전처리와 데이터셋 참조의 존재와 삭제 진행 여부, 모델 입력 정의를 검증해야 한다. 데이터셋을 참조하면 데이터셋과 전처리의 [호환성](../catalog/SRS.md#32-데이터셋)을 확인해야 한다. 삭제 중인 대상의 참조는 거부해야 한다. 검증 오류는 해당 항목과 이유로 제공해야 한다. 거부된 변경은 현재 정의를 유지해야 한다.
- `WM-07` 실행 근거가 준비되기 전에도 유효한 워크로드 정의를 등록할 수 있어야 한다. 이 경우 준비 대기 상태와 부족한 근거를 제공해야 한다. 데이터셋 참조가 비어 있는 워크로드에는 준비 대기 상태와 데이터셋 없음 사유를 제공해야 한다. 측정은 운영자의 요청으로 워크로드의 데이터셋을 사용해 수행한다.
- `WM-08` 서빙 후보는 제공된 자원에서 모델을 실행할 수 있고, 참조 전처리가 해당 모델 산출물의 전처리 산출물을 제공하며, 실행 조건에 맞는 측정 근거를 갖춘 구성으로 한정해야 한다. 모델 산출물은 runtime이 함께 적재하는 하나 이상의 모델 파일로 구성할 수 있다. 측정 근거와 실행 조건의 대응은 [측정 조건](../00_measurement.md#측정의-단위)과 프로파일 조회 계약을 따라야 한다. 실제 노드와 POOL 배정은 구성 선택을 따른다.
- `WM-34` 등록과 수정 시 지정된 `requestLifetime`이 SLO 목표 시간 이상이고 게이트웨이 상한 129초 이하인지 검증해야 한다. 범위를 벗어나면 해당 항목과 이유를 제공하여 변경을 거부하고 현재 정의를 유지해야 한다.

### 3.2 상태의 의미

| 상태 | 의미 | 신규 추론 요청 |
|---|---|---|
| 준비 대기 | 등록은 완료되었으며, 데이터셋 참조, 실행 경로나 해당 조건의 측정 근거 확보가 필요 | 접수 제한 사유 반환 |
| Serving 준비 중 | 사용할 실행 근거가 있으며, 인스턴스 준비나 용량 확보 진행 중 | 설정된 유입 큐와 timeout 범위에서 접수 |
| Serving 준비 완료 | 요청 모델을 처리할 실제 준비 인스턴스와 분배 경로가 있음 | 설정된 큐와 자원 한도 내 접수 |
| 변경 중 | 모델 변경을 위해 기존 요청 마무리와 새 정의 적용 진행 중 | 변경 중 사유 반환 |
| 삭제 중 | 신규 유입 중지 후 기존 요청 마무리와 워크로드 연결 해제 진행 중 | 삭제 중 사유 반환 |

- `WM-09` 신규 요청은 유효한 워크로드와 원시 입력 계약, 해당 조건의 실행 근거를 확인한 뒤 수락해야 한다. 준비 대기, 모델 변경 중, 삭제 중인 워크로드의 신규 요청에는 제한 사유를 반환해야 한다.
- `WM-10` 준비된 인스턴스가 일시적으로 없으면 수락한 요청을 워크로드별 유입 큐에서 관리하고, 실제 준비 상태와 부하를 구성 선택에 전달해야 한다. 설정된 큐 한도와 명시적 timeout 및 취소를 적용해야 한다. 수용 가능한 인스턴스가 준비되면 요청을 전달해야 한다.
- `WM-11` 요청 접수 여부, SLO 목표와 실제 지연 관측을 각각 제공해야 한다. 과부하에서는 가용 자원으로 SLO 우선 대응을 계속하고 실제 지연과 처리 결과를 기록해야 한다. 큐와 요청 수명은 Serving 설정의 한도를 따른다.

## 4. 조회와 수정

### 4.1 조회

- `WM-12` 워크로드 목록과 식별자별 상세를 제공해야 한다. 준비 대기, 준비 중, 변경 중, 삭제 중인 객체도 상태와 함께 조회할 수 있어야 한다. 존재하지 않는 식별자는 조회 오류로 제공해야 한다.
- `WM-13` 변경이나 삭제 요청의 수락과 실제 완료를 구분해야 한다. 진행 중에는 현재 적용 정의와 변경 대상, 진행 단계와 원인을 조회할 수 있어야 한다.

### 4.2 SLO 수정

- `WM-14` SLO만 수정하면 새로 수락하는 요청부터 변경된 SLO를 적용해야 한다. 이미 수락한 요청에는 수락 당시 SLO를 유지해야 한다.
- `WM-15` SLO 변경을 구성 선택과 요청별 배칭 판단에 반영해야 한다. 요청 기록과 통계 조회에서 해당 요청에 적용한 SLO를 확인할 수 있어야 한다.

### 4.3 모델 수정

다음 순서로 요청 의미를 보존하면서 변경한다.

1. 새 정의를 검증하고 변경을 수락한다.
2. 해당 워크로드의 신규 요청 접수를 중지한다.
3. 유입 큐, 인스턴스 큐와 진행 중 실행에 남은 기존 요청을 마무리한다.
4. 기존 정의의 연결을 해제하고 새 정의를 적용한다.
5. 새 정의의 실행 근거와 준비 상태에 따라 요청 접수를 재개한다.

- `WM-16` 모델 또는 전처리 참조를 수정하면 위 순서를 따라야 한다. 이미 수락한 요청은 수락 당시 모델, 전처리와 입력 계약, SLO로 처리해야 한다. 이 참조들과 SLO를 함께 수정하면 이 변경 절차를 적용해야 한다. 데이터셋 참조 수정은 이후 요청하는 측정부터 적용해야 한다.
- `WM-17` 변경이 수락된 뒤에도 실제 적용 단계와 실패를 조회할 수 있어야 한다. 새 정의에 필요한 근거가 없으면 적용 후 준비 대기로 표시해야 한다. 실행 준비나 연결 해제가 실패하면 실제 적용 상태와 원인을 제공해야 한다.
- `WM-18` 워크로드별 변경과 삭제는 한 번에 하나의 관리 작업으로 진행해야 한다. 진행 중인 관리 작업과 충돌하는 수정이나 삭제 요청은 충돌 사유를 반환해야 한다.

## 5. 삭제와 참조 관계

### 5.1 워크로드 삭제

- `WM-19` 삭제를 수락하면 신규 요청 접수를 중지하고 삭제 중으로 표시해야 한다. 유입 큐와 인스턴스 큐, 진행 중 요청은 기존 처리 계약으로 마무리해야 한다. 마무리는 정상 완료, 실제 오류, 명시적 timeout 또는 취소의 결과로 기록해야 한다.
- `WM-20` 남은 요청이 마무리되면 라우팅과 인스턴스의 워크로드 연결을 해제해야 한다. 해당 워크로드만 사용하는 준비 작업과 Serving 자원은 실제 종료를 확인한 뒤 삭제를 완료해야 한다. 실패나 미완료가 있으면 삭제 진행과 원인을 조회할 수 있어야 한다.
- `WM-22` 삭제 완료 후 서비스 목록과 상세에서는 워크로드를 제거해야 한다. 보존된 요청 기록과 실험 자료는 기존 정의를 해석할 수 있도록 유지해야 한다. 동일한 서비스 식별자로 다시 등록해도 각 등록 건의 관측 기록을 구분할 수 있어야 한다.

### 5.2 모델 참조와 동적 서빙 관계

- `WM-23` 워크로드가 참조하는 모델의 삭제는 참조 관계를 확인하고 거부해야 한다. 운영자는 관련 워크로드를 삭제하거나 모델 참조를 변경한 뒤 해당 모델을 삭제할 수 있어야 한다.
- `WM-24` 참조 중인 모델의 실행 산출물이나 입력 정의를 수정하면 영향을 받는 워크로드에 모델 변경 절차를 적용해야 한다. 해당 워크로드들의 기존 요청이 마무리된 뒤 새 실행 정의를 적용해야 한다.
- `WM-25` 워크로드별 활성 POOL의 운영 상태는 현재 소속 노드와 실제 서빙 인스턴스를 보유해야 한다. 구성 전환에 따른 노드 배정과 서빙 관계의 변경은 실제 완료된 전환에 맞춰 갱신해야 한다. 이 과정에서 워크로드의 서비스 식별자와 모델 및 SLO 정의를 유지하고, 기존 요청은 전환 실행 계약에 따라 마무리해야 한다.

## 6. 입력과 요청 결과

- `WM-26` 추론 요청 하나는 원시 표본 1개로 처리해야 한다. CHILL은 노드에 분배하기 전 전역 진입점에서 요청을 참조 전처리의 원시 입력 계약으로 한 번 검증해야 한다. 검증 항목은 필드 이름, 원시 바이트 자료형, 필드별 크기 상한, 이미지 필드의 형식 식별 바이트와 헤더, 텍스트 필드의 UTF-8 형식과 바이트 길이 상한이다. 여러 요청으로 구성된 실행 배치는 해당 워크로드의 호환되는 요청들로 만들어야 한다.
- `WM-27` 각 요청에는 실제 선택한 실행 조건과 사용한 프로파일을 연결해야 한다.
- `WM-28` 수락한 요청에는 워크로드 등록 건, 모델과 전처리 정의, SLO, 최초 CHILL 수신 시각을 연결해야 한다. 실제 분배 시 담당 POOL과 노드 및 인스턴스, 분배 시각을 기록해야 한다. 요청 기록은 [라우팅과 배칭](../03_routing.md#관측할-결과)의 관측 항목과 생성형 모델의 첫 토큰 경과 시간을 기록해야 한다. 분배와 배칭 및 정의 변경 중에도 요청의 처리 기준과 실제 배정 기록을 보존해야 한다.
- `WM-29` 실제 추론 결과와 처리 오류는 해당 요청의 응답으로 반환해야 한다. backend 장애나 연결 종료, 명시적 timeout 및 취소는 요청 경로에서 확인한 결과로 처리해야 한다. 응답 전달이 가능한 경우 호출자에게 결과와 사유를 반환하고, 전달 실패나 관측 시점의 미완료 상태는 요청 기록에 남겨야 한다.

| 상황 | 외부에 제공할 의미 |
|---|---|
| 존재하지 않는 워크로드 | 해당 식별자에 등록된 서비스가 없음 |
| 잘못된 입력 | 원시 입력 계약과 다른 필드 및 이유 |
| 실행 근거 부족 | 데이터셋 참조, 모델 실행 경로나 해당 조건의 측정이 필요 |
| 모델 변경 중 | 현재 관리 작업으로 신규 요청 접수 제한 |
| 삭제 중 | 신규 요청 접수 제한과 삭제 진행 |
| 큐 또는 자원 한도 도달 | Serving 설정의 한도에 따른 거절 또는 오류 |
| backend 실패 | 해당 요청에서 관측한 실행 또는 전달 오류 |
| 전처리 실패 | 해당 요청의 표본에서 관측한 전처리 오류 |
| timeout 또는 취소 | 명시적 설정이나 취소 요청에 따른 종료 |

오류의 전송 형식과 프로토콜별 코드는 API 설계에서 정한다.

## 7. 관측 요구사항

- `WM-30` 워크로드별 유입, 미배정 대기, 인스턴스별 대기 및 진행 상태와 실제 요청 결과를 제공해야 한다.
- `WM-31` 변경과 삭제에는 대상, 적용 전후 정의, 수락과 실제 적용 시각, 결과와 실패 원인을 남겨야 한다. 요청 관측을 그 시점에 적용된 정의와 연결할 수 있어야 한다.
- `WM-32` 요청 수, 지연 분포와 백분위, 실제 처리 결과 및 집계 조건은 시스템 명세의 SLO 관측 계약을 따라야 한다. 실험 결과의 해석은 분석자가 담당한다.

### 8.1 요청 수명 검증과 적용

#### SLO 미만 수명 거부 (`WM-34`)

- Given SLO 목표 시간이 60초인 워크로드 정의가 있다.
- When `requestLifetime`을 59초로 등록하거나 수정한다.
- Then 해당 항목과 SLO 미만 사유로 변경을 거부하고 기존 정의를 유지한다.

#### 게이트웨이 상한 초과 수명 거부 (`WM-34`)

- Given SLO 목표 시간이 60초인 워크로드 정의가 있다.
- When `requestLifetime`을 130초로 등록하거나 수정한다.
- Then 해당 항목과 129초 상한 초과 사유로 변경을 거부하고 기존 정의를 유지한다.

#### 헤더 없는 부하 요청에 워크로드 수명 적용 (`WM-33`)

- Given SLO 목표 시간 60초, `requestLifetime` 120초인 워크로드가 요청을 접수할 수 있다.
- When 부하 생성기가 `X-Chill-Request-Timeout` 헤더 없이 추론 요청을 보낸다.
- Then 요청 수명으로 워크로드 값 120초를 적용하고 응답과 요청 관측 기록에 실제 적용 수명을 제공한다.

## 9. 구현 설계로 연결할 사항

구체적인 리소스와 API, 적용 절차와 코드 재사용 경계는
[워크로드 관리 구현 설계](../../design/serving/workload-management.md)에 정리한다.

| 영역 | 구체화할 구현 |
|---|---|
| 리소스 | Workload의 CRD 여부, 객체 범위와 필드, 기존 식별 및 권한 체계 연결 |
| API | 조회와 관리 및 추론 경로, 원시 표본 인코딩과 접수 검증 위치, 오류 응답과 timeout 및 취소 전달 |
| 변경 적용 | 신규 접수 중지와 기존 요청 마무리의 실제 적용 지점, 모델 변경의 연관 워크로드 처리 |
| 관측 | 요청 및 관리 작업의 기록 저장과 조회, 등록 건 식별과 정의 연결, 단계별 경과 시간과 단위 수의 기록 |

구성 탐색, 워크로드 사이의 자원 할당과 큐 선택, 요청별 시간 예산은 기존 제어 설계에서 구체화한다.
