# 라우팅과 노드별 배칭

CHILL은 워크로드 식별자와 원시 표본 1개로 이루어진 요청을 받아, 요청마다
준비된 모델 인스턴스 하나에 전달한다. 각 인스턴스는 같은 워크로드의 호환되는
요청들을 SLO와 프로파일에 맞게 배칭하여 추론한다. 분배와 배칭 모두
[구성 선택](04_configuration_selection.md)의 에너지 목표를 따른다.

## 요청과 실행 배치

| 단위 | 의미 |
|---|---|
| 사용자 요청 | 워크로드 식별자 + 독립적으로 완료할 수 있는 원시 표본 1개. 응답과 SLO의 기준 |
| 실행 배치 | 인스턴스가 한 번의 실행 단위로 처리하는 같은 워크로드의 요청 묶음 |

하나의 추론에 함께 필요한 여러 원시 필드는 표본 1개를 구성할 수 있다.
독립적인 표본은 각각 별도 요청으로 처리한다. CHILL은 노드에 분배하기 전에 각
요청을 워크로드의 원시 입력 계약에 맞게 한 번 검증한다. 노드 내부의 실행 단위는
한 실행 배치에 대한 전처리, 추론, 후처리다. 전처리에서 실패한 요청은 오류로
종료한다. 같은 배치의 다른 요청은 실행을 완료한다. 각 결과는 해당 요청에 반환한다.

## 워크로드 전체 부하와 인스턴스별 부하

- **워크로드 전체 부하:** 해당 서비스에 들어오는 요청의 양과 처리 상태.
- **인스턴스별 할당 부하:** 서빙 파드에 전달한 요청의 양과 그 노드에서의 합계.
- **인스턴스별 대기와 실행 상태:** 전달받은 요청 중 워크로드별로 기다리거나 처리 중인 양.

워크로드별로 아직 배정하지 않은 요청의 대기 상태를 관리한다. 같은 노드에 파드가
여러 개면 모델 인스턴스까지 구분해 전달하며, 각 인스턴스도 워크로드별 큐를 유지한다.
수용 가능한 준비된 인스턴스가 있으면 유입 측에서 불필요하게 기다리게 하지 않는다.
유입 대기와 인스턴스의 배칭 대기는 구분한다.

부하의 기본 단위는 워크로드별 inputs/s이며, 입력 1개가 요청 1개이므로 요청률과 같다.
큐 길이와 대기와 완료량은 요청 수로 기록하고, 내부 실행 배치 수와 구분한다.
동시 도착한 독립 입력들은 같은 도착 시각의 개별 요청으로 표현한다.
큐의 물리적 배치와 자료 구조는 구현 설계에서 정한다.

요청 수와 전력 같은 관측값, 그 값으로 계산한 요청률, 프로파일로 예상한 후보
전력은 역할이 다르다. 계산에 사용한 구간과 관측 시각을 남기며, 미래 부하
예측 없이도 현재 부하를 기준으로 판단할 수 있다.

## 요청 분배

라우팅은 다음 조건을 만족해야 한다.

- 요청한 워크로드의 모델을 제공하며 추론 준비가 끝난 노드로 전달한다.
- 노드별 프로파일과 현재 상태를 근거로 처리 능력에 맞게 분배한다.
- 분배가 노드의 배칭과 전력 소비에 주는 영향을 구성 비교에 반영한다.
- 준비 중이거나 격리된 노드는 사용 가능한 서빙 용량으로 세지 않는다.

라우팅 가중치 `w`는 워크로드별 요청의 노드 분배 비율이다. 각 비율은 0 이상이고,
분배할 대상이 있을 때 합은 1이다. 요청 수 비율이 연산량이나 에너지 비율과
같다는 뜻은 아니며, 처리 비용은 모델 산출물, 런타임, 전처리 산출물과 데이터셋이
일치하는 프로파일과 관측으로 판단한다.
가중치의 표현과 선택 방식은 구현에서 정한다. 그 결과로 발생하는 부하와 SLO가
판단 대상이며, 효율적인 노드로의 집중과 여러 노드로의 분산 모두 후보가 된다.

배분 선언은 지정, 해제, 선언 삭제를 구분하는 명시적 작업으로만 바뀐다.
실험과 운영 정리는 서버의 원자적 작업으로 원래 상태로 되돌린다.

모델 준비가 완료된 뒤 새 대상에 요청을 보내고, 제외할 노드에는 신규 유입을
중지한 뒤 이미 받은 요청을 처리한다. 구체적인 순서는
[전환 실행](05_transition_control.md)에서 다룬다.

## 노드 내부의 배칭

배칭은 요청을 모아 처리하는 에너지 이득과 기다림에 따른 지연을 함께 다룬다.
인스턴스의 모델과 실행 경로, 전력모드와 자원 할당과 배치별 프로파일과 실제 요청 도착과
대기 상태를 사용해, SLO를 만족하는 범위에서 에너지 비용이 유리하도록 처리한다.

CPU는 예약, 제한과 고정 없이 공유하며 스레드는 런타임 기본 병렬성을 따른다. 각 인스턴스는 한 번에 실행
배치 하나만 처리하며, 실행을 마친 뒤 다음 배치를 시작한다. 한 배치 내부의
병렬 계산과 여러 배치의 동시 실행은 구분한다. 서로 다른 인스턴스는 병렬로 실행할 수 있다.

SLO가 다른 워크로드들은 같은 실행 조건의 프로파일을 재사용하고, 인스턴스 하나는
워크로드 하나의 요청을 처리한다. 워크로드별 부하, 대기시간, SLO는 따로 유지한다.
이미 실행 중인 배치 때문에 대기할 수 있으므로 평균 처리량만으로 SLO 충족을 판단하지
않는다. 구체적인 큐 선택 정책은 설계에서 정한다.

최대 처리량을 내는 배치나 요청당 에너지가 가장 낮았던 측정 배치를 모든 부하에
그대로 적용하지 않는다. 배치를 모으는 대기시간도 지연에 포함되므로, 같은 노드와
모델이라도 요청량에 따라 적절한 배치와 대기 설정은 달라질 수 있다.

서빙 실행기와 동적 배칭 메커니즘은 firstfloor를 재사용한다. CHILL은 evidence 기반
배칭 정책과 워크로드 SLO와 요청별 시간 정보를 제공하고, firstfloor 내부 배처가 현재
요청, 큐와 실행 상태에 정책을 적용해 배치 구성과 추가 대기와 실행 시점을 판단한다.
firstfloor가 요청별 판단과 각 배치의 실행을 소유하고, CHILL 제어 루프는 구성과
정책을 갱신한다. 기존 firstfloor의 큐, 배처와 runner를 같은 실행 경계에서 사용한다.

요청별 CHILL 수신 시각과 firstfloor 큐 진입 시각을 연결한다. 큐 진입 전까지 소비한
시간에 현재까지의 큐 대기를 더해 총 경과 시간을 판단하며, 최초 수신 기준을 유지한다.
후보 배치의 실행 시간, 스케줄러의 [유한 수요 직접 재생 평가](scheduler/SRS.md#유한-수요-직접-재생-평가)에 쓰는 설정 여유와 진행 중인 실행의
영향을 고려해 요청별 추가 대기 여유를 판단하고, 배치의 대기는 포함된 요청들의
허용 여유를 넘기지 않도록 정한다. 그 범위에서 더 모을 에너지 이득이 있는지는
evidence 기반 정책으로 판단한다. 시간 여유가 있다는 이유만으로 기다리지 않는다.

요청별 시간 예산은 워크로드의 백분위 SLO를 따른다. serving 과부하 정책은
`Workload.spec.admission`이 소유하며 applied Definition에 동결한다.
`policy=Reject`(기본)는 SLO 안에 완료할 수 없는 요청을 실행 없이 거절한다.
`Delay`는 정상 요청 뒤로 미뤄 늦은 완료를 허용하며 최종 기한까지 처리한다.
`maxQueuedRequests`는 gateway 정상과 지연 큐 합의 양의 상한이며 기본 1024다.
정책 변경은 새 Workload generation에 적용하고 이미 수락한 요청의 정책은 유지한다.
요청별 정책 전달에는 executor 재시작이 필요 없다.

gateway는 완료 가능한 후보를 고르고 executor는 실행 직전에 실제 남은 SLO를
재확인한다. 판단 입력이 없으면 `AdmissionUnknown`으로 최종 기한까지 기다린다.
fixed-batch는 기존 SLO 판단 예외를 유지한다. 큐 포화는 `QueueFull`(429),
완료 불가능 거절은 `DeadlineInfeasible`(503)이며 gateway/executor 단계를 기록한다.
최종 기한은 수신 때 확정한 요청 lifetime이며 명시 timeout/cancel은 정상과 지연 큐에
함께 적용한다. active batch는 SLO만으로 취소하지 않고 실제 물리 완료까지 점유한다.

gateway와 replay가 쓰는 `EstimateAdmission`은 native snapshot의 나이, 관측 요청,
미관측 assignment와 새 요청을 공유 `ChooseBatch`로 진행한다. 실행 중 batch는
BatchID별 한 번만 세고, service 경과를 조건으로 한 생존 분위수를 남은 시간으로
쓴다. batch별 service 분위수와 수락 때 동결한 POST reserve를 합친 **판단 규칙**이며
E2E 분위수 보장이 아니다. service 표본이 남지 않거나 필요한 입력이 없으면 판단은
unknown이다. idle은 기존 nearest-gap 모형을 유지하며, 관측 idle 지원 범위 밖의
예측이 거절을 결정했으면 `outsideSupport: true`를 거절 metadata에 남긴다.

정상 요청과 지연 요청은 하나의 gateway 소유 큐에 보존하고 두 번의 유한 순회로
처리한다. 공유 실행기로 갈 수 있는 다른 Workload의 정상 요청도 지연 요청보다
먼저 처리한다. 지연 요청은 예상 완료가 가장 이른 실행기로 배정한다.

HTTP 오류의 기존 `code`와 `message` 필드는 유지하고 overload 거절에 `stage`,
`policy`, 선택적 `predictedCompletionNanos`와 `remainingSLONanos`를 추가한다.
server final 행의 적용 정책은 `admissionPolicy`, 거절 결정은 `rejection`에 둔다.
`gatewayWaitNanos`는 enqueue부터 dispatch 또는 큐 안 종료까지, `executorWaitNanos`는
native enqueue부터 running 또는 큐 안 종료까지의 monotonic span이다. 해당 큐에
들어가지 않았으면 필드를 생략하며, 실제 0ns 대기는 숫자 0으로 보존한다.

ModelSpec firstfloor `deadlinePolicy`(drop/keep/defer, 기본 keep)와 frozen profiling
RunConfig는 측정 provenance다. serving 요청의 정책은 이 값에서 선택하지 않는다.
정책 소유와 저장 cutover는 [Workload-Owned Overload Admission](../adr/0033-overload-admission.md)을 따른다.

워크로드별 큐와 실행 배치 분리와 인스턴스별 단일 배치 실행 계약은 유지한다.
firstfloor의 실제 적용으로 이 계약을 확인하며, 시간 정보 전달과 정책 적용 지점과
갱신 시점은 [서빙 설계](../design/serving/README.md)에서 정한다.
POOL 제어와 배칭의 주기 및 계산 규칙은 해당 책임과 측정 조건에 맞춰 설계한다.

## 결과 반환과 SLO

실행 배치의 각 결과를 해당 요청에 연결해 반환한다. 서로 다른 요청의 완료 순서는
독립적이며, 함께 도착한 요청들이 모두 끝날 때까지 응답을 기다리지 않는다.

지연은 CHILL의 요청 수신부터 해당 추론 결과의 응답 반환 완료까지의 경과 시간이다.
유입 대기, 분배, 전달과 노드 대기, 실행과 반환을 포함하며, 인스턴스 전달이나 내부 배칭으로
시작 시각을 재설정하지 않는다. SLO 백분위는 워크로드별 요청 지연으로 계산한다.

CHILL은 요청별 시각과 실제 완료, 오류, 거절과 timeout/cancel와 미완료 상태를 남긴다.
요청 수와 지연 분포와 백분위의 집계는 [SLO 관측과 집계](README.md#slo-관측과-집계)를
따르며, 실험의 성공과 실패 해석은 분석자가 수행한다.

## 관측할 결과

요청별 CHILL 수신, 입력 검사, 분배, firstfloor 큐 진입, 응답 반환 완료 시각과 각 위치의
대기시간을 기록한다.
워크로드별 요청 수와 지연 분포와 백분위, 실현된 실행 배치 크기, 배치별 전처리,
추론, 후처리 경과 시간, 요청별 단위 수, 노드별 처리량과 전력을 기록한다. 요청별
원시 관측에 배정 인스턴스와 실제 처리 상태를 연결해 보존하며, 오류, 거절,
timeout/cancel, 미완료 요청도 함께 드러낸다.
라우팅 결정과 실제 반영 시점을 관측하되, 반영 지연을 예측하는 별도 제어 모델을
기본 요구사항으로 두지 않는다.
