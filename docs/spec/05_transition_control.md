# 전환 실행과 피드백

[스케줄러](04_configuration_selection.md)의 구성 선택은 실행할 목표다.
실행 계층은 작은 제어 동작을 의존관계에 따라 조합하고, 실제 완료·실패와 상태를
스케줄러에 알려 다음 판단의 근거로 사용하게 한다.

## 제어 동작의 단위

동작별로 대상, 시작 조건, 완료 기준, 실패와 관측할 결과를 정한다.
예를 들어 다음 동작들을 하나의 POOL 변경으로 조합할 수 있다.

| 동작 | 확인할 결과 |
|---|---|
| 서빙 배치 생성·모델 준비 | 대상 모델이 요청을 처리할 준비가 되었는가? |
| 전력모드 변경 | 대상 노드가 선택한 모드에 도달했는가? |
| 기존 인스턴스의 CPU·메모리 자원 변경 | 목표 요청량과 연동된 런타임 설정이 실제로 적용되었는가? |
| 라우팅 변경 | 새 분배 대상과 비율이 실제 요청 경로에 반영되었는가? |
| 신규 요청 유입 중지 | 대상에 새 요청이 배정되지 않는가? |
| 진행 중 요청 처리 완료 | 이미 받은 요청이 남아 있는가? |
| 서빙 배치 제거 | 대상의 서빙이 종료되었는가? |

이는 동작의 책임을 나눈 것이며, 특정 API나 범용 워크플로 엔진을 요구하지 않는다.
동작의 의존관계는 필요한 순서를 표현한다. 예를 들어 모델을 준비하기 전에
그 모델의 요청을 새 노드로 보내서는 안 된다.

## 준비와 전환 중 Serving

Pod가 Running인 것만으로 모델 준비가 끝났다고 판단하지 않는다. 라우팅 대상으로
편입할 때에는 해당 모델이 실제로 추론 요청을 받을 준비가 되었는지 확인한다.
노드의 목표 전력모드와 인스턴스의 목표 자원 요청량도 실제 적용 상태와 구분한다.
CPU 할당을 바꿀 때에는 연동된 스레드 설정도 함께 반영한다. 자원 변경의 구체적인
적용 절차와 전환 중 요청 처리 방식은 플랫폼·런타임에 맞춰 정한다.
목표 구성의 일부가 준비되면 나머지 작업 완료를 기다리지 않고 준비된 용량을
배분에 편입한다.

전환 과정은 사용 가능한 처리 능력과 비용에 따라 선택한다.

- 기존 구성이 계속 처리할 수 있으면 새 용량을 준비하는 동안 활용한다.
- 변경할 노드가 서빙을 지속할 수 없으면 요청을 다른 준비된 노드로 옮기는 등의
  처리 경로를 함께 계획한다.
- 임시 노드를 사용하는 방법도 후보가 될 수 있다. 그 준비·Serving·해제 비용까지
  포함해 SLO와 총에너지 관점에서 비교한다.
- 신규 유입이 없는 것과 이미 받은 요청이 없는 것은 다르다. 제거 전에 남은
  요청을 어떻게 마무리할지 정하고, 의도하지 않은 유실을 만들지 않는다.

전환 중 다른 노드가 대신 감당할 수 있는 남은 처리 능력이 전환의 여유 용량이다.
항상 일정 수의 예비 노드를 유지해야 한다는 뜻은 아니다. 노드별 독립 동작은
병렬 실행할 수 있지만, 동시에 빠지는 서빙 용량과 전체 POOL의 SLO 영향을
고려한다. 모든 전환을 직렬로 제한하거나 항상 무중단이라고 가정하지 않는다.

## 진행 상태와 실패

원하는 상태와 실제 상태가 아직 다르다는 이유만으로 실패로 처리하지 않는다.
정상 진행 중인 동작과 실패한 동작을 구분하고, 동작별 실패 판정 조건을 명시한다.

동작이 실패하면 실패 대상과 원인, 실제로 완료된 변경을 기록한다. 그 결과에
의존하는 다음 동작을 성공한 것처럼 실행하지 않는다. 스케줄러는 관측된 상태에서
가능한 차선의 구성이나 동작을 선택한다. 실패한 변경이 모두 원복되었다고
가정하거나, 근거 없는 대체 값을 만들어 계획을 계속하지 않는다.

노드나 서빙 백엔드가 사라지면 가용 대상에서 격리하고 남은 자원으로 판단한다.
복구되어 다시 사용할 수 있는지는 실제 상태로 확인한다. 판단 자체가 실패하면
오류를 기록하며, 아직 실행되지 않은 결정을 적용 완료로 보고하지 않는다.

## 부하 변화와 다음 판단

전환 중에도 요청 부하는 변할 수 있다. 다음 관측에서 실제 부하와 진행 상태를
함께 보고 재판단한다. 진행 중인 일을 새 작업처럼 중복 시작하지 않는다.
제어기는 실제 존재하는 실행기의 장부를 관측과 분리해 유지하고, 진행 중 작업이
예약한 범위 밖은 계속 판단한다.
아직 수행하지 않은 동작을 취소할지, 진행 중인 동작을 완료할지는 해당 동작의
특성과 비용을 고려해 설계한다. 모든 동작에 취소 기능을 요구하지 않는다.

분배·증설은 매 제어 주기에 판단하되 축소와 에너지 목적 교체는 설정된 같은 하강 안정화 기간이 경과한 뒤에만 허용하고, 기간·하강 상태·판단 이유를 기록한다.
전환 중 수요 대비 예비 용량 비율(0=별도 예비 없음)과 후보에 무관한 에너지 비교 기간 H를 설정·기록하며, 실제 준비된 용량의 전환 SLO와 예비 소비를 포함한 전체 POOL 에너지를 평가한다.

## 동작별 관측

제어 동작마다 대상과 사용한 결정 근거, 시작·완료 시각, 소요 시간, 성공·실패,
관측된 상태를 남긴다. 전력과 요청 처리 관측을 같은 시간축에 연결해 전환 중
비용과 SLO 영향을 확인할 수 있어야 한다.

이 기록은 실험과 운영 모니터링의 입력이다. 실행 오류, 가용 용량과 실제 요청
지연·처리 결과를 구분해 보여준다. 요청 결과의 집계와 실험 해석 책임은
[SLO 관측과 집계](README.md#slo-관측과-집계)를 따른다.
관측만으로 설명할 수 있는 현상에 별도의 진단·복구 상태 기계를 추가하는 것을
요구하지 않는다.
