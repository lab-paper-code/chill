# 프로파일링과 Evidence

프로파일링은 [CHILL 스케줄러](README.md)가 구성 선택에 사용할 근거를 실측하는
과정이다. 측정 항목은 스케줄러가 내려야 할 결정에서 도출한다. 측정 기능이나
저장 형식을 먼저 고정하고 제어 목표를 거기에 맞추지 않는다.

## 측정의 단위

프로파일링과 Serving은 같은 firstfloor/backend 실행 경로를 사용한다. 하나의 측정은
대상 장비, 모델 산출물, 전처리 산출물, 데이터셋, firstfloor/backend 버전과 설정,
전력모드, 자원 할당과 스레드 설정, 실행 배치 조건을 고정하고, 이 조건을 측정
결과와 함께 보존한다.

| 측정 | 실행 조건과 관측 |
|---|---|
| 고정 구성 프로파일링 | 실행마다 데이터셋의 프로파일링 부분집합에서 배치 크기만큼 새 표본을 뽑아 전처리부터 후처리까지 반복 실행하여 배치 실행시간 분포, 처리량, 메모리, 노드 벽전력과 에너지를 측정 |
| 모델 로드 유휴 측정 | 같은 firstfloor/backend·모델·자원 조건에서 요청을 처리하지 않는 상태의 소비를 측정 |
| Serving 관측 | 실제 요청의 대기·전달·실행·반환을 포함한 종단 지연과 처리 결과를 기록 |
| 디스패치 점유 측정 | 고정 배치 크기 인스턴스 하나에 그 처리율보다 많은 요청을 보낸 포화 구간에서 지속 처리율을 재고, 요청 하나가 배치 실행시간 밖에서 인스턴스를 점유하는 시간을 장비, 전력모드, runtime, 모델마다 산출. 포화 구간은 인스턴스가 다음 요청을 기다린 시간의 합이 측정 창 길이의 정해진 비율 이하인 구간이다 |

전환 측정은 출발 상태와 도착 상태, 실행한 동작을 함께 기록한다.

원시 trial에는 단계별 전처리, 추론, 후처리 경과 시간과 요청별 단위 수, 사용한 데이터셋
표본의 식별자를 함께 보존한다. 단위 수는 전처리가 요청별로 보고하는 모델 입력 단위의 개수다(예: 이미지
타일 수). 단위 수는 분석용 관측값으로 보존한다.
데이터셋의 프로파일링 부분집합과 평가 부하 부분집합은 서로 다른 표본으로 구성한다.

### 측정 POOL

프로파일링과 전환 비용 측정은 측정 POOL의 노드에서만 수행한다. 측정을 요청하면
CHILL이 대상 노드를 측정 POOL로 옮기고, 측정이 끝나거나 실패하면 가용 노드로
돌려보낸다. 실패는 측정 결과로 기록한다. 활성 POOL에서 서빙 중인 노드에 대한 측정
요청은 거절하고 사유를 남긴다. CHILL이 배치하지 않은 파드가 측정 노드에 있어도 측정을
진행하고, 측정 구간에 있던 그 파드들의 목록을 결과와 함께 기록한다.
한 노드의 측정 요청은 요청 순서대로 하나씩 실행하고, 서로 다른 노드의 측정은 동시에
진행한다. 측정이 노드에 둔 파드는 서빙으로 보지 않는다. 측정 조건의 CPU 할당이 그
전력모드의 온라인 CPU에서 서빙 예약을 뺀 범위에 들지 않거나, 요청이 가리키는 측정 근거가
쓸 수 없으면 요청을 거절하고 사유를 남긴다.

### 자원 할당과 측정 축

Serving에서 사용할 CPU 할당량·할당 방식, 가속기 할당과 런타임 설정을 측정 조건에
연결한다. CPU 추론의 스레드 설정은 CPU 할당량에 연동하고, 인스턴스별 실행은
한 번에 배치 하나로 고정한다. 스레드 수와 동시 추론 수를 독립적인 탐색 축으로
두지 않는다. 요청한 조건과 실제 적용된 조건을 확인할 근거를 남긴다.
CPU quota는 사용량 상한이며 전용 CPU 배정을 뜻하지 않으므로, quota만 같다고
자원 격리 조건까지 같다고 판단하지 않는다.

스케줄러가 선택할 자원·전력모드·배치 등의 실행 구성을 측정한다. CPU 할당량이
여러 개면 그 조건을 구분하되, 연동되는 스레드 설정을 별도 축으로 전수 조합하지 않는다.

같은 자원 조건에서 활성 측정과 유휴 기준을 연결한다. CPU 전체를 사용한 결과를
일부 CPU만 할당받은 파드의 결과로 사용하거나, 다른 할당량의 유휴 기준을 섞지 않는다.
배치 크기는 한 번의 실행 단위에서 함께 처리하는 요청 수다. Serving의 각 요청은
원시 표본 1개이며, 같은 워크로드의 호환되는 요청들을 내부 실행 배치로 묶는다.
프로파일의 배치별 실행 시간·처리량은 요청별 대기와 응답 지연을 판단하는 근거다.

메모리는 배치 가능 여부를 판단하는 근거다. 실행 조건별 메모리 점유와 관측 최대값을
측정 구간과 함께 보존하며, 메모리 한도를 바꿔 성능 곡선을 탐색하지 않는다.
스케줄러는 이 근거로 필요한 메모리를 산정하고, 프로파일에 포함되지 않은 서빙
부가 사용량과 시스템 예약분도 고려해 노드의 가용 예산 안에 배치한다.
관측 최대값을 모든 입력·실행 상태의 절대 상한으로 간주하지 않는다.

### 공존 오차와 서비스 검증

먼저 선택한 할당 조건에서 단독 모델의 특성을 측정하고, 실제 공존 구성에서
지연·처리량·전력의 차이를 확인한다. 공존 여부와 함께 실행한 구성은 해석에 필요한
조건으로 남기되, 가능한 모든 모델 조합을 ProfilingRun의 필수 측정 축으로 넣지 않는다.
관측된 차이가 제어 판단을 방해하는 경우 해당 구성의 추가 측정이나 운용 제한을 정한다.

실행 조건이 같은 워크로드들은 SLO가 달라도 동일한 실행 조건의 성능 측정을
재사용한다. 각 워크로드는 자기 인스턴스에서 처리하고, 프로파일에 배칭과 큐 선택
규칙을 적용한 재생으로 실행 조건과 SLO마다 용량을 계산한다.
계산 결과는 기존 종단 Serving 평가의 실측 지연과 비교한다. SLO나 워크로드마다
같은 단독 추론 측정이나 별도의 부하별 Serving 성능표를 요구하지 않는다.

## 스케줄러가 답을 필요로 하는 질문

| 질문 | 필요한 근거 |
|---|---|
| 이 구성에서 어느 정도의 요청을 맡길 수 있는가? | 실행시간 분포·처리량과 현재 부하·큐·배칭 조건 |
| 워크로드의 SLO를 만족할 수 있는가? | 프로파일과 현재 요청 상태로 계산한 요청별 지연 분포 |
| 같은 부하를 더 적은 에너지로 처리할 수 있는가? | 구성별 전력·에너지, 유휴 소비, 완료 요청 수 |
| 어떤 전력모드와 배치가 유리한가? | 해당 모델·실행 경로에서 설정별 측정 결과 |
| 필요한 인스턴스들을 노드에 배치할 수 있는가? | 실행 조건별 메모리 사용량과 노드의 가용 자원 |
| 다른 구성으로 이동할 가치가 있는가? | 전환 시간·에너지와 그동안의 서빙 가능 여부 |

추론을 연속 실행한 최대 처리량을 SLO를 지키며 감당할 수 있는 요청률과 동일시하지
않는다. 프로파일은 배치별 실행시간과 그 변동성을 제공하고, 스케줄러는 후보 구성의
처리 규칙을 적용한 재생으로 실행 조건의 SLO 용량을 계산하고, 그 용량을 현재
요청률과 대기량에 비교한다.
프로파일에 포함되지 않은 시간 중 인스턴스를 점유하는 부분은 디스패치 점유 측정으로
용량 계산에 더한다. 나머지 전달과 응답 처리 시간은 설정 여유로 반영하고 Serving
관측으로 그 여유를 검증한다. 디스패치 점유는 장비, 전력모드, runtime, 모델마다 한 번
재며, 이 계산에 부하별 Serving 프로파일링 캠페인을 선행 조건으로 두지 않는다.
실제 SLO·에너지와 예측 오차는 기존 종단 평가에서 검증한다.

배치를 키우면 항상 효율이 좋아진다거나, 같은 타입의 노드는 항상 같은 성능을
낸다고 전제하지 않는다. 노드·전력모드·배치의 비교는 해당 측정 결과를 사용한다.

## 전력과 에너지

전력은 노드 전체의 벽전력을 기준으로 관측한다. edge-metrics 같은 수집 경로로
얻은 값에는 대상, 단위, 측정 시각과 측정 구간이 연결되어야 한다.

- 모델이 준비된 채 요청을 처리하지 않는 유휴 상태와 서빙 비참여 상태를 구분한다.
- 연산 중의 전체 노드 전력에 유휴 전력이 이미 포함되어 있으면 다시 더하지 않는다.
- 전체 POOL 전력은 같은 시점의 노드 전력 합이며, 에너지는 해당 기간의 전력을
  누적한 값이다. 활성 POOL의 소비는 별도로 집계할 수 있다.
- 요청당 전체 에너지와 유휴 소비를 뺀 증분 에너지를 구분한다. 증분 에너지를
  전체 소비로 사용하거나 유휴분을 중복 계산하지 않는다.
- 같은 노드에 파드가 여러 개 있어도 노드 전력은 한 번만 집계한다. 각 파드의
  단독 실험에서 측정한 노드 전체 전력을 단순히 더해 공존 비용을 만들지 않는다.
- 운영 전력 창의 읽기 실패는 성공 표본 사이의 gap으로 취급하며 실패 한 건만으로
  불완전 처리하지 않는다. 기록된 최대 gap·최소 coverage·경계 거리 정책으로 판정하고,
  노드별 창 안 읽기 실패 횟수와 실제 표본 최대 간격 및 창 합계/최대값을 보고한다.

운영자는 한 노드의 준비, 유휴, 해제, 빈 노드 전력모드 변경을 순서 있는 측정 요청 하나로
선언한다. 동작마다 기록을 남기고 기록은 그 요청을 가리킨다.

노드 편입·모델 준비·전력모드 변경 등은 소요 시간과 에너지를 측정하고, 전환 중
추론을 계속할 수 있는지 관측한다. 임시 자원을 포함한 POOL 전환 비용의 합성은
[구성 선택](04_configuration_selection.md)에서 다룬다.

## 측정 설정과 실패

반복 횟수, 측정 시간, 워밍업, 통계 계산에 필요한 값은 측정 입력으로 설정하고
결과와 함께 남긴다. 구체적인 값은 측정 목적과 연구 근거에 따라 선택한다.

실행 실패, 필수 관측 누락, 계산 불가능한 입력은 오류로 드러낸다. 없는 수치를
채워 넣지 않는다. 열 상태와 간섭은 필요하면 관측 자료로 보존하되, 별도의 제어
대상이나 자동 합격·불합격 정책으로 요구하지 않는다.

## Evidence Store의 역할

Evidence Store는 측정 설정, 원시 관측, 실행 결과와 파생 결과를 보존한다.
파생 결과에는 어떤 측정과 계산 조건을 사용했는지 연결한다. 이를 위해 별도의
일반화된 신뢰도 판정 시스템을 만들 필요는 없다.
실험 구간의 관측은 사후 재생이 가능한 동안 보존하고, 조회는 보존 위치가 로컬인지
근거 저장소인지에 관계없이 투명하게 같은 구간의 관측을 제공한다.

- 스케줄러는 워크로드와 실행 대상에 맞는 프로파일을 조회하고, 측정한 실행 구성만
  선택한다. 대상이 맞지 않거나 필요한 측정이 없으면 그 후보를 선택하지 않는다.
- 같은 측정 조건의 결과가 여러 개면 최신의 성공한 측정 결과를 우선한다. 한 측정
  안에서 수행한 반복 trial의 집계와, 측정 결과 사이의 최신 선택은 구분한다.
- 프로파일링을 요청하는 것은 운영자의 역할이다. 완료된 측정 결과는 해당 노드를
  그 워크로드의 후보로 만든다. 자동 만료와 노후화 판정은 요구하지 않는다.

조회 결과는 구성별 특성이지 다음 POOL 구성의 정답 자체가 아니다. 스케줄러가
현재 부하와 상태에 대입하여 후보를 비교한다. 필요한 파생 표와 조회 형식은 그
입력이 구체화될 때 정하며, 특정 CRD나 저장 엔진을 명세의 전제로 삼지 않는다.
