# 프로파일링과 Evidence

프로파일링은 [CHILL 스케줄러](README.md)가 구성 선택에 사용할 근거를 실측하는
과정이다. 측정 항목은 스케줄러가 내려야 할 결정에서 도출한다. 측정 기능이나
저장 형식을 먼저 고정하고 제어 목표를 거기에 맞추지 않는다.

## 측정의 단위

프로파일링과 Serving은 같은 firstfloor/backend 실행 경로를 사용한다. 하나의 측정은
대상 장비, 모델 산출물, 전처리 산출물, 데이터셋, firstfloor/backend 버전과 설정,
전력모드, 자원 할당과 스레드 설정, 실행 배치 조건을 고정하고, 이 조건을 측정
결과와 함께 보존한다. Serving은 프로파일을 측정할 때 쓴 실행 이미지를 그대로 써서 준비하며,
이후 선언이 바뀌어도 측정한 이미지로 실행한다. 이미지는 운영자가 쓴 표기 그대로 다루고
형식을 강제하지 않는다. Serving이 실제로 프로파일과 같은 능력을 보이는지는 Serving 관측의
배치 실행시간·노드 전력을 같은 조건의 프로파일과 대조해 확인한다.

| 측정 | 실행 조건과 관측 |
|---|---|
| 고정 구성 프로파일링 | Serving과 같은 요청 경로(실행기 서버의 serving 요청 처리, 대기열, 배치 실행)를 고정 배치 크기로 실행한다. 요청은 다른 노드에서 네트워크로 보낸다. 데이터셋의 프로파일링 부분집합에서 요청마다 새 표본을 쓴다. 단계는 드문 도착(긴 유휴 간격), 포화(지속 처리율), 포화 처리율에 대한 이용률 단계(Poisson 도착)로 이루어지며, Serving이 만드는 직전 유휴 간격과 실행 중 유입 범위를 덮는다. 배치 실행시간 분포, 처리량, 메모리, 단계별 노드 벽전력과 에너지를 측정한다. 단계 구성은 측정 입력이다 |
| 모델 로드 유휴 측정 | 같은 firstfloor/backend·모델·자원 조건에서 요청을 처리하지 않는 상태의 소비를 측정. 정착 시간은 측정 입력이며, 부하 중단 뒤 노드 전력이 안정되는 시간을 근거로 정한다 |
| Serving 관측 | 실제 요청의 대기·전달·실행·반환을 포함한 종단 지연과 처리 결과, 자원 사용·Pod 변화·장애 감지를 기록하고 원래 기록 그대로 API로 제공한다 |
| 디스패치 점유 측정 | 고정 배치 크기 인스턴스 하나에 그 처리율보다 많은 요청을 보낸 포화 구간에서 지속 처리율을 재고, 요청 하나가 배치 실행시간 밖에서 인스턴스를 점유하는 시간을 장비, 전력모드, runtime, 모델마다 산출. 포화 구간은 인스턴스가 다음 요청을 기다린 시간의 합이 측정 창 길이의 정해진 비율 이하인 구간이다. 연속 배치 쌍마다 `d=(다음 배치 시작−앞 배치 시작−앞 배치의 실제 실행시간)/B`로 계산하며, 앞 배치의 실제 실행시간이 없는 쌍은 쓰지 않는다 |

전환 측정은 출발 상태와 도착 상태, 실행한 동작을 함께 기록한다.

원시 trial에는 단계별 전처리, 추론, 후처리 경과 시간과 요청별 단위 수, 사용한 데이터셋
표본의 식별자를 함께 보존한다. 단위 수는 전처리가 요청별로 보고하는 모델 입력 단위의 개수다(예: 이미지
타일 수). 단위 수는 분석용 관측값으로 보존한다.
데이터셋의 프로파일링 부분집합과 평가 부하 부분집합은 서로 다른 표본으로 구성한다.

활성 측정은 마지막 부하의 응답을 모두 회수한 뒤 같은 모델 적재 actor를 유지한다.
필수 측정 입력 `operatingPoints.postLoadDurationSeconds`는 양의 정수 초이며 Run에
동결한다. 이 구간의 시작·종료, 단조 시계 경과, actor 신원·모델 상주 상태와 전후
요청·추론 카운터를 원시 기록에 남긴다. 전력 관측도 구간이 끝날 때까지 유지하여
부하 중단 뒤 안정화 시계열을 보존한다. 이 표본은 활성 단계의 요청당 에너지에 섞지 않는다.
실행 예산은 sparse 표본 하한에 필요한 도착 시간(최초 unknown-gap 배치 포함),
모든 단계의 최소 시간·응답 drain과 후행 무부하 구간을 포함한다. 기존 여유 설정을 유지하며,
확률적 도착이나 느린 실행이 예산을 넘으면 완료로 간주하지 않고 실패로 기록한다.

### 측정 POOL

프로파일링과 전환 비용 측정은 측정 POOL의 노드에서만 수행한다. 측정을 요청하면
CHILL이 대상 노드를 측정 POOL로 옮기고, 측정이 끝나거나 실패하면 가용 노드로
돌려보낸다. 실패는 측정 결과로 기록한다. 활성 POOL에서 서빙 중인 노드에 대한 측정
요청은 거절하고 사유를 남긴다. CHILL이 배치하지 않은 파드가 측정 노드에 있어도 측정을
진행하고, 측정 구간에 있던 그 파드들의 목록을 결과와 함께 기록한다.
한 노드의 측정 요청은 요청 순서대로 하나씩 실행하고, 서로 다른 노드의 측정은 동시에
진행한다. 측정이 노드에 둔 파드는 서빙으로 보지 않는다. 요청이 가리키는 측정 근거를
쓸 수 없거나 메모리·GPU·장치 신원·소유권 조건을 충족하지 못하면 요청을 거절하고
사유를 남긴다. 온라인 CPU·서빙 CPU 예약·affinity는 실행 허가 조건이 아니다.

### 자원 할당과 측정 축

Profiling과 Serving을 포함한 모든 CHILL 연산은 CPU를 예약·제한·고정하지 않는
공유 실행을 사용한다. 장비·전력모드별 CPU 동결표, request/limit/quota, 명시적
affinity/pinning 및 독점 코어 배정은 두지 않는다. CPU 생략을 양수 request나
allocatable 기반 quota·전체 mask로 보충하지 않는다.

런타임 스레드는 quota와 분리하고 런타임 기본·자동 병렬성을 따른다. 인스턴스별 실행은
한 번에 배치 하나이며 스레드 수와 동시 추론 수를 별도 탐색 축으로 두지 않는다.
실제 적용 thread 설정, cpuset/affinity, unlimited를 포함한 cgroup quota,
CPU 사용량과 throttling을 실행 사실로 기록한다.

가속기 할당·장비 신원·런타임·전력모드·배치와 같은 자원 조건에서 활성 측정과 유휴 기준을
연결한다. CPU 관측값의 수치 동일성을 자원 보장이나 matching 조건으로 쓰지 않는다.
과거 quota/affinity 실행 결과를 새 공유 실행의 근거로 자동 재사용하지 않는다.
배치 크기는 한 번의 실행 단위에서 함께 처리하는 요청 수다. Serving의 각 요청은
원시 표본 1개이며, 같은 워크로드의 호환되는 요청들을 내부 실행 배치로 묶는다.
프로파일의 배치별 실행 시간·처리량은 요청별 대기와 응답 지연을 판단하는 근거다.

메모리는 배치 가능 여부를 판단하는 근거다. 실행 조건별 메모리 점유와 관측 최대값을
측정 구간과 함께 보존하며, 메모리 한도를 바꿔 성능 곡선을 탐색하지 않는다.
스케줄러는 이 근거로 필요한 메모리를 산정하고, 프로파일에 포함되지 않은 서빙
부가 사용량과 시스템 예약분도 고려해 노드의 가용 예산 안에 배치한다.
관측 최대값을 모든 입력·실행 상태의 절대 상한으로 간주하지 않는다.

프로파일의 각 배치 `memoryBytes`는 해당 배치의 활성 trial과 같은 프로파일의
모델 로드 유휴 trial에서 보존한 메모리 관측 최대값이다. Lifetime counter가 없는
trial은 검증된 측정 창 `memory.current` 표본 최대값을 사용하며, 이를 load peak로
해석하지 않는다. 다른 배치·프로파일의 값은 섞지 않는다. Catalog read의 배치별
`memoryBasis`는 선택된 관측 종류(`active`, `idle`, `window`)와 원본 evidence
store/key를 제공한다. Raw·result·native bundle 및 observation profile body의
저장 계약과 프로파일 acceptance 기준은 바꾸지 않는다.

### 공존 오차와 서비스 검증

먼저 선택한 할당 조건에서 단독 모델의 특성을 측정하고, 실제 공존 구성에서
지연·처리량·전력의 차이를 확인한다. 공존 여부와 함께 실행한 구성은 해석에 필요한
조건으로 남기되, 가능한 모든 모델 조합을 ProfilingRun의 필수 측정 축으로 넣지 않는다.
관측된 차이가 제어 판단을 방해하는 경우 해당 구성의 추가 측정이나 운용 제한을 정한다.

실행 조건이 같은 워크로드들은 SLO가 달라도 동일한 실행 조건의 성능 측정을
재사용한다. 각 워크로드는 자기 인스턴스에서 처리하고, 프로파일에 배칭과 큐 선택
규칙을 적용한 재생으로 실행 조건과 SLO마다 용량을 계산한다.
계산 결과는 기존 종단 Serving 평가의 실측 지연과 비교한다. SLO나 워크로드마다
같은 단독 추론 측정이나 별도의 부하별 Serving 성능표를 요구하지 않는다.

### 같은 기종 Node 사이의 재사용

같은 기종(DeviceClass), 같은 실행 이미지와 모델·전처리 산출물, 같은 전력모드와
자원 할당·격리·스레드·배치 조건의 프로파일은 다른 Node에 재사용할 수 있다.
같은 기종이라는 선언만으로 동등성을 가정하지 않는다. 대상 Node마다 짧은 활성·모델
로드 유휴 확인 측정을 수행하고, 같은 배치의 평균 서비스 시간과 노드 벽전력을
원본과 비교한다. 허용 상대 차이는 측정 입력 설정값이며 값과 근거, 원본·대상
측정, 판정과 차이를 함께 보존한다. 누락·조건 불일치·허용 차이 초과는 재사용을
거절하고 대상 Node의 독립 측정을 요구한다.

다른 기종·장비 계열 사이의 일반화는 금지한다. 원본의 Node UID, GPU UUID,
전력계 식별자를 대상의 실측 개체 식별자로 바꿔 연결하되 원본 근거를 덮어쓰지 않는다.
재사용 확인은 단독 실행 프로파일의 동등성이지 디스패치 점유, 준비·제거 비용,
전력모드 전환 비용까지 공유할 근거가 아니다. 이 근거들은 대상 Node의 측정을 유지한다.

## 스케줄러가 답을 필요로 하는 질문

| 질문 | 필요한 근거 |
|---|---|
| 이 구성에서 어느 정도의 요청을 맡길 수 있는가? | 실행시간 분포·처리량과 현재 부하·큐·배칭 조건 |
| 워크로드의 SLO를 만족할 수 있는가? | 프로파일과 현재 요청 상태로 계산한 요청별 지연 분포 |
| 같은 부하를 더 적은 에너지로 처리할 수 있는가? | 구성별 전력·에너지, 유휴 소비, 완료 요청 수 |
| 어떤 전력모드와 배치가 유리한가? | 해당 모델·실행 경로에서 설정별 측정 결과 |
| 필요한 인스턴스들을 노드에 배치할 수 있는가? | 실행 조건별 메모리 사용량과 노드의 가용 자원 |
| 다른 구성으로 이동할 가치가 있는가? | 전환 시간·에너지와 그동안의 서빙 가능 여부 |

추론을 연속 실행한 최대 처리량을 SLO를 지키며 감당할 수 있는 요청률과 동일시하지
않는다. 프로파일은 배치별 실행시간과 그 변동성을 제공하고, 스케줄러는 후보 구성의
처리 규칙을 적용한 재생으로 실행 조건의 SLO 용량을 계산하고, 그 용량을 현재
요청률과 대기량에 비교한다.
프로파일에 포함되지 않은 시간 중 인스턴스를 점유하는 부분은 디스패치 점유 측정으로
용량 계산에 더한다. 나머지 전달과 응답 처리 시간은 설정 여유로 반영하고 Serving
관측으로 그 여유를 검증한다. 디스패치 점유는 장비, 전력모드, runtime, 모델마다 한 번
재며, 이 계산에 부하별 Serving 프로파일링 캠페인을 선행 조건으로 두지 않는다.
실제 SLO·에너지와 예측 오차는 기존 종단 평가에서 검증한다.

### 디스패치 점유 d의 공급 조건

고정 outstanding closed-loop 공급의 worker 수이자 outstanding 요청 수 K는
`K=min(64,floor(queueBytesCap/framedDecodedRequestUpperBytes),floor((L−margin)/(B×mu_tail)))`로 한 번 정한다.
B는 profile 배치 크기, mu_tail은 같은 B의 profile 관측 최대 batch 실행시간(초), L은 기존 수명 계산으로
정한 요청 수명(초), margin은 기존 `deliveryMarginMillis/1000`이다.
`queueBytesCap=67108864`이며 `framedDecodedRequestUpperBytes`는 framing을 포함한 요청별 decoded bytes 상한이다.
전달 margin은 별도 측정값이 아니라 기존 전달 예산을 남기는 reserve다.
공급량을 위한 왕복시간·외부 시간 측정이나 별도 출처 입력은 사용하지 않는다.
K는 B의 배수로 올림하지 않으며 기존 validator의 대기 batch 수는 `q=ceil(K/B)−1`이다.
`conditions.inputsJSON.computed.supplySizing`에
`{batch,profileMaxBatchSeconds,serviceTimeSource:"profile.maxObservedSeconds",requestLifetimeSeconds,marginSeconds,workerCap:64,queueBytesCap:67108864,framedDecodedRequestUpperBytes,limitingBound}`를 동결하고
같은 입력으로 K와 q를 정확히 재계산한다. 양의 유한 관측 최대가 없으면 입력을 거절하며 mean×2 등의 대체값을 만들지 않는다.
`limitingBound`는 최소값을 정한 `queue-cap`, `bytes-cap`, `lifetime` 중 하나이며
동률이면 이 순서에서 먼저 나온 항목을 기록한다.
L은 이 공급 규칙 적용 전의 기존 수명 그대로이며 K에 맞춰 확장하지 않는다.
기존 q/tail/prefix 수명 검사, native 대기 개수와 decoded bytes의 공동 조건,
SLO와 gateway 수명 상한을 유지한다. bytes 상한 초과를 이유로 큰 K의 CR을 만든 뒤 거절하는 대신
위 세 상한의 최솟값으로 K를 생성한다. 공급은 K<B일 때만 불가능하며 실행 전에 보고한다.
그 밖의 실행 조건을 만족하지 못해도 실행 전에 보고하며 L이나 예산을 늘리지 않는다.

socket timeout은 `L+delivery`보다 엄격히 크게 최소 1 ms를 더한다.
기존 유한 drain과 전체 3600 s 예산(`e8e018e2`), 공급 연장 `ceil(L+delivery)` 예약을
유지하며 예산을 만족할 수 없으면 실행 전에 보고한다.

유휴는 연속성·실행 근거가 완전하여 식별된 경우에만 허용한다. unknown, hole,
누락 native와 불완전 실행은 기존대로 불충분이며, 알려진 pair의 부분 합으로 통과시키지 않는다.
유휴 비율은 동결된 `maximumIdleFraction` 이하, 요청당 유휴는 기존 1 ms 이하이어야 한다.
`maximumIdleFraction`은 [0,1] 범위 검사하는 설정값이지 고정값 검증이 아니다.
승인값은 0.05로 계획 여유 25%(1.25−1)의 1/5이며, profile에서 더 엄격한 비율을 역산하지 않는다.
초과하면 producer 또는 요청 경로의 한계로 보고하고 K, L, margin이나 cap을 튜닝하거나
자동 재측정하여 통과시키지 않는다.
signed d는 유휴를 빼지 않은 보수적 원 측정값으로 보존한다. 식별된 유휴는 d를 키워
용량 κ를 낮추는 방향이므로 결과에 나노초 단위 `dRange=[d−idleNanosPerRequest,d]`와
`kappaErrorBound=idleFraction`(κ 상대 오차 상한)을 함께 보고한다.
유휴 미식별이면 이 범위와 상한을 보고하지 않으며 부분 유휴로 보정하지 않는다.
[ADR-0028](../adr/0028-identified-idle-acceptance.md)에 판단 근거를 남긴다.
새 K는 Accepted10의 K와 다를 수 있으며 동일성은 불변량이 아니다.
기존 Accepted와 동결 입력은 불변이고 기존 측정을 묵시적으로 재실행하지 않는다.
보고서의 기존·새 결과 비교는 실제 근거로 수행하며 공급 변경 후 비교가 불변이라고 전제하지 않는다.

배치를 키우면 항상 효율이 좋아진다거나, 같은 타입의 노드는 항상 같은 성능을
낸다고 전제하지 않는다. 노드·전력모드·배치의 비교는 해당 측정 결과를 사용한다.

## 전력과 에너지

전력은 노드 전체의 벽전력을 기준으로 관측한다. edge-metrics 같은 수집 경로로
얻은 값에는 대상, 단위, 측정 시각과 측정 구간이 연결되어야 한다.

- 모델이 준비된 채 요청을 처리하지 않는 유휴 상태와 서빙 비참여 상태를 구분한다.
- 연산 중의 전체 노드 전력에 유휴 전력이 이미 포함되어 있으면 다시 더하지 않는다.
- 전체 POOL 전력은 같은 시점의 노드 전력 합이며, 에너지는 해당 기간의 전력을
  누적한 값이다. 활성 POOL의 소비는 별도로 집계할 수 있다.
- 요청당 전체 에너지와 유휴 소비를 뺀 증분 에너지를 구분한다. 증분 에너지를
  전체 소비로 사용하거나 유휴분을 중복 계산하지 않는다.
- 같은 노드에 파드가 여러 개 있어도 노드 전력은 한 번만 집계한다. 각 파드의
  단독 실험에서 측정한 노드 전체 전력을 단순히 더해 공존 비용을 만들지 않는다.
- 운영 전력 창의 읽기 실패는 성공 표본 사이의 gap으로 취급하며 실패 한 건만으로
  불완전 처리하지 않는다. 기록된 최대 gap·최소 coverage·경계 거리 정책으로 판정하고,
  노드별 창 안 읽기 실패 횟수와 실제 표본 최대 간격 및 창 합계/최대값을 보고한다.
  운영 evaluation 에너지 집계의 MaximumGap은 3.0 s, MinimumCoverage는 0.75,
  경계 거리는 1.0 s로 둔다. 단발 실패 실측 공백 ≤2.52 s와 연속 두 번 실패
  공백 ≥3.2 s를 구분하기 위한 설정이며 정확 비용 등 다른 측정 정책은 바꾸지 않는다.

운영자는 한 노드의 준비, 유휴, 해제, 빈 노드 전력모드 변경을 순서 있는 측정 요청 하나로
선언한다. 동작마다 기록을 남기고 기록은 그 요청을 가리킨다.

노드 편입·모델 준비·전력모드 변경 등은 소요 시간과 에너지를 측정하고, 전환 중
추론을 계속할 수 있는지 관측한다. 임시 자원을 포함한 POOL 전환 비용의 합성은
[구성 선택](04_configuration_selection.md)에서 다룬다.

## 측정 설정과 실패

반복 횟수, 측정 시간, 워밍업, 통계 계산에 필요한 값은 측정 입력으로 설정하고
결과와 함께 남긴다. 구체적인 값은 측정 목적과 연구 근거에 따라 선택한다.

실행 실패, 필수 관측 누락, 계산 불가능한 입력은 오류로 드러낸다. 없는 수치를
채워 넣지 않는다. 열 상태와 간섭은 필요하면 관측 자료로 보존하되, 별도의 제어
대상이나 자동 합격·불합격 정책으로 요구하지 않는다.

## Evidence Store의 역할

Evidence Store는 측정 설정, 원시 관측, 실행 결과와 파생 결과를 보존한다.
파생 결과에는 어떤 측정과 계산 조건을 사용했는지 연결한다. 이를 위해 별도의
일반화된 신뢰도 판정 시스템을 만들 필요는 없다.
실험 구간의 관측은 사후 재생이 가능한 동안 보존하고, 조회는 보존 위치가 로컬인지
근거 저장소인지에 관계없이 투명하게 같은 구간의 관측을 제공한다.
실험이 참조하는 부하 trace·씨앗·시작 상태는 내용이 고정된 증거로 보존한다.
실험 정의·실행 기록·판정 증거를 서로 연결하며, 정의가 참조하는 증거는 삭제하지 않는다.

- 스케줄러는 워크로드와 실행 대상에 맞는 프로파일을 조회하고, 측정한 실행 구성만
  선택한다. 대상이 맞지 않거나 필요한 측정이 없으면 그 후보를 선택하지 않는다.
- 같은 측정 조건의 결과가 여러 개면 최신의 성공한 측정 결과를 우선한다. 한 측정
  안에서 수행한 반복 trial의 집계와, 측정 결과 사이의 최신 선택은 구분한다.
- 프로파일링을 요청하는 것은 운영자의 역할이다. 완료된 측정 결과는 해당 노드를
  그 워크로드의 후보로 만든다. 자동 만료와 노후화 판정은 요구하지 않는다.

조회 결과는 구성별 특성이지 다음 POOL 구성의 정답 자체가 아니다. 스케줄러가
현재 부하와 상태에 대입하여 후보를 비교한다. 필요한 파생 표와 조회 형식은 그
입력이 구체화될 때 정하며, 특정 CRD나 저장 엔진을 명세의 전제로 삼지 않는다.
