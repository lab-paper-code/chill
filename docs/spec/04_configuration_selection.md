# 구성 선택과 비용

스케줄러는 **현재 구성에서 출발해, 워크로드의 SLO를 우선 만족시키면서 전환과
Serving의 총에너지가 가장 유리한 운영 선택**을 찾는다. 최종 상태의 전력만
비교하지 않으며, 현재 상태를 그대로 유지하는 선택도 후보에 포함한다.

## 입력과 결정

| 입력 | 용도 |
|---|---|
| 워크로드의 모델과 지연 SLO | 처리할 요청과 지켜야 할 조건 |
| 전체 POOL과 실제 구성 | 노드별 소속(워크로드별 활성 POOL, 측정 POOL, 가용 노드), 노드별 가용 자원과 전력모드, 인스턴스별 모델과 실행 경로 및 자원 할당 |
| 워크로드 전체 및 인스턴스별 부하 | 워크로드별 유입·대기·지연과 인스턴스의 합산 처리 부담 |
| 구성별 프로파일 | 실행시간 분포·처리량·메모리 사용량·전력·에너지의 측정 근거 |
| 전환 프로파일과 진행 상태 | 변경 비용, 준비 시점, 전환 중 처리 능력 |

결정에는 활성 노드, 서빙 파드별 모델·실행 경로·CPU·메모리 요청량,
노드 전력모드, 요청 분배·배칭, 필요한 전환 동작이 포함된다. 기존 인스턴스의 자원
변경도 선택 대상이며, 실행 구성은 측정한 조건에서만 선택한다.
워크로드별 활성 POOL의 소속 노드는 구성 선택과 실제 전환 결과에 따라 갱신한다.
메모리는 프로파일의 사용량을 근거로 배치 가능 여부를 판단하는 제약이지
성능·비용 조절을 위한 독립 탐색 변수가 아니다. 배치 가능한 자원이 남아 있는지와
그 구성으로 SLO를 감당할 수 있는지는 별도로 판단한다. 전력모드는 노드 전체에
적용되므로, 변경이나 인스턴스 제거가 영향을 주는 모든 워크로드를 함께 고려한다.
운영자가 스케줄러 설정에 정한 워크로드별 최소 수요를 계획 수요의 하한으로 쓰고,
적용한 최소 수요를 구성 판단과 함께 기록한다.

### 프로파일에서 요청 지연 계산

프로파일의 실행시간 분포에 배칭과 큐 선택 규칙을 적용한 인스턴스 재생으로 실행
조건과 SLO마다 SLO를 지키는 최대 요청률을 미리 계산하고, 후보 구성은 그 용량의
합과 현재 요청률과 대기량으로 판정한다. CHILL 수신 시각부터
응답 반환까지의 예상 지연으로 워크로드별 SLO를 판단하며, 프로파일에 포함되지 않은
전달·응답 처리 비용은 설정 여유로 반영하고 Serving 관측으로 그 여유를 검증한다.
평균 처리량만으로 지연 백분위를 결정하거나 단계별 지연 백분위를 단순 합산하지 않는다.
용량은 프로파일에서 계산하므로 별도의 부하별 Serving 측정은 요구하지 않고, 실제
SLO와 에너지와 계산의 오차는 기존 종단 평가에서 확인한다.

## 비교할 비용

```text
비교 기간의 총에너지
  = 전환 구간에서 POOL이 소비하는 에너지
  + 전환 이후 Serving 구간에서 POOL이 소비하는 에너지
```

모든 후보를 같은 시간축, 요청 부하 조건, 전체 POOL 범위에서 비교한다. 후보 사이에
같은 항(상태가 바뀌지 않는 노드와 구간)은 소거해 차이로 비교할 수 있다. 전체 POOL
총에너지는 실측으로 집계해 보고한다.
전환 이후 구간의 시작은 해당 후보가 실제로 준비되는 시점이다. 현 상태 유지에는
전환 구간이 없지만, 그 기간의 Serving 에너지는 그대로 발생한다.

전환 구간에는 모델 준비, 전력모드 변경, 계속 요청을 처리하는 기존 노드,
필요하다면 임시 노드의 소비까지 포함한다. 이후 구간에는 활성 노드의 유휴·연산
소비와 비참여 노드의 소비를 포함한다. 같은 구간의 같은 소비를 두 번 더하지 않는다.
전환 프로파일이 전체 에너지가 아니라 기준 소비를 뺀 추가 에너지를 제공한다면,
기준 소비를 포함해 같은 비용 의미로 맞춘 뒤 비교한다.

모델 로드와 유휴 비용은 인스턴스마다 한 번 계산한다.
같은 노드의 여러 파드가 단독 실행될 때 잰 노드 전체 전력을 합산하지 않는다.
공존 비용의 계산은 자원 할당 조건과 관측된 오차를 근거로 하며, 무간섭을 전제하지 않는다.

전환 시간은 에너지와 단위를 섞어 더하지 않는다. 새 용량이 언제 준비되는지,
그동안 어느 노드가 요청을 처리할 수 있는지와 SLO 충족 가능성에 반영한다.

## 현재 상태가 선택에 영향을 준다

같은 부하라도 현재 구성에 따라 좋은 선택은 달라질 수 있다.

- A 노드의 전력모드를 올리는 것과, A를 유지하면서 B를 추가하는 것을 비교한다.
- 더 낮은 전력의 구성이 있어도 전환 비용을 포함하면 유지가 유리할 수 있다.
- 임시 노드가 전환 중 SLO를 돕는다면, 그 준비·운영·해제 비용을 포함해 비교한다.
- 부하가 낮아지면 요청 재분배, 전력모드 변경, 불필요한 서빙 배치 제거를 비교한다.

효율적인 노드부터 부하를 맡기고 필요에 따라 확장하는 방식은 가능한 정책이다.
그러나 고정된 노드 순위나 한 노드의 최대 전력모드를 소진한 뒤 다음 노드를
추가하는 순서가 항상 최적이라고 전제하지 않는다. 최선의 비교 단위는 노드의
순위 하나가 아니라, 현재 상태에서 선택 가능한 POOL 운영과 그 비용이다.

## 시간과 부하 변화

전환 비용을 Serving 절감과 비교하려면 얼마나 긴 기간을 볼지 정해야 한다.
가상의 예로, 전환에 추가로 100J를 쓰고 이후 10W를 절감한다면 같은 조건이
10초 유지되어야 그 추가 비용을 회수한다. 이것은 비용의 의미를 설명하는 예이며
특정 대기 시간이나 전환 규칙을 정하는 공식이 아니다.

비교 기간, 그동안의 부하를 다루는 방법, 후보 탐색 알고리즘은 설계에서 정한다.
미래 부하를 알고 있다고 가정하지 않으며, 부하 예측기의 도입도 전제로 두지 않는다.

스케줄러는 실제 부하와 전환 진행 상태를 관측해 다음 판단에 반영한다. 버스트와
점진적 변화에 서로 분리된 임시 대응을 붙이는 대신 같은 제어 로직을 적용하고
시나리오별 결과를 평가한다. 관찰·제어 주기와 전환 중 재판단 규칙은 명시적으로
정해야 하지만, 고정된 초·분 단위나 특정 트리거를 여기서 강제하지 않는다.

## SLO와 실행 가능성

선택한 구성뿐 아니라 그 구성에 도달하는 과정의 처리 능력도 고려한다.
최종 POOL은 충분해도 준비가 끝나기 전에는 요청을 감당하지 못할 수 있다.
SLO를 만족할 수 있는 선택이 있으면 에너지 절감을 위해 그 조건을 포기하지 않는다.

모든 후보가 SLO를 만족하지 못하면 가용 자원으로 SLO 충족을 우선하는 대응을
계속하고 실제 요청 지연과 처리 결과를 기록한다. 전체 POOL의 한계와 일시적인
전환 중 부족은 구분한다. SLO 목표는 구성 선택의 제어 기준이며, 요청 수명은
명시적인 timeout/cancel과 서빙 자원 한계에 따라 관리한다.
결과의 집계와 분석 책임은 [SLO 관측과 집계](README.md#slo-관측과-집계)를 따른다.

결정은 [전환 실행](05_transition_control.md)과 [라우팅·배칭](03_routing.md)에
전달한다. 실행 실패나 실제 상태 변화가 생기면 원래 계획이 아니라 관측된 상태를
출발점으로 다시 판단한다.
