# CHILL 스케줄러 SRS

## 1. 목적과 범위

이 문서는 CHILL 스케줄러의 판단 근거, 선택 결과, 실행 계층과의 책임 경계,
실제 결과를 다음 판단에 반영하는 기능을 정의한다.
[시스템 명세](../README.md)의 스케줄러 책임을 입력, 출력과 기능 요구사항과
검증 시나리오로 구체화한다. 요구사항 ID의 `SCH`는 스케줄러를 뜻한다.

이 문서는 고수준 요구사항 기준이다. 구현 진도는 실제 소스와 실행 증거로
확인한다. 알고리즘과 계측 제품, API와 저장 형식과 프로세스 배치는 구현 설계에서
선택하고, 각 선택을 이 문서의 요구사항과 검증 시나리오에 연결한다.

#### SLO 우선 구성 선택
스케줄러는 워크로드의 지연 SLO 충족을 첫 번째 선택 기준으로 사용한다. SLO를 만족하는 운영 선택에서는 전환과 Serving의 총에너지를 비교한다. 처리량은 부하 수용 가능성을 판단하는 근거로 사용한다.
#### 현재 상태 기반 구성 비교
스케줄러는 실제 현재 구성과 부하에서 유지와 변경을 비교한다. 노드와 구성의 우선순위는 현재 상태의 전체 비용과 SLO 평가로 정하며, 실제 실행 결과와 부하 변화로 다음 판단을 갱신한다. 각 노드의 소속(워크로드별 활성 POOL, 측정 POOL, 가용 노드)을 실제 전환 상태에 맞춰 갱신한다.

### 1.1 포함하는 책임

- 자동제어가 켜진 워크로드의 활성 POOL 구성과 가용 노드의 편입과 반환 판단
- 서빙 인스턴스의 모델과 실행 경로와 배치 위치와 자원 할당, 노드 전력모드 판단
- 모델과 전처리가 서로 다른 여러 워크로드의 동시 서빙, 워크로드별 요청 분배와 evidence 기반 배칭과 큐 선택 정책 제공
- 전환 중 처리 능력, SLO와 비용을 포함한 유지 또는 변경 판단
- 판단 근거, 목표와 실제 진행과 결과의 구분 및 다음 판단으로의 피드백

### 1.2 다른 영역과의 경계

| 영역 | 소유하는 책임 | 스케줄러와의 연결 |
|---|---|---|
| 워크로드 관리 | 등록, 수정과 삭제, 적용 정의와 요청 접수 계약 | 모델, 입력, SLO와 관리 진행을 제공하고 기존 요청 의미를 보존 |
| 프로파일링과 Evidence Store | 측정 POOL에서 운영자가 요청한 조건의 실측과 근거 보존과 조회 | 후보를 평가할 실행과 전환 프로파일 제공 |
| Serving 유입과 라우팅 | 접수된 요청의 유입 대기와 인스턴스 전달과 결과 반환 | 분배 정책 적용, 요청과 부하와 처리 상태 관측 제공 |
| firstfloor 내부 배처와 실행기 | 현재 큐의 실제 배치 구성, 추가 대기, 실행 시점 판단과 전처리, 추론, 후처리 실행 | CHILL 정책, SLO, 요청별 시간 정보 적용, 실제 대기와 단계별 실행 결과 제공 |
| 전환 실행 계층 | 준비와 자원 변경, 전력모드, 라우팅과 유입 중지와 요청 마무리와 해제 | 선택 목표를 동작으로 적용하고 실제 완료, 실패와 상태 제공 |
| Dashboard와 분석 도구 | 허용된 조회와 설정 변경과 실험 결과 해석 | CHILL이 제공한 판단, 실행과 관측을 사용자 작업 흐름에 연결 |

각 영역은 논리적 책임을 나타낸다. 기존 구현의 서비스, 패키지와 인터페이스에
이 책임을 배치한다. 워크로드 CRUD, 측정 실행, 모델 로딩과 추론과 웹 UI는
각 영역의 기존 계약을 사용한다.

## 2. 역할과 정보 계약

### 2.1 역할

| 역할 | 스케줄러와의 관계 |
|---|---|
| 운영자 | 워크로드와 허용 자원과 운영 설정, 워크로드별 자동제어와 측정을 요청하고 판단과 전환 상태 조회 |
| 서비스 사용자 | 워크로드와 추론 입력을 지정해 요청하고, CHILL이 내부 노드와 배치를 선택 |
| 관측과 근거 제공 영역 | 실제 구성과 요청 상태와 전력과 실행과 전환 프로파일 제공 |
| 실행 계층 | 선택 목표와 정책을 적용하고 실제 상태, 완료와 실패를 반환 |
| 분석자 | 동일 조건의 요청 결과, SLO와 총에너지와 판단과 실행 기록으로 실험 해석 |

### 2.2 입력

| 입력 | 필요한 의미 |
|---|---|
| 워크로드와 요청 정의 | 등록 건 식별, 적용 모델 산출물, 전처리 산출물, 데이터셋 참조와 SLO, 접수 당시 정의와 최초 수신 시각 |
| 전체 POOL과 실제 구성 | 노드별 소속(워크로드별 활성 POOL, 측정 POOL, 가용 노드), 모델 준비, 전력모드, 인스턴스 실행 경로와 실제 할당과 가용 예산 |
| 요청 부하와 진행 | 유입, 접수, 분배와 결과, 미배정 대기, 인스턴스별 워크로드 대기와 실행과 합산 부하, 요청별 경과 시간 |
| 실행 프로파일 | [측정 조건](../00_measurement.md#측정의-단위)이 일치하는 실행시간 분포, 처리량, 메모리, 전력, 에너지 |
| 전환 근거와 진행 | 출발과 목표 상태, 동작, 시간과 에너지, 전환 중 가용 용량, 실제 진행, 완료와 실패와 일부 적용 |
| 운영과 분석 설정 | 관측 구간, 관찰과 제어 주기, 비용 비교 기간, 허용 자원과 제어요소 활성 여부 |

입력은 논리적 정보 계약이다. 각 소유 영역의 경계에서 검증한 정보를 기존
조회와 전달 경로로 사용한다. API와 저장 객체의 구성은 구현 설계에서 정한다.

### 2.3 출력

판단은 현재 상태 유지 또는 변경할 목표 구성과 정책을 제공한다. 변경 대상에는
워크로드별 활성 POOL과 소속 노드, 인스턴스의 모델과 실행 경로와 자원, 노드 전력모드,
워크로드별 분배와 배칭 정책 및 필요한 전환 동작이 포함된다.

판단에는 사용한 입력, 설정과 근거, SLO 충족 가능성과 비교 비용과 조건을 연결한다.
근거 확보 대기, SLO 수용 한계와 판단 실행 오류를 구분한다. 목표 선언과 실제
준비와 정책 반영과 전환 완료는 각각의 상태와 증거로 제공한다.
출력의 API, 필드와 상태 코드 표현은 구현 설계에서 정한다.

#### 워크로드별 분배 가능 상태
인스턴스 출력은 준비 상태와 별도로 워크로드 UID별 `routable`을 제공한다. 값은 서버의 현재 유효 배분 결과에서 산출하며, 준비됐지만 요청을 받을 수 없는 상태를 구분한다.
#### 라이브 인증과 재동기화
라이브 출력은 초기 상태와 상태 변경과 작업 이벤트, 지표와 생존 신호에 순번을 연결하고, 재연결 시 누락 구간을 재개하거나 전체 상태로 재동기화한다. WebSocket은 연결 직후 첫 메시지로 인증하고 인증 전에는 상태를 보내지 않으며, 인증 실패 시 즉시 연결을 닫는다.

라이브 채널은 기존 관측과 작업 결과의 전달 방식이므로 별도 시스템 spec 추가 없이 이 출력 계약과 구현 설계에서 다룬다.

## 3. 기능 요구사항

### 3.1 워크로드와 부하와 시간 의미

#### 워크로드와 요청 정의 식별
판단은 워크로드 등록 건과 적용 정의를 식별한다. 같은 서비스 이름의 재등록과 같은 모델을 참조하는 다른 워크로드를 구분한다. 접수한 요청은 접수 당시 모델과 입력 계약과 SLO와 최초 CHILL 수신 시각을 유지한다.
#### 부하 사건과 모집단 구분
부하 입력은 수신, 접수, 분배와 firstfloor 수신과 실제 처리 결과를 구분한다. 요청 수와 요청률에 사용한 사건, 시각과 모집단을 명시한다. 전체 유입에는 접수 전 거절을 포함한 실제 수신을 사용하고, 수신 구간의 요청 결과와 완료 사건 기준 처리량의 집계 의미를 구분한다.
#### 대기와 실행 상태 구분
미배정 유입 대기, 인스턴스별 firstfloor 대기와 실행 중 요청을 구분해 판단에 사용한다. CHILL 배정과 firstfloor 수신, 대기와 실행은 각 위치의 관측으로 확인한다. phase 확인을 기다리는 요청은 확인 대기 상태로 제공한다.
#### 요청과 배치의 부하 단위
부하는 워크로드별 inputs/s를 기본 단위로 다루고 대기, 실행, 완료량은 요청 수로 다룬다. 실행 배치 수는 별도 단위로 기록하고 배치 크기는 요청 수다. 인스턴스는 워크로드 하나의 부하와 SLO를 맡고 노드는 그 인스턴스들의 합산 부담을 유지하며, 처리 비용은 [측정 조건](../00_measurement.md#측정의-단위)별 프로파일과 관측으로 판단한다.
#### 관측 구간과 시각 기록
운영 부하는 설정된 시간 기반 이동 구간으로, 실험 분석은 지정 구간으로 집계한다. 구간과 경계 규칙, 모집단과 포함 및 제외 조건과 계산 방법과 관측 시각을 기록한다. 사건 발생, 수집과 조회 시각을 구분하고 관측 구간과 제어 주기와 비용 비교 기간을 각각 설정한다.
#### 근거 확보 상태 공개
평가에 필요한 관측과 근거의 확보 상태와 이유를 제공한다. 확보된 관측값, 계산값과 예측값에는 의미와 출처를 연결하고, 관측 공백과 평가 대기는 별도 상태로 드러낸다. 후보의 SLO와 비용 평가는 필요한 정보의 확보 범위에서 수행한다. 한 후보의 근거 확보 대기는 그 후보의 상태로 두고, 다른 후보와 현재 구성의 평가는 계속한다.
#### 명시적 최소 수요
계획 수요는 워크로드별 관측 수요와 운영자가 scheduler 설정 맵에 지정한 최소 수요(inputs/s, 기본 0) 중 큰 값으로 삼는다. 무부하에서도 그 하한을 감당하는 구성을 평가와 선택하고, 적용한 최소 수요와 계획 수요를 판단 및 Run 기록에 남긴다.

### 3.2 근거와 실행 가능한 후보

#### 실행 조건에 맞는 프로파일 선택
후보는 [측정 조건](../00_measurement.md#측정의-단위)과 실제 실행 조건에 맞는 측정 근거를 사용한다. 장비, firstfloor/backend, 전력모드, 자원, 배치 조건을 대응시키고 현재 모델, 기종, 실행 경로와 전력모드 셀의 최신 측정을 선택한다. 최신 실패와 부분 결과를 과거 성공으로 대신하지 않는다. 같은 실행 조건은 SLO가 다른 워크로드에도 재사용한다. 완료된 측정 근거는 해당 노드를 그 워크로드의 후보로 만들며, 요청 지연은 실행 프로파일과 Serving 관측으로 평가한다.
#### 자원 예산 내 인스턴스 배치
인스턴스 배치는 메모리, 가속기, 시스템과 Serving 부가 사용량을 반영한 실제 예산 안에서 선택한다. CPU는 예약과 제한 및 고정 없이 공유하며 GPU는 물리 장치 단위로 할당한다.
#### 단일 실행기와 순차 배치
서빙 파드 하나는 준비된 모델 실행기 하나를 제공한다. 인스턴스 수는 파드 추가와 제거로 조절한다. CPU 스레드는 런타임 기본 병렬성을 따르며 각 인스턴스는 실행 배치를 하나씩 순차 처리한다.
#### 메모리 제약과 공존 오차
메모리는 프로파일과 가용 예산에 근거한 배치 가능성 제약으로 사용한다. 자원 배치 가능성과 SLO 충족 가능성을 각각 판단한다. 관측 최대 메모리는 해당 측정 조건에 연결하고, 단독 실행 근거를 공존 구성에 적용한 오차는 실제 Serving 관측으로 평가해 필요한 측정과 운용 조건을 정한다.

### 3.3 SLO와 전환과 Serving 비용 비교

#### 유한 수요 직접 재생 평가
실행시간 분포와 firstfloor의 배칭과 큐 선택과 실제 진행 요청과 전환을 사용해 후보의 유한 수요를 직접 재생하고 SLO를 평가한다. 시간 피드백과 요청별 POST 동결과 profile routing과 현재 tested-rate κ̂의 의미는 [경로 기반 시간 계약](../../design/serving/analytic-planner.md)을 따른다. κ̂는 검사한 rate의 최대 통과값이며 전체 영역의 완료된 용량을 뜻하지 않는다. 전체 격자 κ는 명시적 offline 계산에 한정하고 online row 준비 여부나 κ̂=0을 후보 제거 gate로 사용하지 않는다. 디스패치 점유의 측정과 설정 선택과 provenance는 [구성 선택 설계](../../design/serving/analytic-planner.md)를 따른다. 유효 시간 표본이 없으면 기존 완료 여유 설정으로 초기화하며 새 관측 대기 gate를 두지 않는다.
#### 워크로드별 SLO 판정
SLO는 워크로드별 지정 백분위와 목표 시간으로 판단한다. 각 워크로드의 직접 replay 결과에서 실패와 성공 지연을 구분해 평가한다([유한 수요 직접 재생 평가](#유한-수요-직접-재생-평가)).
#### 전환과 최종 상태의 SLO
후보의 최종 상태와 준비와 전환 중 가용 처리 능력과 요청 지연을 함께 평가한다. 노드 전력모드 변경이나 인스턴스 제거에 영향받는 모든 워크로드의 SLO를 함께 평가한다. 자동제어가 켜진 모든 워크로드의 SLO를 함께 만족하는 후보를 우선하고 그 범위에서 전체 POOL의 에너지를 비교한다.
#### 전체 자원 풀 총에너지 비교
유지와 변경 후보는 같은 시간축과 부하 조건과 전체 POOL 범위에서 전환과 이후 Serving의 총에너지로 비교한다. 준비 시점부터 새 용량을 반영하고 유지 후보에도 비교 기간의 Serving 소비를 포함한다. Serving 참여 여부에 따른 모든 노드와 필요한 임시 자원의 소비를 집계한다. 후보 사이에 같은 항(상태가 바뀌지 않는 노드와 구간)은 소거해 차이로 비교할 수 있다. 전체 POOL 총에너지는 실측으로 집계해 보고한다.
#### 에너지 중복 집계 방지
모델 로드와 유휴 비용은 인스턴스당 한 번, 전체 노드 전력은 노드당 한 번, 각 소비 구간은 시간축에서 한 번 집계한다. 증분 에너지에 해당 기준 소비를 연결해 전체 에너지로 비교하고, 공존 비용은 자원 조건과 실제 관측에 대응시킨다.
#### 전환 시간과 비교 기간
전환 시간은 용량 준비 시점과 전환 중 처리 능력과 SLO 판단에 적용한다. 시간과 에너지는 각각의 단위로 기록한다. 현재 부하를 기본 판단 근거로 사용하고, 비교 기간과 그동안 부하를 다루는 가정을 설정과 기록한다.

### 3.4 선택 결과와 라우팅과 firstfloor 정책

#### 목표 구성과 실행 정책 전달
선택 결과는 유지 또는 목표 구성, 영향받는 워크로드, 노드와 인스턴스, 분배와 배칭 정책과 전환 동작을 실행 계층에 전달한다. 실제 현재 구성과 비교 후보와 선택 목표와 적용 조건을 구분해 제공한다. 판단 대기와 판단 결과는 각각의 상태로 표현한다.
#### 준비된 인스턴스 분배
요청은 해당 모델을 실제로 처리할 준비가 되고 해당 워크로드에 `routable`인 인스턴스 하나로 분배한다. 확인된 준비 상태와 가용 용량을 사용하고 수용 가능한 대상이 준비되면 요청을 전달한다. 분배 비율은 0 이상이며 대상이 있을 때 합이 1이다. 실현된 부하, 배칭, SLO와 에너지 영향을 다음 판단에 반영한다. 최종 handoff 뒤 정리 중인 범위도 원래 DAG와 예약을 유지하며, 새 target의 재분배는 예약 반환 뒤 다시 허가받는다.
  목표 양수 목적지 일부가 준비 중이어도 old serving 공급을 보존하면서 현재 serving이 없는 독립 Node의 새 Ready 공급을 추가할 수 있다. exact identity와 native policy ACK와 양수 weight와 현재 수요와 timing의 직접 평가를 사용한다. 같은 Node 공급을 중복 합산하지 않고 old 공급과 accepted work를 보존한다. 물리 상태, support와 평가가 미확인이면 current를 유지하며 old capacity row나 κ̂ 미검사만으로 차단하지 않는다.
#### 요청 경과시간 기반 배칭 정보
배칭 정책은 evidence와 워크로드 SLO와 최초 CHILL 수신 이후 요청별 경과 시간을 적용할 정보를 제공한다. firstfloor 큐 진입 이전 소비 시간, 현재 큐 대기와 진행 중 실행, 후보 실행시간과 [유한 수요 직접 재생 평가](#유한-수요-직접-재생-평가)의 요청별 frozen POST를 포함해 추가 대기 여유를 판단한다.
#### 실행기 내부 배칭 책임
firstfloor 내부 배처가 현재 요청, 큐와 실행 상태에 CHILL 정책을 적용해 실제 배치 구성과 추가 대기와 실행 시점을 판단한다. CHILL은 정책과 요청별 정보를 제공하고 기존 firstfloor 큐, 배처와 모델 runner를 재사용한다.
#### 호환 요청의 배치와 큐 정책
같은 워크로드와 불변 정의의 호환 요청을 실행 배치로 구성한다. serving 과부하 정책은 Workload admission이 소유하고 요청에 동결한다. Reject는 완료 불가능 요청을 실행 없이 거절하며 Delay는 정상 요청 뒤로 보낸다. 정상 큐는 stable EDF, 지연 큐는 정상 이후 FIFO다. 지연 큐에서는 현재 대기 요청으로 구성할 수 있는 허용 배치 중 항목당 서비스 시간 분위수가 가장 작은 배치를 선택하며, 같으면 더 큰 배치를 선택한다. ModelSpec deadlinePolicy는 측정 provenance로 유지하며 serving 정책 선택에 쓰지 않는다. 명시 timeout과 취소는 두 큐에 적용하고 active batch는 SLO만으로 선점하지 않는다.
#### 명시적 배분 변경 작업
배분 선언의 변경은 `route`(워크로드별 인스턴스 가중치 지정), `unroute`(선언을 유지한 배분 해제), `release`(선언 삭제 후 Pod 기본 표시 적용)를 구분하는 명시적 작업으로만 받는다. 각 작업은 실제 적용 ACK와 readback을 반환하고, 설정의 `staticRouting`은 읽기 전용으로 제공한다.

### 3.5 전환과 실패와 재판단

#### 전환 목표와 실제 진행 구분
목표 선언과 실행 시작과 정상 진행과 실제 완료, 실패와 일부 적용을 구분한다. 동작별 대상과 시작 조건과 완료 및 실패 기준과 의존관계를 실행 계약에 연결한다. 모델 준비, 전력모드, 자원과 라우팅은 실제 적용 증거로 확인하고 결과를 다음 판단에 사용한다.
#### 준비 용량 편입과 안전한 제거
전환 중 준비된 용량으로 요청을 처리하도록 계획한다. 기존 인스턴스의 처리 지속 가능성, 동시에 빠지는 용량과 임시 용량을 평가한다. 새 대상 준비 후 유입을 옮기고 제거 대상은 신규 유입 중지와 기존 요청 마무리를 차례로 수행한다. 독립 동작은 전체 용량과 SLO 조건에 따라 병렬 실행하고 전환 중 서비스 가용 범위를 기록한다.
#### 실패 격리와 관측 기반 복구
판단과 실행 실패와 노드와 backend 소실의 대상, 원인과 실제 완료 상태를 기록한다. 의존성이 충족된 동작을 진행하고 관측된 상태에서 다음 목표를 선택한다. 소실한 대상은 격리하며 실제 복구를 확인한 대상이 다시 가용 용량에 참여한다.
#### 전환 중 재판단
전환 중 부하와 진행 상태가 변하면 실제 상태에서 재판단한다. 진행 중인 동작은 기존 진행으로 추적한다. 버스트와 점진적 변화와 확장 후 급감과 축소 후 재증가에는 같은 제어 로직을 적용하고 반복 전환 비용을 평가한다. 동작의 계속 수행, 취소와 재선택은 해당 조건과 비용에 따라 정한다.
#### SLO 수용 한계 대응
SLO 수용 한계에 도달하면 가용 자원으로 SLO 충족을 우선하는 대응을 계속한다. 전체 POOL 한계와 일시적 준비 용량 제약과 실행 오류와 근거 확보 대기를 구분하고 실제 지연과 처리 결과로 적용 가능한 부하 범위를 드러낸다. 요청 수명과 큐 한도는 명시적 timeout, 취소와 Serving 자원 설정을 따른다.
#### 준비된 부분 용량 편입
목표 구성의 일부 인스턴스가 Ready가 되면 나머지 준비와 전력 전환 완료를 기다리지 않고 늦어도 다음 제어 주기에 준비된 부분집합을 배분에 편입한다. 드레인 중이거나 전력 변경의 영향을 받는 대상은 제외하고, 최종 목표와 진행 중 동작 및 다른 워크로드의 배분은 유지한다.
#### 정책 반영 대기 상태 보존
정책 변경의 native ACK를 기다리는 인스턴스는 읽기 실패나 부재로 취급하지 않고 마지막으로 확인한 상태로 현재 구성 snapshot에 유지하며, 정책의 목표와 실제 반영을 구분해 '반영 대기'로 표시한다. ACK 대기만으로 인스턴스를 누락하거나 같은 slot에 대체 인스턴스를 중복 준비하지 않는다. 전력 변경 전 정지와 드레인 등 기존 인스턴스에 대한 실행 의무는 ACK 대기 중에도 유지하며, 새 정책의 실제 적용은 ACK로 확인한다.
#### 관측 실패 노드 변경 보류
실제 인스턴스 상태 읽기에 실패한 대상(`InstanceUnavailable`)이 하나라도 있는 Node에서는 상태를 다시 확인할 때까지 새 인스턴스 준비와 전력모드 변경을 수행하지 않고, 읽지 못한 인스턴스의 부재를 근거로 제거 완료를 판정하지 않는다. 읽기 실패와 정책 ACK 반영 대기를 구분해 원인과 대상을 제공한다. 이 제약은 해당 Node의 불확실한 상태에 적용한다. 공유 CPU의 관측값을 이유로 전체 판단을 Pending으로 두지 않는다.
#### Pod별 실물 자원 장부
제어기는 실제 존재하는 실행기를 Pod UID 기준의 실물 장부 항목으로 유지한다. 같은 slot의 Pod도 각각 기록하며, 관측 실패만으로 항목을 삭제하거나 부재와 제거 완료로 판정하지 않는다. 관측은 항목의 최근 상태, 관측 품질(확인됨과 ACK 반영 대기와 읽기 실패 등), 마지막 성공 확인 시각과 실패와 대기 사유의 메모로 갱신하고, 실제 Pod 소멸을 확인한 뒤 항목을 제거한다.
  refresh/probe 진행 자체는 실패로 취급하지 않으며, 다른 실물의 부분 게시와 동시 snapshot에서도 마지막 확인 Ready를 유지한다([정책 반영 대기 상태 보존](#정책-반영-대기-상태-보존)). 실제 읽기 오류와 serving label 불일치와 Pod unready/삭제는 즉시 dispatch 자격을 닫고, 성공 native 재확인 뒤에만 복구한다.
  종료 증거와 실제 삭제로 퇴역한 UID는 늦은 probe/로그 follow 결과로 재생성하거나 runtime에 다시 게시하지 않는다. 같은 이름의 새 Pod UID를 옛 probe의 대리 대상으로 삼지 않으며, Pod 부재만으로 종료 불명 실행기를 stopped로 바꾸지 않는다. 관측되지 않은 실행기의 정리도 finalizer 직접 제거로 종료 증명을 우회하지 않는다.
#### 작업 범위 예약과 효과 반환
작업 시작 시 건드리는 Node와 Workload UID와 실물 Pod UID의 범위를 장부에 예약한다. 자동제어와 수동 작업을 포함한 모든 변경 경로의 허가와 범위 충돌 검사와 예약 해제는 같은 범위를 사용하는 단일 지점에서 수행하고, 겹치는 변경은 시작 전에 거절하며 사유와 소유 작업을 제공한다. 완료, 실패와 취소에 따른 실행 종료와 예약 해제를 구분하며, 실패 시에도 실제 효과가 확인되면 예약을 해제한다. 취소와 timeout 뒤 원격 효과를 확인하지 못한 경우에는 실행은 종료하되 효과 확인 또는 reset에 의한 실제 정리 완료까지 예약을 유지한다. 예약 해제는 실물 장부 삭제나 원복 완료를 뜻하지 않으며 실제 상태와 실패 원인은 남긴다.
  Workload 삭제도 삭제 시작 전에 Workload UID와 소유 실물의 범위를 같은 예약 경로로 획득하고, 자식 종료와 정리와 finalizer 해제 이후 정확한 Workload UID의 실제 삭제 확인까지 유지한다.
#### 예약 범위 밖 판단 지속
계획기는 전역 하나를 유지하며 진행 중 작업이 예약한 범위만 고정하고, 그 밖의 Node, Workload와 실물에 대해서는 현재 부하와 상태로 후보 평가와 확장 판단과 실행 및 준비된 용량의 배분을 계속한다. 모든 작업의 완료를 기다리는 전체 완료 장벽이나 `InProgressTarget`을 근거로 한 전역 판단 대기를 두지 않는다. 예약을 침범하거나 예약 대상의 상태 변경을 전제하는 후보는 허가하지 않으며, 기존 자원과 SLO 제약은 유지한다.
#### SLO 미충족 후보 비교
전체 SLO 충족 후보를 먼저 비교하고 충족 후보끼리는 기존 에너지 순서를 사용한다. 미충족 후보의 failure fraction와 finite-success excess와 conditional potential tuple과 `excess`/`workload` 우선순위는 [경로 기반 후보 비교 계약](../../design/serving/analytic-planner.md)를 따른다. old 최종 충족/κ-only 순서를 tuple 앞에 두지 않으며 SLO 미충족만으로 물리적으로 유효한 개선 후보의 retirement를 일괄 거절하지 않는다. Ready, 소유와 accepted work와 정상 handback과 기존 에너지 보호는 유지한다.
#### 빈 출발의 직접 후보 평가
빈 출발도 profile와 현재 timing와 수요로 직접 평가한다. no-profile와 raw support 부재와 물리 관측 실패는 원인을 기록하되 전체 grid나 capacity row의 Built/pending을 기다리지 않는다. 경과 시간 fallback이나 새 bootstrap 대기 상태는 두지 않는다.
#### 현재 수요의 공통 후보 비교
분배, 증설, 축소와 교체 후보를 매 제어 주기에 같은 현재 유효 수요와 물리 규칙으로 비교한다. 기존 예약, 자원, SLO와 실제 Ready/ACK 제약을 유지한다.
  최종 하강 route와 idle 후처리의 현재 유효 수요×(1+h) 보호와 configured h를 유지하며 현재 routing와 수요 평가에 연결한다. old row/κ̂-only 보장을 사용하지 않는다. bridge/reserve 수요와 실제 요청 J는 할증하지 않는다.
#### 현재 유효 수요와 정책 시간
현재 유효 수요는 max(장기 관측률, 최근 관측률) + outstanding/실제 관측 길이에 minimumDemand 하한을 적용한다. reductionDemand는 같은 현재 수요이며 별도 이력 최대값과 증가 추세와 지속 시간 허가를 두지 않는다. 빈 Node 절전도 동일 수요와 gain/minimumGain/payback을 적용한다.
  정책 시간은 ControlInterval, ObservationWindow, ComparisonPeriod 세 개다. API, ConfigMap, Dashboard, sample, 결정과 Run binding은 동일 계약을 사용한다.
#### 전환 예비 용량 비율
전환 중 수요 대비 예비 비율을 scheduler 설정으로 제공한다(기본 0, 0=별도 예비 없음, 유한한 0~1). 양수이면 실제 Ready, ACK, ownership와 예약상 사용 가능한 공급의 profile-rate estimate로 수요와 설정 예비를 비교한다. 이는 SLO 용량 보장이 아니며 SLO는 별도 직접 replay로 평가한다. 예비 준비, 유지와 해제 에너지도 evaluation 전체 POOL 에너지에 포함하고 비율, 판정과 미확보 이유를 결정과 `binding.schedulerSettings`에 기록한다.
#### 후보와 독립적인 에너지 비교 기간
에너지 비교 기간 H는 양수인 하나의 scheduler 설정으로 고정하여 같은 판단의 keep과 모든 후보에 동일하게 사용한다. 후보의 전환 시간이나 미선택 후보의 추가와 삭제로 H를 늘리지 않으며 사용한 H와 부하 가정을 결정 및 `binding.schedulerSettings`에 기록한다. H는 실제 전환 완료 확인이나 동작 timeout을 대체하지 않는다.
#### 빈 노드 절전의 에너지 허가
빈 Node의 새 `Fixed` 절전도 일반 교체와 동일한 keep 대비 에너지 허가를 받는다. 같은 H 안 nominal 이득이 양수이고 기존 minimumGain 문턱 및 payback을 모두 통과해야 하며, Fixed라는 이유로 비용을 공통 경로에서 소거하거나 검사를 면제하지 않는다. 별도 절전 계산기, 기간과 문턱을 추가하지 않는다. 이미 실행 중인 허가된 동작의 완료 의무는 유지한다.

[Pod별 실물 자원 장부](#pod별-실물-자원-장부)은 [정책 반영 대기 상태 보존](#정책-반영-대기-상태-보존)의 ACK 대기 snapshot 보존과 중복 준비 방지, [관측 실패 노드 변경 보류](#관측-실패-노드-변경-보류)의 읽기 실패 시 부재로 간주하지 않는 처리를 실물 장부로 흡수한다. [정책 반영 대기 상태 보존](#정책-반영-대기-상태-보존)의 목표와 실제 반영 구분 및 ACK 확인과 [관측 실패 노드 변경 보류](#관측-실패-노드-변경-보류)의 해당 Node 준비와 전력 변경 보류는 그대로 유지한다. [작업 범위 예약과 효과 반환](#작업-범위-예약과-효과-반환)은 그 보류와 작업 충돌을 공통 예약 경로에서 집행하며, [예약 범위 밖 판단 지속](#예약-범위-밖-판단-지속)는 [준비된 부분 용량 편입](#준비된-부분-용량-편입)의 준비된 부분집합 배분을 유지하면서 예약 밖의 새 판단까지 계속하도록 확장한다. 관측 실패 노드의 안전한 변경 보류와 예약 밖 판단 지속을 구분한다. [원자적 자원 정리](#원자적-자원-정리)의 중복 실물 전체 reset도 유지하되 [Pod별 실물 자원 장부](#pod별-실물-자원-장부)의 Pod별 장부를 정리 대상으로 사용한다.

### 3.6 관리 연동과 관측과 운영 설정

#### 워크로드 관리 변경 반영
워크로드 등록과 SLO 변경과 모델 변경과 삭제와 POOL 관계 변경을 판단에 반영한다. 기존 요청은 접수 당시 정의와 관리 영역의 마무리 계약을 유지한다.
#### 판단과 전환 근거 기록
사용한 부하, 큐, SLO와 실제 구성, 프로파일과 전환 근거와 비교 기간과 설정과 후보별 적격성 평가, 선택과 반영 결과를 연결해 제공한다. 라우팅 결정 시각과 실제 반영 시각을 각각 기록하고, 제어 동작의 대상과 시작 및 완료 시각과 결과를 요청과 전력과 같은 시간축에 연결한다. 예상 지연과 에너지와 실측 결과를 구분해 종단 평가에서 오차를 확인한다. 탐색 전략과 가지치기 수와 후보 수, fallback와 그림자 비교를 기록한다.
#### 요청 결과와 원시 관측 보존
요청별 시간과 배정 인스턴스와 실제 결과, 실현된 배치와 전력 관측을 보존한다. 완료, 실패, 거절, timeout, 취소, 미완료와 전달 실패와 SLO 초과를 구분하고 모집단과 표본 수를 제공한다. 표본 수 0인 구간의 지연 통계 값은 공란으로 표현한다. 원시 기록과 집계 조건으로 같은 분석을 재계산하고 분석자가 실험 성패를 해석한다.
#### 운영 설정과 비교 실험 관리
허용된 운영자는 시스템 전체의 관측 구간과 관찰 및 제어 주기와 비교 기간과 허용 자원과 제어요소 활성 설정을 조회와 변경한다. 전후 정의와 검증 결과와 영향 범위와 실제 적용 진행과 사용한 설정을 기록한다. 정적 구성과 제어요소별 기여 실험은 동일 부하 조건과 전체 POOL 범위로 평가하고 선택 근거를 보존한다.
#### 워크로드별 자동제어
자동제어는 워크로드별로 켜고 끄며, 최소 수요는 별도의 scheduler 설정 맵([명시적 최소 수요](#명시적-최소-수요))으로 둔다. 켜진 워크로드는 가용 노드, 자기 활성 POOL 노드, 같은 등록 모델을 참조하는 다른 워크로드의 활성 POOL 노드 중 측정 근거가 있는 노드로 첫 구성을 선택해 만들고, 이후 제어 주기마다 다시 판단하며, 인스턴스를 하나 이상 유지한다. 노드마다 서빙 인스턴스를 하나만 배치하며, 실제 메모리와 가속기 예산 및 인스턴스 상한을 지킨다. 측정 근거가 있는 노드가 없는 켜진 워크로드는 측정 근거 대기 상태를 제공하고, 다른 워크로드의 판단과 실행은 계속한다. 꺼진 워크로드는 마지막 구성을 유지하고, 그 워크로드의 수동 변경은 그 워크로드에만 적용한다. 꺼진 워크로드와 공유하는 노드의 전력모드를 바꿀 때는 꺼진 워크로드의 SLO도 함께 평가하고, 꺼진 워크로드의 인스턴스는 그대로 둔다. 가용 노드는 가장 낮은 전력모드로 두고 다시 편입하는 전환 비용을 비교에 포함한다. 활성 POOL 사이에서 노드를 바로 옮기는 것은 전환 하나로 실행하고 그 비용을 비교에 포함한다.
#### 측정 노드 편입과 반환
측정 요청은 대상 노드를 측정 POOL로 옮겨 수행하고, 끝나거나 실패하면 가용 노드로 돌려보낸다. 활성 POOL에서 서빙 중인 노드에 대한 측정 요청은 거절하고 사유를 제공한다. 측정 POOL의 노드는 측정에만 사용한다. CHILL이 배치하지 않은 파드가 있는 노드도 가용 노드로 다루고 전력모드를 바꾸며 측정을 진행하고, 측정 결과에는 그 파드들의 목록을 기록한다. 한 노드의 측정 요청은 요청 순서대로 하나씩 실행하고, 서로 다른 노드의 측정은 동시에 진행한다. 측정이 노드에 둔 파드는 서빙으로 보지 않는다. 메모리나 GPU, 장치 신원 또는 소유권 조건을 충족하지 못하거나 요청이 가리키는 측정 근거가 쓸 수 없으면 요청을 거절하고 사유를 남긴다.
#### 고정 배치 비교 실행
비교 기준 실험으로 운영자는 firstfloor 인스턴스에 고정 배치 크기 B를 설정한다. 같은 워크로드/불변 정의의 호환 요청이 B개 이상 대기하면 실제 요청 정확히 B개를 실행한다. 이 인스턴스의 배치 구성과 실행 시점은 B만으로 정하며 [유한 수요 직접 재생 평가](#유한-수요-직접-재생-평가), [요청 경과시간 기반 배칭 정보](#요청-경과시간-기반-배칭-정보), [호환 요청의 배치와 큐 정책](#호환-요청의-배치와-큐-정책)의 SLO 여유, 완료 여유, deadlinePolicy는 배치 선택에 적용하지 않는다. 남은 요청은 B가 찰 때까지 대기한다. 명시적 timeout, 취소, 큐 한도, 종료는 그대로 적용하고 종료 시 남은 요청은 실행하지 않는다. SLO 초과와 종단 결과는 [요청 결과와 원시 관측 보존](#요청-결과와-원시-관측-보존)대로 기록한다. 자동제어는 고정 배치 크기를 선택하지 않고 이 인스턴스를 후보로 쓰지 않는다. 설정한 B는 실행 설정과 결과에 기록한다.
#### 원자적 자원 정리
서버의 원자적 `reset` 작업은 지정 워크로드 UID 목록(또는 전체 비자율 워크로드)에 대해 자동제어 해제 → 배분 해제와 ACK → 미완료 요청 0까지 드레인 → 소유 인스턴스 stop과 remove와 Pod 소멸 확인 → 배분 선언 삭제 → 빈 노드 최저 전력모드 복귀와 Ready 확인 순서로 수행한다. 같은 slot에 실물 인스턴스가 여러 개 있어도 slot당 하나로 축약하거나 중복을 이유로 거절하지 않고, 대상 워크로드가 소유한 실물 전부를 정리하며 다른 소유자의 인스턴스는 건드리지 않는다. 단계별 시작과 완료 시각과 실제 상태 readback을 반환하고 실패 시 해당 단계와 이유를 기록해 자동 재시도 없이 멈추며, 이미 정리된 상태의 재호출은 변경 없이 성공한다.
#### 과거 관측의 투명 조회
실험 구간의 관측과 원시 기록은 사후 재생이 가능한 동안 보존하며, 조회는 로컬에 없는 시간대의 기록을 근거 저장소에서 투명하게 읽는다. 조회 결과는 실제 보존 범위, 출처와 공백을 드러내고 로컬 보존 기간에 의해 과거 실험 기록을 누락시키지 않는다.
#### 과거 워크로드 정의 보존
관측 기록은 워크로드 UID와 함께 당시 이름, 모델과 적용 정의를 보존한다. 워크로드 삭제나 같은 이름 재등록 뒤에도 UID로 원래 정의를 조회해 과거 결과를 식별한다.
#### 비용과 점유 측정 조회
허용된 조회자는 OperationCostMeasurement와 DispatchOccupancyMeasurement CR의 목록과 상세에서 상태와 결과 요약을 조회한다. 측정 생성과 변경은 기존 CR 경계를 유지한다.
#### 불변 실험 요약 조회
실험 ID별 불변 요약에 단계 경계와 단계별 KPI와 출처 경로를 연결해 근거 저장소에 보존하고 실험 목록과 상세 조회로 제공한다.
#### 운영 상태 축약 조회
상태의 축약 조회는 노드, 인스턴스, 배분과 현재 판단 요약과 진행 작업을 제공하고 프로파일과 κ 표는 제외한다.
#### 실측 기반 작업 예상시간
작업은 해당 조건의 전환 비용 실측 시간에 근거한 예상 소요 시간(`expectedSeconds`)과 그 출처를 제공한다. 예상값과 실제 진행, 경과와 완료 시간을 구분하고 근거가 없으면 예상 시간 미확보를 표시한다.
#### 관측 원시 기록 내보내기
허용된 실험 수집자는 요청, 판단, 정의, 관리, 자원과 클러스터 관측의 원시 기록을 CHILL API로 내보낸다. 조회는 로컬에 없는 시간을 기존 근거 저장소에서 읽고, 열린 기록과 완결된 기록, 보존 위치, 범위, 부재와 읽기 실패를 구분한다. 원시를 재집계와 재인코딩하지 않으며 기존 가공 조회를 대체하지 않는다. 기존 실험 보관본도 같은 저장 계약으로 읽는다.
#### 외부 자원과 온도 관측
CHILL은 모든 대상 Node에서 서빙 인스턴스와 제어 Pod 컨테이너의 CPU, throttle와 메모리 및 센서별 온도 원시 관측을 기록한다. Node와 Pod UID, containerID와 cgroup 버전과 단위와 Node 표본 시각과 서버 수신 시각을 보존하고 시계 차이를 보정하지 않는다. 서버의 GC 누적 CPU와 사이클과 관측 디렉터리 크기도 기록하며, 서버 컨테이너 자원은 외부 Node agent가 잰다. 전송 실패와 미관측은 0이나 보간 표본으로 만들지 않는다.
#### Pod와 장애 사건 기록
CHILL은 서빙과 제어 Pod의 생성, 삭제, Ready, 재시작과 종료 사유와 실행 이미지 식별과 observer 장애 감지의 발생, 변경과 해소를 대상과 시각과 함께 보존한다. 서버 기동은 자기 Pod UID를 남긴다. 기록에 성공한 동일 사실만 라이브 출력으로 전달하고, Node 상태는 기존 판단 기록을 사용하며 cordon을 새 사건으로 기록하지 않는다.
#### 읽기 전용 전력계 선언
운영 설정 조회는 서버가 실제 수락한 전력계 선언과 대상 Node 연결을 읽기 전용으로 제공한다. 선언을 설정 쓰기로 변경하거나 다시 제출하지 않으며, 조회 후 수정하는 실험과 대시보드 클라이언트도 읽기 전용 필드를 제외한다.

#### 노드 소속 갱신 검증

#### 자동제어와 근거 대기 공존 검증

#### 측정 요청 직렬화 검증

### 4.1 전환과 운영 작업 추가 수용 시나리오

#### 느린 전환 중 부분 배분 검증
- Given: 목표 구성 일부가 Ready이고 다른 노드의 느린 전력 전환이 진행 중이다.
- When: 다음 제어 주기가 실행되고 해당 워크로드 요청이 들어온다.
- Then: Ready 부분집합이 나머지 전환을 기다리지 않고 요청을 받으며, 드레인과 전력 변경 대상은 배분에서 제외된다.
- 요구사항: [준비된 인스턴스 분배](#준비된-인스턴스-분배), [준비 용량 편입과 안전한 제거](#준비-용량-편입과-안전한-제거), [워크로드별 분배 가능 상태](#워크로드별-분배-가능-상태), [준비된 부분 용량 편입](#준비된-부분-용량-편입).

#### 무부하 최소 수요 검증
- Given: 관측 수요는 0이고 최소 수요가 양수이며 이를 감당할 측정 근거와 자원이 있다.
- When: 자동제어가 구성을 선택한다.
- Then: SLO를 지키며 최소 수요 이상을 감당하는 구성을 선택하고 적용 하한과 계획 수요를 판단과 Run 기록에 남긴다.
- 요구사항: [유한 수요 직접 재생 평가](#유한-수요-직접-재생-평가), [워크로드별 자동제어](#워크로드별-자동제어), [명시적 최소 수요](#명시적-최소-수요).

#### 배분 선언 삭제 후 분배 검증
- Given: 비자율 워크로드에 unroute 선언이 남아 있고 새 측정 인스턴스는 Pod 기본 표시상 요청 수신 대상이다.
- When: release 작업의 ACK와 readback을 확인한 뒤 준비된 새 인스턴스에 대한 요청을 보낸다.
- Then: 배분 선언은 사라지고 새 인스턴스의 routable이 참이며 실제 요청을 받는다.
- 요구사항: [준비된 인스턴스 분배](#준비된-인스턴스-분배), [워크로드별 분배 가능 상태](#워크로드별-분배-가능-상태), [명시적 배분 변경 작업](#명시적-배분-변경-작업).

#### 원자적 정리 멱등성 검증
- Given: 대상 워크로드에 배분과 미완료 요청과 소유 인스턴스가 있다.
- When: reset이 성공한 뒤 같은 범위로 다시 reset을 호출한다.
- Then: 첫 호출은 배분 해제, 드레인, 제거와 전력 복귀 순서와 실제 완료를 기록하고, 두 번째는 추가 변경 없이 성공한다.
- 요구사항: [명시적 배분 변경 작업](#명시적-배분-변경-작업), [원자적 자원 정리](#원자적-자원-정리).

#### 정책 반영 대기와 중복 준비 검증
- Given: 기존 인스턴스가 확인된 상태이고 배분 변경으로 DecisionID가 바뀌어 native ACK가 아직 오지 않았다.
- When: ACK 대기 중 여러 제어 주기가 실행되고 이후 실제 상태 읽기 실패도 발생한다.
- Then: ACK 대기 중에는 기존 인스턴스가 마지막 확인 상태와 '반영 대기' 표시로 snapshot에 남고 같은 slot의 중복 준비가 없다. 실제 읽기 실패 시에는 해당 Node의 준비와 전력 변경과 부재에 의한 제거 완료 판정이 멈추며, 재확인 전까지 실행되지 않는다.
- 요구사항: [전환 목표와 실제 진행 구분](#전환-목표와-실제-진행-구분), [전환 중 재판단](#전환-중-재판단), [정책 반영 대기 상태 보존](#정책-반영-대기-상태-보존), [관측 실패 노드 변경 보류](#관측-실패-노드-변경-보류).

#### 정책 반영 대기 인스턴스 정지 검증
- Given: 전력모드 변경 대상 Node에 native 정책 ACK 반영 대기 중인 인스턴스가 있고 상태 읽기는 성공한다.
- When: 전력 변경을 위한 신규 유입 중지, 드레인과 정지 절차를 실행한다.
- Then: 반영 대기 인스턴스도 정지 대상에 포함하고 실제 드레인과 정지를 확인한 뒤에만 전력모드를 변경한다. 도중 읽기 실패가 생기면 전력 변경과 부재에 의한 제거 완료 판정은 재확인까지 수행하지 않는다.
- 요구사항: [전환 목표와 실제 진행 구분](#전환-목표와-실제-진행-구분), [준비 용량 편입과 안전한 제거](#준비-용량-편입과-안전한-제거), [정책 반영 대기 상태 보존](#정책-반영-대기-상태-보존), [관측 실패 노드 변경 보류](#관측-실패-노드-변경-보류).

#### 중복 실물 전체 정리 검증
- Given: reset 대상 워크로드가 같은 slot에 실물 인스턴스 여러 개를 소유하고, 대상 밖 소유자의 인스턴스도 존재한다.
- When: 해당 워크로드 UID로 reset을 실행하고 완료 후 같은 범위로 다시 호출한다.
- Then: 중복 slot을 이유로 실패하지 않고 대상 소유 실물 전부의 드레인, stop과 remove와 Pod 소멸을 확인한 뒤 배분 선언 정리와 빈 노드 전력 복귀를 완료한다. 대상 밖 인스턴스는 유지하며, 재호출은 추가 변경 없이 성공한다.
- 요구사항: [명시적 배분 변경 작업](#명시적-배분-변경-작업), [원자적 자원 정리](#원자적-자원-정리).

#### 관측 실패 중 실물 장부 검증
- Given: 같은 slot에 실제 Pod가 존재하고 장부에 Pod UID와 소유 Workload와 Node와 마지막 확인 상태가 기록되어 있다.
- When: 정책 ACK 반영 대기와 실제 상태 읽기 실패를 각각 발생시키고 여러 제어 주기를 진행한다.
- Then: Pod별 항목과 마지막 성공 확인 시각은 유지되고 관측 품질과 사유만 해당 상태로 갱신된다. 읽기 실패를 부재나 제거 완료로 보지 않으며 같은 slot의 중복 준비 횟수는 0이다. 복구 후 같은 Pod 항목의 관측을 갱신하고, 실제 Pod 소멸을 확인한 경우에만 제거한다.
- 요구사항: [원자적 자원 정리](#원자적-자원-정리), [정책 반영 대기 상태 보존](#정책-반영-대기-상태-보존), [관측 실패 노드 변경 보류](#관측-실패-노드-변경-보류), [Pod별 실물 자원 장부](#pod별-실물-자원-장부).

#### 예약 충돌과 효과 반환 검증
- Given: 작업 A가 Node, Workload와 실물 범위를 예약하고 실행 중이며, 자동제어 또는 수동 작업 B가 그 범위와 겹치는 변경을 요청한다.
- When: B의 시작 허가를 검사하고, 이어 A가 완료, 실패와 취소로 종료되며 실제 효과가 확인된 경우와 취소와 timeout 뒤 원격 효과가 미확인인 경우를 각각 진행한다.
- Then: B는 공통 허가 지점에서 시작 전에 거절되고 충돌 범위와 소유 작업과 사유가 제공된다. 실제 효과가 확인된 A는 실패한 경우에도 예약을 해제하여 후속 작업이 현재 실제 상태에서 다시 허가받을 수 있다. 원격 효과가 미확인인 A는 실행 종료 후에도 예약을 유지하여 겹치는 변경을 계속 거절하고, 이후 효과 확인 또는 reset의 실제 정리 완료 뒤에만 해제한다. 해제 후에도 실물 항목과 일부 적용 상태와 실패 원인은 유지된다.
- 성공 cleanup 추가 판정 / 정리 중 라우팅 우회 제거: 최종 route complete 이후 recent 95.3→100.2→97.5/s의 세 제어 주기에서도 예약된 Workload는 Fixed이며 새 target의 route를 원래 owner로 인계하지 않는다. 원래 성공 receipt와 stop 안전 의존성과 old Pod/physical/Node의 stop/drain/remove 의무를 보존하고, 원래 DAG와 효과 반환 확인이 끝난 뒤 예약을 해제한다. 같은 owner 안의 기존 인가 route ACK 직렬화와 중간 순증은 유지한다.
- 중간 순증 추가 판정: old Ready를 유지하고 genesis3만 새 Ready이며 nano가 준비 중인 steady-mixed 조건에서, 같은 owner 예약 안의 현재 demand 평가를 거친 양수 중간 route가 old+genesis3에 적용된다. nano 지연은 순증을 막지 않는다. 같은 Node 중복과 support 부재와 양수 목적지 policy ACK/identity 실패와 물리 실행 불가에서는 current를 보존한다. old row pending만으로 막지 않는다. 최종 DAG와 예약 반환과 기존 bootstrap/stopped/unroutable/retiring 판정은 유지한다.
- 무효과 작업의 생명주기 판정: 순수 `changedWorkloads=[]` route는 부모, 자식과 예약을 만들지 않는다. 비어 있지 않은 route와 prepare/power/resize는 admission하여 route-only 회복도 전체 NotReady 대기 중 Ready 생존자 subset을 적용할 수 있다. retirement만 있으면 현재 dependency/Ready/exact handoff 충족 시에만 admission하고 그 외에는 다음 Tick에 재계획한다. omission 표식과 기존 빈 orphan의 no-effect 반환과 미시작 retirement partial 종결은 없으며 성공 ACK 합성과 frozen DependsOn/RouteTarget 삭제 없이 완료 consumer 또는 frozen empty 최종 scope 판정을 완료, launch와 예약 진단에서 공유한다. 다른 sibling이 진행 중이어도 소비된 bridge를 재실행하거나 부족 proof로 표시하지 않는다. Create 성공/검증 GET의 Pod UID와 Node UID와 인가 prepare와 created/reused 증거는 error와 최종 Capture와 독립 보존하고 terminal 공개 전에 owner scope에 편입한다. 같은 RestartPolicyNever UID의 첫 exact container만 terminal 뒤에도 one-shot 결합하며 타 UID/재결합과 baseline 변경은 금지한다. late 정상 ACK는 원 실패 receipt와 Pod를 보존하고 기존 fresh exact/terminal sibling/power proof 뒤 반환한다. reused/생성 불명은 신규 생성 보상으로 취급하지 않고, 증거/dirty/receipt는 owner 책임 전체 반환까지 GC/reset 경합에도 유지한다. 예약 reason은 blocking action/identity와 부족 proof와 해소 경로를 결정적으로 제공한다.

#### 혼합 부하와 생성기 구분 검증
- Given: Node당 서빙 인스턴스 하나인 전체 POOL과 최종 SLO, 모드와 자원에 맞는 Node별 κ가 있다. `R_w=Σ_Node max eligible κ_w`는 고립 기준이며 세 R을 동시에 사용할 수 없다.
- When: 유한한 [0,1]의 `poolShares={MNV:s_M,PLC:s_P,Smol:s_S}`(기본 .45/.1/.45, 합1)을 동결하고 α=0.3/0.5/0.7/0.9/1.2 단계에서 `rate_w=α_w×s_w×R_w`의 포아송 trace를 만든다. burst에서는 Smol의 α만 바꾼다.
- Then: 잘못된 지분이나 합은 실행 전에 거절한다. `1.2×Σ(s_w×R_w)≤0.8×G`를 확인하고 G의 입력값과 출처, R, s, α, 요청률과 trace를 binding에 동결한다. G 미확정은 명시 경고이며 개시 통과로 세지 않는다. α를 혼합 SLO 보장으로 해석하지 않는다.
- 검증 부하는 고정 배치, α=1.2 총혼합 부하를 120초 동안 한 번 공급한다. 계단 탐색, 최대 G 탐색과 자동 재시도는 하지 않는다. 동결한 trace를 전부 공급하고 PLC p95≤32ms 및 전체 offered 대비 32ms 기한 내 성공률≥95%를 만족해야 한다. gateway 거절, 503, timeout과 미완료는 0건이어야 한다. 서버 throttle, 재시작과 OOM도 0건이어야 한다. 누락 없는 CPU와 메모리 10초 표본을 보존하고 메모리는 동결 limit 미만이어야 한다. 이 조건을 모두 만족하면 PASS, 그 밖에는 FAIL과 원시 사유를 기록한다.
- CPU peak는 absolute cores 관측값으로 보고하며 판정에 쓰지 않는다. native와 client의 한계를 gateway 실패와 구별하고 부하를 자동으로 줄이지 않는다. 통과한 부하점으로 최대 G나 20% 여유를 인증하지 않는다. 공유 CPU 실행에서는 limit 기반 비율이나 코어수 대체 분모 및 새 고정 여유계수를 두지 않는다. 과거 CPU 통제 실행의 판정을 바꾸지 않으며 새 공유 실행에서 측정한다.
- 고정 cap 제어요소 비교: batching OFF는 현재 Workload의 `(MaxBatch, MaxWait)` 집합을 사용하며 측정하고 초기화한 각 cap 변형의 placement/resources/replicas 평가를 유지한다. 측정 없는 cap 1 후보를 만들거나 모든 인스턴스에 cap 1을 강제하지 않는다.
- 요구사항: [부하 사건과 모집단 구분](#부하-사건과-모집단-구분), [자원 예산 내 인스턴스 배치](#자원-예산-내-인스턴스-배치), [유한 수요 직접 재생 평가](#유한-수요-직접-재생-평가), [워크로드별 SLO 판정](#워크로드별-slo-판정), [판단과 전환 근거 기록](#판단과-전환-근거-기록), [요청 결과와 원시 관측 보존](#요청-결과와-원시-관측-보존).

### 4.2 evaluation 증거 API 수용 시나리오

보류된 게이트웨이 분리의 [제어와 요청 전달 프로세스 분리](#제어와-요청-전달-프로세스-분리), [불변 배분표와 요청 버전 고정](#불변-배분표와-요청-버전-고정), [라우터 실제 적용 확인](#라우터-실제-적용-확인), [모든 라우터의 물리 요청 배출](#모든-라우터의-물리-요청-배출), [미확인 라우터 유입 차단](#미확인-라우터-유입-차단), [라우터별 요청 기록 보존](#라우터별-요청-기록-보존), [라우터 요청 모집단 병합](#라우터-요청-모집단-병합) / [분리 프로세스와 버전 고정 검증](#분리-프로세스와-버전-고정-검증), [모든 라우터 적용 장벽 검증](#모든-라우터-적용-장벽-검증), [라우터 물리 점유 배출 검증](#라우터-물리-점유-배출-검증), [미확인 라우터 격리 검증](#미확인-라우터-격리-검증), [다중 요청 스트림 병합 검증](#다중-요청-스트림-병합-검증)과 ID를 공유하지 않는다. 아래는 단일 ChillServer의 수용 기준이며, 문서 추가가 구현, 배포와 검증 완료를 뜻하지 않는다.

#### 완결 원시와 보관본 조회 검증
- Given: 현재 열린 분과 닫힌 로컬 분, 로컬 보존이 끝난 시간과 기존 #213의 보관된 1시간이 있고, 새 stream 배포 이전 시간에는 자원과 클러스터 stream이 없다.
- When: 허용된 하네스가 drain와 묶음 전송 대기와 다음 분 경계 뒤 목록, 원시와 정의를 조회하고 같은 과거 구간의 가공 scheduler 조회도 수행한다.
- Then: 시간 상태와 닫힌 분과 보존 위치를 표시하고 열린 분과 미완결 정의 행은 보내지 않는다. 로컬은 원래 JSONL, 보관본은 이미 저장된 gzip을 전송하며 서버가 즉석 압축하지 않는다. 기존 #213을 버전 변환 없이 읽고, 배포 이전 새 stream 부재는 결손이 아니다. 필요한 자료 부재와 store 오류와 잘린 전송은 무유입/빈 성공으로 숨기지 않는다. 처리 마감과 쓰기 마감은 분리되고 취소와 마감은 저장소 읽기까지 전달된다. 원시 권한이 없는 대시보드와 앞단은 거절되며 가공 조회는 유지된다.
- 요구사항: [과거 관측의 투명 조회](#과거-관측의-투명-조회), [과거 워크로드 정의 보존](#과거-워크로드-정의-보존), [관측 원시 기록 내보내기](#관측-원시-기록-내보내기).

#### 외부 자원 표본과 누적값 검증
- Given: genesis1을 포함한 모든 대상 Node, cgroup v1/v2 컨테이너, 서버, 서빙과 제어 Pod 및 온도 센서가 있고 일부 Node 시계가 다르다.
- When: Node agent가 표본을 묶어 보낸 뒤 전송 실패와 컨테이너 교체와 서버 재시작도 관측한다.
- Then: Node당 묶음 1행에 정확한 Pod UID/containerID와 cgroup 버전과 단위와 두 시각을 남긴다. 같은 이름의 새 컨테이너를 이전 counter에 잇지 않고 실패 구간은 결손으로 남기며 재전송하지 않는다. agent에 Pod 조회 권한을 추가하지 않는다. GC는 프로세스별 누적값의 창 안 차이며 gctrace 사이클 분포와 구분하고, 분 단위 디렉터리 바이트와 genesis1 agent의 서버 컨테이너 표본을 얻는다.
- 요구사항: [관측 구간과 시각 기록](#관측-구간과-시각-기록), [근거 확보 상태 공개](#근거-확보-상태-공개), [외부 자원과 온도 관측](#외부-자원과-온도-관측).

#### Pod와 장애 기록 후 발행 검증
- Given: CHILL 서빙과 제어 Pod와 observer source가 있고 서버 자신의 Pod UID가 제공된다.
- When: 서버 기동, Pod Ready, restart, 종료와 삭제 및 issue 발생과 동일 이유 반복과 이유 변경과 해소를 관측하고 append 실패도 주입한다.
- Then: 기동의 자기 UID와 실제 Pod/imageID/종료 상태를 보존하고 같은 issue 이유의 반복은 새 변경으로 기록하지 않는다. 성공한 기록에서만 같은 사실을 라이브 callback으로 전달한다. append 실패 사실은 발행하지 않으며 읽기 실패를 Pod 삭제와 issue 해소로 간주하지 않는다. Node와 cordon stream을 만들지 않는다.
- 요구사항: [실패 격리와 관측 기반 복구](#실패-격리와-관측-기반-복구), [판단과 전환 근거 기록](#판단과-전환-근거-기록), [라이브 인증과 재동기화](#라이브-인증과-재동기화), [Pod와 장애 사건 기록](#pod와-장애-사건-기록).

#### 읽기 전용 전력계 설정 검증
- Given: 서버가 metric source와 실제 Node UID로 수락한 전력계 선언, CPO와 대시보드의 조회 후 수정 경로가 있다.
- When: 설정 GET 후 다른 쓰기 가능 설정을 바꾸어 두 클라이언트에서 PUT하고, 별도로 `meters`를 포함한 PUT도 보낸다.
- Then: GET의 `meters`는 수락된 ID와 Node 이름/UID, scope와 source 선언이며 표본이나 새로운 설정 원본이 아니다. 두 클라이언트는 `meters`를 제외해 정상 변경하고, 포함한 직접 쓰기는 거절된다. 기존 `powerObservation`과 `staticRouting` 읽기/쓰기 경계도 유지된다.
- 요구사항: [운영 설정과 비교 실험 관리](#운영-설정과-비교-실험-관리), [읽기 전용 전력계 선언](#읽기-전용-전력계-선언).

실물 장부, 영향 범위 예약과 실제 정책 반영 확인은 기존 Pod와 제어 경계에서 수행한다. 예약 밖 판단과 준비된 부분 용량 배분을 계속한다. 새로운 서비스나 저장소를 요구하지 않는다.

## 8. 보류 제안 — 제어와 데이터 평면 분리

**상태: Deferred.** 게이트웨이 분리는 활성 서빙 평가의 선행 요구사항이 아니다. 현행 단일 ChillServer의 관측과 요청 경로는 유지한다.

### 게이트웨이 분리 재개 조건

게이트웨이 분리는 보류한다. 서빙 평가가 끝나고 결과 표를 기입한 뒤, 다음 중 하나를 입증하고 기존 경로의 직접 수정이나 작업 동시성 축소로 해결되지 않을 때 재개를 결정한다.

- 게이트웨이에 귀속되는 [혼합 부하와 생성기 구분 검증](#혼합-부하와-생성기-구분-검증) 실패.
- 제어, 조회 또는 관측 복원 작업의 간섭이 측정 표의 지연이나 성공률을 훼손한다는 근거.

재개 전에 연구 질문, 연결할 측정 표의 행, 비교 조건과 합격 기준을 명시한다. 첫 검증 구성은 제어 프로세스 하나와 라우터 하나다. 라우터를 더 늘리려면 단일 라우터의 한계나 라우터 수 자체를 측정할 연구 필요를 입증하고 별도로 승인받는다.

평가 종료만으로 분리 구현이나 배포를 시작하지 않는다. 승인된 최소 구성의 비교 검증 뒤에 별도 전환을 결정한다. 현재 평가의 조건은 단일 게이트웨이와 해당 부하점에서 확인한 용량이며, 이를 게이트웨이 최대 용량이나 분리 구조의 성능 근거로 해석하지 않는다.

첫 캠페인은 고정 참여 집합을 사용한다. 장애가 나면 신규 유입을 닫고 캠페인 실패와 미확인 물리 점유를 보존한다. 전달 전 배정 기록, 물리 완료 확인과 안전한 정리 의무를 유지한다. 온라인 가입과 제외, 영속 참여 집합, 프로세스 세대 복구, 자동 Pod 교체 복구, 라우터별 할당량 분할과 실행 전 거절 뒤 자동 재배정은 기본 채택 사항에 포함하지 않는다.

재개 시 아래 요구사항은 다음과 같이 축소해 적용한다. 제외한 N>1 능력은 미인증으로 남긴다.

- [제어와 요청 전달 프로세스 분리](#제어와-요청-전달-프로세스-분리): 첫 검증은 control 1 + router 1. "여러 라우터"는 필수가 아니다.
- [불변 배분표와 요청 버전 고정](#불변-배분표와-요청-버전-고정): 원자 적용과 요청별 버전 고정 유지. **표 교체만으로 Receive~Accept 요청을 실패시키지 않는다.**
- [라우터 실제 적용 확인](#라우터-실제-적용-확인): 승인된 고정 참여 집합의 실제 applied 확인 유지. 온라인 가입과 제외는 제외.
- [모든 라우터의 물리 요청 배출](#모든-라우터의-물리-요청-배출), [미확인 라우터 유입 차단](#미확인-라우터-유입-차단), [라우터별 요청 기록 보존](#라우터별-요청-기록-보존): timeout ≠ 점유 0, 미확인 점유와 assigned 보존 유지. 자동 세대 복구 의무는 제외하고 안전한 실패와 정리로 바꾼다.
- [라우터 요청 모집단 병합](#라우터-요청-모집단-병합): 단일 논리 요청 모집단과 전체 offered, coverage와 raw API와 인증된 라이브 전달 일치 유지. 소비자가 없는 별도 도착 카운터는 요구하지 않는다.
- [분리 프로세스와 버전 고정 검증](#분리-프로세스와-버전-고정-검증), [모든 라우터 적용 장벽 검증](#모든-라우터-적용-장벽-검증), [라우터 물리 점유 배출 검증](#라우터-물리-점유-배출-검증), [미확인 라우터 격리 검증](#미확인-라우터-격리-검증), [다중 요청 스트림 병합 검증](#다중-요청-스트림-병합-검증): Given을 router 1개로 한다. [모든 라우터 적용 장벽 검증](#모든-라우터-적용-장벽-검증)의 C 가입과 [다중 요청 스트림 병합 검증](#다중-요청-스트림-병합-검증)의 다중 router 재시작 병합은 N>1 재개 전까지 실행 범위에서 제외한다. 원자 적용과 구표 요청 보호와 실제 applied와 timeout 뒤 물리 drain와 기록 실패 시 native 미호출과 coverage 오류 표시는 축소하지 않는다.

### 8.1 추가 요구사항

#### 제어와 요청 전달 프로세스 분리
중앙 계획기, 관측기와 운영 작업과 관리/조회 API와 추론 요청의 본문 전달은 서로 다른 프로세스로 실행한다. 계획기는 전역 하나를 유지하고, 여러 라우터는 인증과 원시 입력 검증과 미배정 큐와 가중 분배와 물리 점유와 요청 기록을 맡아 native 인스턴스로 직접 전달한다. 요청마다 중앙 picker를 호출하지 않으며, 기존 Workload 정의와 수신 기준 시간 예산과 firstfloor 실행 경계와 [Pod별 실물 자원 장부](#pod별-실물-자원-장부), [작업 범위 예약과 효과 반환](#작업-범위-예약과-효과-반환), [예약 범위 밖 판단 지속](#예약-범위-밖-판단-지속)의 장부와 예약 계약을 유지한다.
#### 불변 배분표와 요청 버전 고정
제어 평면은 독립적인 `planVersion`으로 식별하는 불변 배분표를 라우터에 push한다. 배분표는 Workload UID와 불변 정의 ID와 요청 수명, 대상 Pod UID/container identity와 전용 endpoint와 가중치와 적용에 필요한 정책 참조를 한 snapshot으로 제공한다. 라우터는 검증된 snapshot 전체를 원자적으로 교체하고, 요청이 사용할 snapshot을 잡은 뒤에는 재배정을 포함해 한 버전만 사용하며 요청 기록에 그 버전을 남긴다. `definitionID`, native `DecisionID`, ConfigMap resourceVersion을 `planVersion`의 대용으로 쓰지 않는다.
#### 라우터 실제 적용 확인
라우터는 실제 snapshot 교체 뒤에만 자기 identity와 `applied(planVersion)`을 보고한다. native 정책의 실제 `DecisionID` ACK → 배분표 push → 해당 전환의 모든 유입 참여 라우터 applied 확인 순서를 지키고, 송신 성공과 소켓 연결과 수신 확인을 적용 완료로 간주하지 않는다. 전환 중 라우터 가입과 제외도 추적하며, 새 라우터는 현재 배분표 적용 전에는 유입에 참여하지 않는다.
#### 모든 라우터의 물리 요청 배출
퇴역 인스턴스를 제외하는 배분표의 applied 확인과 신규 배정 차단 뒤, 그 인스턴스에 요청을 배정할 수 있었던 모든 라우터의 물리 `outstanding=0`을 확인해야 기존 source의 drain 완료, stop과 remove를 진행한다. 합계 보고 누락과 라우터 연결 종료와 readiness 제외와 HTTP timeout/cancel을 0으로 간주하지 않는다. 미배정 수락 요청의 대체 경로를 보존하고, 물리 완료는 기존 native 진행/상태 증거로 확인한다. 라우터가 사라져도 미확인 점유와 실물 장부는 남기며 [원자적 자원 정리](#원자적-자원-정리) reset도 같은 조건을 따른다.
#### 미확인 라우터 유입 차단
적용 미확인과 연결 상실과 기록 실패 라우터는 신규 유입 자격을 닫고 이유, 대상과 시각을 제공한다. readiness 제외만으로 기존 연결의 새 추론을 허용하거나 미완료 요청을 폐기하지 않는다. 적용 미확인 라우터가 유입에 남았거나 참여 범위, 배분표와 요청 기록의 완전성을 입증하지 못한 실험은 무효/검증 실패로 명시하며 조용한 fail-open을 금지한다. 전 라우터 동시 원자 전환은 보장하지 않고, 혼합 버전 구간과 라우터별 적용 시각을 기록한다.
#### 라우터별 요청 기록 보존
각 라우터는 고유 `routerID`를 갖는 독립 스트림에 기존 `assigned`/`final` 기록을 쓰고 `requestID`, `planVersion`과 정확한 실물 identity를 보존한다. native 전달 전 assigned append 성공, 취소 뒤 물리 완료 추적, 시간별 archive 성공 전 로컬 삭제 금지와 미완료 assigned 보존을 유지한다. 여러 라우터가 같은 파일/불변 객체를 덮어쓰지 않으며, 재시작 전 라우터의 미완료 기록도 복구와 조회 범위에 남긴다.
#### 라우터 요청 모집단 병합
계획기 부하 λ, 디스패치 점유 d, evaluation 집계와 Dashboard 조회는 모든 참여 라우터의 로컬/근거 저장소 스트림을 `requestID`로 병합해 요청을 한 번만 센다. 기존 `final > open > assigned` 우선순위, 정의/catalog 해석, 접수 구간 모집단과 전체 offered 분모와 오류/미완료 의미를 유지한다. 라우터별 출처와 보존 범위와 공백을 제공하고 누락과 읽기 실패를 무유입 0으로 채우지 않는다. 도착과 검증 카운터를 λ에 쓰는 경우 동일 시간창과 사건의 라우터 합을 사용하고 재접속/재시작 중복과 스트림 집계의 이중 가산을 막는다.

### 8.2 추가 수용 기준 (구현 뒤 실행)

#### 분리 프로세스와 버전 고정 검증
- Given: 제어 프로세스 하나, 라우터 두 개와 준비와 정책 ACK가 확인된 native 대상이 있다.
- When: 서로 다른 배분표 v1/v2를 push하면서 동시 요청과 대기 중 요청을 처리하고 제어 측 조회와 관측 복원을 수행한다.
- Then: 추론 본문은 라우터에서 native로 직접 전달되며 제어 picker 왕복이 없다. 라우터는 snapshot의 일부를 섞지 않고 각 요청의 정의, 수명, identity와 planVersion을 끝까지 유지한다. 제어 측 작업은 라우터 프로세스에서 실행되지 않으며 인증과 입력 검증과 최초 수신 기준 시간 예산이 유지된다.
- 요구사항: [워크로드와 요청 정의 식별](#워크로드와-요청-정의-식별), [요청 경과시간 기반 배칭 정보](#요청-경과시간-기반-배칭-정보), [실행기 내부 배칭 책임](#실행기-내부-배칭-책임), [호환 요청의 배치와 큐 정책](#호환-요청의-배치와-큐-정책), [예약 범위 밖 판단 지속](#예약-범위-밖-판단-지속), [제어와 요청 전달 프로세스 분리](#제어와-요청-전달-프로세스-분리), [불변 배분표와 요청 버전 고정](#불변-배분표와-요청-버전-고정).

#### 모든 라우터 적용 장벽 검증
- Given: 라우터 A/B가 v1을 사용하고 B의 v2 적용을 지연시킨다.
- When: 새 대상의 native ACK 전후에 v2 배포를 시도하고, B의 ACK를 지연과 재전송하며 라우터 C를 가입시킨다.
- Then: native ACK 전에는 새 대상을 편입하지 않는다. A에 대한 송신/적용만으로 전환 완료를 보고하지 않으며, B는 교체 전 applied를 보내지 않는다. C는 현재 버전 적용 전에는 유입을 받지 않고 전환 참여 범위에 반영된다. ACK는 정확한 라우터와 버전과 대조하며 늦은 이전 ACK가 현재 적용 확인을 대신하지 않는다.
- 요구사항: [전환 목표와 실제 진행 구분](#전환-목표와-실제-진행-구분), [명시적 배분 변경 작업](#명시적-배분-변경-작업), [정책 반영 대기 상태 보존](#정책-반영-대기-상태-보존), [불변 배분표와 요청 버전 고정](#불변-배분표와-요청-버전-고정), [라우터 실제 적용 확인](#라우터-실제-적용-확인).

#### 라우터 물리 점유 배출 검증
- Given: source를 제외한 배분표가 적용됐지만 A의 해당 source 점유는 0, B의 점유는 1이며 B의 클라이언트는 timeout됐다.
- When: stop/remove 또는 reset을 요청하고, 이어 B 연결을 끊었다가 물리 완료 증거와 상태 보고를 복구한다.
- Then: B의 점유가 미확인이거나 1이면 drain 완료, stop과 remove를 진행하지 않는다. readiness 제외나 연결 종료도 0의 대용이 아니다. 모든 기존 소유 라우터의 0과 native 물리 완료를 확인한 뒤에만 진행하며 수락된 미배정 요청과 정확한 Pod UID의 장부를 보존한다.
- 요구사항: [준비 용량 편입과 안전한 제거](#준비-용량-편입과-안전한-제거), [원자적 자원 정리](#원자적-자원-정리), [Pod별 실물 자원 장부](#pod별-실물-자원-장부), [작업 범위 예약과 효과 반환](#작업-범위-예약과-효과-반환), [모든 라우터의 물리 요청 배출](#모든-라우터의-물리-요청-배출).

#### 미확인 라우터 격리 검증
- Given: A는 v2, B는 v1이고 B의 적용 채널이 끊겼으며 기존 클라이언트 연결이 남아 있다.
- When: 신규 요청, B 재연결 및 제어 프로세스 재시작을 발생시킨다.
- Then: B의 신규 유입 gate와 readiness는 닫히며 기존 연결도 새 추론을 시작하지 못한다. 재동기화와 실제 적용 확인 전에는 재가입하지 않는다. 연결 단절 전 이미 시작한 요청은 물리 완료까지 추적한다. 버전 재사용/역행으로 이전 ACK가 새 배분표를 승인하지 못하고 라우터별 적용 시각과 혼합 구간과 미확인 상태가 남는다. stale 유입 또는 증거 결손이 있으면 실험을 통과 처리하지 않는다.
- 요구사항: [근거 확보 상태 공개](#근거-확보-상태-공개), [실패 격리와 관측 기반 복구](#실패-격리와-관측-기반-복구), [불변 배분표와 요청 버전 고정](#불변-배분표와-요청-버전-고정), [라우터 실제 적용 확인](#라우터-실제-적용-확인), [모든 라우터의 물리 요청 배출](#모든-라우터의-물리-요청-배출), [미확인 라우터 유입 차단](#미확인-라우터-유입-차단).

#### 다중 요청 스트림 병합 검증
- Given: 두 라우터의 assigned/final, archive에만 있는 assigned와 로컬의 늦은 final, 재시작 전 미완료 및 같은 이름의 다른 Workload UID가 있다.
- When: 로컬 시간 보존 만료와 archive 조회와 라우터 재시작을 거쳐 λ, d, evaluation와 Dashboard를 집계하고, 한 라우터의 stream 누락과 저장소 오류도 각각 주입한다.
- Then: 완전한 자료에서는 단일 논리 요청 집합의 요청 수와 단계 수, 지연과 점유 결과와 같고 늦은 final/재전송을 중복 가산하지 않는다. assigned 쓰기 실패 요청은 native에 전달되지 않는다. 삭제된 정의도 원래 UID/catalog로 해석하며 참여 라우터, 출처와 공백을 표시한다. 누락/오류는 0이나 성공이 아니고 evaluation 분모에서 사라지지 않는다.
- 요구사항: [부하 사건과 모집단 구분](#부하-사건과-모집단-구분), [관측 구간과 시각 기록](#관측-구간과-시각-기록), [근거 확보 상태 공개](#근거-확보-상태-공개), [요청 결과와 원시 관측 보존](#요청-결과와-원시-관측-보존), [과거 관측의 투명 조회](#과거-관측의-투명-조회), [과거 워크로드 정의 보존](#과거-워크로드-정의-보존), [라우터별 요청 기록 보존](#라우터별-요청-기록-보존), [라우터 요청 모집단 병합](#라우터-요청-모집단-병합).

## 9. 설정 소유권과 기록 (활성 요구사항)

이 설정 요구사항은 보류된 게이트웨이 분리와 독립이다.
이 절의 전체 grid와 이분 설정과 관련 수용 수치는 명시적 offline κ 계산에 적용한다. online tested-rate κ̂와 직접 후보 평가의 범위는 [유한 수요 직접 재생 평가](#유한-수요-직접-재생-평가)과 승인 경로 기반 수요 재생 계약을 따른다. 기존 설정 범위와 기록 계약은 유지한다.
아래 기본값과 유효 범위는 설정 선택 계약이다. 실제 실행 수용은 별도 근거로 확인한다.

#### 운영 정책 설정 선택
운영 중 조정할 serving 정책은 기존 settings API에서 조회와 변경한다. 아래 필드를 생략하면 현재 기본값을 채우고 응답과 판단에는 실제 선택값을 남긴다. 유효 범위의 비기본값도 실제 소비해야 하며 하나의 값만 허용하는 필드는 두지 않는다.
#### 실제 판단 설정의 권위
판단 적용값의 권위는 기존 Decision.Settings다. PUT 사전/후속 행을 유지하고 초기와 외부 설정은 실제 사용 Decision으로 해석한다. 첫 판단 전 모든 적용 이벤트 복원과 refresh 합성 행과 초기 before=after 행과 별도 provenance 저장소는 요구하지 않는다. 출처는 실제 보존 참조/binding 범위만 주장한다.
#### 서버 기동 설정 기록
기존 cluster stream의 server-start를 재사용한다. 기존 Pod UID/namespace/name과 run()의 실제 started를 쓰고 sourceIntervalNanos와 profileIntervalNanos만 보강한다. gateway 큐 상한은 Workload `spec.admission.maxQueuedRequests`를 Definition에 동결한다. 기존 append 실패→기동 실패를 유지한다. 별도 scheduler startup 행은 없다. request/drain timeout과 directory interval과 control scope는 기존 설정 유지다.
#### 용량 설정의 전체 소비자 전달
추가 용량 설정은 CapacityInput와 용량 행과 모든 typed 소비자에 전달하며 판단 snapshot을 섞지 않는다. CI는 BEO 측정 정책, reuse는 요청 annotation, power1분은 C다. 입력 경계에서 구조와 의미를 검증하며 새 바이트/hash 관문은 없다.

### 9.1 추가 settings 필드

| JSON 필드명 | 의미와 단위 | 허용 범위 | 기본값 |
|---|---|---|---:|
| capacityGridSteps | κ 부하 격자 구간 수 | 정수 ≥1 | 20 |
| capacityBisectionWidth | μ 대비 이분 종료 폭 | finite (0,1] | 0.005 |
| capacityTailSamples | SLO 분위 위 꼬리 표본 목표 수 | 정수 ≥1 | 100 |

이 절에서 추가한 필드는 위 3개이며 기존 settings는 유지한다. 정수는 Go 필드 표현 범위 안이다. capacityGridSteps는 offline 전체 격자 순회와 격자율, capacityBisectionWidth는 width×μ 종료 조건에 쓴다. capacityTailSamples는 기존 rate 판정의 ceil(tailSamples/(1−p/100)) 계산에 쓰며 p=100 현재 분기는 유지한다. 세 값 모두 offline CapacityInput→용량 행에 동결한다.
offline 기본값도 새 κ 키를 만들므로 cache miss와 재계산은 의도된 결과다. 옛 키 우회, omitempty와 dual lookup은 없다. CI CLI/values/생성자 경로는 삭제하고 측정별 단일 정책을 사용한다.
source/profile interval은 API 조정 후보였지만 이 작업에서는 기동값으로 유지한다.
기존 powerObservation.sampling/coverage와 읽기 전용 meters는 settings로 중복 이동하지 않는다.

### 9.2 수용 시나리오

#### 기본값과 비기본 정책 소비 검증
- Given: 변경 전20/.005/100 리터럴과 fixture와 새 생략/명시 기본값 입력이 있다.
- When: 각각 실제 용량 계산을 수행하고 비기본값과 범위 오류를 전달한다.
- Then: 새 두 경로끼리만 비교하지 않고 변경 전 μ1000/κ959.375와 Grid/Bisection/판정을 유지한다. GET/Decision/기록은 실제값이며 유효 다른 값도 소비한다. 범위 밖과 NaN/Inf는 적용 전 거절한다. 키 동일성과 바이트/hash 비교는 요구하지 않는다.
- 요구사항: [운영 정책 설정 선택](#운영-정책-설정-선택), [용량 설정의 전체 소비자 전달](#용량-설정의-전체-소비자-전달).

#### 설정 시도와 실제 적용 기록 검증
- Given: 정상 변경과 사전/후속 append 실패와 refresh 실패와 외부 설정 갱신이 있다.
- When: 기존 PUT 순서와 refresh/판단을 수행한다.
- Then: 사전 append 실패는 변경 전 중단한다. 저장 성공/refresh 실패는 요청과 적용 불일치 가능, refresh 성공/후속 append 실패의 HTTP 오류는 미적용을 뜻하지 않는다. 이후 적용은 Decision.Settings로 해석하고 증거가 부족하면 미확인이다. 초기/외부 합성 행이나 과거 UID/RV를 꾸미지 않는다.
- 요구사항: [실제 판단 설정의 권위](#실제-판단-설정의-권위), [용량 설정의 전체 소비자 전달](#용량-설정의-전체-소비자-전달).

#### 실제 기동값과 재시작 검증
- Given: Workload의 큐 상한 1024와 source1초/profile60초, 운영 source2초를 각각 선택한다.
- When: 서버 기동과 재시작과 기존 server-start append 실패를 다룬다.
- Then: 기존 cluster/server-start에 실제값과 기존 Pod identity/실제 started가 남고 실패 시 기동을 거부한다. 새 stream와 scheduler startup 행은 없다. requestTimeout을 모든 handler 실제값으로 해석하지 않으며 infer129초 분기를 유지한다.
- 요구사항: [서버 기동 설정 기록](#서버-기동-설정-기록).

#### 저장 계약과 전체 소비자 전환 검증
- Given: static_routing와 hack/kappa 직접 decode, bind_before.SETTINGS, Dashboard typed round-trip/fixture, 구조체 테스트와 샘플과 bootstrap raw replay가 있다.
- When: 승인된 증거 API 배포, 리허설과 하네스 cutover와 브라우저 수용 완료 뒤 캠페인 사이 한 번 cutover한다.
- Then: 생략 defaulting은 SchedulerSettingsInput에 모으고 모든 소비자가 새3필드를 보존한다. v1alpha5와 archive/publication #213~#225는 보존한다. 과거 필드 부재는 미기록이지 현재 기본값이 아니다. 단일 reader를 유지하고 영향 작업용 CR/파생 객체만 운영자가 열거와 정리한다. 과학 원시 삭제, migration와 alias는 없다.
- 요구사항: [운영 정책 설정 선택](#운영-정책-설정-선택), [실제 판단 설정의 권위](#실제-판단-설정의-권위), [서버 기동 설정 기록](#서버-기동-설정-기록), [용량 설정의 전체 소비자 전달](#용량-설정의-전체-소비자-전달); Durable Stored-Contract Compatibility, Configuration Ownership and Freezing Paths.
