# CHILL 스케줄러 SRS

## 1. 목적과 범위

이 문서는 CHILL 스케줄러의 판단 근거, 선택 결과, 실행 계층과의 책임 경계,
실제 결과를 다음 판단에 반영하는 기능을 정의한다.
[시스템 명세](../README.md)의 스케줄러 책임을 입력·출력·기능 요구사항과
검증 시나리오로 구체화한다. 요구사항 ID의 `SCH`는 스케줄러를 뜻한다.

이 문서는 고수준 요구사항 기준이다. 구현 진도는 실제 소스와 실행 증거로
확인한다. 알고리즘·계측 제품·API·저장 형식·프로세스 배치는 구현 설계에서
선택하고, 각 선택을 이 문서의 요구사항과 검증 시나리오에 연결한다.

- `SCH-01` 스케줄러는 워크로드의 지연 SLO 충족을 첫 번째 선택 기준으로 사용한다. SLO를 만족하는 운영 선택에서는 전환과 Serving의 총에너지를 비교한다. 처리량은 부하 수용 가능성을 판단하는 근거로 사용한다.
- `SCH-02` 스케줄러는 실제 현재 구성과 부하에서 유지와 변경을 비교한다. 노드와 구성의 우선순위는 현재 상태의 전체 비용과 SLO 평가로 정하며, 실제 실행 결과와 부하 변화로 다음 판단을 갱신한다. 각 노드의 소속(워크로드별 활성 POOL, 측정 POOL, 가용 노드)을 실제 전환 상태에 맞춰 갱신한다.

### 1.1 포함하는 책임

- 자동제어가 켜진 워크로드의 활성 POOL 구성과 가용 노드의 편입과 반환 판단
- 서빙 인스턴스의 모델·실행 경로·배치 위치와 자원 할당, 노드 전력모드 판단
- 모델과 전처리가 서로 다른 여러 워크로드의 동시 서빙, 워크로드별 요청 분배와 evidence 기반 배칭과 큐 선택 정책 제공
- 전환 중 처리 능력·SLO·비용을 포함한 유지 또는 변경 판단
- 판단 근거·목표·실제 진행과 결과의 구분 및 다음 판단으로의 피드백

### 1.2 다른 영역과의 경계

| 영역 | 소유하는 책임 | 스케줄러와의 연결 |
|---|---|---|
| 워크로드 관리 | 등록·수정·삭제, 적용 정의와 요청 접수 계약 | 모델·입력·SLO·관리 진행을 제공하고 기존 요청 의미를 보존 |
| 프로파일링·Evidence Store | 측정 POOL에서 운영자가 요청한 조건의 실측과 근거 보존·조회 | 후보를 평가할 실행·전환 프로파일 제공 |
| Serving 유입·라우팅 | 접수된 요청의 유입 대기·인스턴스 전달과 결과 반환 | 분배 정책 적용, 요청과 부하·처리 상태 관측 제공 |
| firstfloor 내부 배처와 실행기 | 현재 큐의 실제 배치 구성, 추가 대기, 실행 시점 판단과 전처리, 추론, 후처리 실행 | CHILL 정책, SLO, 요청별 시간 정보 적용, 실제 대기와 단계별 실행 결과 제공 |
| 전환 실행 계층 | 준비·자원 변경·전력모드·라우팅·유입 중지·요청 마무리·해제 | 선택 목표를 동작으로 적용하고 실제 완료·실패·상태 제공 |
| Dashboard·분석 도구 | 허용된 조회·설정 변경과 실험 결과 해석 | CHILL이 제공한 판단·실행·관측을 사용자 작업 흐름에 연결 |

각 영역은 논리적 책임을 나타낸다. 기존 구현의 서비스·패키지·인터페이스에
이 책임을 배치한다. 워크로드 CRUD, 측정 실행, 모델 로딩·추론과 웹 UI는
각 영역의 기존 계약을 사용한다.

## 2. 역할과 정보 계약

### 2.1 역할

| 역할 | 스케줄러와의 관계 |
|---|---|
| 운영자 | 워크로드·허용 자원·운영 설정, 워크로드별 자동제어와 측정을 요청하고 판단·전환 상태 조회 |
| 서비스 사용자 | 워크로드와 추론 입력을 지정해 요청하고, CHILL이 내부 노드·배치를 선택 |
| 관측·근거 제공 영역 | 실제 구성·요청 상태·전력과 실행·전환 프로파일 제공 |
| 실행 계층 | 선택 목표와 정책을 적용하고 실제 상태·완료·실패를 반환 |
| 분석자 | 동일 조건의 요청 결과·SLO·총에너지와 판단·실행 기록으로 실험 해석 |

### 2.2 입력

| 입력 | 필요한 의미 |
|---|---|
| 워크로드와 요청 정의 | 등록 건 식별, 적용 모델 산출물, 전처리 산출물, 데이터셋 참조와 SLO, 접수 당시 정의와 최초 수신 시각 |
| 전체 POOL과 실제 구성 | 노드별 소속(워크로드별 활성 POOL, 측정 POOL, 가용 노드), 모델 준비, 전력모드, 인스턴스 실행 경로·실제 할당과 가용 예산 |
| 요청 부하와 진행 | 유입·접수·분배·결과, 미배정 대기, 인스턴스별 워크로드 대기·실행과 합산 부하, 요청별 경과 시간 |
| 실행 프로파일 | [측정 조건](../00_measurement.md#측정의-단위)이 일치하는 실행시간 분포, 처리량, 메모리, 전력, 에너지 |
| 전환 근거와 진행 | 출발·목표 상태, 동작·시간·에너지, 전환 중 가용 용량, 실제 진행·완료·실패와 일부 적용 |
| 운영·분석 설정 | 관측 구간, 관찰·제어 주기, 비용 비교 기간, 허용 자원과 제어요소 활성 여부 |

입력은 논리적 정보 계약이다. 각 소유 영역의 경계에서 검증한 정보를 기존
조회·전달 경로로 사용한다. API·저장 객체의 구성은 구현 설계에서 정한다.

### 2.3 출력

판단은 현재 상태 유지 또는 변경할 목표 구성과 정책을 제공한다. 변경 대상에는
워크로드별 활성 POOL과 소속 노드, 인스턴스의 모델·실행 경로·자원, 노드 전력모드,
워크로드별 분배와 배칭 정책 및 필요한 전환 동작이 포함된다.

판단에는 사용한 입력·설정·근거, SLO 충족 가능성과 비교 비용·조건을 연결한다.
근거 확보 대기, SLO 수용 한계와 판단 실행 오류를 구분한다. 목표 선언과 실제
준비·정책 반영·전환 완료는 각각의 상태와 증거로 제공한다.
출력의 API·필드·상태 코드 표현은 구현 설계에서 정한다.

- `SCH-36` 인스턴스 출력은 준비 상태와 별도로 워크로드 UID별 `routable`을 제공한다. 값은 서버의 현재 유효 배분 결과에서 산출하며, 준비됐지만 요청을 받을 수 없는 상태를 구분한다.
- `SCH-37` 라이브 출력은 초기 상태·상태 변경·작업 이벤트·지표·생존 신호에 순번을 연결하고, 재연결 시 누락 구간을 재개하거나 전체 상태로 재동기화한다. WebSocket은 연결 직후 첫 메시지로 인증하고 인증 전에는 상태를 보내지 않으며, 인증 실패 시 즉시 연결을 닫는다.

라이브 채널은 기존 관측·작업 결과의 전달 방식이므로 별도 시스템 spec 추가 없이 이 출력 계약과 구현 설계에서 다룬다.

## 3. 기능 요구사항

### 3.1 워크로드·부하와 시간 의미

- `SCH-03` 판단은 워크로드 등록 건과 적용 정의를 식별한다. 같은 서비스 이름의 재등록과 같은 모델을 참조하는 다른 워크로드를 구분한다. 접수한 요청은 접수 당시 모델·입력 계약·SLO와 최초 CHILL 수신 시각을 유지한다.
- `SCH-04` 부하 입력은 수신·접수·분배·firstfloor 수신과 실제 처리 결과를 구분한다. 요청 수·요청률에 사용한 사건·시각·모집단을 명시한다. 전체 유입에는 접수 전 거절을 포함한 실제 수신을 사용하고, 수신 구간의 요청 결과와 완료 사건 기준 처리량의 집계 의미를 구분한다.
- `SCH-05` 미배정 유입 대기, 인스턴스별 firstfloor 대기와 실행 중 요청을 구분해 판단에 사용한다. CHILL 배정과 firstfloor 수신·대기·실행은 각 위치의 관측으로 확인한다. phase 확인을 기다리는 요청은 확인 대기 상태로 제공한다.
- `SCH-06` 부하는 워크로드별 inputs/s를 기본 단위로 다루고 대기, 실행, 완료량은 요청 수로 다룬다. 실행 배치 수는 별도 단위로 기록하고 배치 크기는 요청 수다. 인스턴스는 워크로드 하나의 부하와 SLO를 맡고 노드는 그 인스턴스들의 합산 부담을 유지하며, 처리 비용은 [측정 조건](../00_measurement.md#측정의-단위)별 프로파일과 관측으로 판단한다.
- `SCH-07` 운영 부하는 설정된 시간 기반 이동 구간으로, 실험 분석은 지정 구간으로 집계한다. 구간·경계 규칙·모집단·포함 및 제외 조건·계산 방법과 관측 시각을 기록한다. 사건 발생·수집·조회 시각을 구분하고 관측 구간·제어 주기·비용 비교 기간을 각각 설정한다.
- `SCH-08` 평가에 필요한 관측·근거의 확보 상태와 이유를 제공한다. 확보된 관측값·계산값·예측값에는 의미와 출처를 연결하고, 관측 공백과 평가 대기는 별도 상태로 드러낸다. 후보의 SLO·비용 평가는 필요한 정보의 확보 범위에서 수행한다. 한 후보의 근거 확보 대기는 그 후보의 상태로 두고, 다른 후보와 현재 구성의 평가는 계속한다.
- `SCH-38` 계획 수요는 워크로드별 관측 수요와 운영자가 scheduler 설정 맵에 지정한 최소 수요(inputs/s, 기본 0) 중 큰 값으로 삼는다. 무부하에서도 그 하한을 감당하는 구성을 평가·선택하고, 적용한 최소 수요와 계획 수요를 판단 및 Run 기록에 남긴다.

### 3.2 근거와 실행 가능한 후보

- `SCH-09` 후보는 [측정 조건](../00_measurement.md#측정의-단위)과 실제 실행 조건에 맞는 측정 근거를 사용한다. 장비, firstfloor/backend, 전력모드, 자원, 배치 조건을 대응시키고 같은 조건의 최신 성공 측정을 우선한다. 같은 실행 조건은 SLO가 다른 워크로드에도 재사용한다. 완료된 측정 근거는 해당 노드를 그 워크로드의 후보로 만들며, 요청 지연은 실행 프로파일과 Serving 관측으로 평가한다.
- `SCH-10` 인스턴스 배치는 현재 자원 할당과 시스템·Serving 부가 사용량을 반영한 가용 예산 안에서 선택한다. CPU는 분리된 할당, GPU는 물리 장치 단위의 전용 할당을 사용한다. GPU 파드의 CPU·메모리도 자원 할당에 포함한다.
- `SCH-11` 서빙 파드 하나는 준비된 모델 실행기 하나를 제공한다. 인스턴스 수는 파드 추가·제거로 조절하고 기존 인스턴스의 자원 변경도 선택 대상으로 삼는다. CPU 스레드 설정은 CPU 할당량에 연동하고 각 인스턴스는 실행 배치를 하나씩 순차 처리한다.
- `SCH-12` 메모리는 프로파일과 가용 예산에 근거한 배치 가능성 제약으로 사용한다. 자원 배치 가능성과 SLO 충족 가능성을 각각 판단한다. 관측 최대 메모리는 해당 측정 조건에 연결하고, 단독 실행 근거를 공존 구성에 적용한 오차는 실제 Serving 관측으로 평가해 필요한 측정·운용 조건을 정한다.

### 3.3 SLO와 전환·Serving 비용 비교

- `SCH-13` 실행시간 분포에 firstfloor의 배칭과 큐 선택 규칙을 적용한 인스턴스 재생으로 실행 조건과 SLO마다 SLO를 지키는 최대 요청률(용량)을 미리 계산하고, 후보의 SLO 충족은 그 용량의 합을 현재 요청률과 대기량에 비교해 판정한다. 인스턴스가 요청마다 배치 실행시간 밖에서 점유되는 시간은 노드, 전력모드, runtime image, 모델마다 측정한 디스패치 점유를 재생의 배치 시간에 더해 반영하고, 그 측정이 없는 실행 조건은 용량을 계산하지 않는다. 그 밖의 유입, 전달, 응답 비용은 시스템 전체에 하나로 둔 완료 여유 설정으로 반영한다. 판단은 요청의 예상 완료 시각을 firstfloor 처리가 끝날 예상 시각에 완료 여유를 더해 계산하고, firstfloor 배칭도 같은 완료 여유를 사용한다. Serving 관측은 완료 여유를 검증하는 데 사용한다. 완료 여유는 관측 여부와 상관없이 항상 적용할 수 있으므로 후보 평가를 대기시키는 근거가 되지 않는다. 용량 계산은 포아송 도착의 독립 창마다 요청별 종단 지연 분포에서 SLO 백분위를 구하고, 설정한 수 이상의 창이 SLO를 지키는 최대 요청률을 용량으로 둔다.
- `SCH-14` SLO는 워크로드별 지정 백분위와 목표 시간으로 판단한다. 각 워크로드는 자기 인스턴스의 용량으로 평가한다(`SCH-13`).
- `SCH-15` 후보의 최종 상태와 준비·전환 중 가용 처리 능력·요청 지연을 함께 평가한다. 노드 전력모드 변경이나 인스턴스 제거에 영향받는 모든 워크로드의 SLO를 함께 평가한다. 자동제어가 켜진 모든 워크로드의 SLO를 함께 만족하는 후보를 우선하고 그 범위에서 전체 POOL의 에너지를 비교한다.
- `SCH-16` 유지와 변경 후보는 같은 시간축·부하 조건·전체 POOL 범위에서 전환과 이후 Serving의 총에너지로 비교한다. 준비 시점부터 새 용량을 반영하고 유지 후보에도 비교 기간의 Serving 소비를 포함한다. Serving 참여 여부에 따른 모든 노드와 필요한 임시 자원의 소비를 집계한다. 후보 사이에 같은 항(상태가 바뀌지 않는 노드와 구간)은 소거해 차이로 비교할 수 있다. 전체 POOL 총에너지는 실측으로 집계해 보고한다.
- `SCH-17` 모델 로드와 유휴 비용은 인스턴스당 한 번, 전체 노드 전력은 노드당 한 번, 각 소비 구간은 시간축에서 한 번 집계한다. 증분 에너지에 해당 기준 소비를 연결해 전체 에너지로 비교하고, 공존 비용은 자원 조건과 실제 관측에 대응시킨다.
- `SCH-18` 전환 시간은 용량 준비 시점·전환 중 처리 능력·SLO 판단에 적용한다. 시간과 에너지는 각각의 단위로 기록한다. 현재 부하를 기본 판단 근거로 사용하고, 비교 기간과 그동안 부하를 다루는 가정을 설정·기록한다.

### 3.4 선택 결과·라우팅과 firstfloor 정책

- `SCH-19` 선택 결과는 유지 또는 목표 구성, 영향받는 워크로드·노드·인스턴스, 분배·배칭 정책과 전환 동작을 실행 계층에 전달한다. 실제 현재 구성·비교 후보·선택 목표·적용 조건을 구분해 제공한다. 판단 대기와 판단 결과는 각각의 상태로 표현한다.
- `SCH-20` **변경(2026-10-25)** 요청은 해당 모델을 실제로 처리할 준비가 되고 해당 워크로드에 `routable`인 인스턴스 하나로 분배한다. 확인된 준비 상태와 가용 용량을 사용하고 수용 가능한 대상이 준비되면 요청을 전달한다. 분배 비율은 0 이상이며 대상이 있을 때 합이 1이다. 실현된 부하·배칭·SLO·에너지 영향을 다음 판단에 반영한다.
- `SCH-21` 배칭 정책은 evidence·워크로드 SLO와 최초 CHILL 수신 이후 요청별 경과 시간을 적용할 정보를 제공한다. firstfloor 큐 진입 이전 소비 시간, 현재 큐 대기·진행 중 실행, 후보의 실행 시간과 `SCH-13`의 설정 여유를 포함해 요청별 추가 대기 여유를 판단한다.
- `SCH-22` firstfloor 내부 배처가 현재 요청·큐·실행 상태에 CHILL 정책을 적용해 실제 배치 구성·추가 대기·실행 시점을 판단한다. CHILL은 정책과 요청별 정보를 제공하고 기존 firstfloor 큐·배처·모델 runner를 재사용한다.
- `SCH-23` 실행 배치는 같은 워크로드/불변 정의의 호환 요청으로 구성한다. normal queue는 stable EDF, deferred queue는 normal 이후 FIFO로 실행한다. SLO 여유와 evidence 기반 energy gain으로 배치·대기를 정하고 모델의 deadlinePolicy(drop/keep/defer, 기본 keep)를 actual과 용량 계산 재생에 동일하게 적용한다. keep의 overdue/infeasible 선택은 현재 fillable minimum-C batch(동률은 큰 batch)이며 drop은 queued 요청 종료, defer는 후순위 이동이다. explicit timeout/cancel은 세 모드에 별도로 적용하며 active batch는 SLO만으로 취소하지 않는다.
- `SCH-39` 배분 선언의 변경은 `route`(워크로드별 인스턴스 가중치 지정), `unroute`(선언을 유지한 배분 해제), `release`(선언 삭제 후 Pod 기본 표시 적용)를 구분하는 명시적 작업으로만 받는다. 각 작업은 실제 적용 ACK와 readback을 반환하고, 설정의 `staticRouting`은 읽기 전용으로 제공한다.

### 3.5 전환·실패와 재판단

- `SCH-24` 목표 선언·실행 시작·정상 진행·실제 완료·실패·일부 적용을 구분한다. 동작별 대상·시작 조건·완료 및 실패 기준·의존관계를 실행 계약에 연결한다. 모델 준비·전력모드·자원·라우팅은 실제 적용 증거로 확인하고 결과를 다음 판단에 사용한다.
- `SCH-25` 전환 중 준비된 용량으로 요청을 처리하도록 계획한다. 기존 인스턴스의 처리 지속 가능성, 동시에 빠지는 용량과 임시 용량을 평가한다. 새 대상 준비 후 유입을 옮기고 제거 대상은 신규 유입 중지와 기존 요청 마무리를 차례로 수행한다. 독립 동작은 전체 용량·SLO 조건에 따라 병렬 실행하고 전환 중 서비스 가용 범위를 기록한다.
- `SCH-26` 판단·실행 실패와 노드·backend 소실의 대상·원인·실제 완료 상태를 기록한다. 의존성이 충족된 동작을 진행하고 관측된 상태에서 다음 목표를 선택한다. 소실한 대상은 격리하며 실제 복구를 확인한 대상이 다시 가용 용량에 참여한다.
- `SCH-27` 전환 중 부하·진행 상태가 변하면 실제 상태에서 재판단한다. 진행 중인 동작은 기존 진행으로 추적한다. 버스트·점진적 변화·확장 후 급감·축소 후 재증가에는 같은 제어 로직을 적용하고 반복 전환 비용을 평가한다. 동작의 계속 수행·취소·재선택은 해당 조건과 비용에 따라 정한다.
- `SCH-28` SLO 수용 한계에 도달하면 가용 자원으로 SLO 충족을 우선하는 대응을 계속한다. 전체 POOL 한계·일시적 준비 용량 제약·실행 오류·근거 확보 대기를 구분하고 실제 지연·처리 결과로 적용 가능한 부하 범위를 드러낸다. 요청 수명과 큐 한도는 명시적 timeout·취소·Serving 자원 설정을 따른다.
- `SCH-40` 목표 구성의 일부 인스턴스가 Ready가 되면 나머지 준비·전력 전환 완료를 기다리지 않고 늦어도 다음 제어 주기에 준비된 부분집합을 배분에 편입한다. 드레인 중이거나 전력 변경의 영향을 받는 대상은 제외하고, 최종 목표와 진행 중 동작 및 다른 워크로드의 배분은 유지한다.
- `SCH-48` 정책 변경의 native ACK를 기다리는 인스턴스는 읽기 실패나 부재로 취급하지 않고 마지막으로 확인한 상태로 현재 구성 snapshot에 유지하며, 정책의 목표와 실제 반영을 구분해 '반영 대기'로 표시한다. ACK 대기만으로 인스턴스를 누락하거나 같은 slot에 대체 인스턴스를 중복 준비하지 않는다. 전력 변경 전 정지·드레인 등 기존 인스턴스에 대한 실행 의무는 ACK 대기 중에도 유지하며, 새 정책의 실제 적용은 ACK로 확인한다.
- `SCH-49` 실제 인스턴스 상태 읽기에 실패한 대상(`InstanceUnavailable`)이 하나라도 있는 Node에서는 상태를 다시 확인할 때까지 새 인스턴스 준비와 전력모드 변경을 수행하지 않고, 읽지 못한 인스턴스의 부재를 근거로 제거 완료를 판정하지 않는다. 읽기 실패와 정책 ACK 반영 대기를 구분해 원인·대상을 제공한다. 이 제약은 해당 Node의 불확실한 상태를 다루는 것으로, 기존 `ExclusiveCPUInfeasible` 시 전체 판단을 Pending으로 두는 정책을 완화하지 않는다.
- `SCH-50` 제어기는 실제 존재하는 실행기를 Pod UID 기준의 실물 장부 항목으로 유지한다. 같은 slot의 Pod도 각각 기록하며, 관측 실패만으로 항목을 삭제하거나 부재·제거 완료로 판정하지 않는다. 관측은 항목의 최근 상태, 관측 품질(확인됨·ACK 반영 대기·읽기 실패 등), 마지막 성공 확인 시각과 실패·대기 사유의 메모로 갱신하고, 실제 Pod 소멸을 확인한 뒤 항목을 제거한다.
  refresh/probe 진행 자체는 실패로 취급하지 않으며, 다른 실물의 부분 게시와 동시 snapshot에서도 마지막 확인 Ready를 유지한다(SCH-48). 실제 읽기 오류·serving label 불일치·Pod unready/삭제는 즉시 dispatch 자격을 닫고, Pod Ready 사건만이 아니라 성공 native 재확인 뒤에만 복구한다.
  종료 증거와 실제 삭제로 퇴역한 UID는 늦은 probe/로그 follow 결과로 재생성하거나 runtime에 다시 게시하지 않는다. 같은 이름의 새 Pod UID를 옛 probe의 대리 대상으로 삼지 않으며, Pod 부재만으로 종료 불명 실행기를 stopped로 바꾸지 않는다. 관측되지 않은 실행기의 정리도 finalizer 직접 제거로 종료 증명을 우회하지 않는다.
- `SCH-51` 작업 시작 시 건드리는 Node·Workload UID·실물 Pod UID의 범위를 장부에 예약한다. 자동제어와 수동 작업을 포함한 모든 변경 경로의 허가·범위 충돌 검사·예약 해제는 같은 범위를 사용하는 단일 지점에서 수행하고, 겹치는 변경은 시작 전에 거절하며 사유와 소유 작업을 제공한다. 완료·실패·취소에 따른 실행 종료와 예약 해제를 구분하며, 실패 시에도 실제 효과가 확인되면 예약을 해제한다. 취소·timeout 뒤 원격 효과를 확인하지 못한 경우에는 실행은 종료하되 효과 확인 또는 reset에 의한 실제 정리 완료까지 예약을 유지한다. 예약 해제는 실물 장부 삭제나 원복 완료를 뜻하지 않으며 실제 상태와 실패 원인은 남긴다.
  Workload 삭제도 삭제 시작 전에 Workload UID와 소유 실물의 범위를 같은 예약 경로로 획득하고, 자식 종료·정리와 finalizer 해제 이후 정확한 Workload UID의 실제 삭제 확인까지 유지한다.
- `SCH-52` 계획기는 전역 하나를 유지하며 진행 중 작업이 예약한 범위만 고정하고, 그 밖의 Node·Workload·실물에 대해서는 현재 부하와 상태로 후보 평가·확장 판단·실행 및 준비된 용량의 배분을 계속한다. 모든 작업의 완료를 기다리는 전체 완료 장벽이나 `InProgressTarget`을 근거로 한 전역 판단 대기를 두지 않는다. 예약을 침범하거나 예약 대상의 상태 변경을 전제하는 후보는 허가하지 않으며, 기존 자원·SLO 제약은 유지한다.
- `SCH-53` 과부하 후보는 기존 전체 충족·최종 충족 우선순위를 유지한 뒤, 각 Workload의 최종·전환 초과량 중 큰 값을 나쁜 순으로 정렬한 목록을 사전식 최소화한다. 최악 값이 같으면 다음 값을 비교하고 모든 값이 같은 경우에만 에너지를 비교한다. 용량 없는 Workload의 무한 초과량이 다른 Workload의 개선을 가리지 않아야 한다.
- `SCH-54` 실제 인스턴스가 없는 출발에서는 선택 가능한 모든 후보의 κ 계산이 끝나거나 설정된 대기 상한에 도달하기 전까지 목표 확정·예약을 보류한다. 첫 빈 출발 판단부터 잰 대기 시작·상한·대기 후보를 결정에 기록한다. 상한은 범위 검증된 scheduler 설정이며 결정 설정에 고정한다. 실물이 있거나 작업 예약이 있는 정상 운전에는 이 출발 대기를 적용하지 않는다.
- `SCH-55` 분배와 증설은 매 제어 주기에 판단하고, 축소와 에너지 목적 교체는 같은 하강 안정화 기간이 경과한 뒤에만 후보로 허용한다. 준비된 부분집합 배분과 예약 밖 확장은 계속하며, 기존 예약·자원·SLO·실제 Ready/ACK 제약을 면제하지 않는다.
- `SCH-56` 하강 판정은 Kubernetes HPA scale-down stabilization window 방식으로 통일한다. 기존 `scaleDownStabilizationNanos`(기본 300초, 시연 120초)의 지난 기간에 관측된 Workload별 유효 수요(최소 수요 포함)의 최대값을 현재 하강 판정 수요로 사용하며, 그 값이 현재 실제 가용 공급 κ보다 엄격히 작을 때만 축소·에너지 교체에 적격이다. 축소 후보도 이 수요를 감당해야 한다. 빈 Node 새 절전에는 동일한 Workload별 판정을 적용하여 모든 제어 Workload가 비증가(최대 수요≤공급), 하나 이상이 엄격한 여유(최대 수요<공급)를 가져야 한다. 합계 상쇄, 기준률 미만 유지 timer와 별도 전역 timer를 쓰지 않는다. 전체 기간의 유효 관측이 없으면 보류하고, 공백·재시작·설정 변경·UID 교체 뒤 새 관측 기간을 채운다. 0은 추가 기간 대기만 없애며 현재 수요·공급 검사는 유지한다. 기간·관측 범위·최대 수요·공급·허가/보류 이유를 결정에 기록하고 설정을 Run의 `binding.schedulerSettings`에 고정한다.
- `SCH-57` 전환 중 수요 대비 예비 용량 비율을 scheduler 설정으로 제공한다(기본 0, 0=별도 예비 없음, 유한한 0~1). 양수이면 영향을 받는 워크로드마다 실제 준비·ACK된 가용 용량으로 수요와 설정 예비를 감당하고 기존 전환 SLO 검사도 통과해야 한다. 예비를 위한 준비·유지·해제 에너지도 E5 전체 POOL 에너지에 포함하고 비율·판정·미확보 이유를 결정과 `binding.schedulerSettings`에 기록한다.
- `SCH-58` 에너지 비교 기간 H는 양수인 하나의 scheduler 설정으로 고정하여 같은 판단의 keep과 모든 후보에 동일하게 사용한다. 후보의 전환 시간이나 미선택 후보의 추가·삭제로 H를 늘리지 않으며 사용한 H와 부하 가정을 결정 및 `binding.schedulerSettings`에 기록한다. H는 실제 전환 완료 확인이나 동작 timeout을 대체하지 않는다.
- `SCH-59` 빈 Node의 새 `Fixed` 절전도 일반 교체와 동일한 keep 대비 에너지 허가를 받는다. 같은 H 안 nominal 이득이 양수이고 기존 minimumGain 문턱 및 payback을 모두 통과해야 하며, Fixed라는 이유로 비용을 공통 경로에서 소거하거나 검사를 면제하지 않는다. 별도 절전 계산기·기간·문턱을 추가하지 않는다. 이미 실행 중인 허가된 동작의 완료 의무는 유지한다.

SCH-50은 SCH-48의 ACK 대기 snapshot 보존과 중복 준비 방지, SCH-49의 읽기 실패 시 부재로 간주하지 않는 처리를 실물 장부로 흡수한다. SCH-48의 목표·실제 반영 구분 및 ACK 확인과 SCH-49의 해당 Node 준비·전력 변경 보류는 그대로 유지한다. SCH-51은 그 보류와 작업 충돌을 공통 예약 경로에서 집행하며, SCH-52는 SCH-40의 준비된 부분집합 배분을 유지하면서 예약 밖의 새 판단까지 계속하도록 확장한다. SCH-49의 `ExclusiveCPUInfeasible` 전역 Pending은 자원 불가능성 정책으로 유지하며, 진행 중 작업 전체의 완료를 기다리는 장벽과 구분한다. SCH-41의 중복 실물 전체 reset도 유지하되 SCH-50의 Pod별 장부를 정리 대상으로 사용한다.

### 3.6 관리 연동·관측과 운영 설정

- `SCH-29` 워크로드 등록·SLO 변경·모델 변경·삭제와 POOL 관계 변경을 판단에 반영한다. 기존 요청은 접수 당시 정의와 관리 영역의 마무리 계약을 유지한다.
- `SCH-30` 사용한 부하·큐·SLO·실제 구성·프로파일·전환 근거·비교 기간·설정과 후보별 적격성 평가, 선택·반영 결과를 연결해 제공한다. 라우팅 결정 시각과 실제 반영 시각을 각각 기록하고, 제어 동작의 대상·시작 및 완료 시각·결과를 요청·전력과 같은 시간축에 연결한다. 예상 지연·에너지와 실측 결과를 구분해 종단 평가에서 오차를 확인한다.
- `SCH-31` 요청별 시간·배정 인스턴스·실제 결과, 실현된 배치와 전력 관측을 보존한다. 완료·실패·거절·timeout·취소·미완료·전달 실패·SLO 초과를 구분하고 모집단·표본 수를 제공한다. 표본 수 0인 구간의 지연 통계 값은 공란으로 표현한다. 원시 기록과 집계 조건으로 같은 분석을 재계산하고 분석자가 실험 성패를 해석한다.
- `SCH-32` 허용된 운영자는 시스템 전체의 관측 구간·관찰 및 제어 주기·비교 기간·허용 자원·제어요소 활성 설정을 조회·변경한다. 전후 정의·검증 결과·영향 범위·실제 적용 진행과 사용한 설정을 기록한다. 정적 구성과 제어요소별 기여 실험은 동일 부하 조건·전체 POOL 범위로 평가하고 선택 근거를 보존한다.
- `SCH-33` **변경(2026-10-25)** 자동제어는 워크로드별로 켜고 끄며, 최소 수요는 별도의 scheduler 설정 맵(`SCH-38`)으로 둔다. 켜진 워크로드는 가용 노드, 자기 활성 POOL 노드, 같은 등록 모델을 참조하는 다른 워크로드의 활성 POOL 노드 중 측정 근거가 있는 노드로 첫 구성을 선택해 만들고, 이후 제어 주기마다 다시 판단하며, 인스턴스를 하나 이상 유지한다. 노드마다 서빙 인스턴스는 하나다. 측정 근거가 있는 노드가 없는 켜진 워크로드는 측정 근거 대기 상태를 제공하고, 다른 워크로드의 판단과 실행은 계속한다. 꺼진 워크로드는 마지막 구성을 유지하고, 그 워크로드의 수동 변경은 그 워크로드에만 적용한다. 꺼진 워크로드와 공유하는 노드의 전력모드를 바꿀 때는 꺼진 워크로드의 SLO도 함께 평가하고, 꺼진 워크로드의 인스턴스는 그대로 둔다. 가용 노드는 가장 낮은 전력모드로 두고 다시 편입하는 전환 비용을 비교에 포함한다. 활성 POOL 사이에서 노드를 바로 옮기는 것은 전환 하나로 실행하고 그 비용을 비교에 포함한다.
- `SCH-34` 측정 요청은 대상 노드를 측정 POOL로 옮겨 수행하고, 끝나거나 실패하면 가용 노드로 돌려보낸다. 활성 POOL에서 서빙 중인 노드에 대한 측정 요청은 거절하고 사유를 제공한다. 측정 POOL의 노드는 측정에만 사용한다. CHILL이 배치하지 않은 파드가 있는 노드도 가용 노드로 다루고 전력모드를 바꾸며 측정을 진행하고, 측정 결과에는 그 파드들의 목록을 기록한다. 한 노드의 측정 요청은 요청 순서대로 하나씩 실행하고, 서로 다른 노드의 측정은 동시에 진행한다. 측정이 노드에 둔 파드는 서빙으로 보지 않는다. 측정 조건의 CPU 할당이 그 전력모드의 온라인 CPU에서 서빙 예약을 뺀 범위에 들지 않거나, 요청이 가리키는 측정 근거가 쓸 수 없으면 요청을 거절하고 사유를 남긴다.
- `SCH-35` 비교 기준 실험으로 운영자는 firstfloor 인스턴스에 고정 배치 크기 B를 설정한다. 같은 워크로드/불변 정의의 호환 요청이 B개 이상 대기하면 실제 요청 정확히 B개를 실행한다. 이 인스턴스의 배치 구성과 실행 시점은 B만으로 정하며 `SCH-13`, `SCH-21`, `SCH-23`의 SLO 여유, 완료 여유, deadlinePolicy는 배치 선택에 적용하지 않는다. 남은 요청은 B가 찰 때까지 대기한다. 명시적 timeout, 취소, 큐 한도, 종료는 그대로 적용하고 종료 시 남은 요청은 실행하지 않는다. SLO 초과와 종단 결과는 `SCH-31`대로 기록한다. 자동제어는 고정 배치 크기를 선택하지 않고 이 인스턴스를 후보로 쓰지 않는다. 설정한 B는 실행 설정과 결과에 기록한다.
- `SCH-41` **변경(2026-10-26)** 서버의 원자적 `reset` 작업은 지정 워크로드 UID 목록(또는 전체 비자율 워크로드)에 대해 자동제어 해제 → 배분 해제와 ACK → 미완료 요청 0까지 드레인 → 소유 인스턴스 stop·remove와 Pod 소멸 확인 → 배분 선언 삭제 → 빈 노드 최저 전력모드 복귀와 Ready 확인 순서로 수행한다. 같은 slot에 실물 인스턴스가 여러 개 있어도 slot당 하나로 축약하거나 중복을 이유로 거절하지 않고, 대상 워크로드가 소유한 실물 전부를 정리하며 다른 소유자의 인스턴스는 건드리지 않는다. 단계별 시작·완료 시각과 실제 상태 readback을 반환하고 실패 시 해당 단계·이유를 기록해 자동 재시도 없이 멈추며, 이미 정리된 상태의 재호출은 변경 없이 성공한다.
- `SCH-42` 실험 구간의 관측과 원시 기록은 사후 재생이 가능한 동안 보존하며, 조회는 로컬에 없는 시간대의 기록을 근거 저장소에서 투명하게 읽는다. 조회 결과는 실제 보존 범위·출처·공백을 드러내고 로컬 보존 기간에 의해 과거 실험 기록을 누락시키지 않는다.
- `SCH-43` 관측 기록은 워크로드 UID와 함께 당시 이름·모델·적용 정의를 보존한다. 워크로드 삭제나 같은 이름 재등록 뒤에도 UID로 원래 정의를 조회해 과거 결과를 식별한다.
- `SCH-44` 허용된 조회자는 OperationCostMeasurement와 DispatchOccupancyMeasurement CR의 목록·상세에서 상태와 결과 요약을 조회한다. 측정 생성·변경은 기존 CR 경계를 유지한다.
- `SCH-45` 실험 ID별 불변 요약에 단계 경계·단계별 KPI·출처 경로를 연결해 근거 저장소에 보존하고 실험 목록·상세 조회로 제공한다.
- `SCH-46` 상태의 축약 조회는 노드·인스턴스·배분·현재 판단 요약·진행 작업을 제공하고 프로파일과 κ 표는 제외한다.
- `SCH-47` 작업은 해당 조건의 전환 비용 실측 시간에 근거한 예상 소요 시간(`expectedSeconds`)과 그 출처를 제공한다. 예상값과 실제 진행·경과·완료 시간을 구분하고 근거가 없으면 예상 시간 미확보를 표시한다.

### 4.1 전환·운영 작업 추가 수용 시나리오

#### SCH-AC-30 — 시연 B: 느린 전력 전환 중 부분 배분
- Given: 목표 구성 일부가 Ready이고 다른 노드의 느린 전력 전환이 진행 중이다.
- When: 다음 제어 주기가 실행되고 해당 워크로드 요청이 들어온다.
- Then: Ready 부분집합이 나머지 전환을 기다리지 않고 요청을 받으며, 드레인·전력 변경 대상은 배분에서 제외된다.
- 요구사항: SCH-20, SCH-25, SCH-36, SCH-40.

#### SCH-AC-31 — 시연 A: 무부하 최소 수요
- Given: 관측 수요는 0이고 최소 수요가 양수이며 이를 감당할 측정 근거와 자원이 있다.
- When: 자동제어가 구성을 선택한다.
- Then: SLO를 지키며 최소 수요 이상을 감당하는 구성을 선택하고 적용 하한과 계획 수요를 판단·Run 기록에 남긴다.
- 요구사항: SCH-13, SCH-33, SCH-38.

#### SCH-AC-32 — release 뒤 새 측정 인스턴스 배분
- Given: 비자율 워크로드에 unroute 선언이 남아 있고 새 측정 인스턴스는 Pod 기본 표시상 요청 수신 대상이다.
- When: release 작업의 ACK와 readback을 확인한 뒤 준비된 새 인스턴스에 대한 요청을 보낸다.
- Then: 배분 선언은 사라지고 새 인스턴스의 routable이 참이며 실제 요청을 받는다.
- 요구사항: SCH-20, SCH-36, SCH-39.

#### SCH-AC-33 — reset 두 번 호출
- Given: 대상 워크로드에 배분·미완료 요청·소유 인스턴스가 있다.
- When: reset이 성공한 뒤 같은 범위로 다시 reset을 호출한다.
- Then: 첫 호출은 배분 해제·드레인·제거·전력 복귀 순서와 실제 완료를 기록하고, 두 번째는 추가 변경 없이 성공한다.
- 요구사항: SCH-39, SCH-41.

#### SCH-AC-34 — 배분 변경 중 ACK 대기와 중복 준비 방지
- Given: 기존 인스턴스가 확인된 상태이고 배분 변경으로 DecisionID가 바뀌어 native ACK가 아직 오지 않았다.
- When: ACK 대기 중 여러 제어 주기가 실행되고 이후 실제 상태 읽기 실패도 발생한다.
- Then: ACK 대기 중에는 기존 인스턴스가 마지막 확인 상태와 '반영 대기' 표시로 snapshot에 남고 같은 slot의 중복 준비가 없다. 실제 읽기 실패 시에는 해당 Node의 준비·전력 변경·부재에 의한 제거 완료 판정이 멈추며, 재확인 전까지 실행되지 않는다.
- 요구사항: SCH-24, SCH-27, SCH-48, SCH-49.

#### SCH-AC-35 — 전력 변경 전 ACK 대기 인스턴스도 정지
- Given: 전력모드 변경 대상 Node에 native 정책 ACK 반영 대기 중인 인스턴스가 있고 상태 읽기는 성공한다.
- When: 전력 변경을 위한 신규 유입 중지·드레인·정지 절차를 실행한다.
- Then: 반영 대기 인스턴스도 정지 대상에 포함하고 실제 드레인·정지를 확인한 뒤에만 전력모드를 변경한다. 도중 읽기 실패가 생기면 전력 변경과 부재에 의한 제거 완료 판정은 재확인까지 수행하지 않는다.
- 요구사항: SCH-24, SCH-25, SCH-48, SCH-49.

#### SCH-AC-36 — 같은 slot의 중복 실물 reset
- Given: reset 대상 워크로드가 같은 slot에 실물 인스턴스 여러 개를 소유하고, 대상 밖 소유자의 인스턴스도 존재한다.
- When: 해당 워크로드 UID로 reset을 실행하고 완료 후 같은 범위로 다시 호출한다.
- Then: 중복 slot을 이유로 실패하지 않고 대상 소유 실물 전부의 드레인·stop·remove와 Pod 소멸을 확인한 뒤 배분 선언 정리·빈 노드 전력 복귀를 완료한다. 대상 밖 인스턴스는 유지하며, 재호출은 추가 변경 없이 성공한다.
- 요구사항: SCH-39, SCH-41.

#### SCH-AC-37 — 관측 실패 중 실물 장부 유지와 중복 준비 방지
- Given: 같은 slot에 실제 Pod가 존재하고 장부에 Pod UID·소유 Workload·Node와 마지막 확인 상태가 기록되어 있다.
- When: 정책 ACK 반영 대기와 실제 상태 읽기 실패를 각각 발생시키고 여러 제어 주기를 진행한다.
- Then: Pod별 항목과 마지막 성공 확인 시각은 유지되고 관측 품질·사유만 해당 상태로 갱신된다. 읽기 실패를 부재나 제거 완료로 보지 않으며 같은 slot의 중복 준비 횟수는 0이다. 복구 후 같은 Pod 항목의 관측을 갱신하고, 실제 Pod 소멸을 확인한 경우에만 제거한다.
- 요구사항: SCH-41, SCH-48, SCH-49, SCH-50.

#### SCH-AC-38 — 작업 범위 예약 충돌 거절과 해제
- Given: 작업 A가 Node·Workload·실물 범위를 예약하고 실행 중이며, 자동제어 또는 수동 작업 B가 그 범위와 겹치는 변경을 요청한다.
- When: B의 시작 허가를 검사하고, 이어 A가 완료·실패·취소로 종료되며 실제 효과가 확인된 경우와 취소·timeout 뒤 원격 효과가 미확인인 경우를 각각 진행한다.
- Then: B는 공통 허가 지점에서 시작 전에 거절되고 충돌 범위·소유 작업·사유가 제공된다. 실제 효과가 확인된 A는 실패한 경우에도 예약을 해제하여 후속 작업이 현재 실제 상태에서 다시 허가받을 수 있다. 원격 효과가 미확인인 A는 실행 종료 후에도 예약을 유지하여 겹치는 변경을 계속 거절하고, 이후 효과 확인 또는 reset의 실제 정리 완료 뒤에만 해제한다. 해제 후에도 실물 항목·일부 적용 상태·실패 원인은 유지된다.
- 요구사항: SCH-24, SCH-26, SCH-41, SCH-50, SCH-51.

#### SCH-AC-39 — 1회차 B 재현: jetsono 전력 전환 밖 확장과 배분
- Given: jetsono의 느린 전력 전환 작업이 해당 Node·Workload·실물을 예약하고 진행 중이며, 예약 밖의 다른 Node와 Workload에 확장 수요·측정 근거·가용 자원이 있다.
- When: jetsono 전력 전환이 끝나기 전에 다음 제어 주기들이 실행된다.
- Then: 단일 전역 계획기가 예약 범위를 유지하면서 다른 Node의 확장 후보를 평가·선택하고 준비 작업을 시작한다. 준비된 용량은 늦어도 다음 제어 주기에 실제 분배에 편입되어 요청을 받으며, 이 판단·준비·분배 시각은 jetsono 전환 완료보다 앞선다. jetsono 예약을 침범하는 변경과 중복 작업은 없고 전체 완료 장벽으로 대기하지 않는다.
- 요구사항: SCH-20, SCH-25, SCH-27, SCH-40, SCH-50, SCH-51, SCH-52.

#### SCH-AC-40 — 무한 초과량에서도 독립 개선 선택
- Given: 한 Workload는 모든 후보에서 용량이 없고 다른 Workload에는 양수 용량 후보가 있다.
- When: 공동 후보와 아무것도 하지 않는 keep을 비교한다.
- Then: 같은 무한 초과량 다음의 초과량을 비교하여 나머지 Workload를 살리는 후보가 keep을 이긴다. 모든 초과량이 같은 경우에만 에너지·keep·논리 key 순서를 적용한다.
- 요구사항: SCH-53.

#### SCH-AC-41 — 빈 출발 κ 완료 순서 독립
- Given: 실물과 예약이 없고 Smol/PLC/MNV의 수요가 .3/40/20이며 Smol genesis2 FP32 행, PLC 행, MNV 행 순서로 계산 결과가 도착한다.

- Then: 부분 결과에서는 목표 확정·예약을 하지 않고, 완료 후 공동 배치하여 세 Workload 모두 양수 용량을 얻는다. 상한 도달 시에는 현재 근거로 진행하며 시작·상한·남은 후보가 기록된다. 실물이 있는 독립 확장은 기다리지 않는다.
- 요구사항: SCH-52, SCH-54.

#### SCH-AC-42 — 최대 수요 창의 공통 하강 판정
- Given: 설정 기간 W와 실제 공급 κ, 정상 관측, 축소·교체·빈 Node 절전 후보가 있다.
- When: (1) 100 req/s 일정 부하에 관측 잡음을 섞어 W보다 오래 유지하고, (2) 실제 하강 전 높은 수요가 있는 창에서 낮은 수요로 전환하여 W 경계 전후를 비교하며, (3) 빈 출발·증설을 실행한다.
- Then: (1) 잡음의 국소 고점으로 timer가 시작되어 축소·새 절전이 허가되지 않는다(공급은 창 최대 수요 이하인 재현 입력). (2) 높은 수요가 창에서 빠지고 전체 W의 유효 관측 및 최대 수요<현재 공급 조건이 충족되면 기존 이득·SLO 조건을 통과한 후보를 허용한다. Workload와 빈 Node는 같은 창 정의를 쓰며 UID 사이 증감을 합계로 상쇄하지 않는다. 공백·restart·설정 변경·UID 교체 후 불완전 창은 보류한다. (3) SCH-54 빈 출발과 매 주기 증설·부분 Ready 배분·예약 밖 진행은 불변이다. 0 설정도 현재 수요·공급 검사는 남긴다. 결정에는 창·최대 수요·현재 공급·보류 이유가 남는다.
- 추가 후보 보호: 창 최대 110 req/s·현재 수요 20 req/s·현재 공급 160 req/s인 동일 입력에서는 gate가 열려도 후보 공급 60은 거절하고, 후보 공급 120은 전환·SLO·본전 등 기존 조건을 충족하면 허용한다. gate뿐 아니라 후보 검사에도 최대 수요를 사용하며, 증설 후 여유 공급에서 과거 최대 수요를 보존하는 축소까지 금지하지는 않는다.
- 요구사항: SCH-40, SCH-52, SCH-54, SCH-55, SCH-56.

#### SCH-AC-43 — 양수 예비 비율의 전환 SLO와 에너지
- Given: 양수 예비 비율과 이를 감당할 실측 용량·자원이 있는 전력 변경 후보가 있다.
- When: 준비되지 않은 공급만 있는 경우와 실제 Ready·ACK 예비가 확보된 경우를 실행한다.
- Then: 전자는 변경을 허가하지 않고 후자는 수요 대비 예비와 기존 전환 SLO를 만족하며 전환 중 실제 요청 SLO를 확인한다. 비율 0은 추가 예비 제약만 끄며 SLO 검사는 유지한다. 예비의 준비·Serving·해제 소비는 E5 에너지에서 빠지지 않는다.
- 요구사항: SCH-15, SCH-16, SCH-25, SCH-57.

#### SCH-AC-44 — 후보와 무관한 고정 H
- Given: 동일 snapshot·설정 H와 keep·변경 후보가 있다.
- When: 더 긴 전환의 미선택 후보를 추가·삭제한다.
- Then: 공통 후보의 H와 [0,H] 비용은 동일하고 H 초과 후보는 기간을 늘리는 대신 명시적 부적격으로 기록한다. 설정·결정·Run binding의 H가 일치한다. 빈 Node Fixed 절전도 동일 keep/minimumGain/payback 경로를 사용하며, jetsono MAXN→15W의 H=600초 이득 −699J·손익분기 약 52분 입력에서는 실행하지 않는다. 양수 이득이어도 minimumGain 또는 payback 미충족이면 실행하지 않는다.
- 요구사항: SCH-16, SCH-18, SCH-58, SCH-59.

#### SCH-AC-45 — E5 실패 주입의 격리·대체·복구
- Given: 세 Workload의 최종 승인된 α=0.3 부하(`rate_w=α×s_w×R_w`), 대체 가능한 Accepted 근거, 정상 Ready/route와 사전 고정한 대상 Pod UID·Node가 있다.
- When: 15분 E5-7에서 180초에 서빙 Pod 하나를 강제 삭제하고, 360초에 Node 하나를 cordon한 뒤 그 Node의 대상 서빙 Pod를 삭제하며, 600초에 uncordon한다. 기존 공개 API와 kubectl만 사용한다.
- Then: 삭제 실물과 실패 동작의 대상·원인·시각을 기록하고 소실 용량을 배분에서 격리한다. 남은 가용 자원에서 대체를 선택하고 실제 Ready·ACK 후 편입하며, 복구 Node도 실제 Ready·관측 회복 전에는 용량으로 세지 않는다. 대체 불가/미회복도 원인과 함께 실패 결과로 남긴다. cordon만으로 네트워크 단절이나 기존 Pod 종료를 입증하지 않는다.
- 집계: 첫 준비 요청을 전체 offered 분모에 유지하고 별도 집단으로 표시한다. Node 차단/복구 구간은 전체 결과를 유지한 채 표시하고 그 구간을 뺀 별도 집계를 병기한다. 원시 요청·전력·동작·route·Node 시각으로 재계산 가능해야 한다.
- 요구사항: SCH-07, SCH-08, SCH-24, SCH-26, SCH-30, SCH-31.

#### SCH-AC-46 — E5 혼합 POOL 지분 단계와 게이트웨이 구분
- Given: Node당 서빙 인스턴스 하나인 전체 POOL과 최종 SLO·모드·자원에 맞는 Node별 κ가 있다. `R_w=Σ_Node max eligible κ_w`는 고립 기준이며 세 R을 동시에 사용할 수 없다.
- When: 유한한 [0,1]의 `poolShares={MNV:s_M,PLC:s_P,Smol:s_S}`(기본 .45/.1/.45, 합1)을 동결하고 α=0.3/0.5/0.7/0.9/1.2 단계에서 `rate_w=α_w×s_w×R_w`의 포아송 trace를 만든다. burst에서는 Smol의 α만 바꾼다.
- Then: 잘못된 지분/합은 실행 전에 거절한다. 설정 검증은 `1.2×Σ(s_w×R_w)≤0.8×G`이며 G 입력값·출처와 R·s·α·요청률·trace를 binding에 동결한다. G 미확정은 명시 경고이며 개시 통과가 아니다. α를 혼합 SLO 보장으로 해석하지 않는다. G 확인은 고정 배치·α=1.2 총혼합120초 단1회(계단/최대G 탐색/자동재시도 없음)다. 동결trace 공급, PLC p95≤32ms 및 전체offered 대비32ms deadline성공≥95%, gateway거절/503/timeout/미완료0, cs throttle/restart/OOM0, 누락없는cs CPU/메모리10초표본·동결limit미만이면 PASS, 아니면 FAIL과원시사유다. native/client한계는 gateway실패와 구별하고 자동clip하지 않는다. 통과점은 최대G 또는20%여유 인증을 대신하지 않는다.
- 요구사항: SCH-04, SCH-10, SCH-13, SCH-14, SCH-30, SCH-31.

## 6. 고수준 요구사항과 구현 설계의 구분

이 SRS는 목표 우선순위·책임 경계·입출력 의미·기능 요구사항과 검증 결과를
정한다. 구현 설계는 다음 선택을 요구사항과 측정 질문에 연결한다.

| 설계에서 선택할 항목 | 지켜야 하는 요구사항 |
|---|---|
| 후보 탐색·비교와 예상 완료 시각 계산 알고리즘 | 측정 조건·현재 큐·진행 상태, SLO 우선·총에너지 비교 |
| 비교 기간·부하 가정·관찰·제어·재판단 규칙 | 설정·비교 조건 기록, 실제 상태에서 동일 제어 로직 적용 |
| 계측 수집·시간창 집계·원시 보존 | 사건·단위·등록 건·시각·공백 의미, 운영과 실험 구간 구분 |
| 라우팅·firstfloor 정책 적용 및 갱신·큐 선택·추가 대기 | 준비된 대상·종단 시간·Workload 배치 분리·실행기 내부 판단 |
| 판단·설정·전환 API와 객체·프로세스 배치 | 현재·목표·실제 진행·결과와 근거, 기존 관리·실행 경계 연결 |

Counter·Gauge, Prometheus 구간 집계, Knative 부하 관측·안정화, Envoy 입장 제어와
기존 실행기의 메트릭은 재사용을 검토할 참고 사례다. 구체적인 수집 제품·안정화
정책·공식과 관측 기록 조회 사용은 요구사항과 측정 조건에 따라 선택한다.
기존 계측·실행 기능을 확인하고 필요한 연결을 기존 구현에 추가한다.
