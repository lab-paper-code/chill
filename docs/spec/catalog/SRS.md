# 데이터셋과 전처리 관리 SRS

## 1. 목적과 범위

이 문서는 CHILL 워크로드가 참조하는 전처리와 데이터셋의 등록, 조회, 수정, 삭제와
참조 관계를 정의한다. [시스템 명세](../README.md)의 워크로드 정의에서 전처리 참조와
데이터셋 참조가 가리키는 대상을 구체화한다.

요구사항 ID의 `DP`는 데이터셋과 전처리를 뜻한다. 각 요구사항은 구현과 검증의 기준이다.
이 문서의 정보 이름은 외부에서 관찰할 의미를 나타내며, 리소스와 API 표현은 구현 설계에서 정한다.

| 관련 영역 | 책임과 원본 |
|---|---|
| 모델 등록 | 모델 산출물과 실행 경로는 [모델 경계 ADR](../../adr/0012-model-artifact-compatibility-boundary.md)을 따름 |
| 워크로드 참조 | 참조 검증, 원시 표본 접수 검증, 모델 변경 절차와 요청 기록은 [워크로드 관리 SRS](../workloads/SRS.md)를 따름 |
| 프로파일 | 데이터셋 표본을 사용한 측정과 측정 조건은 [프로파일링과 Evidence](../00_measurement.md)를 따름 |
| 요청 실행 | 실행 배치의 전처리, 추론, 후처리 순서는 [라우팅과 배칭](../03_routing.md)을 따름 |

## 2. 사용자와 관리 정보

### 2.1 역할

| 역할 | 동작 |
|---|---|
| 운영자 | 전처리와 데이터셋을 등록, 수정, 삭제하고 워크로드에서 참조 |
| CHILL | 선언 검증, 참조 보호, 실행 준비 시 전처리 코드 제공, 변경 적용 |

### 2.2 정의 정보

| 정보 | 소유와 의미 |
|---|---|
| 전처리 식별자 | 워크로드가 참조할 전처리 이름. 전처리 식별 범위에서 유일 |
| 원시 입력 계약 | 표본 1개를 구성하는 필드별 이름, 자료형, 크기 상한과 내용 형식. 자료형은 원시 바이트, 내용 형식은 이미지 형식이나 UTF-8 텍스트 |
| 원시 출력 계약 | 요청자가 응답으로 받는 필드별 이름, 자료형과 의미 |
| 전처리 산출물 | 대상 모델과 모델 산출물, 내용이 고정된 코드의 위치와 장비 아키텍처 |
| 데이터셋 식별자 | 워크로드가 참조할 데이터셋 이름. 데이터셋 식별 범위에서 유일 |
| 데이터셋 표본 | 내용이 고정된 위치에 보관한 원시 표본 모음과 그 레코드 필드 선언 |
| 표본 부분집합 | 프로파일링에 사용할 프로파일링 부분집합과 평가 부하에 사용할 평가 부하 부분집합 |

## 3. 요구사항

### 3.1 전처리

- `DP-01` 전처리는 식별자, 원시 입력 계약, 원시 출력 계약과 하나 이상의 전처리 산출물을 필수 정보로 가져야 한다. 원시 입력 계약은 표본 1개를 구성하는 모든 필드를 선언해야 한다.
- `DP-02` 전처리 산출물은 대상 모델과 그 모델의 산출물 하나를 지정해야 한다. 한 전처리에서 대상 모델 산출물마다 전처리 산출물은 정확히 하나여야 한다.
- `DP-03` 전처리 산출물의 코드는 내용이 고정된 위치와 장비 아키텍처로 식별해야 한다. CHILL은 실행 준비 시 이 코드를 대상 모델 산출물과 함께 실행 위치에 제공해야 한다. 코드가 사용하는 라이브러리는 대상 모델 산출물을 실행하는 runtime 환경이 제공해야 하며, 코드 적재 실패는 해당 인스턴스의 실행 준비 오류와 원인으로 드러내야 한다.
- `DP-04` 전처리 코드는 한 실행 배치의 원시 표본들을 모델 입력으로 바꾸고, 추론 결과를 요청별로 원시 출력 계약의 응답으로 바꿔야 한다.
- `DP-05` 전처리 코드는 배치의 요청마다 성공 결과와 [단위 수](../00_measurement.md#측정의-단위) 또는 실패 사유를 보고해야 한다. 보고 수가 배치의 요청 수와 다르거나 성공 요청의 단위 수가 1보다 작으면 CHILL은 해당 배치를 오류로 처리해야 한다.

### 3.2 데이터셋

- `DP-06` 데이터셋은 식별자, 내용이 고정된 표본 위치, 레코드 필드 선언, 프로파일링 부분집합과 평가 부하 부분집합을 필수 정보로 가져야 한다. 두 부분집합은 서로 다른 표본으로 구성해야 한다.
- `DP-07` 데이터셋과 전처리의 호환성은 데이터셋의 레코드 필드 선언과 전처리의 원시 입력 계약을 비교해 판단해야 한다. 원시 입력 계약의 모든 필드가 같은 이름과 자료형으로 레코드 필드에 선언되고, 각 레코드 필드의 크기 상한과 내용 형식이 계약 범위 안에 있으면 호환이다. 판단에는 두 선언만 사용해야 한다.

### 3.3 등록, 조회, 수정, 삭제

- `DP-08` 운영자는 전처리와 데이터셋을 등록, 목록 조회, 상세 조회, 수정, 삭제할 수 있어야 한다. 관리 변경 권한은 [WM-01](../workloads/SRS.md#21-역할)을 따라야 한다. 미등록 식별자의 조회는 조회 오류로 제공해야 한다.
- `DP-09` 등록과 수정 시 식별자 중복, `DP-01`과 `DP-02`의 조건, `DP-06`의 필수 정보, 전처리 산출물이 지정한 모델 산출물의 존재와 삭제 진행 여부를 검증해야 한다. 검증 오류와 거부된 변경의 처리는 [WM-06](../workloads/SRS.md#31-등록-검증)을 따라야 한다.
- `DP-10` 워크로드가 참조하는 전처리를 수정하면 영향을 받는 워크로드에 [모델 변경 절차](../workloads/SRS.md#43-모델-수정)를 적용해야 한다. 데이터셋 수정은 이후 요청하는 측정부터 적용해야 한다. 이 수정은 해당 워크로드들이 함께 참조하는 데이터셋과 전처리가 `DP-07`의 호환성을 유지할 때 수락해야 한다.

### 3.4 참조 보호

- `DP-11` 워크로드가 참조하는 전처리와 데이터셋의 삭제는 [WM-23](../workloads/SRS.md#52-모델-참조와-동적-서빙-관계)의 모델 참조와 같은 방식으로 거부해야 한다.
- `DP-12` 전처리 산출물이 대상으로 지정한 모델 산출물을 제거하는 모델 수정과 해당 모델의 삭제는 참조하는 전처리를 이유로 제공하며 거부해야 한다.

## 5. 구현 설계로 연결할 사항

구체적인 리소스와 API, 코드 전달 방식은
[이기종 워크로드 구현 설계](../../design/serving/heterogeneous-workloads.md)에 정리한다.

| 영역 | 구체화할 구현 |
|---|---|
| 리소스 | 전처리와 데이터셋의 리소스 표현, 객체 범위와 필드, 내용이 고정된 위치의 표현 |
| API | 관리 경로, 변경 전제조건과 오류 응답 |
| 코드 실행 | 코드 전달과 적재 위치, runtime 환경의 라이브러리 제공, 배치 입력과 응답 및 단위 수의 전달 형식 |
| 데이터셋 | 레코드와 부분집합의 표현, 프로파일링 표본 추출과 평가 부하 재생에서의 사용 |

## 6. U2 전력모드 평가 커버리지

- `PC-01` 평가 대상은 Node 식별자·선언된 전력모드·모델·실행 방식·자원 할당·배치의 조합으로 열거해야 한다. 선언된 모드와 실제 평가할 모드를 구분하고, 미평가 조합의 제외 사유를 제공해야 한다.
- `PC-02` 평가할 조합에는 실행 프로파일, dispatch occupancy d, 준비·제거 비용, 유휴 기준, 모드 간 전환 비용의 다섯 근거를 연결해야 한다. 각 근거는 정확한 조건과 원시 결과 식별자 및 수용 상태를 제공해야 하며, 전환은 시작·목표 모드와 방향을 식별해야 한다. 노드·모드 공통 근거는 해당 적용 범위를 명시해 연결할 수 있지만, 다른 모드나 실행 이미지의 값을 묵시적으로 대체해서는 안 된다.
- `PC-03` 평가 시작 전 커버리지 표에서 보유·누락·구규칙 재인증 대기·거절·미확인을 구분해야 한다. 선언만 된 모드, 부적격 자원, 실패한 측정과 빈 조회 결과를 용량 0 또는 수용된 근거로 처리해서는 안 된다.

| 수용 시나리오 | 확인 결과 | 요구사항 |
|---|---|---|
| Jetson 3대의 두 모드와 세 모델을 평가 대상으로 선택 | Node×모드×모델×실행 방식×자원 할당×배치별 행이 있으며 다섯 근거와 원시 식별자, 모드 쌍 양방향 비용을 추적할 수 있음 | PC-01, PC-02 |
| 추가 모드에 실행 프로파일 또는 새 규칙 d 누락 | 해당 칸을 누락/재인증 대기로 표시하고 평가 적격으로 세지 않음; 다른 모드의 수치나 0으로 대체하지 않음 | PC-02, PC-03 |
| 모든 선택 조합의 근거 수용과 계획기 연결 확인 | 해당 측정 계약의 Accepted/Complete 및 admission 수용을 확인하고 실제 계획기 입력의 profile/d/cost/baseline 참조가 표와 일치함; 거절 행은 원인과 함께 별도 보고 | PC-02, PC-03 |

구현 설계·측정 순서는 [전력모드 커버리지 계획](../../plans/2026-10-27-power-mode-coverage.md)을 따른다.

## 7. U4 같은 기종 프로파일 재사용

- `PR-01` 원본과 대상은 같은 DeviceClass(기종), 모델·전처리 산출물·데이터셋, 내용 고정 실행 이미지, 실행 경로·runtime 설정, 전력모드와 자원 할당·격리·스레드 조건이어야 한다. 다른 계열, quota만 같은 다른 격리 조건, 확인하지 않은 배치의 재사용은 거절해야 한다.
- `PR-02` 대상 Node는 원본의 재사용할 모든 배치에서 짧은 활성 측정과 모델 로드 유휴 측정을 수행해야 한다. 원본을 분모로 한 `abs(대상−원본)/원본`을 배치별 평균 서비스 시간·활성 노드 벽전력과 유휴 벽전력에 각각 적용하고, 모두 설정된 허용 차이 이하일 때만 수락해야 한다. 분모가 0이거나 필수 관측이 없으면 거절해야 한다. 권고 허용 차이는 0.05(5%): 계획 여유 25%의 1/5로 초기 동등성 screening에 사용하며 SLO·전력 오차의 통계적 상한으로 해석하지 않는다. 값은 (0,1) 안의 설정값이고 5%를 고정 검증하지 않는다.
- `PR-03` 원본·확인 측정의 UID와 불변 결과 참조, 대상 Node UID·GPU UUID·전력계, 확인 창·반복 수, 허용 차이와 실제 차이·수락/거절 사유를 조회·재현할 수 있어야 한다. 권고 확인 창은 활성·유휴 각각 30초 이상, trial 3개 이상이고 원본의 warmup·settling·관측 품질 조건은 유지한다. 확인 원시 기록을 원본 분포에 합치거나 원본을 덮어쓰지 않는다.
- `PR-04` 수락한 재사용 행은 대상 Node의 실행·계획 후보가 되어야 한다. GPU UUID 등 물리 개체 고유값과 유휴 기준은 대상 확인 측정의 값을 쓰고, 메모리는 원본·대상 관측 최대 중 큰 값으로 보수적으로 배정하며 서비스 분포·증분 에너지는 원본에서 가져온다. 거절·원본 삭제/무효화·조건 불일치이면 해당 재사용 행을 제공하지 않고 대상의 독립 측정을 요구해야 한다. d, 준비·제거·모드 전환 비용은 자동 공유하지 않는다.

| 수용 시나리오 | 확인 결과 | 요구사항 |
|---|---|---|
| genesis2와 genesis3의 같은 조건, 모든 확인 차이 4% | genesis3 UID·GPU UUID·meter의 행이 catalog와 planner option에 연결되고 원본/확인 근거와 실제 차이가 조회됨 | PR-01..04 |
| 상대 차이 정확히 5%, 설정 5% | 수락; 설정 3%에서는 거절 | PR-02 |
| 이미지·기종·CPU affinity 불일치 또는 확인 배치/벽전력 누락 | 거절 사유를 제공하고 재사용 행 없음, 독립 측정 요구 | PR-01..04 |
| 5% 초과, 원본 미존재·무효화·다른 재사용 행을 원본으로 지정 | 거절 및 근거 보존, 전이적/계열 간 일반화 없음 | PR-01..04 |
| 대상 GPU UUID만 원본과 다름 | 대상의 실측 UUID로 준비·실물 검증하고 원본 UUID를 target 자원에 사용하지 않음 | PR-03..04 |

저장·판정과 genesis2→genesis3 운영 절차는 [측정 API §11](../../design/serving/measurement-api.md#11-같은-기종-node-프로파일-재사용--pr-0104)에 정의한다.

## 8. 측정 정책의 선택과 동결

- `PC-04` 측정 길이 수용 오차·신뢰수준·최소 trial·occupancy 실험 하한/seed처럼 결과와 수용을 바꾸는 값은 기존 측정 CR spec으로 선택한다. 기본값은 현재값으로 유지하고 선택값과 출처를 불변 Run/attempt 입력 및 집계 결과에 연결한다. 부모의 나중 설정 변경으로 진행 중 실행을 재정의하지 않는다.
- `PC-05` 이미 있는 minimumRuns·trialsPerBatch·acceptedCountTarget은 재사용한다. 설정 밖의 추가 floor를 숨겨 강제하지 않으며 통계 primitive의 실제 지원 정의역 밖에서는 명시 오류를 낸다. 값 하나만 받는 새 정책 필드와 조용한 근사는 금지한다.
- `PC-06` E5 하네스 정책은 실험 config가 소유한다. bind에서 실제 적용 기본값을 모두 채운 config·출처·scheduler 설정·schedule/seed를 binding에 기록하고 실행·분석은 그 binding을 사용한다. 같은 실험의 완결 binding은 수정하지 않고 새 선택은 새 binding으로 만든다. serving API로 하네스 정책을 바꾸지 않는다.
- `PR-05` 재사용 확인의 최소 active/idle 창과 trial 수는 SCH-71의 settings로 선택한다. 확인 기록은 선택 당시 최소값과 실제 측정량을 함께 제공하며 기존 상대 차이·조건 일치 검사는 유지한다.

| 수용 시나리오 | 확인 결과 | 요구사항 |
|---|---|---|
| 기본 측정 정책: tolerance0.5s/CI0.95/min3/전이target5/occupancy60s·1.2·seed0 | 현재 수용 결과 유지, CR→불변 실행 입력→집계가 같은 실제값·출처를 가짐 | PC-04, PC-05 |
| 유효한 다른 tolerance/CI/minimumRuns/target/seed와 경계 밖 입력 | 유효값은 실제 측정·수용에 쓰고 잘못된 범위·관계는 경계에서 거절, hidden floor나 단일값 gate 없음 | PC-04, PC-05 |
| bind 후 환경 config를 변경하고 실행/분석 | 선택값은 기존 binding 그대로이며 실행 중 config 재조회로 바뀌지 않음; 새 bind만 새 조건을 선택 | PC-06 |
| 기본 E5 config와 기본값 생략 config를 bind | effective config에 모든 기본값이 있고 schedule·offered수·수용 결과 의미 동일, 바이트/hash 비교 관문 없음 | PC-06 |
| 재사용 확인 최소 창/trials를 유효한 다른 값으로 변경 | 선택값과 실제값으로 수락/거절, 원본/대상 증거·차이·조건 검사는 그대로 | PR-05 |
