# 데이터셋과 전처리 관리 SRS

## 1. 목적과 범위

이 문서는 CHILL 워크로드가 참조하는 전처리와 데이터셋의 등록, 조회, 수정, 삭제와
참조 관계를 정의한다. [시스템 명세](../README.md)의 워크로드 정의에서 전처리 참조와
데이터셋 참조가 가리키는 대상을 구체화한다.

요구사항 ID의 `DP`는 데이터셋과 전처리를 뜻한다. 각 요구사항은 구현과 검증의 기준이다.
이 문서의 정보 이름은 외부에서 관찰할 의미를 나타내며, 리소스와 API 표현은 구현 설계에서 정한다.

| 관련 영역 | 책임과 원본 |
|---|---|
| 모델 등록 | 모델 산출물과 실행 경로는 [모델 경계 ADR](../../adr/0012-model-artifact-compatibility-boundary.md)을 따름 |
| 워크로드 참조 | 참조 검증, 원시 표본 접수 검증, 모델 변경 절차와 요청 기록은 [워크로드 관리 SRS](../workloads/SRS.md)를 따름 |
| 프로파일 | 데이터셋 표본을 사용한 측정과 측정 조건은 [프로파일링과 Evidence](../00_measurement.md)를 따름 |
| 요청 실행 | 실행 배치의 전처리, 추론, 후처리 순서는 [라우팅과 배칭](../03_routing.md)을 따름 |

## 2. 사용자와 관리 정보

### 2.1 역할

| 역할 | 동작 |
|---|---|
| 운영자 | 전처리와 데이터셋을 등록, 수정, 삭제하고 워크로드에서 참조 |
| CHILL | 선언 검증, 참조 보호, 실행 준비 시 전처리 코드 제공, 변경 적용 |

### 2.2 정의 정보

| 정보 | 소유와 의미 |
|---|---|
| 전처리 식별자 | 워크로드가 참조할 전처리 이름. 전처리 식별 범위에서 유일 |
| 원시 입력 계약 | 표본 1개를 구성하는 필드별 이름, 자료형, 크기 상한과 내용 형식. 자료형은 원시 바이트, 내용 형식은 이미지 형식이나 UTF-8 텍스트 |
| 원시 출력 계약 | 요청자가 응답으로 받는 필드별 이름, 자료형과 의미 |
| 전처리 산출물 | 대상 모델과 모델 산출물, 내용이 고정된 코드의 위치와 장비 아키텍처 |
| 데이터셋 식별자 | 워크로드가 참조할 데이터셋 이름. 데이터셋 식별 범위에서 유일 |
| 데이터셋 표본 | 내용이 고정된 위치에 보관한 원시 표본 모음과 그 레코드 필드 선언 |
| 표본 부분집합 | 프로파일링에 사용할 프로파일링 부분집합과 평가 부하에 사용할 평가 부하 부분집합 |

## 3. 요구사항

### 3.1 전처리

#### 전처리 필수 입력과 출력 계약
전처리는 식별자, 원시 입력 계약, 원시 출력 계약과 하나 이상의 전처리 산출물을 필수 정보로 가져야 한다. 원시 입력 계약은 표본 1개를 구성하는 모든 필드를 선언해야 한다.
#### 모델 산출물별 전처리 유일성
전처리 산출물은 대상 모델과 그 모델의 산출물 하나를 지정해야 한다. 한 전처리에서 대상 모델 산출물마다 전처리 산출물은 정확히 하나여야 한다.
#### 전처리 코드 제공과 적재 실패
전처리 산출물의 코드는 내용이 고정된 위치와 장비 아키텍처로 식별해야 한다. CHILL은 실행 준비 시 이 코드를 대상 모델 산출물과 함께 실행 위치에 제공해야 한다. 코드가 사용하는 라이브러리는 대상 모델 산출물을 실행하는 runtime 환경이 제공해야 하며, 코드 적재 실패는 해당 인스턴스의 실행 준비 오류와 원인으로 드러내야 한다.
#### 배치 전처리와 요청별 후처리
전처리 코드는 한 실행 배치의 원시 표본들을 모델 입력으로 바꾸고, 추론 결과를 요청별로 원시 출력 계약의 응답으로 바꿔야 한다.
#### 요청별 단위 수와 보고 검증
전처리 코드는 배치의 요청마다 성공 결과와 [단위 수](../00_measurement.md#측정의-단위) 또는 실패 사유를 보고해야 한다. 보고 수가 배치의 요청 수와 다르거나 성공 요청의 단위 수가 1보다 작으면 CHILL은 해당 배치를 오류로 처리해야 한다.

### 3.2 데이터셋

#### 데이터셋과 표본 부분집합
데이터셋은 식별자, 내용이 고정된 표본 위치, 레코드 필드 선언, 프로파일링 부분집합과 평가 부하 부분집합을 필수 정보로 가져야 한다. 두 부분집합은 서로 다른 표본으로 구성해야 한다.
#### 데이터셋과 전처리 호환성
데이터셋과 전처리의 호환성은 데이터셋의 레코드 필드 선언과 전처리의 원시 입력 계약을 비교해 판단해야 한다. 원시 입력 계약의 모든 필드가 같은 이름과 자료형으로 레코드 필드에 선언되고, 각 레코드 필드의 크기 상한과 내용 형식이 계약 범위 안에 있으면 호환이다. 판단에는 두 선언만 사용해야 한다.

### 3.3 등록, 조회, 수정, 삭제

#### 전처리와 데이터셋 CRUD
운영자는 전처리와 데이터셋을 등록, 목록 조회, 상세 조회, 수정, 삭제할 수 있어야 한다. 관리 변경 권한은 [관리 변경 권한](../workloads/SRS.md#관리-변경-권한)을 따라야 한다. 미등록 식별자의 조회는 조회 오류로 제공해야 한다.
#### 카탈로그 등록과 수정 검증
등록과 수정 시 식별자 중복, [전처리 필수 입력과 출력 계약](#전처리-필수-입력과-출력-계약)과 [모델 산출물별 전처리 유일성](#모델-산출물별-전처리-유일성)의 조건, [데이터셋과 표본 부분집합](#데이터셋과-표본-부분집합)의 필수 정보, 전처리 산출물이 지정한 모델 산출물의 존재와 삭제 진행 여부를 검증해야 한다. 검증 오류와 거부된 변경의 처리는 [등록과 수정 검증](../workloads/SRS.md#등록과-수정-검증)을 따라야 한다.
#### 전처리와 데이터셋 수정 적용
워크로드가 참조하는 전처리를 수정하면 영향을 받는 워크로드에 [모델 변경 절차](../workloads/SRS.md#43-모델-수정)를 적용해야 한다. 데이터셋 수정은 이후 요청하는 측정부터 적용해야 한다. 이 수정은 해당 워크로드들이 함께 참조하는 데이터셋과 전처리가 [데이터셋과 전처리 호환성](#데이터셋과-전처리-호환성)의 호환성을 유지할 때 수락해야 한다.

### 3.4 참조 보호

#### 워크로드 참조 카탈로그 삭제 보호
워크로드가 참조하는 전처리와 데이터셋의 삭제는 [참조 중인 모델 삭제 보호](../workloads/SRS.md#참조-중인-모델-삭제-보호)의 모델 참조와 같은 방식으로 거부해야 한다.
#### 전처리 대상 모델 산출물 보호
전처리 산출물이 대상으로 지정한 모델 산출물을 제거하는 모델 수정과 해당 모델의 삭제는 참조하는 전처리를 이유로 제공하며 거부해야 한다.

## 5. 구현 설계로 연결할 사항

구체적인 리소스와 API, 코드 전달 방식은
[이기종 워크로드 구현 설계](../../design/serving/heterogeneous-workloads.md)에 정리한다.

| 영역 | 구체화할 구현 |
|---|---|
| 리소스 | 전처리와 데이터셋의 리소스 표현, 객체 범위와 필드, 내용이 고정된 위치의 표현 |
| API | 관리 경로, 변경 전제조건과 오류 응답 |
| 코드 실행 | 코드 전달과 적재 위치, runtime 환경의 라이브러리 제공, 배치 입력과 응답 및 단위 수의 전달 형식 |
| 데이터셋 | 레코드와 부분집합의 표현, 프로파일링 표본 추출과 평가 부하 재생에서의 사용 |

## 6. 전력모드 측정 범위 전력모드 평가 커버리지

#### 전력모드 평가 조합 열거
평가 대상은 Node 식별자와 선언된 전력모드, 모델과 실행 방식과 자원 할당과 배치의 조합으로 열거해야 한다. 선언된 모드와 실제 평가할 모드를 구분하고, 미평가 조합의 제외 사유를 제공해야 한다.
#### 평가 조합의 다섯 측정 근거
평가할 조합에는 실행 프로파일과 d, 준비와 제거 비용, 유휴 기준 및 모드 간 전환 비용의 입력을 연결해야 한다. 실행 프로파일은 실측 근거를 사용하며 점유와 동작 비용 및 유휴 기본값을 선택하면 실측과 구별해 값과 출처를 제공해야 한다. 각 근거는 정확한 조건과 원시 결과 식별자 및 수용 상태를 제공해야 하며, 전환은 시작과 목표 모드와 방향을 식별해야 한다. 노드와 모드 공통 근거는 해당 적용 범위를 명시해 연결할 수 있지만, 다른 모드나 실행 이미지의 값을 묵시적으로 대체해서는 안 된다.
#### 측정 커버리지 확보 상태
평가 시작 전 커버리지 표에서 보유, 누락과 구규칙 재인증 대기, 거절과 미확인을 구분해야 한다. 선언만 된 모드, 부적격 자원, 실패한 측정과 빈 조회 결과를 용량 0 또는 수용된 근거로 처리해서는 안 된다.

| 수용 시나리오 | 확인 결과 | 요구사항 |
|---|---|---|

## 7. 측정 정책의 선택과 동결

#### 측정 길이 오차와 신뢰수준
길이 오차는 ProfilingRun.spec.measurement.durationToleranceSeconds(현재0.5초, finite ≥0와 duration 미만)로 독립 idle protocol에서 전달한다. BEO.spec.session.confidenceLevel은 [0.5, 1) 십진 문자열이고 세션 계산의 모든 통계 판단이 같은 선택값을 쓴다. 독립 idle CR의 기존 CI 소유권은 유지한다. Profile.ConfidenceLevel과 CI 메시지도 실제값이다. 기존 immutable spec와 실행/결과 참조를 재사용하고 중복 snapshot은 없다.
#### 측정 반복과 공급 정책
독립 idle은 pointPolicy.minimumRuns ≥2와 attemptLimit 2~100을 사용하고 attemptLimit≥minimumRuns를 지킨다. 전이는 acceptedCountTarget≥2, attemptLimit≥2와 attemptLimit≥acceptedCountTarget을 지킨다. 점유 측정은 선택한 worker 수, 예열, 측정 길이, 최소 배치 쌍 수, 요청 수명, 전달 여유, 실행 상한과 seed를 동결한 closed-loop 공급을 사용한다.
#### 실험 정책 선택과 동결
실험은 EvaluationRun과 독립 실행 주체를 사용한다. 부모 prepare에서 선택한 부하 정의, 워크로드 적용 정의와 운영 정책을 한 번 동결하고 단계는 그 snapshot을 사용한다. 실행 중 설정 재조회로 조건을 바꾸지 않는다. 장애 주입은 선언한 계획과 공개 Kubernetes API를 사용한다.

| 수용 시나리오 | 확인 결과 | 요구사항 |
|---|---|---|
| 기본 측정 정책: 오차 0.5초와 전이 목표 5회 | 현재 수용 결과 유지, CR→불변 실행 입력→집계가 같은 실제값과 출처를 가짐 | [측정 길이 오차와 신뢰수준](#측정-길이-오차와-신뢰수준), [측정 반복과 공급 정책](#측정-반복과-공급-정책) |

## 8. 측정 커버리지 조회 API

화면 요구는 [Dashboard SRS](../dashboard/SRS.md) [측정 범위와 조합 진행](../dashboard/SRS.md#측정-범위와-조합-진행), [서버 측정 상태와 품질 표시](../dashboard/SRS.md#서버-측정-상태와-품질-표시), [서버 집계 커버리지 조회](../dashboard/SRS.md#서버-집계-커버리지-조회), [정확 조건 목록과 회차 연결](../dashboard/SRS.md#정확-조건-목록과-회차-연결), [측정 요청 편집과 점검](../dashboard/SRS.md#측정-요청-편집과-점검), [측정 결과의 수치와 품질](../dashboard/SRS.md#측정-결과의-수치와-품질), [실패 회차의 원인과 후속 조치](../dashboard/SRS.md#실패-회차의-원인과-후속-조치), [점유시간과 변경 비용 표시](../dashboard/SRS.md#점유시간과-변경-비용-표시), [실험 대응 관계와 차이 해석](../dashboard/SRS.md#실험-대응-관계와-차이-해석), [선택 서비스와 공통 부하 추세](../dashboard/SRS.md#선택-서비스와-공통-부하-추세)를 유지하며,
아래 요구는 그 화면이 소비할 서버/게시자 사실의 소유권을 정한다.

#### 정적 실행 호환성과 출처
모델 실행 경로×DeviceClass×구체 Node의 현재 trusted runtime 선언에 근거한 정적
  호환성, 입력 UID/resourceVersion와 출처, 판정 사유를 읽기 전용 API로 제공해야 한다.
  Compatible/Incompatible/Unknown을 구분하고 누락과 모호한 선언이나 조회 실패를 미지원으로
  바꾸지 않아야 한다. 같은 기종이라는 이유로 Node-bound 선언을 모든 Node로 확대하지 않는다.
  전처리/데이터셋과 모드/CPU admission, 현재 준비 상태와 측정 완료는 각각 별도로 확인해야 한다.
#### 배치별 입력당 에너지
프로파일의 배치 크기별 입력당 줄(J/input)과 구성별 유휴 전력, 깨어 있는 전력 증가, 유지 시간을 각 값의 식별 여부와 식별하지 못한 사유, 값이 움직이는 범위와 함께 제공해야 한다. 식별하지 못한 값을 0이나 다른 값으로 채우지 않는다. 입력당 줄을 식별하지 못한 배치 크기는 서빙에 제공하지 않는 배치 크기로 구분한다. 저장된 세션 결과를 수정하거나 현재 catalog 값으로 바꾸지 않는다.
#### 처리 시간 분위수
배치 크기별 처리 시간 기록 중 질의한 직전 유휴 간격에 가장 가까운 N개의 경험적 분위수를 제공해야 한다. N은 백분위의 표본 하한이다. 기록이 N개보다 적으면 측정 없음으로 구분하고 0으로 만들지 않는다. 원근거 부재와 읽기 오류와 무효 근거를 구분한다.
#### 동작 단계의 실제 시간과 에너지
OperationCostMeasurement list/detail은 CR이 가리킨 정확 단계의 실제 operation identity,
  실제 시간(ns), 전체 Node 벽에너지(J)와 원 판정과 사유와 출처를 제공해야 한다.
  수용된 0과 미관측/null, 실패 단계의 실제 시간과 에너지 수용을 구별하고 계획 idle 시간과 최신 다른
  operation의 값으로 채우지 않는다. 개별 단계 수용과 전체 순서 성공을 구별한다.
#### 실험 예정 부하와 시간 출처
실험 게시자는 기록된 frozen schedule에서 workload별 α(무차원)와 예정 substage offset,
  기록된 해당 producer 시작에 고정한 시각과 출처를 게시해야 한다. 두 기존 publisher shape에 같은
  metadata 의미를 적용한다. 직접 rate만 설정한 실험/미기록 α는 null이며 offered/기간과 stage ID로
  역산하지 않는다. 예정 구간과 실제 관측 사건을 구분하고 0부하의 시작 anchor 부재를 보존한다.
#### 기록 당시 워크로드 정의 투영
실험 게시자는 KPI 모집단의 기록 당시 workload UID와 definition identity와 그 출처를
  보존된 binding/definition/snapshot에서 투영해야 한다. 혼합/미기록 identity는 미확인 사유를 남기며
  현재 같은 이름의 Workload로 채우지 않는다. 기존 publication/관측 archive는 소급 수정과 재게시하지 않는다.
  실행 결과와 게시자 소유권은 [실험 관리 SRS](../experiments/SRS.md)가 정본이다. [실험 예정 부하와 시간 출처](#실험-예정-부하와-시간-출처), [기록 당시 워크로드 정의 투영](#기록-당시-워크로드-정의-투영)의 게시 정보 의미는 유지한다.

| 수용 시나리오 | 확인 결과 | 요구사항 |
|---|---|---|
| trusted runtime 충돌, 누락과 중복, 같은 class의 Node-bound GPU | 명시 충돌만 미지원, 부재/모호함은 Unknown; 정확 Node 출처와 조회 오류 유지, POST/preflight는 여전히 별도 | [정적 실행 호환성과 출처](#정적-실행-호환성과-출처) |
