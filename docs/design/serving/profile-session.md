## 문제 정의

프로파일은 스케줄러의 입력이다. 스케줄러가 한 구성(장치, 전력 모드, 모델, 실행 경로)에 대해 묻는 것은 넷이다.

| 질문 | 프로파일의 내용 |
|---|---|
| 이 부하에서 지연 목표를 지키는가 | 배치 크기별 처리 시간과 직전 유휴 간격의 짝, 배치 사이 점유 시간 |
| 이 부하에서 노드가 전력을 얼마나 쓰는가 | 부하에 대한 노드 전력 |
| 노드에 올라가는가 | 메모리 최댓값 |
| 옮길 가치가 있는가 | 준비, 제거, 전력 모드 변경의 시간과 에너지 |

배포 `958b26c7`의 측정은 이 내용을 내지 못했다. 원인은 셋이다.

1. 측정이 서빙과 별개의 장치다. 전용 Pod, 전용 부하 Job과 제어 프로토콜, Python 측정 서버, 결과 형식 넷, 크기 예산, 검증기 셋, Pod 주소 직접 접속으로 이루어진다. Core 실패 27건이 모두 이 장치 안에서 났다. 서빙은 인스턴스 준비와 제거, Service 전달, 배치별 처리 시간과 유휴 간격 기록, 노드 전력 기록, 컨테이너 메모리 최댓값 기록을 이미 한다.
2. 에너지 모델이 실제 전력과 다르다. 프로파일은 `유휴 전력 + 요청당 에너지 × 요청률`을 담는다. genesis2 영상 분류 CUDA의 실측은 유휴 66.1W, 초당 33건 127.5W, 100건 145.3W, 포화 133건 154.2W다. 요청이 들어오면 전력이 한 번 오르고 그 뒤로 완만히 오른다. 현재 모델의 오차는 GPU 서버에서 최대 54~64W다.
3. 측정 시간이 내용과 무관하다. 한 조건이 배치 1~8에 2.6시간 걸렸다. 단계 길이가 고정이고 배치와 시도마다 모든 단계를 반복한다.

같이 드러난 스케줄러 쪽 결함: 처리 시간 분위수 계산이 유휴 간격이 나노초까지 같은 기록끼리 묶는다(`internal/firstfloor/service_distribution.go`). 묶음 하나에 기록이 1.0~1.25개라 분위수가 기록 서너 개의 최댓값이 되고, 표본을 늘려도 수렴하지 않는다.

## 원칙

- 프로파일은 통제된 부하를 준 서빙 관측이다. 측정은 서빙과 같은 준비 동작, 같은 전달 경로, 같은 기록을 쓴다.
- 프로파일에는 스케줄러가 읽는 값과 그 값을 다시 계산할 수 있는 관측만 담는다.
- 단계는 필요한 표본이 차면 끝난다.
- 한계에 닿아 멈추는 것은 정상 종료다. 실패는 원래 오류 문장을 그대로 싣는다.
- 한도를 올려 통과시키지 않는다. 보정 계수, 대체 경로, 조용한 근사를 두지 않는다.
- 저장 형식은 한 번 바꾼다. 이전 형식 객체는 읽지 않고 지운다.
- 평가는 CHILL 밖에서 한다.

## 프로파일의 내용

### 처리 시간

배치 크기마다 `(처리 시간, 직전 유휴 간격)` 기록의 목록이다. 기록은 서빙 실행기가 배치마다 남기는 값 그대로다.

스케줄러의 조건부 분위수는 질의한 유휴 간격에 가장 가까운 기록 N개의 경험적 분위수다. 거리는 유휴 간격의 로그로 잰다. N은 질의한 분위수 p가 정하는 최소 표본 수(`ceil(ln(1−p)/ln(p))`, 95분위는 59)다. 분위수 100은 받지 않는다. 세션은 `activeProtocol.workload`의 분위수로 N을 정해 수준이 끝나는 표본 수로 쓴다. 기록이 N개보다 적은 배치 크기는 측정 없음으로 다룬다. 간격 구간 경계 같은 새 상수를 두지 않는다. 계획기, 실행기 배치 선택, 수락 판단, 피드백과 재생이 같은 계산을 쓴다.

준비 동작은 인스턴스가 쓸 모든 배치 크기를 준비 실행한다. 서빙과 측정이 같다. 그래서 첫 실행은 따로 구분하지 않고, 직전 유휴 간격이 없는 기록은 버린다. 아직 뜨지 않은 후보도 예상 부하의 유휴 간격으로 같은 질의를 한다.

### 점유 시간

포화 구간에서 연속한 두 배치의 시작 간격에서 앞 배치의 처리 시간을 뺀 값을 배치 크기로 나눈 것이다. 기존 정의와 같다. 별도 측정 요청은 없어지고 계획기는 프로파일에서 읽는다.

### 노드 전력

네 값이다.

| 값 | 뜻 | 측정 |
|---|---|---|
| 유휴 전력 `I` | 모델을 올린 채 요청이 없고 전력이 가라앉은 상태 | 부하를 끊은 뒤 관측의 끝부분 |
| 깨어 있는 전력 증가 `S` | 요청을 처리한 직후 노드가 머무는 상태와 유휴의 차이 | 부하 수준들의 전력 |
| 유지 시간 `τ` | 마지막 실행 뒤 깨어 있는 상태가 이어지는 시간 | 부하를 끊은 뒤 전력이 내려가는 시점, 저부하 수준의 전력 |
| 요청당 에너지 `e_b` | 배치 크기 b에서 요청 하나가 더하는 에너지 | 부하 수준들의 전력 기울기 |

노드 전력 예측은 `I + S × a + e_b × λ`다. `a`는 노드가 깨어 있는 시간 비율, 곧 실행 중이거나 마지막 실행이 끝난 뒤 `τ` 안에 있는 시간의 비율이다.

값을 구할 때 `a`는 가정하지 않고 실행기 기록의 실행 시작과 종료 시각에서 수준마다 직접 계산한다. 실행기 시계의 차이만 쓴다: 수준의 첫 실행 시작에서 전력계 지연만큼 지난 시점부터 마지막 실행 종료까지다. 부하 생성기의 수준 시작과 첫 실행 시작의 차이는 관측값으로만 남긴다. 이웃한 두 꺾임점(관측된 유휴 간격과 구간 경계) 사이에서 `a`는 `τ`에 선형이므로, 구간마다 `S ≥ 0`, `e_b ≥ 0`과 `τ`가 구간 안에 있다는 조건에서 수준별 평균 전력에 비음수 최소제곱을 풀고 가장 작은 잔차를 고른다. 탐색의 분해능: 이웃한 꺾임점은 합친 구간에서 어느 수준의 `a` 변화량에 (수준 평균 전력의 최댓값 − 유휴 전력)을 곱한 값이 수준 평균 전력 표준 오차의 최솟값 이하인 동안 한 구간으로 합친다. 측정이 구분하지 못하는 만큼만 `τ`가 예측 전력을 움직이는 곳은 나누지 않는다. 푼 구간 수와 분해능(W)은 결과에 남는다. 비음수 최소제곱은 자유 열 집합을 모두 나열해 각 집합의 최소 노름 해를 SVD로 구한다. 부하 뒤 전력에서 감쇠가 보이면(`t50`에서 전력계 지연을 뺀 값이 표본 간격의 중앙값보다 크면) `τ`는 감쇠에서 읽는다. 값마다 최적 결합 해의 값과, 잔차가 잡음 한계 안인 모든 해에서 취하는 범위를 남긴다. 잡음 한계는 최적 잔차에 맞춘 값 수만큼의 자유도를 가진 카이제곱 분위수와 수준 평균 분산의 평균의 곱을 더한 것이고, 최적 잔차와 함께 결과에 남는다. 설계가 그 값을 정하지 못하거나, `τ`의 범위가 탐색한 유지 시간의 위 끝에 닿을 때만 `NotIdentified`다. 0으로 추정된 값도 범위와 함께 값으로 남는다. `NotIdentified` 값은 결과에 값이 없고 다른 값으로 채우지 않는다. 보관된 측정에서 한 세션의 값으로 다른 회차의 모든 수준을 예측한 최대 오차는 genesis2 2.7~3.1W, jetsono 0.55~1.0W, lattepanda 0.12~0.15W다.

스케줄러가 예측할 때 `a`는 노드 단위로 계산한다. 서빙 인스턴스는 대기열이 쌓일 때만 배치를 키우므로 유휴 기간은 다음 요청 하나가 올 때 끝난다. 노드의 요청률 합이 `λ`, 이용률 합이 `ρ`(1 이하)일 때 `a = 1 − (1−ρ) × exp(−λτ)`다. 깨어 있는 전력 증가는 노드에 한 번 더한다. 한 노드에 구성이 여럿이면 `S`와 `τ`는 함께, 깨어 있는 전력 증가가 가장 큰 한 구성의 값을 쓴다. 두 값은 맞춤에서 서로 맞바뀌므로 각각의 최댓값을 따로 고르지 않는다. 요청당 에너지와 이용률은 부하를 감당하는 가장 작은 측정 배치 크기의 값을 쓴다. 이 노드 단위 규칙은 여러 인스턴스가 함께 도는 시범 측정으로 확인한다.

`S`, `τ`는 구성마다 한 값이고 `e_b`는 배치 크기마다 다르다.

### 메모리

컨테이너 수명 전체의 최댓값이다. 서빙의 노드 에이전트 기록을 쓴다. 최댓값 계수기가 없는 커널에서는 같은 기록의 현재값 표본 중 최댓값이다. 모델 적재가 포함된다.

### 전환 비용

세션이 준비와 제거를 측정 동작으로 실행하므로 배치 크기마다 준비와 제거의 시간과 에너지가 하나씩 남는다. 기존 동작 비용 기록 형식과 위치를 쓴다.

## 측정 세션

한 구성에 세션 하나다. ChillServer가 실행한다. 측정 요청(BatchEnergyOptimization)의 spec은 `state`(실행 경로 후보와 대상 노드), `activeProtocol`(지연 목표와 분위수를 주는 `workload`, `warmupIterations`, `dataset`)과 필수 `session`이고 불변이다. `session`은 이 절의 설정값과 준비, 제거, 전력 모드 변경의 관측 설정(`observation`)을 담는다.

1. 측정 노드 승인. 기존 방식 그대로다.
2. 노드가 대상 전력 모드가 아니면 전력 모드를 바꾼다(측정 동작).
3. 배치 크기 1부터 2배씩, 실행 경로가 선언한 최대 배치까지:
   1. 준비(측정 동작). 서빙의 준비 동작으로 고정 배치 인스턴스를 띄운다. 프로파일은 없다.
   2. 부하. 기존 Go 부하 생성기가 ChillServer 노드에서 인스턴스의 Service 주소로 요청을 보낸다. 수준은 셋이다.
      - 포화: 동시 요청 2B개를 유지한다. 배치 하나가 실행되는 동안 다음 배치가 채워져 기다리는 상태다. 처리 시간, 점유 시간, 포화 처리율과 전력을 얻는다.
      - 중간: 포화 처리율의 설정된 비율로 Poisson 도착. 전력 곡선의 두 번째 점과 밀리초대 유휴 간격을 얻는다.
      - 저부하(배치 크기 1에서만): 요청 하나를 보내고, 끝난 뒤 지수 분포의 유휴 간격을 두고 다음을 보낸다. 긴 유휴 간격의 처리 시간과 저부하 전력을 얻는다. 서빙에서 긴 유휴 뒤의 실행은 배치 크기 1이므로 다른 배치 크기에서는 하지 않는다.
   3. 마지막으로 측정한 배치 크기에서 부하를 끊고 `postLoadWindowSeconds` 동안 전력을 관측한다. 유지 시간과 유휴 전력을 얻는다. 용량 한계 말고 다른 이유로 멈춘 배치 크기에서는 그 배치 크기가 관측하고, 용량 한계로 멈추면 마지막으로 측정한 배치 크기를 다시 준비해 관측한다.
   4. 제거(측정 동작).
4. 계산과 결과 저장. 노드 반환.

복구 차단은 ChillServer의 이전 프로세스에서 물려받은 실행기에 적용한다. 현재 프로세스가 Pod 생성 성공 응답을 받은 경우 `RecordCreatedPod`의 기존 생성 근거로 복구 차단을 제외한다. 서빙과 측정 Pod에 같은 규칙을 쓴다. 실행기의 빈 요청 목록은 모드와 관계없이 같은 물리 상태를 뜻하므로 관측 확인에 `serving` 모드를 요구하지 않는다. 서빙 라우팅의 실행 모드 검사는 별도 서빙 승인에 남는다.

준비와 제거 비용은 세션의 부산물이다. 비용 창, 격리 증거 또는 무추론 증거가 부족하면 비용 값 없이 원문 이유를 기록하고 세션을 계속한다. 준비가 실제 Ready 인스턴스를 만들지 못하면 세션이 실패한다. 비용 관측이 동작을 실행하지 못했어도 실제 준비와 제거는 실행하고 측정되지 않았음을 기록한다.

세션은 자신이 만든 정확한 Pod UID를 항상 제거한다. 자체 측정 Pod 제거는 서빙 트래픽의 복구, 정지, 분리, native drain 증명을 요구하지 않는다. Kubernetes의 실제 종료와 삭제를 확인한 다음 Service와 전력 모드를 정리하고 taint를 반환한다. 반환 자체가 실패하면 BEO의 `NodeReturned=False` 조건에 원문을 남긴다. 재시작 뒤 terminal 세션의 남은 Pod도 이 반환 경로로 정리하며, 측정의 terminal 결과는 유지한다.

수준의 종료 조건:
- 처리 시간 표본이 최소 표본 수에 닿고, 전력 관측이 설정된 최소 시간을 채우면 끝난다. 전력 관측은 수준 시작 뒤 전력계 지연 시간만큼을 버린다.
- 수준은 설정된 수준 시간 한도 안에서 돈다. 한도에 닿으면 수준이 `LevelLimitReached`로 끝나고 한도와 그때까지 모인 표본 수를 문장으로 남긴다. 포화 수준이면 그 배치 크기는 "측정하지 않음"으로 끝나고 그 앞 배치까지가 결과다. 중간과 저부하 수준이면 그 수준만 제외한다. 예상 소요 시간으로 미리 멈추지 않는다.
- 인스턴스의 실행기 기록은 Pod 로그 스트림으로 전달되고 Pod가 제거되면 스트림이 끝난다. 세션은 부하 생성기가 센 수만큼 기록이 도착할 때까지 수준 시간 한도 안에서 기다린 뒤 인스턴스를 제거한다.
- 전력계 지연, 최소 전력 관측 시간, 중간 수준의 비율, 저부하 유휴 간격의 평균, 수준 시간 한도, 부하 뒤 관측 시간, 요청 수명, 전달 여유, 요청 크기 상한, 신뢰 수준은 측정 요청의 설정이고 결과에 함께 남는다. 최소 표본 수는 `activeProtocol.workload`의 분위수에서 정해 결과에 남는다. 신뢰 수준은 [0.5, 1) 안의 값이고 계산의 모든 통계 판단이 이 값을 쓴다.
- 유휴 전력은 부하 뒤 시계열에서 감쇠가 끝난 시점(`t50`에 전력계 지연을 더한 시점)부터 관측 끝까지의 평균이다. 표준 오차는 배치 평균법(묶음 크기 `⌊√n⌋`)으로 자기상관을 반영한다. 끝나기 전 마지막 최소 전력 관측 시간 동안의 기울기는 관측값으로 남기고 판단에 쓰지 않는다. 감쇠가 끝난 시점에서 관측 끝까지 최소 전력 관측 시간이 남지 않거나 전력 표본이 모자라면 `NotIdentified`다.

수준의 요청에는 `세션/배치 크기/수준` 식별자가 실린다. 실행기 기록이 이 식별자를 그대로 남기므로 수준의 기록을 시계 없이 고른다. 읽는 구간은 세션 시작부터 읽는 시점까지이고 양쪽에 기록 읽기의 전달 여유(ChillServer에서 129초와 배수 시간의 합)를 더한다. 실행기 시계가 ChillServer 시계와 이 여유보다 적게 어긋나면 같은 기록이 골라진다. 실행기는 단계마다 진행 기록을 한 줄씩 남기므로 기록은 요청 식별자로 먼저 합친 뒤 배치로 묶는다. 부하 생성기가 센 배치 수와 기록의 배치 수가 다르면 그 수준은 "native rows n of m"으로 제외된다.

배치 크기 탐색의 종료:
- 준비가 메모리 부족으로 실패하거나, 포화의 두 배치가 실행기 큐 한도를 넘거나, 그 배치 크기의 실행이 한 번도 끝나지 못한 채 메모리 할당 실패가 나면 용량 한계다. 그 앞 배치까지가 결과다.
- 포화 수준의 첫 배치에서 배치 둘의 처리 시간이 요청 수명을 넘으면 그 배치 크기는 서빙할 수 없다. 그 앞 배치까지가 결과다.
- 배치 크기 1에서 한계에 닿으면 세션은 한계 종류와 원문 문장으로 `Failed`가 된다. 프로파일은 공개되지 않는다.
- 중간과 저부하 수준의 요청 수명 만료, 실행기 기록 개수가 맞지 않는 수준, 전력 창이 짧은 수준은 그 수준만 제외한다. 메모리 기록을 읽지 못한 배치 크기는 메모리 없이 남고 서빙에 제공되지 않는다. 구하지 못한 전력 값은 `NotIdentified`로 남는다. 포화 수준이 유효한 배치 크기가 하나도 없으면 세션이 실패하고, 실패는 각 포화 수준의 원래 문장을 싣는다.
- 준비 실패와 부하 Job 실패는 세션 실패다. 실패한 동작의 오류 문장 첫 줄, 부하 Job의 종료 메시지, Pod 실패 사유가 측정 상태에 그대로 실린다.

배치 크기마다 인스턴스를 새로 준비한다. 실행기는 고정 배치의 제자리 변경을 받지 않는다.

## 구성 요소와 바뀌는 지점

| 지점 | 변경 |
|---|---|

| 메모리 기록 대상 선택(`cmd/chill-server/resources.go`) | 세션 인스턴스도 대상이다. 인스턴스는 세션이 공개할 프로파일의 이름을 표식으로 단다. |
| 부하 생성기(`cmd/chill-server/session_load.go`) | Service 주소로 보낸다. 수준과 종료 조건을 위 정의대로 한다. 수준별 시작과 종료 시각, 보낸 수와 끝난 배치 수를 종료 메시지로 낸다. |
| 세션 실행(`internal/serving/kube`) | 측정 요청을 ChillServer가 실행한다. |
| 기록 읽기(`internal/serving/observation`) | 세션 인스턴스의 실행기 기록을 구간으로 읽는 기존 읽기를 쓴다. 메모리 기록 읽기를 더한다. 로그 재연결로 생긴 중복 기록은 요청 식별자로 한 번만 센다. |
| 계산(`internal/profiling/derivation`) | 처리 시간 목록, 점유 시간, 전력 네 값, 메모리를 서빙 기록에서 계산한다. |
| 저장 결과 | 측정 결과 객체 하나. 새 형식. |
| 카탈로그(`internal/serving/kube/catalog.go`) | 새 결과 객체 하나를 읽는다. |
| 프로파일 형식(`internal/serving/types.go`) | 유휴 전력, 깨어 있는 전력 증가, 유지 시간, 값마다의 표시, 점유 시간을 담는다. 배치별 요청당 에너지는 기울기이고 필드 이름을 바꿔 이전 뜻으로 읽는 곳이 컴파일에서 드러나게 한다. |
| 에너지 계산(`internal/serving/scheduler_capacity_*.go`, `scheduler_state.go`) | 노드 단위로 위 전력 식을 쓴다. 탐색의 이동별 평가도 같은 식을 쓴다. |
| 분위수 계산(`internal/firstfloor/service_distribution.go`) | 가장 가까운 유휴 간격 기록 N개의 경험적 분위수. 소비자 다섯 곳이 함께 바뀐다. |
| 준비 실행(`internal/firstfloor`, 준비 동작) | 인스턴스가 쓸 모든 배치 크기를 준비 실행한다. |
| 같은 기종 재사용 확인 | 없다. 세션이 몇 분이므로 노드마다 잰다. |
| 조회와 대시보드 | 측정 결과와 측정 범위가 새 결과 객체를 읽는다. 회차 목록은 없어진다. |

## 저장 결과

`batch-energy-optimizations/<UID>/result.json`, 새 형식 버전 하나.

- 조건: 장치, 전력 모드, 모델과 전처리 산출물, 실행 경로, 실행 이미지, 실행기 설정, 전달 정보.
- 측정 설정: 위 설정값 전부.
- 전력: 유휴 전력, 깨어 있는 전력 증가, 유지 시간, 부하 뒤 전력 시계열.
- 배치별: 배치 크기, 처리 시간과 유휴 간격 기록, 점유 시간 표본, 요청당 에너지, 메모리 최댓값, 수준별 요청률과 평균 전력과 표본 수와 시각.
- 종료: 멈춘 배치 크기와 사유 문장.
- 전환 비용 기록의 위치.

오프라인 평가 도구(`hack/evaluation`)는 이 객체와 서빙 관측 조회를 읽도록 같은 변경에서 고친다.

이전 형식의 측정 결과, 실행 단위 증거와 프로파일은 읽지 않는다. 운영 세션이 제품 삭제로 지운다.

## 남은 옛 장치

측정 요청 제어기와 BEO의 시도 수, 재시도, 점 정책, 유휴 프로토콜, 운영점, 지표 관측 필드는 없다. ProfilingRun 실행 경로(프로파일러 제어기, 측정 작업자 Pod와 지표 관측과 작업 관측 보조 컨테이너, Python 측정 서버)는 전력 모드 전환 비용이 읽는 모델 적재 유휴 기준선(ModelLoadedIdleBaseline) 측정에만 남는다. 이 경로의 정리와 전환 비용 측정의 세션 통합이 남은 작업이다.

## 수용 기준

### 배포 전 코드

- 보관된 실측 한 시도로 구한 전력 값이 같은 조건의 다른 시도들의 수준별 전력을 예측한다(genesis2 영상 분류 CUDA, jetsono, lattepanda). 오차를 수치로 남긴다.
- 같은 기록에서 가장 가까운 N개 분위수가 표본을 늘릴 때 수렴한다.
- 측정 계획 점검(`hack/`): 계획한 구성마다 알려진 처리율로 수준별 예상 시간, 기록 수, 요청 수명 종료, 최소 표본 수 충족을 계산한다. 제품 밖 도구다.
- 세션 실행이 가짜 동작과 가짜 기록으로 끝까지 가고, 용량 한계, 서빙 불가, 실패의 세 종료가 구분된다.
- 프로파일 없는 고정 배치 준비 요청이 Pod를 만들고 실행기 준비 완료로 끝난다(envtest).
- 저장소 게이트 전부 통과.

### 운영 시범 측정

운영 세션이 수행한다. 조건을 넓히기 전에 장치 등급마다 하나씩 한다. 첫 실측은 genesis2의 CUDA 한 조건에서 마쳤다.

- genesis2 영상 분류 CUDA, jetson-nano PLC CUDA, jetsono PLC CPU, orin-nano 한 조건, lattepanda 영상 분류 CPU, SmolVLM 한 조건.
- 확인: 세션이 끝난다. 수동 경로 없이 진행된다. 부하 생성기가 센 배치 수와 서빙 기록의 배치 수가 같다(가장 빠른 모델 포함). 세션 시간.
- 한 노드에 인스턴스 둘을 함께 서빙해 노드 전력을 전력 식의 예측과 비교한다.
- 공개된 프로파일로 서빙한 구간의 노드 전력을 예측과 비교한다.
- 공개된 프로파일로 같은 고정 배치의 서빙 인스턴스를 준비해 처리 시간 분위수와 준비 비용을 세션 값과 비교한다(오프라인).
- 판단 시간: 공개된 프로파일을 읽은 스케줄러의 판단 소요.

합격 수치를 두지 않는다. 남은 실패는 원문 오류 문장으로 분류한다.

## 데이터가 뒷받침하지 못하는 것

- SmolVLM은 완료된 부하 측정이 없다. 느린 모델의 수준 시간 상한은 시범 측정으로 정한다.
- 전력계는 1초 간격이고 2~3초 늦다. 3초보다 짧은 유지 시간은 부하 뒤 관측으로 읽을 수 없고 저부하 수준의 전력으로만 정해진다.
- CPU 경로에서는 깨어 있는 전력 증가와 요청당 기울기가 서로 덜 분리된다.
- 배치 16 이상, 메모리 한계 종료, 한 노드의 여러 인스턴스, 실제 서빙 트래픽에서의 전력 식은 확인하지 않았다.

## 기록 수와 메모리

처리 시간 기록은 배치 실행마다 하나다. 수준은 최소 표본 수와 최소 전력 관측 시간을 모두 채우면 끝나므로, 빠른 모델의 수준 길이는 전력계 지연과 최소 전력 관측 시간의 합이다. 초당 690건을 처리하는 모델이 기본 설정(전력계 지연 3초, 최소 전력 관측 15초)으로 배치 1부터 16까지 재면 포화 수준에서 약 2만 4천 개, 중간 수준에서 약 6천 개가 나와 세션 하나에 약 3만 개다.

기록당 비용(120만 개 기록으로 잰 값):

| 위치 | 기록당 |
|---|---|
| 저장 결과와 실행기 묶음 | 14바이트 |
| ChillServer의 공개된 프로파일(기록, 분포, 분위수 표 하나) | 76바이트 |
| 관측 기록의 프로파일 본문 | 약 110바이트 |

세션 하나가 3만 개일 때 프로파일 하나는 ChillServer에서 약 2.3MB, 관측 기록에서 약 3.3MB다. 조건 200개면 각각 약 460MB와 660MB다.

최소 전력 관측 시간을 수백 초로 늘리면 기록 수가 그만큼 늘어난다. 220초 이상이면 빠른 모델의 세션이 100만 개를 넘고, 그런 프로파일 13개 안팎에서 ChillServer의 과부하 보호 한도(3GiB의 90%)에 닿는다. 관측 기록이 프로파일 본문을 다시 담지 않고 저장 결과를 가리키게 하는 것과, 쓰이지 않는 프로파일의 기록을 메모리에 두지 않는 것은 옛 측정 장치 삭제와 함께 한다. 시범 측정은 프로파일마다 기록 수를 보고한다.

## 범위 밖

- 전력 모드 전환 비용 측정과 동작 비용 측정 요청의 통합.
- 엣지 Pod 주소 구성, orin-nano GPU 메모리, 주인 없는 저장 객체 제거: 운영 세션에 전달한다.
