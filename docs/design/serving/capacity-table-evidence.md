상태: evidence — E1 시제품과 후속 탐색 선택의 측정 근거다. **현행 수식·입력·제어 계약은 [용량표 계획기](analytic-planner.md)가 권위**이며 아래 옛 DP·d 없는 κ·가변 T를 구현 지시로 사용하지 않는다. 도구 `hack/kappa`는 `serving.EvaluateScheduler`를 재사용한다. 클러스터 변경은 없다.

## 4. rasp5 profile과 실측

E1 2 req/s 창의 rasp5 q1 요청 121건을 요청 행의 시각으로 나눴다.

| 구간 | p50 (ms) | p95 (ms) |
|---|---|---|
| received → validated (ChillServer 인증, 본문 decode, 입력 계약 검사. 전처리는 runner의 `serviceMS` 안) | 14.7 | 103.2 |
| assigned → backend_queued (전달) | 7.2 | 13.7 |
| backend_running → 첫 backend_finished (native 실행) | 30.9 | **32.8** |
| backend_running → backend_exchange_finished | 32.0 | **86.8** |
| 종단 (response_finished) | 55.1 | 209.7 |

- profile b1 실행시간은 p50 27.9 ms, p95 30.9 ms(표본 903개)다. 실측 native 실행 p95 32.8 ms는 profile보다 6% 길다. 86.8 ms는 실행 뒤 응답 교환까지 포함한 구간이다.
- 같은 부하의 재생 예측 p95는 m 50(E1 설정)에서 85.2 ms, m 139에서 174.2 ms다. 실측 209.7 ms보다 각각 124 ms, 36 ms 낮다. 지연 예측의 낙관은 실행 밖 구간(인증과 입력 검사 p95 103 ms, 응답 교환)이 m보다 길어서 생긴다. 구간별 정리는 [용량표 계획기 5장](analytic-planner.md#5-완료-여유-규칙)이다.
- κ는 m에 둔감하다. tight κ는 m 139에서 34.3, m 179(실측 종단 p95 − profile p95)에서 34.2다. 무릎에서는 큐 대기가 지연을 정하기 때문이다.
- κ는 인스턴스 점유 시간에 비례해 줄어든다. 실행 6% 차이는 κ를 약 6% 낮춘다 `[INFERENCE]`. 응답 교환 구간까지 인스턴스를 점유한다면(실행시간 × 2.818) tight κ는 10.8, relaxed κ는 11.7로 profile 값의 1/3이 되고, 그 κ도 검증에서 같은 모양(0.9κ 20/20, 1.0κ 17/20, 1.2κ 0/20)이다. 교환 구간 동안 firstfloor가 다음 배치를 시작하는지는 이 자료로 가릴 수 없다 `[INFERENCE: 2 req/s에서 backend_queued → backend_running p95가 0.1 ms라 대기가 없었다]`.
- m4 r3 Q2에서 포화한 rasp5 q1 인스턴스의 지속 처리율은 26.9 req/s였다(34.3과 10.8 사이). 이 차이는 [용량표 계획기 2장](analytic-planner.md#2-용량표)의 디스패치 점유로 κ에 들어간다.

## 7. 계획 탐색

[계획기 4장](analytic-planner.md#4-노드-계획과-탐색)의 이웃 탐색을 고른 근거와 구현의 측정이다. 7.1과 7.3은 탐색 전의 노드 DP(부하 칸으로 요청 에너지를 배정하는 Pareto DP, commit a9e3829의 `solve`)를 쟀다. 그 측정 test는 DP와 함께 지웠고 표는 그 실행의 값이다.

### 7.1 DP 부하 칸 크기

commit `a9e3829`의 폐기 DP(`solve`)는 m4r7의5노드/MNV9 option과 합성PLC·Smol을 T600초/50부하 조합으로 전수2,800~7,776개와 비교했다. 칸2/5/10에서 최대163.1J/76,418.8J=.21% 차이,26칸부터 일치했으나 두 Workload26칸16~33초/50칸85~200초, 세 Workload26칸529~1,448초였다. 전수9~31ms 대비 Pareto 점581~849/2,594~2,950개가 비용을 키웠고 Tick목표100ms의850배 이상이었다. 이 측정 test와 DP는 제거되어 현행 결과로 재사용하지 않는다.

### 7.3 DP와 이웃 탐색 시제품의 시간과 에너지 차

같은5노드를 합성8노드로 키운 `a9e3829` PlanSearch 시제품(옛 복수인스턴스 규칙)은 k1 최대22.8~34.1%, k2 고부하 최대6.94%, k3도6.94%를 놓쳤다. 비운 출발 k3 일회시험은 해당 해에 닿아 두 출발점의 근거가 됐다. 충족 판정은 전수와 같았다.
8노드 b1/2모드에서 DP2칸>5분/전수60초/k2 67ms/k3 .16초; b2/4모드260계획에서는 k2 .863초(126,360평가),k3 8.6초(1,303,528평가). 평가4.4~6.8µs였다. 이는 폐기된 도구의 당시 결과이며 현재 속도는7.7절이다.
### 7.4 대안 비교

당시 예산은10초 제어·서버4CPU·에너지 차≤.5%였다. Pareto는 DP에 이미 있고8노드DP>5분, 전수 임계값→DP와 시간별 칸 조절도 최소2칸부터>5분이라 기각했다. k2 이웃탐색만 b2 1.0~1.7초/전체4.7~7.5초(1goroutine)에 들었지만 고부하3/24개는4.1~6.9% 차이여서 전역최적 보장은 없다.

### 7.5 결정

사용자가 (c)를 승인했다(2026-10-22). E5 규모에서 제어 주기 안에 끝나는 것은 (c)뿐이다. (a)는 DP 안에 있었고, (b)와 (d)는 E5에서 DP로 돌아가며 DP는 노드 8개에서 5분을 넘는다. 구현(commit 103df6c)은 계획기 4장이다.

- keep에서 k = 2로 걷고, 더 좋은 이웃이 없으면 그 자리에서 k = 3으로 이어 간다. 평가는 `evaluate`와 `better`를 그대로 쓰고 칸이 없다. 인스턴스 상한은 집합마다 센다.
- 동시 평가 수는 설정 `planSearchWorkers`(sample 3)다. ChillServer CPU 한도 4에서 CPU 하나를 게이트웨이와 나머지 Tick 작업에 남긴다.
- 시간 예산은 판단 시작부터 `controlIntervalNanos`의 절반(10 s 주기에서 5 s)이다. 예산에 닿으면 그때까지의 가장 좋은 집합을 쓰고 `decision.capacity.search.budgetCut`을 남긴다.
- 코드: `scheduler_capacity.go` +125, −419줄(DP, 부하 칸, Pareto 값, `elideCounts`, `serveTable`).

그 뒤 사용자 결정 셋을 더했다(2026-10-23).

- 노드마다 서빙 인스턴스 하나(D-R8-1). 노드의 큰 용량은 CPU 할당이 넓은 측정 option이 맡는다. 계획 공간은 7.2절이다.
- 최소 이득은 T 동안 nominal 이득이 operation/선택 baseline의 B 민감도 문턱을 넘을 때 keep을 이긴다. profile 통계오차 미포괄과 공유 근거 상쇄는 [계획기 14장](analytic-planner.md#14-구현-규칙)에 정의한다.
- 두 번째 출발점(commit 9fa47cc). 모든 노드를 비운 집합에서도 같은 탐색을 하고 두 끝 중 나은 쪽을 쓴다.

### 7.6 구현의 에너지 차: 한 판단과 반복 Tick

7.3절의 공간 셋과 부하 조합 24개씩에서 구현의 탐색(예산 없음)을 정확한 최소(인스턴스 상한을 지키고 새 인스턴스에 가중치 0을 주지 않는 모든 계획 집합의 전수)와 비교했다. 반복 Tick은 앞 판단이 고른 구성과 가중치를 [교체 회수와 최소 이득](analytic-planner.md#14-구현-규칙) 뒤에 다음 Tick의 지금 구성으로 둔다. keep과 같은 가중치를 고르거나, 떠난 구성과 가중치로 돌아오면(순환) 멈춘다. 끝의 값은 마지막 구성을 T 동안 유지하는 에너지이고, 비교 대상은 같은 규칙으로 Tick마다 전수를 쓴 끝 구성이다. 도구는 `CHILL_PLAN_SEARCH=1 go test ./internal/serving -run PlanSearchE5 -v -timeout 0`이다(약 5분, 이 호스트 12 CPU).

아래 실행 표의 측정조건은 profile half-width heuristic이다. 로컬 BEO 결과11개(rasp5 5, lattepanda4, genesis2 2, 신뢰수준0.95, trial셋)의 model-loaded idle 반폭0.84~9.95% 중 중앙1.84%를 모든 option에 사용했고 입력당 에너지 반폭은0이었다. 이 표는 그 조건의 탐색/반복 Tick 근거로 보존하며 현재 B-only 정책의 결과는 해당 source에서 수행한 검증으로 구분한다.

| 공간 | 규칙 | 한 판단: 다른 해, 최대 차 | 반복 Tick 끝: 0.5% 넘는 조합(차), 차 범위 | Tick 수(탐색, 전수) | 순환(탐색, 전수) |
|---|---|---|---|---|---|
| 노드 5개 b1 | 측정조건 | 0개, 0 | 0개, 0 | 4, 4 | 0, 0 |
| | D-R8-1 전, keep 출발, 최소 이득 없음 | 0개, 0 | 0개, 0 | 5, 5 | 0, 0 |
| 노드 5개 b2 | 측정조건 | 0개, 0 | 0개, 0 | 4, 4 | 0, 0 |
| | keep 출발만 | 1개, 0.070% | 1개(0.637%) | 4, 4 | 0, 0 |
| | 최소 이득 없음 | 0개, 0 | 0개, 0 | 4, 4 | 0, 0 |
| | D-R8-1 전, keep 출발, 최소 이득 없음 | 1개, 0.070% | 3개(0.64%, 5.02%, 5.85%), 0~5.85% | 4, 4 | 0, 0 |
| 노드 8개 b1 모드 2 | 측정조건 | 2개, 0.057% | 0개, 0~0.469% | 3, 3 | 0, 0 |
| | keep 출발만 | 2개, 0.057% | 1개(0.649%) | 3, 3 | 0, 0 |
| | 최소 이득 없음 | 2개, 0.057% | 1개(0.548%) | 6, 5 | 4, 5 |
| | D-R8-1 전, keep 출발, 최소 이득 없음 | 6개, 6.94% | 0개, −0.013~+0.013% | 5, 5 | 3, 3 |

- "측정조건"은 노드마다 서빙 인스턴스 하나, 두 출발점과 위 profile half-width heuristic이다. "keep 출발만"과 "최소 이득 없음"은 그 조건에서 하나를 끈 일회 실행이다. Tick 수는 최대값이다.
- 첫 판단의 충족 판정은 모든 조합에서 전수와 같다.
- 앞선 5.02%와 5.85% 조합(노드 5개 b2, mobilenet 110, PLC 15와 40, SmolVLM 1.2 req/s)은 지금 규칙에서 차 0으로 끝난다. keep 출발만인 실행과 최소 이득 없는 실행에서도 0이므로, 같은 노드 인스턴스 둘을 지운 규칙(D-R8-1)이 푼 것으로 본다 [추론: 그 규칙만 켠 실행은 하지 않았다].
- 0.637%와 0.649% 조합(노드 5개 b2 mobilenet 20 + PLC 15 + SmolVLM 0.3, 노드 8개 mobilenet 60 + PLC 40 + SmolVLM 0.3 req/s)은 비운 출발점이 푼다.
- 이 표의 profile half-width 조건에서는 노드8의 순환이 탐색0/전수0이고 해당 문턱을 끈 실행에서는4/5다. 현재 B-only 회귀 `TestCapacityTransitionNeedsGainBeyondDeterministicBound`는 nominal 이득2.7 J와 B0의 전환, equality keep과 strict 초과 전환을 구분한다. 이 표의 순환 억제 결과를 현재 B-only의 보장으로 사용하지 않는다.
- 순환으로 보던 노드 5개 b1의 mobilenet 110 req/s 세 조합은 구성은 같고 가중치만 다른 Tick을 지나 넷째 Tick에 멈춘다. 그 사이 rasp5가 q2 → q1 → q2로 두 번 바뀐다(둘째 바꿈의 이득 122 J, 문턱 약 75 J: rasp5 idle 반폭 0.09 W × 600 s의 두 항). 순환 판정이 구성만 보던 측정 도구의 오류였고 지금은 구성과 가중치를 함께 본다.

### 7.7 구현의 시간

부하 mobilenet 60, PLC 40, SmolVLM 1.2 req/s, `planSearchWorkers` 3, 시간 예산 5 s(제어 주기 10 s의 절반)에서 7.3절의 공간을 키운 시간이다. 지금 규칙(노드마다 서빙 인스턴스 하나, 두 출발점)이다. 같은 도구가 잰다.

| 노드 5개 b1 | 25 | 2.7×10³ | 4,426, 9 ms | 4,426, 10 ms | 1,133, 3 ms |
| 노드 5개 b2 | 45 | 4.9×10⁴ | 25,944, 55 ms | 25,944, 60 ms | 8,824, 27 ms |
| 노드 8개 b1 모드 2 | 54 | 2.4×10⁶ | 71,135, 202 ms | 71,135, 215 ms | 16,433, 68 ms |

- 모든 행이 k = 3까지 갔다. 마지막 행은 k = 3 훑기 도중 예산에 닿았고, 고른 집합과 에너지(140,849.7 J)는 예산 없이와 같다.
- 비운 출발점이 평가 수를 3~5배 늘린다. 비운 집합에서 노드마다 계획을 하나씩 채우는 걸음이 많기 때문이다.
- 평가 하나는 goroutine 셋에서 약 2.9~3.4 µs다.
- 실제 E5 공간(7.2절)으로 옮기면: b2까지는 k = 2 한 번 훑기가 22,380개(약 0.07 s)이고 두 출발점의 k = 2 걸음(합 약 10~16번)이 약 0.7~1.2 s다. 이어 k = 3 한 번 훑기(1,220,928개)가 약 3.5~4.2 s라 합이 예산 가까이 간다. batch 상한 전부는 k = 2 한 번 훑기가 99,197개(약 0.3 s)라 두 출발점의 k = 2만으로 약 3~5.4 s이고 예산에 닿을 수 있다 [추론: 위 걸음 수와 평가 속도로 계산]. 예산에 닿으면 그때까지의 가장 좋은 집합이고 `budgetCut`이 그 판단을 가리킨다.
- E5의 실클러스터 측정(Tick CPU, 탐색 시간, 탐색 구간의 게이트웨이 지연 p99, 분 단위 SLO)은 [workload-pools 9.2절](workload-pools.md#92-실클러스터-e2e)이 정한다.
