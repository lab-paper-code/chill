## 4. rasp5 profile과 실측

E1 2 req/s 창의 rasp5 q1 요청 121건을 요청 행의 시각으로 나눴다.

| 구간 | p50 (ms) | p95 (ms) |
|---|---|---|
| received → validated (ChillServer 인증, 본문 decode, 입력 계약 검사. 전처리는 runner의 `serviceMS` 안) | 14.7 | 103.2 |
| assigned → backend_queued (전달) | 7.2 | 13.7 |
| backend_running → 첫 backend_finished (native 실행) | 30.9 | **32.8** |
| backend_running → backend_exchange_finished | 32.0 | **86.8** |
| 종단 (response_finished) | 55.1 | 209.7 |

- profile b1 실행시간은 p50 27.9 ms, p95 30.9 ms(표본 903개)다. 실측 native 실행 p95 32.8 ms는 profile보다 6% 길다. 86.8 ms는 실행 뒤 응답 교환까지 포함한 구간이다.
- 같은 부하의 재생 예측 p95는 m 50(E1 설정)에서 85.2 ms, m 139에서 174.2 ms다. 실측 209.7 ms보다 각각 124 ms, 36 ms 낮다. 지연 예측의 낙관은 실행 밖 구간(인증과 입력 검사 p95 103 ms, 응답 교환)이 m보다 길어서 생긴다. 구간별 정리는 [용량표 계획기 5장](analytic-planner.md#5-완료-여유-규칙)이다.
- κ는 m에 둔감하다. tight κ는 m 139에서 34.3, m 179(실측 종단 p95 − profile p95)에서 34.2다. 무릎에서는 큐 대기가 지연을 정하기 때문이다.
- κ는 인스턴스 점유 시간에 비례해 줄어든다. 실행 6% 차이는 κ를 약 6% 낮춘다 `[INFERENCE]`. 응답 교환 구간까지 인스턴스를 점유한다면(실행시간 × 2.818) tight κ는 10.8, relaxed κ는 11.7로 profile 값의 1/3이 되고, 그 κ도 검증에서 같은 모양(0.9κ 20/20, 1.0κ 17/20, 1.2κ 0/20)이다. 교환 구간 동안 firstfloor가 다음 배치를 시작하는지는 이 자료로 가릴 수 없다 `[INFERENCE: 2 req/s에서 backend_queued → backend_running p95가 0.1 ms라 대기가 없었다]`.
- m4 r3 Q2에서 포화한 rasp5 q1 인스턴스의 지속 처리율은 26.9 req/s였다(34.3과 10.8 사이). 이 차이는 [용량표 계획기 2장](analytic-planner.md#2-용량표)의 디스패치 점유로 κ에 들어간다.

## 7. 계획 탐색

[계획기 4장](analytic-planner.md#4-노드-계획과-탐색)의 이웃 탐색을 고른 근거와 구현의 측정이다. 7.1과 7.3은 탐색 전의 노드 DP(부하 칸으로 요청 에너지를 배정하는 Pareto DP, commit a9e3829의 `solve`)를 쟀다. 그 측정 test는 DP와 함께 지웠고 표는 그 실행의 값이다.

### 7.1 DP 부하 칸 크기

commit `a9e3829`의 폐기 DP(`solve`)는 m4r7의5노드/MNV9 option과 합성PLC·Smol을 T600초/50부하 조합으로 전수2,800~7,776개와 비교했다. 칸2/5/10에서 최대163.1J/76,418.8J=.21% 차이,26칸부터 일치했으나 두 Workload26칸16~33초/50칸85~200초, 세 Workload26칸529~1,448초였다. 전수9~31ms 대비 Pareto 점581~849/2,594~2,950개가 비용을 키웠고 Tick목표100ms의850배 이상이었다. 이 측정 test와 DP는 제거되어 현행 결과로 재사용하지 않는다.

### 7.3 DP와 이웃 탐색 시제품의 시간과 에너지 차

같은5노드를 합성8노드로 키운 `a9e3829` PlanSearch 시제품(옛 복수인스턴스 규칙)은 k1 최대22.8~34.1%, k2 고부하 최대6.94%, k3도6.94%를 놓쳤다. 비운 출발 k3 일회시험은 해당 해에 닿아 두 출발점의 근거가 됐다. 충족 판정은 전수와 같았다.
8노드 b1/2모드에서 DP2칸>5분/전수60초/k2 67ms/k3 .16초; b2/4모드260계획에서는 k2 .863초(126,360평가),k3 8.6초(1,303,528평가). 평가4.4~6.8µs였다. 이는 폐기된 도구의 당시 결과이며 현재 속도는7.7절이다.
### 7.4 대안 비교

당시 예산은10초 제어·서버4CPU·에너지 차≤.5%였다. Pareto는 DP에 이미 있고8노드DP>5분, 전수 임계값→DP와 시간별 칸 조절도 최소2칸부터>5분이라 기각했다. k2 이웃탐색만 b2 1.0~1.7초/전체4.7~7.5초(1goroutine)에 들었지만 고부하3/24개는4.1~6.9% 차이여서 전역최적 보장은 없다.

### 7.5 결정

### 7.6 구현의 에너지 차: 한 판단과 반복 Tick

7.3절의 공간 셋과 부하 조합 24개씩에서 구현의 탐색(예산 없음)을 정확한 최소(인스턴스 상한을 지키고 새 인스턴스에 가중치 0을 주지 않는 모든 계획 집합의 전수)와 비교했다. 반복 Tick은 앞 판단이 고른 구성과 가중치를 [교체 회수와 최소 이득](analytic-planner.md#14-구현-규칙) 뒤에 다음 Tick의 지금 구성으로 둔다. keep과 같은 가중치를 고르거나, 떠난 구성과 가중치로 돌아오면(순환) 멈춘다. 끝의 값은 마지막 구성을 T 동안 유지하는 에너지이고, 비교 대상은 같은 규칙으로 Tick마다 전수를 쓴 끝 구성이다. 도구는 `CHILL_PLAN_SEARCH=1 go test ./internal/serving -run PlanSearchE5 -v -timeout 0`이다(약 5분, 이 호스트 12 CPU).

#### 7.8.1 환원 1 (1단계)

현재 main의 backlog는 `B = q + max(0, λ − κ_ret)·r`이다. `κ_new ≥ κ_ret`인 유지·증설도 `B > 0`이면 `B/κ_new ≤ s`를 만족해야 한다. 충족 조건은 route 존재, 최종 수요 충족, backlog 대기시간 충족이다. `κ_new = 0`은 `λ = 0`이고 `B = 0`일 때만 충족하며, `B > 0`이고 `s ≤ 0`이면 충족하지 않는다. `B = 0`에서는 slack과 무관하게 전환 초과량을 0으로 둔다.

실수 수학의 하한은 `λ̃ = max(λ, B/s)`(`B = 0`이면 `λ̃ = λ`, `B > 0`이고 `s ≤ 0`이면 `+Inf`)다. float64 경계 판정과 초과량 비교는 main의 연산 순서를 보존한다. `κ_new > 0`, `B > 0`, `s > 0`에서 초과량은 `max(λ/κ_new − 1, (B/κ_new)/s − 1)`이며, 이를 `λ̃/κ_new − 1`로 다시 계산하면 반올림이 달라질 수 있다. route가 없거나 필요한 분모가 0이면 초과량은 `+Inf`다.

`scheduler_capacity_judge_test.go`는 고정 seed 무작위 10,000개, 경계 데카르트 곱 2,592개, 하한 인접 float64 탐침을 유지한다. 같은 표본에서 closed form, search 판정의 충족·최종 판정·초과량, cover 수요·backlog 유무를 대조한다. 초과량은 허용 오차 없이 일치해야 한다. 별도 회귀 사례는 유지·증설의 큐 대기, retained surplus가 큐를 지우지 않는 조건, slack 경계를 고정한다. 이전 실행 기록은 충족 동치 39,199회와 초과량 12,592회 일치다. 이번 main 이식에서 테스트는 재실행하지 않았으므로 이전 수치를 현재 변경의 통과 증거로 사용하지 않는다.

#### 7.8.2 계획표와 cap 하위 선택 (2단계)

`scheduler_capacity_table.go`, `scheduler_capacity_cap.go`. 하네스 전제 수정: `evaluationScaled`의 b2 변형이 e 0.9×를 주던 것을 계획기와 같은 b1 에너지(같은 e)로 바꿨다. 정확성 게이트(노드 5 b2 공간 × 24 조합, 상태 34개 = keep·빈 집합·무작위 32, 이동 17,952): 하위 선택 후보 ≤ 2개 중 v1 `evaluate`+`better` 최선이 모든 cap 변형의 최선과 **불일치 0**. 부호 조건이 고른 우선 후보 하나만으로 일치 17,737/17,952 = 98.8%. 게이트 0.4 s.

제안서 §4.1 규칙 2 정정: "Overload에서는 항상 κ 최대"는 1,833 이동에서 틀렸다. 빠진 항은 환원 1의 B_w = 0 클램프다. B_w > 0이면 초과량 λ̃/κ − 1이 κ에 엄격 감소라 κ 최대 하나가 leximin 최선이지만, B_w = 0이면 충족 cap들의 초과량이 0으로 같아 에너지·key가 가르므로 {κ 최대, κ 최소 충족} 두 후보를 그대로 둔다. 같은 option의 변형은 다른 Workload의 κ·r·κ_ret을 바꾸지 않으므로 w의 초과량만 보면 된다. 재현: mix mnv2 20·plc 15, 상태 `[2 3 1 3 0]`, 이동 genesis2/mnv2/cpu-q1, Σκ_others 124.906, λ̃ 20, B = 0: b2 76,808.20 J 대 b1 76,735.38 J(초과량 동일).

#### 7.8.3 증분 평가기 (3단계)

`scheduler_capacity_greedy.go`는 재사용 상태·`apply`·`delta`·`orderKey`를, `_greedy_weights.go`는 정수 가중치와 Workload 항을, `_greedy_table.go`는 탐색용 표 전처리를 맡는다. v1 `search`·`sweep`·`evaluate`는 변경하지 않았다. 상태·후보 버퍼는 처음 한 번 할당하며 `delta`의 결과 버퍼를 보존하려면 미리 할당한 `orderKey`에 `copyInto`한다. `bounded`·`searchable`·`unroutedPrepare`는 순서 키의 별도 허가 플래그다. `better` 자체는 v1 전순서를 그대로 따른다.

main 재적용에서는 순서 키에 `keepJoules`·고정 `period`도 보존하고 main의 `joules - keepJoules` 비교를 따른다. `pendingReplicas`는 replica 상한에 포함하며 capacity item 수나 total occupancy에 중복 가산하지 않는다. 아래 기존 측정 수치는 재적용 전 기록이며 새 장기 하네스 측정 전까지 그대로 둔다.

정확성: `evaluationScaled(1,0)`, `(2,0)`, `(1,2)` × `e5Mixes` 24 × 고정 seed 무작위 이동 96 = routing ON 6,912회. 노드 5 b1의 앞 네 조합에서 routing OFF 384회를 더해 **7,296회** 비교했다. 각 이동은 현재 상태와 이동 뒤 모두 v1 `evaluate(choice, routeOf(choice))`로 검증한다. 충족·최종·초과량 벡터(무한대 포함)·J·keep·key·가중치 초과·`unroutedPrepare`·route·인스턴스 상한이 모두 일치하며 J 최대 차는 **0**이다. `delta`가 원상태를 바꾸지 않는지도 검사했다. 연속 `apply` 뒤 집계·전체 수·route·노드 에너지·Workload 항은 새로 만든 상태와 정확히 같아 누적 오차가 없었다.

기존 실제 planner fixture(`BatchLimitChangeIsPolicyRoute`, `SingleNodeStoppingModeRaiseNeedsSpareSupply`)의 slow 경로도 비교했다. 수요 50/150·Allowed 참/거짓·growing 참/거짓과 모드 변경 수요 5/30에서 적격 bounded 집합 20회, slow 계획 10개, 계획 단위 timing 제외 4개다. bridge 결과 제외는 **0개**이며 timing/예비 사유 때문에 정확 평가가 거절한 결과도 수치 비교에서 빼지 않았다. 별도 정수 가중치 비교 20,000회(ON/OFF 각 10,000), 할당 없는 판정식 비교 10,000회, zero-weight prepare·others 포함 상한·replicas OFF·여러 retained item·비교 대상 아닌 노드 회귀도 통과했다.

논리 key까지 가는 하네스 동률이 31회 있었다. 계획 인덱스 비교는 쓰지 않는다. 표에 미리 만든 `nodeUID=planKey` 조각과 `|`를 바이트 스트림으로 비교하므로 문자열 생성 없이 v1 연결 문자열 순서를 정확히 따른다. 빈 key·접두 key·구분자가 든 key를 포함한 별도 동률 비교 2,256회도 일치했다.

제안서 §3·§4.2 식의 정정/구체화:

- 노드 에너지는 main의 클램프 식과 동일한 `preJ + mid*max(0,min(r,H)-tauPre) + postJ + after*max(0,H-r-tauPost)`다. 요청 에너지도 main처럼 앞 구간에 `min(r,H)`, 뒤 구간에 `max(0,H-r)`를 적용하며 더하는 순서를 유지한다. 정상 계획은 `r >= preMax >= tauPre`이므로 짧은 H에서의 `min(r,H)<tauPre`, `H-r<tauPost`, `r>H`를 실제 하네스 계획으로 비교하고, 명시 route 평가의 `r<tauPre`도 별도로 비교한다. 결합 가지치기의 에너지 하한은 각 클램프 항의 구간별 최솟값을 합하며, 같은 route에서 최솟값을 동시에 달성할 필요가 없어 과대 평가하지 않는다.
- 요청 평균은 연속 κ 비율 대신 정수 가중치로 계산한 `Σ(y·e)/Σy`이며, slow 보호 수요는 `capacityEnergyLoad`로 실제 수요로 되돌린 뒤 에너지에 넣는다. `κ=(1,2), e=(1,2), λ=3, H=60, r=0`에서 정수 가중치 `333:667`은 둘째에 `2.001 req/s`를 보내 final을 실패시킨다. 초과량은 v1·delta 모두 **0.00049999999999994493**, 요청 에너지는 **300.05999999999995 J**다. 연속 κ 비율 식은 **300 J**다.
- retained 초기 요청 전력은 노드/item 순서대로 `min(λ,κ_ret)*weight/weightSum*e`를 더한다. `min(λ,κ_ret)*Σ(e·weight)/Σweight`로 재결합하지 않는다. 상태 집계도 변경된 Workload만 같은 순서로 다시 접어 반복 차감·추가의 부동소수점 누적 오차를 없앤다. 바뀌지 않은 Workload 항과 동일 retained 목록의 항은 재사용한다.

#### 7.8.6 활성 m 기본값 결정 (4·5단계 게이트 정리)

§7.8.4·§7.8.5 측정으로 `planPolishActive` 기본값을 **8**로 정한다(제안서 §9 열린 결정 (2)). 근거: m = 4는 한 판단 차 최악 8.156%·반복 Tick 15.237%로 품질 게이트 미달, m = 8 + 가격 유도 출발점은 한 판단 최악 0.020%(5 b2 mnv2 20·plc 40·vlm 0.3 한 조합, v1은 그 조합에서 전수 일치이므로 "모든 조합에서 v1 이하"는 이 한 조합 0.020%만 미달), 반복 Tick 최악 0.022%, over 0.5% 0, 순환은 전수와 같은 2회, fallback 0, `surrogateGapJoules` 0. m = 전체는 품질 0%이지만 최대 공간에서 예산·마감에 닿는다.

4단계 게이트 중 미달로 남은 항목: (1) 위 한 조합의 v1 대비 +0.020%; (2) 비용 — 노드 8 b2 모드 4 공간에서 m = 8은 기본 예산 500,000회에서 잘리며 370~515 ms(J는 예산 없는 m = 4·v1과 동일), m = 4도 270~477 ms로 ≤ 100 ms 게이트를 넘는다. 원인은 증분 평가 실측 0.65 µs(제안서 가정 0.2 µs)와 결합 탐색의 분기한정이 자르는 가지가 적어 평가 수가 추정보다 많은 것이다. 제안서 §8 표에 "활성 m의 품질·비용 상충" 행이 더해졌다(§7.8.4). 당시 실제 E5 비용 재측정을 7단계로 계획했으나 실행 근거는 없다. 당시 설정 기본 전략은 `v1`이었다.

#### 7.8.7 그림자 운영(당시 미실행)

`planSearchStrategy: shadow`와 `search.shadow` 기록 경로는 당시 구현됐으나 테스트베드 캠페인은 실행하지 않았다. **이 모드와 비교 진단은 2026-11-08 폐기되었다.** 아래 §7.8.8의 그림자 관련 서술은 그 브랜치의 역사적 변경 사실이며 현재 설정·운영 지시가 아니다. §7.8.6의 하네스 품질 차 +0.020%와 비용 게이트 미달을 live 통과로 해석하지 않는다. 현행 공식 선택은 [계획기](analytic-planner.md)를 따른다.
