## 1. CHILL의 목적과 적용 범위

- **대상:** 이기종 워커노드 POOL에서 모델 추론 서비스를 제공하는 시스템.
- **최적화 원칙:** SLO를 충족할 수 있는 선택 중 총에너지가 가장 유리한 구성을 선택한다.
- **제어 범위:** 노드 참여, 모델 인스턴스의 배치와 자원, 전력모드, 라우팅, 배칭 및 전환 동작. 현재 구성의 유지도 선택에 포함한다.
- **평가 관점:** 요청 지연, 처리 결과, 총에너지로 판단한다. 처리량은 부하 수용 능력을 판단하는 근거다.
- **보장 범위:** 버스트, 준비 지연, POOL 용량 한계로 발생하는 SLO 위반을 관측한다. 가용 자원으로 SLO 우선 대응을 계속하며, 충족 가능한 조건과 한계를 실험으로 확인한다.

## 2. 시스템 전체 흐름과 책임

```text
운영자의 측정 요청 → 프로파일링 → Evidence Store
                                    ↓
        프로파일 + 워크로드 SLO + 현재 부하와 큐 + 실제 구성과 전환 상태
                                    ↓
                   스케줄러의 구성 선택 → 전환 실행
                                    ↓
요청 수신 → 워크로드 확인 → 인스턴스 분배 → Triton 배칭과 추론 → 요청별 응답
                                    ↓
                부하, 지연, 전력, 실행 상태 관측 → 다음 판단
```

| 역할 | 책임 |
|---|---|
| 운영자 | 모델과 워크로드 관리, 측정 요청과 프로파일 적용 대상 지정 |
| 프로파일링 / Evidence Store | 판단에 필요한 실측 근거 생산 / 조건, 원시 관측, 실행 및 파생 결과 보존 |
| 스케줄러 | 프로파일과 현재 상태를 적용해 POOL의 노드 구성과 서빙 워크로드 관계, 분배와 배칭 정책 및 전환 선택 |
| 전환 실행 계층 | 제어 동작의 의존관계에 따른 실행, 실제 완료 여부와 실패 및 상태 보고 |
| 요청 처리 경로 | 워크로드 확인, 요청별 인스턴스 분배, 시간 정보 연결, 결과 반환 |
| Triton | 모델 로딩과 추론 실행, CHILL 정책을 적용한 내부 배칭과 대기 및 실행 판단 |
| 분석자 | 요청 결과와 에너지의 해석, 실험 성패 판단 |

CHILL은 정책과 판단 근거를 제공하고 Triton의 실행 메커니즘을 재사용한다. 목표 구성의 선언과 실제 반영 완료는 구분한다.

## 3. 워크로드와 요청 및 SLO

| 항목 | 계약 |
|---|---|
| 워크로드 | 서비스 식별자, 등록된 모델 참조와 지연 SLO |
| SLO | 지정한 지연 백분위와 목표 시간. 같은 모델에 서로 다른 SLO의 워크로드 정의 가능 |
| 추론 요청 | 워크로드 식별자 + 독립적으로 완료 가능한 추론 입력 1개. 하나의 입력은 여러 tensor나 파일로 구성 가능 |
| 요청 정의 | 각 요청에 등록된 워크로드의 모델과 SLO 정의를 적용 |
| 종단 지연 | CHILL 수신부터 해당 응답 반환 완료까지. 유입 대기, 분배, 전달, 실행, 반환을 모두 포함 |
| 응답 | 각 결과를 해당 요청에 연결해 완료 시점에 개별 반환 |

- 독립 입력은 각각 별도 요청으로 처리한다. 내부 배칭과 인스턴스 전달 후에도 지연 측정의 기준은 최초 CHILL 수신 시각으로 유지한다. 외부 클라이언트의 왕복 지연은 별도로 관측한다.
- 사용자는 워크로드 목록과 상세에서 식별자, 모델, SLO, 입력 형식과 요청 가능 상태를 조회한다. 내부 노드 배치와 실행 배치 크기는 CHILL이 관리한다.
- 운영자는 모델과 워크로드를 생성, 조회, 수정, 삭제하고 모델 연결과 SLO를 관리한다. 현재 서빙 배치는 POOL 운영 상태에서 조회한다. 수정이나 삭제 시 이미 수락한 요청의 의미를 유지하고 요청 유실을 방지한다.

## 4. POOL과 노드 자원 및 모델 인스턴스

| 구분 | 기준 |
|---|---|
| 전체 POOL | 운영자가 제공한 전체 워커노드 범위. 모든 후보의 비용을 같은 범위에서 비교 |
| POOL | 현재 소속 노드와 서빙 중인 워크로드를 참조하는 동적 자원 집합. 노드는 동시에 하나의 POOL에 배정되며 구성 선택과 전환에 따라 소속 갱신 |
| 활성 POOL | 현재 Serving에 참여하는 노드 집합. 비참여 노드의 소비도 전체 POOL 비용에 포함 |
| 자원 공유 | POOL의 현재 배정 자원으로 워크로드들을 서빙하며, 자원이 허용하면 한 노드에 여러 서빙 파드 배치 |
| 모델 인스턴스 | 서빙 파드당 하나. Triton `instance_group.count=1`로 고정하고 파드 추가와 제거로 인스턴스 수 조절 |
| CPU와 GPU | 파드별 연산 자원 전용 할당. CPU는 분리된 CPU 집합, GPU는 물리 장치 단위로 할당 |
| 실행 병렬성 | CPU 스레드는 CPU 할당량에 연동. 인스턴스별 한 번에 배치 하나를 완료하며, 배치 내부 계산과 인스턴스 간 병렬 실행은 가능 |
| 메모리 | 프로파일 사용량과 관측 최대값, Serving 부가 사용량, 시스템 예약분을 반영한 배치 제약 |
| 전력모드 | 같은 노드의 모든 인스턴스에 영향을 주는 호스트 단위 설정 |

- GPU 파드의 보조 CPU와 메모리도 할당에 포함한다. 자원이 분리되면 CPU 파드와 GPU 파드가 같은 노드에 공존할 수 있다. 이미 배정된 자원은 순간 사용률과 관계없이 해당 파드의 할당으로 유지한다.
- 모델 산출물, 런타임, 입력 조건이 같은 워크로드들은 인스턴스를 공유할 수 있다. 유입 측과 인스턴스 내부의 큐, SLO, 실행 배치는 워크로드별로 구분한다.
- 자원 배치 가능성과 SLO 충족 가능성은 별도로 판단한다. 자원 분리 후에도 메모리 대역폭, 전력, 열의 상호 영향을 관측한다.

## 5. 프로파일링과 Evidence 관리

**측정은 스케줄러가 내려야 할 결정에서 도출한다. 프로파일링과 Serving은 같은 Triton/backend 실행 경로를 사용한다.**

| 측정 대상 | 확보할 근거 |
|---|---|
| 고정 실행 구성 | 배치 실행시간 분포, 처리량, 메모리, 노드 벽전력, 에너지 |
| 모델 로드 유휴 상태 | 같은 실행 및 자원 조건에서 요청이 없을 때의 소비 |
| 구성 전환 | 출발 상태와 도착 상태, 동작, 소요 시간과 에너지, 전환 중 추론 지속 가능 여부 |
| 실제 Serving | 대기, 전달, 실행, 반환을 포함한 요청별 종단 지연과 처리 결과 |

- **조건 일치:** 장비, 모델 산출물과 입력, Triton/backend 버전과 설정, 전력모드, 자원, 스레드, 실행 배치 조건을 고정해 보존한다. 요청한 조건과 실제 적용 조건의 근거를 남긴다. CPU quota는 사용량 상한이며, 전용 CPU 배정은 실제 할당 결과로 확인한다. 활성 측정과 유휴 측정은 같은 자원 조건으로 연결한다.
- **공존 검증:** 단독 모델 특성을 먼저 측정하고 실제 공존 시 지연, 처리량, 전력 오차와 공존 구성을 기록한다. 오차가 제어 판단을 방해하면 해당 구성의 추가 측정 또는 운용 제한을 정한다. 메모리 관측 최대값은 해당 입력과 측정 조건에서의 사용량으로 해석한다.
- **측정 재사용:** 실행 조건이 같으면 SLO가 다른 워크로드에도 재사용한다. 노드별, 배치별 성능과 에너지는 각 실행 조건의 실측값으로 비교한다.
- **설정과 오류:** 반복 횟수, 측정 시간, 워밍업, 통계 설정을 결과와 함께 남긴다. 실행 실패, 필수 관측 누락, 계산 불가능한 입력은 오류로 기록한다.
- **저장과 조회:** 설정, 원시 관측, 실행 결과, 파생 결과와 계산 근거를 보존한다. 동일 조건에서는 최신 성공 측정을 우선하며, 한 측정 내 반복 trial 집계와 구분한다. 선택 후보는 실행 조건에 맞는 측정 근거를 갖춘 구성으로 한정한다.
- **적용 책임:** 운영자가 측정과 적용 대상을 지정한다. Evidence는 구성의 특성을 제공하고, 스케줄러가 현재 상태에 대입해 운영 선택을 결정한다.

## 6. 구성 선택과 에너지 비용 비교

### 6.1 판단 입력과 선택 대상

- **입력:** 모델과 SLO, POOL 자원과 실제 구성, 워크로드별 유입과 큐 및 진행 상태, 실행 프로파일, 전환 프로파일과 진행 상태.
- **선택:** 활성 노드, 파드 배치, 모델, 실행 경로, CPU와 메모리 요청량, 공유 워크로드, 전력모드, 분배와 배칭, 전환 동작. 기존 인스턴스의 자원 변경과 현 상태 유지를 포함한다. 메모리 할당은 가용성 제약으로 산정한다.
- **SLO 계산:** 실행시간 분포에 실제 요청 상태와 후보의 분배, 배칭, 큐 선택 규칙을 적용해 요청별 예상 완료 시각을 계산한다. 프로파일에 포함되지 않은 전달과 응답 비용은 Serving 관측으로 보완한다. 처리량은 부하 수용 능력의 근거로 사용하고, 지연 백분위는 요청별 종단 지연 분포에서 산출한다.

### 6.2 비용의 범위와 비교 기준

> 비교 기간 총에너지 = 전환 구간의 POOL 에너지 + 전환 이후 Serving 구간의 POOL 에너지

- 모든 후보는 **같은 시간축, 요청 부하, 전체 POOL 범위**에서 비교한다. 후보별 준비 완료 시점부터 전환 이후 구간이 시작되며, 유지 후보도 그동안의 Serving 소비를 부담한다.
- 전환 중 모델 준비, 전력모드 변경, 기존 Serving, 임시 노드의 준비와 사용 및 해제를 포함한다. 이후에는 활성 노드의 유휴 소비와 연산 소비, 비참여 노드의 소비를 포함한다.
- 전력은 노드 벽전력으로 관측하고 대상, 단위, 시각, 구간을 연결한다. 같은 시점의 노드 전력을 합산하고 기간에 걸쳐 누적해 에너지를 구한다. 모델 로드 유휴와 비참여 상태, 전체 에너지와 유휴분을 뺀 증분 에너지를 구분한다.
- 같은 노드 전력, 유휴 소비, 공유 모델의 로드 비용은 한 번만 계산한다. 공존 비용은 자원 할당 조건과 관측된 오차를 반영해 노드 단위로 계산한다. 추가 에너지 형태의 전환 측정은 기준 소비를 포함해 총에너지와 같은 의미로 맞춘다.
- 전환 에너지는 비용으로 평가하고, 전환 시간은 용량 준비 시점, 전환 중 처리 능력, SLO에 반영한다.

### 6.3 제어 원칙

- 현재 상태에서 선택 가능한 POOL 운영을 비교한다. 전력모드 조정, 노드 추가, 재분배, 축소, 임시 용량 활용을 같은 목표 아래 판단한다.
- 전환 과정까지 SLO를 평가한다. 모든 후보가 SLO 목표를 초과하면 가용 자원으로 SLO 우선 대응을 계속하고, 전체 용량 한계와 일시적 준비 지연을 구분해 기록한다.
- 미래 부하는 불확실한 입력으로 다룬다. 실제 부하와 진행 상태를 관측해 재판단하며, 버스트, 점진 변화, 반복 증감을 같은 제어 로직으로 다룬다.

## 7. 요청 라우팅과 배칭

| 단계 | 처리 원칙 |
|---|---|
| 유입 관리 | 미배정 요청과 인스턴스 내부 대기 및 실행 상태를 워크로드별 관리. 수용 가능한 인스턴스가 준비되면 바로 전달 |
| 인스턴스 선택 | 요청 모델의 추론 준비와 가용 상태가 확인된 인스턴스에 프로파일과 현재 처리 능력에 맞게 분배 |
| 분배 비율 | 워크로드별 요청 분배 비율은 0 이상이며 대상이 있을 때 합은 1. 요청 수 비율과 연산 및 에너지 비율은 구분 |
| 배치 구성 | 같은 워크로드의 호환 요청만 묶음. 각 큐의 SLO와 이미 실행 중인 배치의 대기 영향을 함께 고려 |
| 대기와 실행 판단 | CHILL 수신 후 경과 시간, Triton 큐 대기, 후보 배치의 실행과 반환 비용, 진행 중 실행으로 추가 대기 여유 산정 |
| 요청 수명 | 명시적 timeout, 취소, 큐 및 자원 한계를 네이티브 기능으로 처리. SLO 초과는 제어와 관측에 반영 |

- 라우팅의 집중과 분산이 만드는 배칭과 전력 차이를 구성 비교에 반영한다. 현재 부하와 요청 대기를 반영해 배치 크기와 대기 설정을 선택한다.
- 배치는 포함 요청들의 허용 대기 여유 안에서, 더 모을 에너지 이득이 있을 때 기다린다. 실행 시점에는 해당 인스턴스의 자원 가용 시점을 함께 반영한다.
- CHILL은 근거, SLO, 요청별 시간 정보를 제공한다. **Triton 내부 batcher가 현재 큐와 실행 상태, 각 요청의 경과 시간에 정책을 적용해 대기 종료와 실행을 판단**한다. Triton 큐 timeout의 범위는 큐 대기다.
- Triton의 기존 설정과 공식 확장 지점을 우선 활용하며, 워크로드별 큐와 배치 분리, 단일 배치 실행 계약이 실제로 충족되는지 검증한다.

## 8. 구성 전환과 실패 대응

| 제어 동작 | 완료 확인 |
|---|---|
| 서빙 파드 생성과 모델 준비 | 실제 추론 요청 수용 가능 |
| 전력모드 변경 | 목표 모드의 실제 적용 |
| 기존 인스턴스 자원 변경 | CPU와 메모리 할당, 연동 스레드와 런타임 설정의 적용 |
| 라우팅 변경과 신규 유입 중지 | 새 분배 기준 반영, 기존 대상에 신규 요청 배정 중지 |
| 남은 요청 처리와 파드 제거 | 이미 받은 요청의 마무리와 서빙 종료 |

- **순서:** 동작별 대상, 시작 조건, 완료 기준, 실패 조건을 정하고 의존관계에 따라 실행한다. 완료 여부는 실제 추론 준비와 목표 전력모드 및 자원 설정의 적용 상태로 확인한다.
- **전환 중 서비스:** 기존 용량을 활용하고 필요하면 다른 준비된 노드나 임시 용량을 사용한다. 제외 대상의 신규 유입을 중지한 뒤 남은 요청을 마무리해 요청 유실을 방지한다.
- **동시 실행:** 독립 동작은 동시에 빠지는 용량과 POOL 전체 SLO를 고려해 병렬 실행할 수 있다. 여유 용량은 전환을 대신 감당할 수 있는 잔여 능력이다.
- **실패:** 정상 진행과 실패를 구분한다. 실패 원인과 실제 완료된 변경을 기록하고 실패 동작에 의존한 후속 실행을 멈춘다. 부분 완료를 포함한 실제 상태에서 차선의 선택을 계산한다.
- **격리와 재판단:** 사라진 노드와 백엔드는 가용 대상에서 제외하고 복구는 실제 상태로 확인한다. 진행 중 동작은 기존 실행으로 추적하며 부하 변화와 함께 다음 판단에 반영한다. 미실행 동작 취소와 진행 동작 완료 여부는 동작의 특성과 비용에 따라 정한다. 판단 실패는 오류로 남기며, 결정과 동작의 상태는 실제 진행 단계를 기준으로 보고한다.

## 9. 관측 기록과 실클러스터 평가

### 9.1 관측과 집계

- **요청:** CHILL 수신, 분배, Triton 큐 진입, 응답 완료 시각과 대기시간, 배정 인스턴스, 실현된 실행 배치를 기록한다. 각 요청에 완료, 오류, 거절, timeout, 취소, 미완료 결과를 연결한다.
- **부하:** 워크로드별 `inputs/s = requests/s`. 전체 유입과 인스턴스별 할당, 대기, 실행을 구분하며, 동시 도착 입력은 같은 도착 시각의 개별 요청으로 기록한다. 큐 길이는 요청 수로 세고 내부 배치 수와 구분한다.
- **제어와 전력:** 동작별 대상, 판단 근거, 시작과 완료 시각, 소요 시간, 결과, 실제 상태를 기록한다. 라우팅 결정과 반영 시점, 노드별 처리량과 전력을 같은 시간축에 연결한다. 관측값, 파생 요청률, 프로파일 예측값과 사용 구간을 구분한다.
- **집계:** 운영은 시간 기반 이동 구간, 실험은 지정 구간으로 집계한다. 집계 길이, 제어 주기, 비용 비교 기간은 별도 설정으로 기록한다. 표본 수와 관계없이 같은 측정 절차를 적용하며, 지연 표본이 없으면 표본 수 0과 값 없는 통계를 남긴다.
- **해석과 재현:** 원시 요청 기록과 집계 조건으로 통계를 재계산한다. SLO 위반, 실행 오류, 용량 부족을 구분하고, 처리한 작업량과 에너지를 함께 해석한다. 실험 성패 판단은 분석자가 담당한다.

### 9.2 검증 시나리오와 비교 기준

외부 클라이언트가 워크로드별 부하를 재생하여 프로파일 기반 판단부터 실제 배포, 전력모드, 라우팅, 배칭, 응답까지 검증한다.

| 시나리오 | 확인할 결과 |
|---|---|
| 일정 부하 | 유지 구성의 지연 분포와 에너지 |
| 점진적 증가와 감소 | 확장, 축소, 재분배 |
| 갑작스러운 버스트 | 대응 시작, 용량 준비, 전환 중 지연 |
| 전환 직후 급감과 재급증 | 반복 전환 비용과 대응 |
| POOL 용량 초과 | 실제 요청 결과, 지연, 가용 자원 활용 |
| 노드, 서빙, 제어 실패 | 격리, 대체 선택, 복구 상태 |

- **주 평가:** 동일 부하 시나리오의 워크로드별 지연 분포와 처리 결과, 전환을 포함한 전체 POOL 총에너지. 활성 POOL 소비를 별도로 제공하고 완료, 실패, 거절, 취소, 미완료 수를 함께 남긴다.
- **비교:** 제어요소별 비활성화 실험과 선택 근거가 명확한 정적 구성을 비교한다. 판단과 실행을 분리해 다른 연구의 정책으로 교체하여 비교할 수 있게 한다.
- **재현 자료:** 시나리오, 프로파일과 설정, 초기 구성, 제어 동작과 실제 상태 변화, 요청 결과와 전력 관측을 남긴다. 조건이 대응하는 Serving 구간에서 지연과 에너지의 예측값을 실측값과 비교한다.

## 10. 후속 설계 사항과 지원 범위

### 10.1 확정된 요구를 구체화할 기술 설계

| 영역 | 남은 설계 |
|---|---|
| 구성 선택 | 비용 비교 기간과 부하 처리 방법, 후보 탐색 및 비교 알고리즘 |
| 제어와 전환 | 관찰과 제어 주기, 전환 중 재판단과 취소 및 완료 규칙, 플랫폼별 자원 변경 절차 |
| Triton 연동 | 요청별 시간 예산, 에너지 기반 배칭, 큐 선택 규칙, 시간 정보 전달, 정책 적용 및 갱신 지점 |
| 워크로드와 자원 | 리소스와 API 표현, 워크로드 관리 SRS의 적용 구현, 워크로드 간 자원 할당 |
| 라우팅과 측정 | 분배 기준 표현과 선택 및 갱신 방식, 제어 로직에 필요한 세부 측정 항목과 절차 및 조회 형식 |

후속 설계는 위 요구를 구체적인 실행 규칙으로 완성한다. 알고리즘, 공식, 제어 주기와 API, CRD, 저장 엔진은 해당 설계에서 결정한다.

### 10.2 기본 구현 범위

| 영역 | 구현 기준 |
|---|---|
| 추론 실행 | Triton의 모델 로딩, 추론, 내부 배칭을 재사용하고, CHILL 정책은 기존 설정과 공식 확장 지점을 우선 활용해 연결 |
| 자원과 탐색 축 | GPU는 물리 장치 단위 전용 할당, 메모리는 배치 제약, CPU 스레드는 할당량에 연동, 인스턴스별 동시 실행은 배치 하나 |
| 부하와 성능 근거 | 현재 관측과 실행 프로파일로 판단하고, 같은 실행 조건의 측정은 워크로드와 SLO에 걸쳐 재사용 |
| 공존과 프로파일 운영 | 단독 측정 후 실제 공존 오차를 관측하고 필요에 따라 추가 측정이나 운용 제한 적용. 운영자는 측정 요청과 적용 대상 지정 |
| 관측과 해석 | 실행 오류와 필수 관측 누락을 검출하고 열과 간섭을 관측 자료로 보존. 실험 결과는 분석자가 해석 |
| 전환 실행 | 실제 잔여 용량과 동작 의존관계에 따라 실행. 병렬화, 서비스 지속, 취소 가능성은 각 동작의 특성과 비용을 기준으로 판단 |
| 제어 구조 | POOL 제어와 배칭은 각각의 특성에 맞는 주기로 동작. 라우팅 반영, 실패, 복구는 실제 상태와 관측을 바탕으로 처리 |
