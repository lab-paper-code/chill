# 구조 검토: 다섯 본질과 현재 처리 상태
2026-10-26 07:34Z 기록. 약25개 발견(K1–K5); 현재 정본은 [scheduler SRS](../spec/scheduler/SRS.md), [구현 설계 §5.4](../design/serving/scheduler-implementation.md), [ADR 0023](../adr/0023-resource-ledger.md). 코드 읽기와 운영 실증을 구분하며 새 검증은 하지 않았다.
사용자 결정: 안 나, 시연 3회차 전 Pod 물리 실재/관측 분리·작업 영향 범위 예약·무관 자원 판단 지속. 새 서비스·저장소·CRD 없음. 해결은 발견 범위에 한정한다.
- **K1-1 정책 응답 대기를 실물 소실로 해석** — 발견: 정상 정책 변경 중 ACK(수락 응답)를 기다리는 인스턴스가 오류 목록으로 빠졌다. 피해: 빈 자리로 계산해 같은 CPU에 두 번째 Pod를 준비했다. 근거: 사고 경로 `observer.go`, `scheduler_capacity.go`; 상세는 postmortem을 따른다. **현재: 해결됨.** 실물 장부가 관측 실패에도 점유를 보존하고 정책 대기를 별도 이유로 드러낸다. 후속: rev77 Ready 전체 초기화도 제거했으며 metadata/native not-ready는 dispatch를 차단한다.
- **K1-2 시작 사건은 기억하지만 종료 사건 유실을 회복하지 못함** — 현재 근거: `runtime.go:919–939`, `c.progress != nil`이면 부재 readback으로 종료하지 않는다. **현재: 미해결.** 과거 queued/running 기록이 있는 요청은 현재 native 부재만으로 소유권을 해제하지 않는다. 주의: 단순 timeout이나 목록 누락만으로 실행이 끝났다고 선언하면 안 된다.
- **K1-3 전력 모드의 저장값과 물리 관측 신선도** — 근거 범위: node-agent/전력 readback 및 scheduler capture 경계. **현재: 미해결.** 구조 장부 도입만으로 장치 원천 관측 시각·만료 계약을 완성한 것은 아니다. 주의: 현재 Node API 조회 성공을 장치의 현재 전력 확인으로 바꾸지 않는다.
- **K1-4 독립 실행원의 관측을 전체 lock 아래 직렬 수집** — 현재 근거: `observer.go:254–289`는 goroutine별 probe 후 짧은 lock 아래 개별 게시하고 대기 중 lock을 해제한다. **현재: 해결됨(직렬 native probe와 일괄 게시).** Ready 초기화도 제거돼 다른 probe의 미완료가 기존 Ready를 지우지 않는다. 초기 전체 메타데이터 조회 실패 영역은 K4-6에 별도로 남는다. 실증 경계: 코드의 병렬 게시 계약 확인이며 모든 관측 의존성의 장애 격리 완료는 아니다.
- **K1-5 로그 전달 장애를 추론 실행원 장애로 번역** — 현재 근거: `observer.go:887–904`, `runtime.DisableInstance(id, err.Error())`. **현재: 미해결.** 로그 통로의 실패가 Ready에 영향을 주는 경로는 남는다. 주의: 로그를 버리면 finality가 보장된다는 뜻이 아니며 요청 소유 증거를 보존해야 한다.
- **K2-1 정책을 ConfigMap과 Pod에 순차 기록** — 현재 근거: `operations.go:1152–1168`, ConfigMap patch 뒤 Pod 기대 DecisionID patch. **현재: 미해결.** 첫 쓰기 성공 뒤 실패를 지속적으로 완성할 권위·재조정 책임이 별도 확정되지 않았다.
- **K2-2 movingNodes 실패 경로 누수** — 현재 근거: `operations.go:829–836`, 표시 등록→detach 오류 반환 뒤에 defer 등록. **현재: 미해결.** detach 실패 시 임시 표시가 남을 수 있다. 이는 같은 프로세스의 예외 안전성 문제이며 분산 합의·영속 작업 엔진은 필요 없다.
- **K2-3 정리 주소를 잔재보다 먼저 삭제** — 현재 근거: `operations.go:724` 이후 finishInstanceRemoval의 종료 확인·Service·finalizer 처리. **현재: 미해결.** 물리 종료 증거 보존은 강화됐으나 Pod 뒤 잔재 정리의 재발견 책임까지 닫힌 근거는 없다. 주의: 이미 Service ownerReference와 finalizer가 있으므로 ‘GC/finalizer 전면 부재’로 기술하지 않는다.
- **K2-4 실행원 생성 전 Pod를 일반 정리 경로가 받지 못함** — 현재 근거: `removeInstance(..., podUID, id, ...)`는 빈 실행 ID와 Pod 신분을 분리한다. **현재: 해결됨.** Pending 준비 Pod hand-back 차단 수정과 late-probe 정리가 반영됐다. Pod UID를 생성 의도의 신분으로 유지하고 종료 증거 없이 가동 Pod를 지우지 않는다. 이 해결은 K2-3의 모든 ConfigMap 잔재 수명 문제까지 해결했다는 뜻이 아니다.
- **K3-1 마지막 Tick 스냅샷으로 수동 삭제·배분 승인** — 현재 근거: `measurement_sequence.go:303–307`가 허가 직전 `c.capture`를 수행한다. **현재: 해결됨.** rev84에 반영됐고 과거 snapshot이면 통과했을 거절2건을 기록했다. 작업 완료 뒤 다음 Tick 전의 route/remove도 현재 상태로 승인한다. 효과 실행 전체의 보호는 별도 예약이 맡는다.
- **K3-2 route가 영향 Node를 검사하지만 실행 중 소유하지 않음** — 현재 근거: `kube/reservation.go`, `target_scope.go`, `reservation_tick_test.go`. **현재: 해결됨.** 공통 영향 범위 예약으로 source/destination Node와 Workload를 보호한다. 종료 partial route는 fresh UID/container·Ready·정책 효과 재확인 뒤 해제한다. reset의 종료 owner 인계도 범위 내 원자 인계로 제한된다.
- **K3-3 같은 Workload를 다른 Node에서 동시 측정** — 현재 근거: 공통 예약의 Workload 충돌 검사와 측정 범위. **현재: 해결됨.** Node별 비충돌만으로 Workload 공유를 허용하지 않는다. 살아 있는 측정 owner를 reset이 인계하지 못한다. 측정 컨트롤러 프로세스 이중 실행 여부는 별도 운영 확인으로 남는다.
- **K3-4 논리 자리와 물리 인스턴스 대응 파괴** — 사고: 같은 slot·CPU의 Pod 둘, reset도 같은 자리의 복수 실물로 실패. 현재 근거: Pod UID/container 기준 실물 장부와 source 종료 확인. **현재: 해결됨.** 관측 소실로 점유를 반납하지 않고 물리 신분을 유지한다. 늦은 probe가 퇴역 source를 되살리는 후속 결함도 수정됐다. API 객체 부재만으로 아직 실행 중인 물리가 종료됐다고 간주하지 않는다.
- **K4-1 전역 CPU 검사·긴 목표 장벽** — **현재: 해결됨.** 예약된 범위만 Fixed로 남기고 독립 자원 판단을 계속한다. 확장 시험(나)는 긴 Smol 준비 중 rasp5 MNV 준비18초 완료로 실증했다. 남은 한계: 같은 진행 목표에 나중에 풀린 Node를 보충 확장하는 경로는 미해결이다.
- **K4-2 끝없는 route/제어 State 조회** — 현재 근거: `scheduler.go:1026` 기본 action context는 WithCancel, 정책 State는 작업 ctx 사용. **현재: 미해결.** 독립 범위의 진행성은 회복됐지만 모든 작업의 유한 종료를 보장하지 않는다. timeout은 물리 효과 부재가 아니므로 예약 자동 해제 근거로 쓰지 않는다.
- **K4-3 한 Workload의 κ 계산 불능이 전체 대기로 합쳐짐** — **현재: 해결됨(기존 전역 대기).** leximin과 예약 범위별 판단으로 불가능 Workload가 나머지 후보를 동점으로 만들지 않는다. 빈 출발은 후보 κ 전체를 기본10분/0–1시간 상한으로 기다리는 의도된 예외다. **보류:** κ 대기 Workload를 위한 Node 선점 금지(B안)는 알려진 한계이며 미구현이다. 빈 출발 정보 장벽과 전역 실행 완료 장벽을 같은 것으로 보지 않는다.
- **K4-4 증거 저장소 갱신 실패와 기존 판단의 결합** — **현재: 미해결.** 새 갱신 실패와 마지막 승인 설정의 명시적 무효화를 구별할 필요가 남는다. 기존 추론이 S3 LIST 실패만으로 즉시 중단된다는 주장은 아니다. 해당 Admit/Tick 진행의 결합이다.
- **K4-5 기록 오류 래치가 복구 뒤에도 admission 차단** — 현재 근거: `runtime.go:176,260,367,721,1056`의 observationError. **현재: 미해결.** 실패 기록 재시도와 사용 가능 상태 복구의 책임이 분리돼 있다. ENOSPC는 소스상 가능한 조건이며 이번 실제 발생 사례로 주장하지 않는다. 임의 성공 append 한 번으로 과거 오류를 지우는 안은 채택하지 않는다.
- **K4-6 전체 관측 메타데이터 실패 확산** — 현재 근거: `observer.go:197–217`의 Nodes/Pods/resources/DeviceClass 실패→refreshFailure. **현재: 미해결.** 초기 메타데이터의 전체 실패 영역은 남는다. K1-4의 native probe 병렬화와는 별개다. UID selector 성능 수정은 이 장애 의미를 바꾸지 않았다. 국소안은 대상별 마지막 검증 결과와 유효기간을 제한적으로 보존하는 것이다.
- **K5-1 중간 배분에 최종 비율을 재정규화** — 현재 근거: `scheduler.go:967` readySubset은 여전히 목표 상대 가중치를 보존한다. **현재: 미해결.** 부분 목표 의존성 장벽 수정은 비대칭 용량 배분의 안전성 증명이 아니다. 예비 용량 비율 설정은 별도 안전 여유이며 이 발견 전체를 자동 해결하지 않는다.
- **K5-2 backlog의 나이·남은 수명 무시** — **현재: 미해결.** 집계 B/W 계산은 개별 요청이 route 이전 만료될 가능성을 전부 표현하지 않는다. 준비100초 뒤 큰 κ가 생긴다는 사실로 수명2초 요청의 실패를 회복했다고 세지 않는다.
- **K5-3 outstanding을 수요와 backlog에 중복 반영** — **현재: 미해결.** 외부 ingress와 제어·반환 지연의 재고를 분리하는 후속 수정 근거가 없다. 실제 과잉 생성 인과가 입증됐다는 주장은 아니며 식의 되먹임 위험이다.
- **K5-4 noisy 수요 비교로 축소 보호 즉시 반전** — **현재: 해결됨.** 빠른 증설·느린 축소/에너지 교체, 같은 안정화 기간을 채택했다. 기본300초·시연120초, 전환 reserve비율0, 모든 값은 설정·범위 검사·실행 기록에 고정. 하강 baseline 미만 유지 수정 후 실제127.96초에 축소 허용을 확인했다.
- **K5-5 선택하지 않은 후보가 에너지 비교기간을 늘림** — **현재: 해결됨.** 후보 무관 comparisonPeriodNanos600초 고정, 기간 초과 전환은 제외한다. 근거: Jetson 전력 전환 약150초, Smol 준비270–290초, 보수적 직렬 조합 약490초. 후보마다 다른 기간을 쓰는 안이 아니라 같은 설정 기간으로 공정 비교한다.
