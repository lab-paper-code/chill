## T5: 라이브 계약에서 놓치면 안 되는 것

- `hello`, `snapshot`, `delta`, `event`, 1초 `metrics`, `heartbeat`와 단조 순번을 사용한다. 정확한 필드·버전은 현행 설계에서 확정한다.
- 판단·작업 시작/종료·요청 집계·전력 표본의 발행 경계를 실제 기록 완료와 맞춘다. 아직 확정되지 않은 사실을 완료 이벤트로 발행하지 않는다.
- 연결 시 snapshot과 후속 delta의 경계가 원자적으로 이어져야 한다. resume 순서와 checkpoint, 버퍼 밖 재동기화를 먼저 닫는다.
- 느린 수신자는 유한 큐와 snapshot 재동기화로 처리한다. 일부 metrics를 버렸으면 누락/완전성 상태를 명시하고 임의의 0으로 채우지 않는다.
- 큰 κ(실측 재생 용량), d(요청당 dispatch 점유), 비용, 에너지 이득 근거는 라이브 프레임에 반복 싣지 않고 판단 ID로 읽는다.
- 폴링을 라이브 채널 대안으로 쓰지 않는다. 브라우저 첫 메시지 인증과 앞단→서버의 기존 인증 전달을 혼동하지 않는다.

## T6: 화면이 설명해야 하는 것

- 맨 위 띠: 실시간/기록 재생, 시나리오 단계, 자동제어 여부, 마지막 관측과 경과 시간, UTC/KST.
- 세 워크로드 카드: offered·완료·실패·SLO 만족과 유입/대기/실행을 구분. HTTP 성공과 지연 목표 만족은 별개다.
- 배치 지도: 실제 Pod 기준 인스턴스, 현재 분배, 목표 구성, 준비/드레인/제거와 노드 전력 상태를 분리한다.
- 시간축: 부하·성공/SLO·배치·전력의 공통 시간축과 작업 시작/완료. 준비·관측 공백을 성공률0 또는 전력0으로 그리지 않는다.
- **추가 요구: 예약 표시.** Node/Workload별 예약 owner, 영향 범위, 진행/실패 후 유지 이유를 실물과 따로 보여 준다. 예약 밖 제어가 계속되는 이유와 사용할 수 없는 자원을 운영자가 이해해야 한다. 기존 DTO에 없으면 서버 장부의 읽기 projection을 먼저 정의한다.
- 상태 문구는 등록됨 / 요청 받음 / 실행 준비됨 / 실제 처리 중 네 단계를 구분한다. SLO 목표 충족과 판단 근거 부족은 별도 표시하고 근거 없는 “정상”으로 합치지 않는다.
- 재생은 현재 Workload 목록이 아니라 기록 당시 정의를 사용한다. 삭제된 Workload 이름·모델을 보존하고 미확정/누락 구간을 표시한다.
- 과거 `/records`, `/settings`, 준비 중 페이지 중심 구조는 새 탐색 흐름으로 대체한다. 기능 삭제와 화면 경로 폐기를 혼동하지 않는다.
