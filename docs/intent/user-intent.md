# 사용자 의도와 작업 방식

## 작업 순서와 소유권

- 근원 spec → 분야별 소프트웨어 요구사항 명세(Software Requirements Specification, SRS) → 구현 설계 → 구현 → 실제 클러스터 검증 순서로 진행한다. 요구사항 변경은 사용자 승인 후 정본부터 반영한다.
- 작게 나누고 의존성 순서대로 진행한다. 독립 작업은 병렬로 하며 한 파일은 한 담당이 소유한다. 라이브 클러스터 변경은 한 운영 담당이 직렬 수행한다.
- 최소 단위로 커밋하고 정식 리뷰와 과설계 중심 ponytail 리뷰를 거친다. 각 커밋은 필요한 정의를 포함해 독립적으로 빌드 가능해야 한다. 커밋에 관련 SRS 요구사항과 설계 절을 연결한다.
- 2026-10-25 미커밋 정의를 참조한 9개 커밋 사고 뒤, 커밋 전 clean copy의 build/vet, 주제 완료 시 통합 담당의 lint/test 확인이 실행 규칙이 됐다. 검증은 측정 및 부하와 겹치지 않게 조율한다.
- 구현 담당의 완료 보고와 통합 담당의 실제 근거 확인을 구분한다. 사용자 승인, 실행 승인 전달과 실행 완료도 각각 구분한다.
- 현재 작업 저장소는 `main`의 `/home/genesis1/ETRI/chill`이다. 과거 `chill-pools` 전용 작업 및 main 수정 금지 지시는 통합 결정으로 대체됐다. spec 전체는 공개 가능한 추적 문서다.

## 설계 선호

- 쉬운 말을 쓴다. 축약어와 내부 코드명만으로 설명하지 않고 필요한 전문 용어는 처음에 풀어 쓴다. 문서는 긍정문으로 쓰고 불필요한 변경 흔적과 새 가운뎃점을 피한다.
- 같은 절차가 모든 워크로드에 적용되어야 한다. 특정 모델 이름이나 노드에 맞춘 분기, 손으로 넣은 속도 추정과 예외 계수는 피한다.
- 클라이언트는 원시 표본 1개를 요청하고 전처리는 CHILL이 수행한다. 입력 검사는 분배 전에 수행하며 단계별 경과 시간을 남긴다.
- 서비스 수준 목표를 먼저 지키고 에너지를 줄인다. 노드 후보는 측정 근거를 가져야 하며 첫 구성은 자동 생성한다. 운영자의 최소 수요는 명시적 설정과 실행 기록으로 남긴다.
- 필요한 가장 작은 일반 해법을 선택한다. 기존 기능과 도구를 재사용하고 측정 근거 없는 복구 장치나 별도 프레임워크를 추가하지 않는다. 구조 검토에서 승인한 자원 장부도 기존 서비스와 저장 경계 안에 둔다.
- 성능 퇴행은 프로파일링으로 원인을 확정한다. 서버 증설로 가리지 않는다. 관측과 증거 기록 역시 실제 요청 경로에 주는 영향을 확인한다.
- 대시보드 실시간 전달은 WebSocket을 사용한다. 폴링으로 대체하지 않고 연결 직후 첫 메시지로 인증한다. 기록 재생은 근거 저장소에서 조회한다.

## 승인과 운영 경계

- 이미 승인된 조건과 연속 단계는 재질문하지 않는다. 실제 새 측정 조건, 계수, 판정, 계획기 동작, 범위 확대와 승인 밖 배포는 사용자에게 제시한다.
- 같은 승인 조건의 legacy 및 결측 대체 재측정, 실패의 동일 조건 재시도 최대 1회는 승인 범위 안에서 수행 후 보고한다. 옛 기록 정리는 대체 소비와 검증된 백업 및 해당 삭제 승인을 먼저 확인한다.
- runtime 이미지 7종 digest를 유지한다. 변경 시 프로파일, dispatch 점유 보정값 d, 비용과 비교 기준의 재측정 영향을 먼저 제시한다.
- 실행을 좌우하는 숫자는 설정으로 두고 범위를 검사하며 실행 기록에 고정한다. 측정 조건은 대상의 실측 분포와 목표에서 계산한다.
- 실험 조종 코드는 `hack/`에서 관리한다. 환경값은 설정과 인자로 분리하고 실행 기록, 원시 결과, 백업과 비밀값은 저장소 밖에 둔다.
- 긴 캠페인은 대화 세션에 종속시키지 않는다. 클러스터 작업 큐와 재개 가능한 저장소 스크립트를 사용한다.
- 전력 결측 허용은 진단에만 사용한다. E5 평가에서는 허용하지 않는다. 옛 완료 Job은 증거 저장소 연결 정보 의존을 확인하기 전 삭제하지 않는다.

## 근거와 보고

- 원시 값, 실제 관측 시각과 출처를 보존한다. 사용자 메시지의 시각 표기와 실제 실행 시각을 구분하며 폴더 이름이나 시스템 날짜로 관측 시각을 대체하지 않는다.
- 표본 확인은 그 표본의 확인으로 보고한다. 표본 5개의 증거 읽기 성공을 전체 Job의 독립적 읽기 성공으로 일반화하지 않는다. legacy 소비를 새 규칙 인증으로 세지 않는다.
- 관측 없음과 unknown은 그대로 남긴다. 결측을 0으로 채우거나 과거 원시 및 상태를 재작성하지 않는다. 통계적 계획 수준과 실제 보장 범위를 구분한다.
- 측정 보고에는 `예상과 다른 관찰`을 포함하고 없으면 `없음`으로 적는다. 설명되지 않은 실패를 다음 우선순위에 반영한다.
- 단계 전환과 실패는 원칙적으로 다섯 줄 이내로 완료, 다음, 차단, 세 분모(d/비용/평가), 다음 보고 시각을 알린다. 긴 작업은 시작과 예상 종료, 두 배 초과 시 원인과 선택지를 보고한다.
- 준비와 실제 실행을 따로 보고한다. 시연과 진단은 연구 결과에서 제외하며 전환 중 실패, 준비 지연과 부하 창을 숨김 없이 공개한다.
- 추가 인계 영수증과 증인 파일을 늘리기보다 기존 원자료와 단계 결과를 바로 사용한다. [목표 점검 다섯 질문](north-star.md)을 단계 전환과 승인 경계에서 실제로 검토한다.
